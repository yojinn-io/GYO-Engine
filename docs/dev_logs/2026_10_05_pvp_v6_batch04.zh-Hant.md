### 第 3 項重現（L3，使用者在場）

正式 Client 試玩，四個程序（Match、Gateway、Client A、Client B），三者都開 `--movement-trace`。程序由 Claude 啟動，日誌寫進跑次目錄。

1. A 在大廳建房，B 加入。兩個視窗並排，不重疊。
2. 先靜置約 20 秒，作為對照。
3. 使用者在 A 上依序操作，每次之間間隔約 10 秒，並口頭（聊天）告知大約時間：
   - 拖動標題列約 3 秒，放開；重複 3 次。
   - 拖動右下角縮放約 3 秒，放開；重複 3 次。
4. 正常關閉兩個 Client 視窗，再由 Claude 結束 Gateway 與 Match。

記錄：
- `render_ms`、`frame_gap_ms`：Client 日誌。產品只在第一個世界幀、render ≥250 ms 或 delta ≥0.25 秒時記錄（`PvpApplication.cpp:938-942`），所以長幀之外的分布不在本次資料內；需要時由 probe 取得。
- Held 比例：Match movement trace 的 `resolved` 事件依 `source` 計數，每位玩家依權威 Tick 切成 600 Tick（10 秒）的窗口，各窗口 Held＋Neutral 的比例（門檻 5%）。
  這是從 trace 重算的，窗口起點不保證與 Host 內部的品質窗口相同，報告會註明。
- 連線品質：A 畫面是否出現 `CONNECTION POOR`（使用者目視），以及 Gateway／Client 日誌中的移出紀錄。

判定：任何一次拖動或縮放出現 render_ms ≥250 ms，即為重現。

### 第 6 項重現（L3）

使用者指出 Claude 能監控 Match，死亡由 Claude 自己製造與擷取即可，不需要使用者操作（2026-10-05，量測開始前）。所以分兩步：

1. **probe 自動重現（Claude 執行）**：在上表 4 個跑次之後，另跑一次 `run_action_short.py --case action60`，**不計次、不算量測**。
   - `action_short` 的 actor 會被擊殺、經過 180 Tick 死亡等待後重生，走的是產品的同一條 `PvpApplication` 呈現路徑。
   - 跑的同時，Claude 以 `screencapture -x -t jpg` 每約 0.25 秒擷取一次全螢幕，檔名帶時間。
   - 死亡區間由 probe 的逐幀紀錄（`local.dead`、`presented`、`presented_weapon`）與畫面上的死亡倒數 HUD 對齊。
   - 判定：actor 視窗在死亡區間出現第一人稱持槍手臂，即為重現。
2. **正式 Client（只在第 1 步未重現時）**：比照第 3 項的 session，用 A 擊殺 B，Claude 連續擷取 B 的視窗；至少兩次，第二次交換角色。
   這一步的射擊由使用者操作；若改由 Claude 以 OS 層合成輸入操作，需要使用者另外開放「輔助使用」權限，屆時再確認。

截圖方式的更正（量測開始前）：第一次測試時 `screencapture` 被 macOS 權限擋下（could not create image from display），原本寫成由使用者截圖；使用者開放權限後重測可以擷取全螢幕（3584×2240），所以改由 Claude 連續擷取。本機沒有 ffmpeg，不用錄影。
`submitted_meshes` 在 `!Alive()` 時被產品設為 0（`PvpApplication.cpp:516`），欄位為 0 不代表畫面上沒有手臂，以截圖為準。

未重現時，記錄嘗試的操作，列出已排除的假設，停下回報；第 05 批不執行。
