## 原有缺口與本批處理

- 已有真 socket 射擊矩陣只有六秒、60 Hz／30 Hz 冷卻壓力；不能當作合法射擊的
  30 分鐘共存驗收。新增能力限於既有產品 probe 與分析器，不建立通用測試平台。
- 既有 timing runner 支援三輪 GUI，但首輪失敗會缺總摘要。補齊失敗／未執行狀態、
  JSON／可讀報告與非零退出；新目錄防止覆寫，原始 trace 保留。
- 正式程序已支援 `--movement-trace`，Gateway 已有關閉時統計。本批指南沿用；
  不把沒有逐槍紀錄的試玩日誌當成零重複傷害或射擊分位數證據。
- 第 04 批只有靜態移除檢查；本批在隔離副本真正移除 owner 的內容與 registration，
  重建獨立 Engine／fixture，並核對 Match 沒有 Client 模型依賴。

## GUI 首輪失敗與排程干擾

第一輪 120 秒／200 個預排事件全部配對，P50 **52.02 ms** 超過 50 ms，P95
52.73 ms 符合 80 ms。14,400 原始移動命令 Actual 100%，首次成功送出 P95
16.06 ms，Actual P50／P95 40.81／50.06 ms，零 epoch 重設及診斷遺失。
兩端實際約 59.72 FPS；全部慢幀保留。**沒有放寬門檻或將整輪寫成通過。**

同一時間啟動了隔離移除驗證的 nice19／單工作建置與 configure。這是 Agent 的排程
疏漏；低 priority／單工也不等於無干擾。`command-evidence.disturbed=false` 只代表
它的內部判定未見已編碼干擾，不代表外部不存在負載。另保存 workload 時間來源，
不能只因重疊就認定它造成 P50 超標。停止其他建置／測試後，有限追加一輪相同設定
排查；兩份報告並列，不覆寫第一輪，不挑好的當成三輪驗收。

第一輪證據：`build/target/_build/test/logs/pvp-v4-batch05-gui-120-1/`。

公共實作 hash 保持相同、沒有下載依賴，無有效 owner 路徑殘留。

- `object_fps`／`object_fps_v2` configure 通過且沒有 PvP target；**未重建／試玩這兩個
  完整遊戲**，不擴大宣稱。
- 實際 Ninja link graph 及 readelf 確認 Match 不依賴 SDL／Model／Renderer／UFBX。
- 起始第 04 批 manifest 137 檔全部相符；Match／Gateway 與第 03 批指紋相同。
  該 manifest 不是所有 Go／Engine 來源的全量驗證。

證據：`build/target/fitness/pvp-removal-v4-batch05-20260928/logs/fitness-result.json`、
同目錄 README、腳本與原始 logs。沒有修改正式 Engine／公共 Gateway／公共建置。

wire／資產格式及正式遊戲責任不變。

## 合法射擊與移動共存短測

每案實時量測 10 秒，另有兩秒暖機、兩秒裁決排空。每 ActionId 只取得一次終局裁決，
兩端逐 Snapshot Tick 核對累計唯一傷害與 HP；每位玩家都真正損失 100 HP。

| 迴圈 Hz | 提交／裁決／接受 | 移動 Actual | 產生→Match 裁決上界 P95 | 產生→Client 取得 P95 |
|---:|---:|---:|---:|---:|
| 30 | 48／48／48 | 100% | 12.02 ms | 100.00 ms |
| 60 | 50／50／50 | 100% | 12.24 ms | 83.37 ms |
| 144 | 50／50／50 | 100% | 17.92 ms | 97.23 ms |

三案零重設／排程長停頓／診斷遺失，30 FPS 沒有半速。Match 時間是同 resolvedTick
緊接裁決之 snapshot_produced 單調時間，屬保守上界，不虛構精確逐槍時間戳。
HP=0 後後續命中傷害為 0；去重仍需唯一 ID／不可變裁決／完整退休及既有 domain
測試支持，不能單靠飽和的 HP 說明沒有重做。

證據：`build/target/_build/test/logs/pvp-v4-batch05-legal{30,60,144}-1/`。
最終分析器另對完整單調時間覆蓋、幀間隔、暖機／排空及截斷做核對，不能只靠
宣告 `duration=1800` 冒充實際長測。Probe 以 2,048 筆有界佇列在背景輸出 JSONL；
溢位記錄 loss 並使跑次失敗，寫檔錯誤／缺 footer 均不可默認成功。

## 射擊故障與恢復補驗

四個新增短案通過：RTT 0／20／40 ms 各自疊加最多 10 ms 單向抖動與 5% 設定
隨機丟包，另有連續兩包遺失。注入僅在產品 probe relay，不修改正式程序。
三個持續干擾案例停止干擾後，新裁決最慢 **217.18 ms**，Actual／積欠／窗口與
時間線穩定恢復並觀察 250 ms，最慢於 **350.51 ms** 證明成立，符合 1.5 秒。

RTT 20 案 30 次請求有 29 次接受、一次明確 Cooldown 拒絕（Player1 ActionId6，
Tick249，damage=0、target=0），30 次裁決完整交付。故障可壓縮到達間隔；這是
權威拒絕，不把它排除出結果或偽裝全部接受。乾淨合法射擊三案仍要求全部接受。

network0 最初分析器將 Leave 之後空房重啟的 Tick1 與本次玩家生命週期的 Tick1
混在一起，報重複 Tick。保留 `result.json` 原失敗；修正為只索引 probe 有效玩家
生命週期內的 Tick，再由同份原始資料得到 `result-final.json`。沒有改產品、重跑
挑值或放寬門檻。最終分析器亦檢查拒絕必須零傷害、缺失／截斷、偽造長度與異常
時間覆蓋，11 個短單測通過。

總入口：`build/target/_build/test/logs/pvp-v4-batch05-action-summary.json`，其中列原始
與最終分析、來源／產物 SHA、拒絕原因及恢復數據。初版短案 action probe SHA
`523e3ac3…`，最終版只補正 writer 的 overflow loss footer；最終 `10763eb6…` 實際
跑過 network20／network40／burst2。合法三 FPS 原始證據由最終分析器再核對，兩版
正式 Client／Match／Gateway 不變；不隱藏 probe 版本差異。

第 03 批的 ACK／首包／結果遺失、重複／亂序／衝突、32 槽凍結及各處 250 ms／1 秒
阻塞等 16 案，以及第 04 批 GPU／射擊操作矩陣，依相同正式產品來源重用。不是
宣稱本批重新跑過全部案例，也不是實體 LAN／kernel socket 飽和證明。

burst2 另用原始四個 dropped-packet 時刻界定最後干擾解除，確認每 Session 恰好
連丟兩個射擊封包。新動作恢復 414.44 ms；解除時仍待裁決的兩筆原始動作在
81.09 ms 內全部交付。因此四案的最慢新裁決為 **414.44 ms**，前述 217.18 ms
僅指三個持續網路干擾案。四案共120筆請求、120個終局裁決，119接受、1拒絕。
最終均看 `result-final.json`；不覆寫原始結果，沒有新增跑次。

## 真 GUI 移動＋射擊＋HP 整合

依使用者補充要求，純移動跑次只作診斷。GUI probe 新增 acceptance-only `--combat`，
真 SDL 左鍵上升沿每0.8秒一槍，同時保留原本 W／S 預排交越；兩個 spawn 同一 x 軸、
射手沿 z5↔5.9 移動、目標 z12，因此不修改瞄準／移動幾何或原延遲門檻。
正式產品沒有測試控制，不額外 Drain、不透過測試 API 補造射擊／HP。

先做16秒／20事件／20槍短整合，再做唯一一次120秒共存。計時只收集有界記憶體
觀測；不存圖、不做GPU readback，結束後寫檔。任何裁決計數跳躍、缺少某槍或
下一成功 Presented 回饋均使測試失敗。HP 和 HUD 各用對應 snapshot／呈現 Tick，
不能拿下一幀的新血量比上一幀HUD。

| 預排移動／配對 | 200／200，100% |
| 跨視窗 P50／P95 | **42.29／43.48 ms** |

槍動畫時間不是實體點擊到發光。GUI沒有精確Match動作wall-time，100ms裁決門檻由
上述action probe分段證據支持。GUI短／120秒兩端均沒有pointer-release記錄。

不能從該行斷定OS焦點原因。它們仍不是乾淨combat整合或使用者三輪完整驗收。

## 交付與停止

第05批**工具／整合／指南交付完成**；完整驗收仍待使用者，v4保持候選版本。
正式Client／Match／Gateway及政策未更改；已重建受影響probes，全部自建程序關閉。
沒有執行三輪combat GUI或任何30分鐘長測，沒有提交commit或啟動人工試玩服務。

[手動指南](../object_fps_pvp/plans/v4/MANUAL_ACCEPTANCE.md) 包含核對過的8段shell，
正常退出與日誌保存、GUI三輪 `--combat`、60／144Hz各1800秒合法射擊共存，
JSON／文字報告與退出碼。所有結果逐輪保存，失敗後不自動重跑；GUI其餘輪標記
not_run，長測必須顯式--soak。短跑不能靠宣告時間長度冒充長測。

後續只等使用者回傳[狀態表](../object_fps_pvp/plans/v4/ACCEPTANCE_STATUS.md)與實際摘要；
先核對版本、完整性、失敗及干擾，再決定是否可升格。不覆寫歷史v3 release manifest。
