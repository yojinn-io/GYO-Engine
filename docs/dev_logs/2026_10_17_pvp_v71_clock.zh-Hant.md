## 做了什麼

- 目的（盤點的 P2、P3）：先有對得上的時間，才能判斷延遲出在哪一段。兩批都只作診斷，不影響任何判定。
- 心跳對時（heartbeat-sync）：Gateway 與 Match 之間每秒一次心跳，用四個時間戳算出兩端時鐘的偏移與往返時間；每 10 秒結算一個視窗，偏移取往返最短的樣本，另外算跳變與漂移，兩端寫同格式的 `clock sync` 行。
  - Match 的回覆放在單槽（新蓋舊），排在其他寫出之後；Gateway 的心跳由獨立的診斷 goroutine 組，寫出時不碰資料路徑。
  - 活性規則：runtime link 的 5 秒期限只由 Snapshot、JoinResult、Evicted、Error 刷新，心跳回覆不算；剩餘時間 ≤0 時直接逾時。
  - 隔離（D32）：原始碼守衛確認判定相關的檔案不引用時鐘符號；差分測試讓同一情境有心跳、沒心跳各跑一次，判定與最後的 snapshot 逐位元相同。
- 時間回聲（time-echo）：時間樣本搭在既有的 Hello／Welcome 上，不新增封包種類。Gateway 每個 session 一份估計器，Client 每次建立連線時重設；樣本不合法只計數，連線與加入照常。

## 驗證與經過

- heartbeat-sync：全量 CTest 71／71、`go test -race -count=3` 通過、digest 兩樹比較 0 差異；突變選出 149 個（本批 15 個）全部 killed。兩個突變先是逾時判讀失敗，修測試（加 REQUIRE、ipc 測試的 TIMEOUT 由 60 秒放寬到 120 秒，給 Go 測試加截止時間）後 killed。
- 一開始依會話的 ultracode 開關啟動了設計 workflow，D101 之後停止（沒有 agent 完成），改照計畫：high 實作、時鐘域局部 xhigh。xhigh 檢查（約 30 分）沒有 must 級缺陷；過程中發現 reader 的活性從 goroutine 啟動起算，改成從 `run()` 起算。
- 同機長跑次（soak-long，約 30 分，只記錄）：兩端各約 180 個視窗、1810 個樣本，缺樣本、跳變、不合法都是 0，偏移只飄 32～87 µs。soak 本身的判定兩次都沒通過：第 1 次撞上審查者反覆跑 `go test -race`，第 2 次的異常都在使用者移動機器、改用電池的那幾分鐘，判斷為主機干擾、不是回歸。
- time-echo：全量 CTest 71／71、digest 0 差異、突變 80 個（本批 5 個）全部 killed。短跑次中 Gateway 與 Client 量到的偏移正負相反、大小相同，差在幾十 µs 以內。實際約 0.7 h（估 4 h）。
- heartbeat-sync 實際約 3.1 h（估 9 h）；四平台 L1：heartbeat-sync run 38850836007、time-echo run 38855969436。
- 睡眠那段（D102，延到 2026-10-17，只記錄）：讓 Mac 睡眠約 34 秒。Go 的單調時鐘睡眠時停止，C++ 的 `steady_clock` 繼續走，Match 醒來後量到一次約 26.73 秒的偏移跳變，和事前推論一致，契約裡的〔推論〕改成實測。runtime link 撐過睡眠；Client 在醒來後約 1 秒以逾時斷線，這是既有行為，醒來後要不要重連記在未結事項。
- 跨機器的回聲量測排在 Windows LAN 場次（`lan15-windows`）。
