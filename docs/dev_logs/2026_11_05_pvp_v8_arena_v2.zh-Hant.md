# PvP v8：v8-product-arena-v2（arena v2、烘焙地圖、出生點支撐、搬進 maps/）

日期：2026-11-05。分支 `claude/v8-tool-voxel-map-plan`（PR #152）。產品批，由 voxel 地圖編輯器的會話做（使用者：「ここでやる」）。上段；實作是主會話（Opus 5.5／high），審查和 §14.4 的驗證者都是子 Agent（Opus 5.5／high）。

事前宣告在 [voxel-map-editor.md](../tools/plans/v8/voxel-map-editor.md)「v8-product-arena-v2 的事前宣告」，2026-11-05 使用者核准（「承認」）。實作後的變更列在同一節的「實作後的變更」。記錄器是 [voxel-map-editor-HANDOFF.md](../tools/plans/v8/voxel-map-editor-HANDOFF.md)。

**狀態：** 本機判定 P1、P2、P4～P8、P11 通過；全套 cpu|shader 128／128。P3 依使用者決定降為回歸檢查，也通過。P9（L1）待 CI，P10（L3）待使用者。`maps` 守衛的 §14.4 已核准。

## 做了什麼

- **arena 檔的 schema 2**：`"version": 2`，用 `"geometry"`（相鄰的純檔名）引用 `gyo.voxel_mesh`，取代 `walls`。
  - `Arena::Load` 同時接受 1 和 2。v2 的牆＝產物的碰撞盒，順序依產物。
  - 記憶體裡的 `Arena.version` 維持 1，所以成員、digest 演算法、wire 都不變。
  - 載入失敗時不交出 geometry。
- **出生點規則**：`y==0`，或依共用函式 `IsCharacterSupported`（`CharacterCollision`）有支撐。`Movement` 的著地判定改呼叫同一個函式。
- **Client（R2）**：烘焙地圖畫成一個 mesh 加一張調色盤貼圖，v1 仍畫盒子。
  - 換算與選擇抽成可測的函式：`ArenaMesh.cpp` 的 `DrawsBakedMesh`、`ArenaRenderMesh`、`ArenaPaletteImage`、`InstalledArenaIndex`。
  - 上傳 GPU 後釋放 CPU 端的 geometry；建立貼圖失敗時釋放已建立的 mesh。
- **工具**：碰撞盒合併改成條帶式（`v8-product-arena-v2-merge`），黃金產物重新產生，並加一個合成的「環形牆＋柱子」測試。
- **兩張地圖轉成 v2**：
  - 用 `import-boxes … /walls` 產生格子，再 `build`；
  - 格子原始檔放主 checkout 的 `build/art-source/object_fps_pvp/maps/`（附 README）；
  - v1 檔凍結在 `tests/object_fps_pvp/fixtures/arena_v1/`；
  - 牆的顏色是舊的線性 tint .20／.31／.39 換成 sRGB：124／151／168。
- **搬進 `maps/`**（`v8-product-arena-v2-maps-move`，併進延後的 `v8-product-asset-path-loaded-move`）：
  - `arenas.json`、兩張 arena、兩個產物搬進 `maps/`；`movement_rules.json` 搬進 `rules/`；
  - 改了 Match 的預設路徑、Client、驗收（`gui_aim.hpp`、`sound_l2.py`、`run_network.py`）、測試、catalog、`RETAINED`；
  - 根目錄的 6 筆例外刪除；`FOLDER_TYPES` 加 `maps`；
  - 文件：資產標準、`asset-layout.md`、`network-architecture`、protocol-v6 §2 的補記、protocol-v8 的範例路徑。

| 判定 | 結果 |

## 經過

1. **實作**：
   - 支撐判定抽成共用函式；
   - `LoadInstalledArenas`／`Arena::Load` 多一個可選的輸出參數，用來交出 geometry（`Arena` 不能加成員）；
   - 兩張地圖轉換後，碰撞盒是 5 個，分法和 v1 相同：東西牆含角落，南北牆在中間。
2. **既有測試失敗 2 件**：`ArenaDigestTests` 只把 arena 的 JSON 複製到暫存資料夾，沒有複製相鄰的產物。屬於測試準備（Test 自身），補上複製後通過，判定不變。
3. **突變第一輪**：產品 10／10、工具 21／21。
4. **使用者問產物能不能放進資料夾**（「这2个问题就能放到pvp的assets的config下么」）。查了資產計畫，`asset-arena-maps` 已經寫明「voxel 地圖出現時，arena 一組搬進 `maps/`」；使用者選「今 maps/ に移す」。
   - 搬移後，既有突變 `v8-asset-layout-guard-exception-dropped` 所依賴的 root-file 例外不存在了，所以改掛到剩下的 definition-name 例外。第一次重跑是 wrong_failure：守衛會抓到，但抓到它的是 `test_names_follow_the_naming_rules`。預期訊息改正後 killed。
5. **審查（Opus／high）：沒有 blocker**。
   - 實測發現：P3 的軌跡從沒碰到柱子；而且在柱子與角落附近的 3840 條軌跡裡，「柱子切成兩塊」「牆反序」「舊合併的分法」都是 0 條不同。也就是說，P3 對集合相同、分法不同的分解沒有檢出力。
   - 這推翻了計畫的前提「軌跡等價是獨立的證據」，所以照 AGENTS §14 停下回報，沒有提交修正。使用者決定：P3 降為回歸檢查（`v8-product-arena-v2-p3-regression`）、`maps` 守衛照 §14.4 走程序、P10 採建議的定義。
   - 其他 should-fix 照審查修：
     - 載入失敗時清空 geometry；
     - Movement 側另寫一份判定時要能抓到（柱子邊緣的比對）；
     - Client 依 id 選地圖可測（`InstalledArenaIndex`）；
     - 資產守衛的路徑判定要有實證（新突變 `av2-maps-folder-type-dropped`）；
     - protocol-v6 的補記、工具文件的合併說明、宣告的「實作後的變更」、`voxel-mesh.md` 的狀態、`content_deep_path.py` 的說明；
     - nit：Client 釋放資源、P2 比對純量與出生點、`ArenaMeshTests` 比對 x 和 z。
   - 審查者的計測程式存到 `build/evidence/tool-v8-voxel-map/arena-v2/review-p3/`。
6. **修正後突變 14／15**：`av2-movement-own-rule` 倖存。原因是新的柱子邊緣測試把腳放在 y＝2，邊緣外的膠囊其實懸空，沒碰到稜邊，所以 0.5 < normal.y < 1 的情況一次都沒出現。改成把球放在剛好碰到稜邊的高度（y＝2＋√(r²−dx²)−r），並檢查這個區間至少取到 4 點。重跑後 killed，產品批合計 15／15。
7. **`content_deep_path` 的常數沒有改**。說明裡「下一個已知的失敗點是產品的 `arenas.json`（約 P＝219）」已經過時：
   - os-files-write 之後，產品經 engine/io 讀 arena，深路徑也讀得到（`ArenaDigestTests` 的深路徑測試）；
   - content probe 根本不讀 arena；
   - `maps/` 底下最長的路徑（`assets/object_fps_pvp/maps/pvp_corners.voxel_mesh.json`，54 字元），在 P＝200 時是 254。
   
   所以宣告的範圍仍成立，只更正了說明文字。

## 資產守衛的 §14.4 報告（驗證者確認後的版本）

DI-2 守衛（`test_asset_catalog.py`）這一批的變更，相對於基準 `650739c5`：

1. **守的性質**：catalog 裡的每個項目，都在允許該 type 的第一層資料夾，或是根目錄的 manifest，或是登記的例外（DI-2）。「資產根目錄下的每個檔都在 catalog 裡」由 DI-1 的 `test_every_asset_file_is_in_the_catalog` 守，兩者合起來才是「每個檔都在正確的位置」。
2. **放寬的面**：
   - `maps/` 底下、type 為 text 的 catalog 項目，現在能通過（以前算未知的第一層資料夾）。
   - `RETAINED` 新增 2 個 id（`object_fps_pvp.arena.mesh`、`object_fps_pvp.arena.corners.mesh`），它們不必被產品程式以 id 引用（DI-5 的機制；確實是以路徑載入：arena 檔的 `geometry`）。
   - 其他常數與判斷函式都沒變（驗證者以 2420 個路徑×type 組合比對，放寬的 28 筆全是 `('maps', 'text')`）。
3. **收緊的面**：根目錄的 4 筆例外刪除（`arenas.json`、`pvp_arena.json`、`pvp_corners.json`、`movement_rules.json`），這 4 個檔放回根目錄會失敗。另外 2 筆 `voxel_mesh` 例外是這條分支中途加上又刪掉的，相對於基準不算。
4. **放寬處仍受守護**：
   - `maps/` 只收 text（texture、model、sound 都會失敗）；
   - catalog 成員、產品使用或 RETAINED、snake_case、大小寫、id 與 type 的規則照樣適用；
   - 拿掉 `maps` 時真實的樹會失敗（突變 `av2-maps-folder-type-dropped` killed）；資產守衛的其他突變 13／13 killed。
5. **證據**：`test_asset_catalog` 28／28；主 checkout 的 `build/evidence/tool-v8-voxel-map/arena-v2/` 的 `mutations-layout-final.json`、`mutations-product-final.*`、`mutations-movement-rerun.txt`；驗證者（Opus／high，另一個子 Agent）以暫存區的複本實測 (a)～(f)，腳本與輸出在會話暫存區，未存證，只當出處。
