## S5

- 工具：主 checkout `build/evidence/gyo2-big-map/s5/`（`s5_linux.sh` 一支腳本：check／build／map／match／client／calibrate；`probe/` 的 GPU probe 與 Match probe；`content.py`；`watch.py` 每 0.5 s 記 RSS 與 VRAM、超過上限就停）。只寫 Linux 的 `~/Code/gyo2-big-map-s5`。
- 開跑時桌面還沒登入（GDM 畫面、karasu 讀不到 renderD128），先做不需要 GPU 的部分；使用者登入後才跑 Client。
- 中途遇到的事：
  - 1000 格不是 16 的倍數（`synthesize` 拒絕），三級改成 1008／1504／2000。
  - gyo2 這期間 arena 檔升到 v4，`content.py` 跟著寫 v4（照 pvp_arena 的 floor 0、kill_height -10、fall_damage）。
  - 合成格子是 1 m 一格，km² 的格子檔超過 16 MiB 不能重烘；烘好後把索引改成 0.5 m。256 格時和正規重烘逐位元組相同（`s5/cell_equivalence.txt`）。
  - 主機沒接螢幕（所有輸出埠 disconnected），Wayland 沒有 display；Client 改用 SDL 的 offscreen（Vulkan headless surface，只用 radeon 的 ICD），先在 S1 的 250 m 圖上校正，和 S1 的視窗一致。
- 結果與讀法：宣告 5.2.2。1 km：Match 讀圖＋建牆 7.9 s、峰值 471 MB、查詢 p95 ≤ 5.1 µs；Client 最壞 p95 1.27 ms（畫 14～22 個 region）、probe 峰值 1.79 GB。
- 處置：S7 延後；記憶體先做「上傳 GPU 後放掉 CPU 端的頂點」；平行解析留待辦。

## 記憶體批

1. **render**：`ModelRef` 多 `shared_ptr<HandedModel>`（Bevy 的 `RenderAssetUsages::RENDER_WORLD`＋`take_gpu_data`）。沒有蒙皮的網格都做好 GPU 網格的那一幀拿走頂點與索引，留 nodes 與蒙皮的網格。`ModelMeshKey::held` 改成 `const void*`，`RenderModelMeshes` 的 holder 改成 `shared_ptr<const void>`（握著 `HandedModel` 本身，不握資料）。
2. **mesh_render**：`MeshRenderOptions::meshBytesPerFrame`（Bevy 的 `RenderAssetBytesPerFrame`，預設不限），軟上限。
3. **PvP**：region 的模型交給 render；Render World 每幀 64 MiB。
4. **測試**：`render.pipeline3d` 2 案（每幀上限、交出模型的拿法與蒙皮）、`render.extract` 1 案（拿走的時機、整個模型被放掉、之後照畫；有上限時等兩個網格都做好才拿）；PvP 的 region 測試改成看交出的模型。
5. **突變**：render 8 個（`mh-handed-*` 3、`p3-handed-*` 2、`p3-bytes-*` 3），PvP 1 個（`pvp-region-not-handed`），連同既有的 `mh-end-frame-skipped` 共 10/10 killed。每個各守 17.3／17.5 的一個獨立決定（拿與不拿、拿的時機、沒畫的網格也要做、蒙皮不拿、留 node、有上限、軟上限、每幀重算、PvP 交出）。
