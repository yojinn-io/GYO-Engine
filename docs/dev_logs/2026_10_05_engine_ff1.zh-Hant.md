## 開始

接續使用者「把 Engine 側的功能完成」的指示。檔位 high（計畫建議值），不用 ultracode。

## 做法

- 語料 `tests/common/collision/CollisionCorpus.{hpp,cpp}`：
  - 輸入由 SplitMix64 產生的整數換成 1/128 格點的 float，與手寫的邊界情境。每個平台的輸入位元都相同。
  - 每筆紀錄是一行文字：查詢、目標與情境編號、標籤、輸入的位元（hex）、結果的位元（命中與否、距離或 fraction、Contact 各欄位）。
- runner `gyo_collision_corpus`：`--out FILE` 寫紀錄（兩樹比對用）、`--stats` 印膠囊兩個多載的比較、`--degenerate` 印退化膠囊的現況。
- 測試 `CollisionCorpusTests.cpp`（併入 `gyo_collision_tests`）：
  - 涵蓋全部公開查詢；
  - process 內產生兩次相同；
  - 命中與未命中都有；
  - 統計的分類加總等於案例數。
- 比對腳本 [`compare_collision_corpus.py`](../architecture/plans/foundation-followups/scripts/compare_collision_corpus.py)（放在計畫夾的 `scripts/`，比照 math-foundation）。

## 過程中的問題

1. 退化膠囊報告第一次執行時，在第一個情境就 terminate：float 查詢的 `Math::Clamp` 前置條件斷言發生在 noexcept 函式內，可拋出的 assertion handler 也攔不住。
   以 Python 的 float32 模擬確認哪些輸入會讓 segment 上端低於下端，runner 改為不執行這些情境的 float 查詢，只記錄判斷結果。
2. 第一次靈敏度檢查時，double 路徑的 `kTolerance`（1e-7→1e-5）沒有改變任何紀錄。原因是它只用在「初始重疊且分離」的判斷，語料缺淺重疊情境。
   補上深度 5e-8～5e-5 往外與切線移動的情境後，改大改小都會改變紀錄。

## 驗證

- 同機重跑兩次：16,940 筆逐位元相同；scratch 改容差後還原，紀錄與原本相同。
- 靈敏度：float `kEpsilon` 1e-6→1e-5：9 筆（`RaycastAabb` 5、`SweepSphereAgainstCapsule/vertical` 4）；double `kTolerance` 1e-7→1e-5：32 筆、→1e-9：14 筆（兩種 VerticalCapsule 掃掠）。
- CTest 56／56。CI 只驗測試通過與自洽，不比對跨平台紀錄（計畫的平台表）。
