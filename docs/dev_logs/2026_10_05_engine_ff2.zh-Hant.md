# Engine FF-2：共通測試的計時假設改為結構條件

日期：2026-10-05。**完成**（PR 待開）。分支 `claude/engine-ff2`，base master `6381e9d`。
計畫見 [基礎後續整理 PLAN 的 FF-2 節](../architecture/plans/foundation-followups/PLAN.md)，項目來源見 [HANDOFF](../architecture/plans/foundation-followups/HANDOFF.md) B 節。

## 開始時的決定（寫於實作之前）

檔位：MeshUpdateSmoke 用 high（需要讀懂 render 的 `PresentStatus` 與 scene capture），package checks 與 AssetWatcher 用 medium。不用 ultracode。

### B1 MeshUpdateSmoke（`tests/common/render/sdl_gpu/MeshUpdateSmoke.cpp`）

讀過的事實：

- `Renderer::Render`（`engine/render/src/Renderer.cpp:316-318`）：`AcquireFrame` 回傳空值時回 `Skipped`，不送出任何工作。
- scene capture 只在 `Presented` 的幀執行（`:364`）；`Skipped` 的幀不消耗 `RequestSceneCapture`，請求會留到下一個 `Presented` 幀。

新判定（N、K 在實作前固定，之後不為了通過而調整）：

- 更新迴圈：每次嘗試都更新頂點再 render，最多 N＝240 次嘗試；`Skipped` 不判失敗；必須累積 K＝16 個 `Presented`（與現行「16 幀都 Presented」的覆蓋量相同）。嘗試用盡仍不足 K 就失敗。
- 內容一致：迴圈後以只含 world 網格的 queue 做兩步，每步都 `RequestSceneCapture` 後 render 到 `Presented` 為止（同樣以嘗試次數為界，不用時間）：
  1. 頂點為原始方塊：畫面中心是方塊的顏色。
  2. 以 `UpdateMeshVertices` 把方塊整個移出視野：畫面中心變成清除色。
  這證明「最後呈現的內容就是最後一次更新」。
- 先確認新條件在現行的阻塞取得下通過。

### B2 package checks（`tests/common/ci/test_package_checks.py` 的 `test_timeout_preserves_partial_output`）

- 現況：子程序必須在 runner 的 0.2 秒 timeout 內啟動 Python 並印出 `started`；慢的 CI 主機上 Python 啟動本身就可能超過。
- 新做法：runner（`build/acceptance/common/run_package_checks.py`）不改。測試內把 runner 模組使用的 `subprocess.run` 換成「先等子程序送出就緒訊號（就緒檔），才開始計時」的包裝；計時之後的行為（逾時就終止、帶部分輸出拋出 `TimeoutExpired`）與 `subprocess.run` 相同。
  等待就緒有一個安全上限，只用來避免卡死，不是判定門檻；子程序在就緒前結束時直接收集結果。

### B3 AssetWatcher（`tests/common/core/asset/AssetWatcherTests.cpp`）

- watcher 只比較 mtime（`AssetWatcher.cpp` 的 `ProbeFile`）。測試改為寫入後把 mtime 明確往前推 1 小時（大於 FAT 的 2 秒精度），不再 sleep 20 ms。
- 刪除的測試不依賴時間，拿掉 sleep。

### 突變（驗收 L1）

- MeshUpdateSmoke：所有嘗試都當成 `Skipped`；以及第 2 步不送出頂點更新。兩者都必須失敗。
- package checks：子程序不送出就緒訊號，且不印 `started`。必須失敗。
- AssetWatcher：不改寫檔案、也不推 mtime。必須失敗。
- 突變以複製備份再還原，不用 `git checkout`。

## 實作與驗證（2026-10-05）

### B1 MeshUpdateSmoke

- 照宣告實作（N＝240、K＝16；兩步內容檢查）。現行阻塞取得下：`presented=16 attempts=16`，通過（本機 macOS Intel／Metal，`gpu` 標籤）。
- 突變（備份後修改，再以 `cmp` 確認還原）：
  - M1 每次嘗試都當成 `Skipped`：`presented=0 attempts=240`，exit 1。
  - M2 不送出最後一次頂點更新：`presented frame did not show the latest vertex update`，exit 1。
  - 還原後 exit 0。

### B2 package checks

- 照宣告實作（`run_after_ready`：就緒檔出現或子程序結束後才開始計時；安全上限 30 秒）。`test_package_checks` 28 個測試通過。
- 突變（子程序不印 `started`、不寫就緒檔，只 sleep 20 秒）：計時從未開始，子程序 20 秒後正常結束，runner 判為通過，測試的 `assertFalse` 失敗 → 測試判失敗，突變被抓到。

### B3 AssetWatcher

- 照宣告實作（寫入後把 mtime 推前 1 小時；刪除測試拿掉 sleep）。兩個測試通過。
- **突變結果與宣告不符**：不改寫檔案、不推 mtime 時，20 次中 18 次失敗、2 次通過。
- 原因（已確認）：`engine/asset/src/AssetWatcher.cpp` 的 `FileTimeToSystemNs` 每次都用當下的 `file_clock::now()` 與 `system_clock::now()` 換算，同一個沒變的檔案時間每次換算結果會差到微秒。
  以 scratch 程式複製同一換算：同一個檔案時間換算 100,000 次，有 2,228 次（約 2.2%）與第一次不同。所以 watcher 在檔案沒變時也會偶發回報 `Modified`。
- 這是 Engine 的 AssetWatcher 缺陷，不是測試的計時假設；修正它屬於範圍擴大。**依「超出事前宣告」停下回報**，由使用者決定。

## 使用者決定：AssetWatcher 在 FF-2 一起修（2026-10-05）

- 修正（`engine/asset/src/AssetWatcher.cpp` 的 `FileTimeToSystemNs`）：`file_clock` 與 `system_clock` 的差只在 process 內取樣一次，同一個檔案時間永遠換算成同一個值。公開介面、`AssetChange`、`WatchedInfo` 的欄位都不變；`writeTimeNs`／`lastWriteTimeNs` 仍是 best-effort 的 system_clock 時間。
- 新測試 `AssetWatcher: an unchanged file is never reported`：沒變的檔案連續 Poll 1,000 次，一次都不能回報。
  - 對舊實作：10／10 失敗（抓得到缺陷）。
  - 對新實作：20／20 通過。
- 原先宣告的突變（不改寫、不推 mtime）對新實作：20／20 失敗，符合宣告。
- 使用者：`engine/asset/src/AssetManager.cpp`（hot reload）。行為只少了誤報。
