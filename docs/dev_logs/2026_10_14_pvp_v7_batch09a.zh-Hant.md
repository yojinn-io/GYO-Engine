日期：2026-10-10～14。**完成**（`c26f9c4`；和第 09b 批合併做一次 L2，132／132 完成，Jab5 不成立，記為已知限制，D71）。
計畫與紀錄見[第 09a 批](../object_fps_pvp/plans/v7/09a-input-send-pinning.md)；交接見 [v7 交接](../object_fps_pvp/plans/v7/HANDOFF.md)的「現況」與「P2 進度」。隨 P2 的 PR #73 合併（`6d3f287`，2026-10-14）。

## 做了什麼

- 問題：Client 送輸入的 token 補充率（每秒 60）正好等於命令的產生率，所以 token 沒有力量回到上限。一次停頓或往前的相位修正讓 token 掉到 1 以下之後，每個命令都要多等 11～16 ms 才送出，一直維持下去（「送出被釘住」）。v6 也有同一條規則，但 v6 每個畫面幀發布一次，比較少碰到；v7 由模擬角色以 60 Hz 發布，每個 FPS 都會碰到。
- 修法（設計文件的選項 C 修正版）：補充率與上限都不變；新命令必須等待時，那次送出依等待的時間按比例少扣 token。等待只算到 token 出現為止，送出後不超過 1 個 token。折讓的速率 `InputSendDrainRate`＝80（範圍 75＜R≤85；R 要大於往前修正時 75 Hz 的產生率，又不能讓惡意發布超過 Gateway 每秒 120 包的上限）。
- 恢復步數在實作前先推導：最後一次擾動之後，最多 4 個命令還要等待。
- 等待的紀錄有四個清除點：送出時、連線重設、epoch 變更、完整 ACK。
- 產品三檔（`Movement.hpp`、`ClientConnection.cpp`、`MovementRecoveryTests.cpp`）和 D48 第③步的原型 `e6885b7`（本機 worktree，未合併）逐字相同。`worker_main.cpp` 加實時測試，總預算改用 Input(100,100)，並加「至少 55 次重送」的斷言。
- 不改 wire、不改 Gateway、不改 FireGate。Architecture Delta 很小：`Movement.hpp` 多一個常數並改契約註解。

## 驗證與經過

- 設計（2026-10-10）：1 位 high 設計＋1 位 xhigh 對抗式檢查。檢查推翻了原本的選擇理由與「R 可以改 75」，也修正了突變的預期訊息與測試的插入位置。
- 實作前先停下（D44 的提前條件）：送出被釘住其實「吸收」了 late 修正多出來的領先，修好之後傳輸型的 late 修正可能更常變成 backlog 重設。使用者決定先用 D48 的三步量測確認（記錄在第 09b 批）。之後的量測證實：09a 單獨上線時，100 ms 延遲的重設從 3／16 變成 16／16，所以 09a 必須和 09b 的 B2 一起上（D66）。
- 09a-impl（2026-10-13）第一次停在停止條件「有突變沒被殺」：`wait-not-cleared-at-reset` 存活。推論它是等價突變（連線重設會把 token 補滿，第一次送出的折讓恆為 0）；xhigh 審查確認，並指出等價依賴兩個條件，所以第四個清除點保留（D67）。
- 突變 `v7-09a` 7／7 killed；`drain-85`（仍在設計範圍內）與上面的等價突變寫成「預期存活」。worker 測試的容許值用「30 次最大偏差」與「突變最小偏差」的中點（1.0／1.75／2.25 ms）。
- 全量 CTest 69／69、worker probe 30／30、權威 digest 0 差分（scale 1、3 各 35 情境）。
- 09ab-L1（和 09b 一起）：整份突變目錄 344／344 killed、TSan 0 警告、沒有觸發停止條件。
- 09ab-L2（2026-10-14，修之前 `eabb107` 對修之後 `b205615`，132 次）：修之後被釘住在 17 個案例全部 0（修之前在 x1、ramp 與格點有 1～37）；32 個 late 修正事件之後的送出等待最大 0.833 ms（門檻 1.0）。
- 留下的事：往前的 late slew 期間，命令以 75 Hz 產生，送出每次固定多等約 3.3 ms，這讓 B2 的撤回少 3.3 ms（記在第 09b 批的已知限制）。token 規則有三份拷貝（產品、Arm、測試模型），列為 code smell，本批不處理。
