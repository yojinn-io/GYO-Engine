# PvP v7 第 07 批：Match 的 Tick 改用 Waiter，IpcHost 改用 asio

日期：2026-10-09。**完成**（A `ffe9a99`、B `10003b9`；L2 通過）。
計畫與紀錄見[第 07 批](../object_fps_pvp/plans/v7/07-match-tick-ipc.md)；交接見 [v7 交接](../object_fps_pvp/plans/v7/HANDOFF.md)的「現況」與「P2 進度」。

## 做了什麼

- A：`MatchRuntimeHost` 自己擁有模擬角色（`GYO::Threads`），以 Waiter 等「取樣時刻＋到下一個 Tick 的秒數」這個絕對期限；重設以 Notify 即時喚醒；發布 snapshot、結果、驅逐或完成重設時通知 IpcHost；記錄 snapshot 槽被覆蓋的次數。
- B：IpcHost 改為一條 asio io 執行緒。accept、讀、寫、計時器都是非同步的，1／5／10 ms 的輪詢全部移除。寫出時在 socket 可寫的那一刻選 frame，所以優先序、未開始的 snapshot 可替換、寫到一半的 frame 先寫完，這些行為都不變。連線結束的原因各自記一行。

## 驗證與經過

- 全量 CTest 69／69（權威 digest 不變）、Go 的測試、TSan（IPC 與 host 角色的測試）沒有報告。
- 新的測試：Match 角色 5 件、IpcHost 4 件（真實的 loopback TCP）。突變 3／3 killed。
- 「斷線後要重設」原本抓不到，因為下一次 accept 時也會重設：補了「下一個連線之前 Match 就已清空」的斷言。
- 「改回相對等待」的突變需要對晚醒時間下斷言，在忙碌的 CI 上會誤判，所以不放，改由 L2 的晚醒分布證明。
- 開發跑次：clean-60 的 Tick 晚醒全部 <250 µs（P2-log 以 2～4 ms 為主），Match 程序 CPU 約為 P2-log 的 1/3；backpressure probe 6 案（第一次誤用 action probe，保留）與 25 案矩陣全部通過。

- L2（使用者核准，60 次）通過：after 的 Tick 晚醒全部 <250 µs（兩種主機狀態都一樣），before 的 P99 上界 8 ms；Match 程序 CPU 約 -41％。
- 橫向對比（使用者要求）：第 06 批 L2 後段變慢，是 8 ms 主機狀態下舊 Match 的晚醒與補步，第 07 批之後消失；clean-30 仍受主機狀態影響，可能來自 Client 端，第 08 批之後再對比。
