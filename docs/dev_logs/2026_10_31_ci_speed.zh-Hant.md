# CI 加速：ci-sccache-image-key、ci-drop-macos-x64、ci-fetch-shallow、ci-ctest-parallel

日期：2026-10-31。分支 `claude/ci-speed`。檔位 high（快取 key 那一批是 medium）。引擎 Opus 5.5。

**狀態：** 四批完成。本機 248 個 Python 政策測試全過。ci-ctest-parallel 照使用者核准的判定通過了壓力輪。映像 key 的效果要合併後 master 存了新 seed 才看得到，目前還沒驗證（見「CI 實測」）。

現況報告（量測、候選清單與證據）在共享筆記 `ci-optimization-report.zh-Hant.md`；這份只記這次做了什麼。

## 做了什麼

### ci-sccache-image-key：編譯快取 key 加 runner 映像版本

- **觀測到的問題**：
  - 10-30 的 4 個 macOS L1 job 裡，2 個還原了快取，命中率卻只有 2.8%，build 26～29 分（正常約 3 分）。
  - 這 2 個跑在映像 `macos-15-arm64 20261028.0489`；命中率 86～92% 的 2 個跑在 `20260907.0337`。
  - 原本的 key 只含 clang 版本字串，兩種映像的字串相同。
- **改法**（`.github/actions/native-setup/action.yml`）：
  - 儲存的 key 加入 `image-<ImageVersion>-`。
  - restore-keys 先找同映像的前綴，沒有才退回原本的 family 前綴；原本的前綴也能對到改版前存的 seed。
- **守衛**：`test_workflow_gates.py` 改為要求「先同映像、後 family」的順序，以及 key 含映像。只有收緊。突變（兩行 restore-keys 對調）→ 測試失敗。

### ci-drop-macos-x64：macos-x64 下架發布，本機仍可建置

- **使用者的決定**：拿掉 CI 的 macos-x64。知道本機是 Intel Mac 後，選了「下架發布、本機仍可建置」。
- **Architecture Delta**：
  - `build/acceptance/common/package_contract.py` 分成兩個概念：
    - `PLATFORMS`：可建置的平台，4 個。
    - `RELEASE_PLATFORMS`：CI 建置、驗證並發布的平台，3 個。
  - 只用 `RELEASE_PLATFORMS` 的地方：
    - CI 的 L1 列與封裝列（`app_registry.py` 的 `TOOLCHAINS`，以及 registry 與工具 registry 的匯出）
    - release train、壓縮檔名稱、Draft 的 release evidence
    - Go 服務的交叉編譯
  - registry 與產品宣告的 macos-x64 一律濾掉。
  - 依賴方向和 owner 都沒有變。
- **保留**（Intel Mac 本機要用）：
  - CMake 的平台判定（Darwin/x86_64 → macos-x64）
  - `ci-macos-x64` preset：v7 時在本機用它打過 LAN 測試包，所以留下，只改說明
  - 產品的 `checks.json` 與 Go 服務宣告：產品檔案都沒改
- **刪除**：
  - native-setup 的 Rosetta 2 步驟、`cpu-execution` 輸入、macOS x64 host 分支
  - `cpu_execution` 的 `rosetta2` 值
- **失去的保證**：x86_64 macOS 的建置、CPU 測試與安裝驗收不再由 CI 檢查。
- **測試**：
  - 新增：
    - registry 匯出會濾掉 macos-x64
    - 只宣告 macos-x64 的 release evidence 或 Go 服務會明確失敗；和其他平台混在一起時只濾掉它
    - 沒有 Rosetta 步驟
  - 改了判定的測試：
    - 以前要求 4 列 L1 和 4 個 toolchain 包，現在是 3 個。
    - 以前接受 `rosetta2`，現在拒絕。
  - 這是使用者決定的下架造成的必然變更，沒有為了讓測試通過而放寬的地方。
  - 突變：拿掉下面任一處過濾，對應的測試都會失敗。
    - `go_checks` 的平台過濾
    - release evidence 的平台過濾
    - `export_registry` 的平台過濾
- **文件**：`docs/releasing.ja.md`、`docs/releasing.zh-Hant.md`
  - 第 2、3、5、6、7、10 節的平台數、L1 列數、附件數
  - 第 5 節新增「macos-x64 只供本機建置」與失去的保證

### ci-fetch-shallow：其餘 FetchContent 依賴改為 shallow clone

- 原本 doctest、imgui、nlohmann_json、SDL3、SDL3_image、SDL3_ttf 會 clone 整個 git 歷史。這次加 `GIT_SHALLOW TRUE`，和已經這樣做的 protobuf、asio、httplib、ufbx 一致。tag 與內容都不變。
- **本機量測**：

  | 依賴 | 完整 clone | shallow | 大小 |
  | --- | --- | --- | --- |
  | json | 19 秒 | 2 秒 | 351 MB → 28 MB |
  | SDL | 11 秒 | 2 秒 | |
  | imgui | 12 秒 | 1 秒 | |

- **本機全新 configure（`test` preset）**：成功，12 個 clone；sdl3_ttf 是 shallow，freetype 子模組也有取到。
- **和計畫不同的地方**：計畫寫的是「快取依賴原始碼」，這次改成 shallow。
  - 理由 1：Windows configure 的 130 秒裡還夾著 protobuf 等依賴自己的 configure 檢查，純 clone 時間比原本估的少，快取能省的也跟著變少。
  - 理由 2：快取有「宣告改了卻用到舊原始碼」的風險。
  - 預期節省修正為每個 job 約 35～45 秒。要不要再做快取，等 CI 量完再決定。

### ci-ctest-parallel：ctest 並行

- **改法**：L1（`cross-platform.yml`）與封裝 job（`build-and-validate.yml`）的 ctest 加上 `--parallel $env:CMAKE_BUILD_PARALLEL_LEVEL`，並行數和該列的建置相同：Windows／Linux 為 4、macOS 為 2。本機 preset 不變。
- **守衛**：`test_workflow_gates.py` 改為 `--parallel` 必須存在，其餘選項仍只允許 `--output-junit`，L1 不能加 filter。只有收緊：舊判定擋下的「加了 filter」的情況，新判定一樣擋下。
- **事前盤點**：
  - 沒有任何測試標 `RESOURCE_LOCK`／`RUN_SERIAL`。
  - IPC 類測試以「綁 port 0 取號、關掉再用」找空 port（`tests/object_fps_pvp/IpcHostTests.cpp:48`），並行時理論上可能撞號。
  - 對時序敏感的測試：`steady_clock`、`close_timing`、`platform_sdl_concurrency`、threads／time 等。
- **判定**（看結果前宣告並經使用者核准）：
  - 分支上暫時加一步 `ctest --parallel P --repeat until-fail:5`，L1 三列都要 0 失敗。
  - 之後移除這一步，再跑 2 輪正常 L1（一輪推送觸發，一輪手動 dispatch，含 Quick）。
  - 有任何失敗就停下回報，不重跑覆蓋。
- **結果**：
  - 壓力輪 run 41162780271：三列都 0 失敗，各列的總執行次數如下表。暫時步驟由 commit 233aa4e1 移除。
  - 2 輪正常 L1：見「CI 實測」。

  | 列 | 總執行次數 |
  | --- | --- |
  | windows-x64 | 530 次（106 個測試） |
  | linux-x64 | 510 次（102 個測試） |
  | macos-arm64 | 510 次（102 個測試） |

- **過程中的失誤**：
  - 移除壓力步驟時，`git revert` 沒有成功，接著的 `--amend` 改到了壓力 commit 本身，推送被拒。
  - 修正方式：在遠端的壓力 commit 上，用 `commit-tree` 接一個樹和 bd0f4378 相同的 commit 再推送，沒有改寫遠端歷史。

**映像 key**：
- 這兩輪都還原到改版前的 family seed（例如 `...-ci-macos-41156597023-1`）。master 還沒存過含映像的 seed，所以還原時都走 fallback。
- macOS 這次跑在 `20261028.0489`，命中率 91～92%，因為最新的 seed 剛好也來自這個映像。
- 效果要合併後 master 存了新 seed，再遇到映像混用時才看得到。目前尚未驗證。
