# Engine IP-2：縮放時不停住主迴圈（live frame）

日期：2026-10-05。**完成（縮小交付）**，PR [#53](https://github.com/yojinn-io/GYO-Engine/pull/53) 已合併（`db1815c`）。分支 `claude/engine-ip2`，疊在 FF-7（`b2fda8c`）上。
計畫見 [輸入與呈現 PLAN 的 IP-2 節](../architecture/plans/input-and-present/PLAN.md)，紀錄見 [HANDOFF 的 IP-2 紀錄](../architecture/plans/input-and-present/HANDOFF.md)。

## 開始

使用者指示「先把 Engine 的任務清了」，並做了以下決定：

- D16：IP-2 同時處理拖動與縮放。
- D17：xhigh 審查 agent 1 個。
- D18：PR 以功能線為單位。
- FF-7 先做。

檔位 high。

讀 SDL 3.4.0 原始碼（靜態）確認：

- macOS 縮放時，Cocoa 在 `SDL_PollEvent` 內執行追蹤迴圈。開始縮放後，SDL 以 60 Hz 送出 `SDL_EVENT_WINDOW_EXPOSED`（`data1`＝1），並允許在 event watcher 中直接重繪。
- Windows 的拖動與縮放 modal 迴圈，走同一條路徑。

## 做法

1. **`RuntimeLoop::RunLiveFrame`**：在 `ProcessEvents` 進行中，執行一組 `Update`／`Render`。
   - frame 編號以組為單位；delta 是與前一組開始的時間差，總和等於經過時間。
   - 沒有 live frame 時，行為與先前逐一相同。
   - live frame 中要求 Stop 時，在 `ProcessEvents` 返回後結束。
2. **`SdlPlatform::SetLiveFrameHandler`**：event watch 只在設定了處理函式時存在。
   - 只處理本視窗的 `EXPOSED`（`data1`＝1）。
   - 先確認在主執行緒，才讀取平台狀態。
   - 只在 `PumpEvents` 執行中呼叫，而且不會重入。
3. **提出需求的消費端的接線**（同一個 PR）：
   - live frame 中使用空的輸入幀：不消費按鍵、指標、UI 輸入，也不切換相對滑鼠模式。
   - `pump` 前段產生的點擊與 R 邊緣，保留給之後的正規更新。
   - 慢事件處理的日誌加上 `observer_ms` 與 `live_frames`。
4. **取得的拆分診斷**：`SDL_WaitForGPUSwapchain`（fence）＋`SDL_AcquireGPUSwapchainTexture`（drawable）。兩者合計 ≥50 ms 時記錄 `fence_wait_ms`、`drawable_ms`。量測後保留為常駐診斷。

## 收尾（D19）

使用者決定 D7 選 B（分執行緒），但延到消費端的下一個版本，另立計畫：主執行緒（事件＋畫面）、模擬、網路三個角色分離。理由是剩下的兩種停頓，在單執行緒上無法一一補齊：

- 按住空窗；
- `nextDrawable` 停頓。

IP-2 交付：

- 2b：縮放拖動中不停住；依原始碼推斷 Windows 的 modal 迴圈也適用，但沒有實測。
- 拆分診斷。

2c 不實作。xhigh 審查只審 2b，在 session 重新載入、審查 agent 可以使用後執行。

## Architecture Delta

見 PLAN「2026-10-05 範圍擴大」節的七點：

- `RuntimeLoop` 新增「`ProcessEvents` 期間可以插入 live frame」的契約，只對 opt-in 的消費端生效。
- `SdlPlatform` 新增 event watch 與處理函式。
- 沒有新增依賴邊：由消費端把 platform 與 `RuntimeLoop` 接起來。
