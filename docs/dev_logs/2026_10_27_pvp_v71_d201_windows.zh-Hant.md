## 2. 確認案例真的跑了（`-s`）

| 指令 | exit | 結果 |
|---|---|---|
| `gyo_os_tests -s -tc="*resolve*"` | 1 | 5 案例：2 passed、3 failed（98 斷言 6 失敗）。`DefineDosDeviceW` 的磁碟代號案例**有跑**（Z:）；`\\localhost\C$` 案例**有跑**（可連到） |
| `gyo_os_tests -s -tc="*symbolic*"` | 0 | **提早返回**：`symbolic links unavailable here: Function not implemented`（0 斷言） |
| `engine_tests -s -tc="*symbolic link*"` | 0 | **提早返回**：同上（`NativeFileSystemTests.cpp:107`，0 斷言） |
| `gyo_ui_editor_core_tests` | 0 | 輸出有 `symbolic links unavailable here: Function not implemented` → **提早返回** |

`*resolve*` 的 3 個失敗（對照值是 libstdc++ 的 `weakly_canonical`，和 MSVC 不同）：
- `FileChangeTests.cpp:192`：輸入 `.../real/file.txt/`，引擎 `.../real/file.txt/`，對照 `.../real/file.txt`（結尾 `/`）
- `FileChangeTests.cpp:247`（磁碟代號 Z:）：引擎解析成實際目錄 `C:/Users/.../gyo-os-resolve-drive-.../existing/missing/y.json`，對照保留 `Z:/existing/missing/y.json`（3 個斷言）
- `FileChangeTests.cpp:270`（UNC）：`//localhost/C$/.../existing` 時對照拋例外 `cannot make canonical path`；`.../existing/missing/x.json` 時引擎回傳 `/localhost/C$/...`（**少一個斜線，產品碼**：`engine/os/src/windows/Files.cpp:617` 的 `lexically_normal()`），對照 `C:/localhost/C$/...`

symlink 為什麼不可用：libstdc++ 的 `create_directory_symlink` 在 Windows 上回 "Function not implemented"（和 Developer Mode 無關），所以 MinGW 建置下所有 symlink 案例都提早返回。

### 基準線（相同方法，120 s 上限）
11 條裡 10 條通過。**os-g18-windows-extra-link 不通過**：它跑全部的 `gyo_os_tests`，56 個案例中 2 個失敗：
- `Os files record the process ANSI code page`：ACP＝65001（同 os-f4）
- `Os files list the font directories that exist, system first`（`FileChangeTests.cpp:341`）：`C:/Users/<user>/AppData/Local/Microsoft/Windows/Fonts is not a documented font directory in its place`。契約（`docs/architecture/os.md:121`）有列 `%LOCALAPPDATA%\Microsoft\Windows\Fonts`，但測試在 Windows 上的預期清單（`FileChangeTests.cpp:318-323`）只放了系統的 `Fonts`。這台有使用者安裝的字型，那個資料夾存在。**這是測試的缺漏**，和工具鏈無關；CI 的 runner 沒有使用者字型，所以沒抓到。

### 突變（10 條）：9/10 killed
```
run_mutations.py --build-dir build/target/_build/ci-windows --catalog docs/architecture/plans/os-subsystem/scripts/mutations.json --only <10 ids>
```
exit 1。
- killed：p1-no-long-path-form、p1-long-path-from-too-high、os-f9-windows-unc-long-path、os-f10-windows-unc-passthrough、os-f11-windows-namespace-as-unc、os-x7-windows-rename-not-replacing、os-x8-windows-final-path-prefix-kept、os-x10-windows-resolve-stops-early、os-x11-windows-root-opened
- **survived：os-w10-windows-root-created**。原因是從程式碼推論的，沒有另外實驗：突變讓 `CreateDirectories` 從第 1 個字元開始，對 `C:/...` 只多檢查 `C:`。`C:` 是 C 槽目前的資料夾，`IsDirectory` 成立就直接 `continue`，行為不變。只有 UNC 根目錄（`//server`、`//server/share`）才會不同，但 `*create directories*` 的兩個案例都在 `%TEMP%`（磁碟路徑）底下，沒有 UNC 案例。**任何 Windows 機器上都會存活，是測試缺案例**，不是環境問題。

### 結論
- 在 MinGW 上看到的 `remove_all` 卡死、UNC 和磁碟代號語意的失敗，**MSVC 上都沒有出現**。確認是 MinGW libstdc++ 的問題。
