最大的一塊是**卡片 dispatch 順帶跑的 Quick（40%）**，比卡片 dispatch 的 L1 本身還多。卡片 dispatch 是為了替 draft PR 拿 L1（`Report dispatched L1` 也只回報 L1），PR 的合併門檻從來不含 Quick。

其他查到的事實：

- `concurrency` 的 group 只有 PR 事件按 PR 編號共用；dispatch 與 push 都是 `run_id`，永遠不互相取消（卡片 brief 第 5 點屬實）。
- gyo2 沒有 branch protection 與 ruleset；master 的必要檢查只有 `CI gate`。
- 合併前 `gh pr ready` 觸發的 ready_for_review run：head 若已有 dispatch 的綠 L1，原本的 docs-increment 不看 head 本身（a8587193 起「head 自身は使わない」，當時還沒有 dispatch），所以整套 L1 重跑；PR 合完那個 run 還在跑。

## 改了什麼

- `build/ci/common/ci_scope.py`
  - 沿用 L1 的走訪從 head 本身開始。head 包含目標分支尖端、且三列 L1 的最新 check run 都成功時，理由 `head-verified`，略過 L1。條件與 docs-increment 相同（目標分支只前進 → 當時測的合併結果就是 head 的樹），所以不放鬆門檻；目標分支前進了就照常跑 L1。
  - 手動執行時，分支有 open PR（`--open-pull-requests N`，N > 0）就只跑 L1，理由 `pull-request-dispatch`；沒有 PR 的分支、tag 照舊 `integration`（L1＋Quick），gyo2 與 master 的整合紀錄不變。
- `.github/workflows/cross-platform.yml`
  - PR 觸發加 `closed`：關閉或合併時，同一 PR group 的新 run 取消還在跑的 run；closed 事件本身 `scope` 與 `CI gate` 都不執行（沒有合併在等這個結論；重新開啟會再跑）。
  - dispatch 依 ref 共用 group，新的取消舊的（`cancel-in-progress: event_name != 'push'`）；推送 master 仍各自一組。
  - `scope` 對 dispatch 的分支查 open PR 數，傳給 `ci_scope.py`。
  - `Report dispatched L1` 改成 `!cancelled()`：被新 dispatch 取代的 run 不寫 `L1 (dispatch)` status，也不把 PR 留言改成 failure。
- 測試：`test_ci_scope.py`、`test_workflow_gates.py` 跟著改（觸發清單、concurrency、classifier 的 env 與 gh 呼叫、gate 與 report 的條件、head-verified、pull-request-dispatch）。
- 文件：`docs/releasing.zh-Hant.md`、`docs/releasing.ja.md` 的 §1、§3、§4、§9 規則 5、§10.1。規則 5（改 `.github/` 等的 PR 要確認 Quick 封裝）改成用 `package` 標籤或手動 Package trial，因為有 PR 的分支手動執行 Cross-platform CI 已不跑 Quick。

## 比過、沒做的

- 拿掉 `ready_for_review`：Ready 之後 head 上的 `CI gate` 會停在 draft 時「略過 L1」的通過結果，master 的必要檢查等於沒有 L1 也能過，是放鬆門檻。改成保留觸發、能沿用就沿用。
- `paths-ignore` 只改 docs：觸發層的篩選會讓 `CI gate` 不回報；ci_scope 已有 `docs-only` 在 job 內判斷，維持現狀。
- dispatch 也沿用已綠的 commit：`Report dispatched L1` 要另外處理「略過但沿用」的回報，卡片每次 dispatch 幾乎都是新 commit，收益小，不做。
- merge queue：會改合併流程與門檻的形狀，照卡片指示不在本卡做。
- gyo2 合併後的驗證頻率：主會話自己改（一批一次），不在本卡。
