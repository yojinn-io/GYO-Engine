## 02a：舊驗收模式移除與版本常數

### 停止與重新決定（D14）

計畫依 D11④「附涵蓋對照表後刪除」，前提是 `weapon_short` 的涵蓋已由動作短測取代。開工盤點後發現這個前提只有一部分成立：
只有觀察方的「HP=0 仍可移動與射擊」是 v4 語意，其餘多數斷言別處沒有涵蓋。依停止條件停下回報後，
使用者決定：**把獨有斷言移進 `action_short`，再刪除 `weapon_short`**（D14）。

### `weapon_short` 涵蓋對照表

| `weapon_short` 的斷言 | 處置 |
|---|---|
| 觀察方 HP=0 仍可移動、射擊（v4 語意） | 刪除；v5 的死亡抑制由 `action_short` 的 `dead-click`／`dead-move`／`dead-stop` 涵蓋 |
| 擷取點擊不產生射擊 | `action_short` 既有 `capture` |
| 按住射擊只出一發、一次動畫 | `action_short` 既有 `held_fire_one_shot` |
| 本機射擊回饋出現在首個成功 Presented 幀，且早於權威裁決 | 移入：每發射擊檢查，`local_feedback_before_decision` |
| 射擊到首個 Presented 的時間 | 移入：逐發記錄 `submission_to_presented_seconds`；分析器要求筆數等於射擊數、值有限且 ≥0 |
| 明確注入第二發，權威回 Cooldown 拒絕 | 移入：在 `held-shot` 後注入，`authority_cooldown_wall_and_hit` |
| 打牆得到 World 判定、命中標記、命中次數 | 移入：同上（打牆 11 發、擊殺 4 發） |
| 移動＋轉向＋射擊同一幀，滑鼠位移只消耗一次 | 移入：第一發打牆改為 `combined-wall-shot`，`movement_turn_shoot_mouse_once` |
| 下一幀不重播滑鼠位移 | 移入：`mouse_delta_not_replayed` |
| 失焦、失焦中按住、Tab、拖動視窗：不產生射擊並釋放擷取 | 移入：`focus-loss`／`focus-gain-held`／`tab-release`／`drag`，檢查不配發 ID 且擷取已釋放 |
| ESC 清空武器狀態 | 移入：`escape_clears_weapon` |
| 重新加入時滿血、沒有殘留射擊或裁決 | 移入：`rejoin_full_hp_no_stale_effects`（另加彈匣全滿） |
| ESC 前 ID 數＝SDL 送出數＋1 次注入 | 移入：`escape` 事件的檢查 |
| 存活時每個 Presented 幀都提交第一人稱武器 mesh 與材質 | 移入：逐幀檢查 |
| 第一人稱 GPU capture：draw／shoot／resize／wall-depth | 移入 `action-capture`：攻擊方 8 張（原 4 張＋這 4 張），觀察方 4 張 |
| `run_weapon_short.py` 的 `latency` 案例 | 刪除；`run_timing.py --gui --short` 跑同一個 `--latency-short` 模式，並有自己的視窗干擾閘門測試 |
| `weapon_result` 的平均 FPS ≥ 名義×0.85 | 刪除；屬第 8 項的計時假設，不搬到新位置 |

時程：攻擊方的動作排在原本的 v5 動作之後（10.2 秒起依序是視窗互動、resize、走向牆邊 2 秒、ESC 與重新加入），
ESC 排在目標重生被呈現之後。預設長度由 15 秒改為 18 秒，範圍 18～25 秒。

### 第 6 項需要的逐幀欄位

- `action_short` 的每個 Presented 幀記錄 `presented_weapon`（`active`、`dead`、`life`、`submitted_meshes`、`shooting`、`last_action`）。
  選 `action_short` 而不是 `player_short` 的理由：它已經有本機死亡與重生的時程。
- 分析器（`run_action_short.py`）：本機死亡且某個 Presented 幀的 `submitted_meshes>0` 判失敗。突變測試：`test_dead_local_player_presenting_weapon_meshes_fails`。
- 限制（照計畫）：產品在 `!Alive()` 時直接把這個欄位設為 0，所以它抓不到不經 `SubmitWeapon` 的殘留畫面；第 05 批要另訂觀測量。

### legal 模式涵蓋對照表

`run_action_legal.py`、probe 的 `--legal-shots`、`action_evidence.analyze_legal` 都刪除。
`analyze_legal` 的檢查在 v5 長測分析器 `gameplay_soak_evidence.py` 中的對應：

| `analyze_legal` | `gameplay_soak_evidence` |
|---|---|
| 原始送出不重複、裁決不重複、裁決都有對應送出、沒有遺漏 | 重複送出、重複裁決、遺漏預宣告動作、終局裁決不符 |
| 量測窗口與宣告長度一致 | 預宣告的循環分母、probe 在宣告結束前停止 |
| 射擊間隔 ≥400 ms（v4 定速規則） | v5 以預宣告計畫與 10 Tick 冷卻取代：裁決必須與計畫一致 |
| 接受與拒絕碼一致、拒絕不造成傷害、傷害歸屬 | 同名檢查 |
| 每位玩家都有實際 HP 下降 | 每個循環的預宣告致命命中恰好傷害該生命一次 |
| 裁決有 Match Tick、產生到裁決 P95 ≤100 ms、到 Client P95 ≤150 ms | 同門檻 |
| 幀時間單調、每幀 HP 與已知效果一致 | 幀時間單調、權威 HP／彈藥／換彈與逐生命效果一致 |
| 送出數＝裁決數＝退休數、批次 ≤8、datagram ≤1200 | 動作 ID 連續並跨生命退休、批次與 datagram 上限 |
| 移動與動作窗口上限 | 有界命令／動作窗口 |
| 乾淨跑次沒有 ≥100 ms 間隔、沒有凍結、移動證據通過 | 全程 ≥100 ms 幀、Match 掉時、移動 Actual 門檻與 ≥99% |

`action_probe.py` 的 `network*`／`burst2` 原本靠 `--legal-shots` 在非 gameplay 模式運作。現在改為明確報錯並指向 `run_gameplay.py`；
v5 的 25 案矩陣一直是經 `run_gameplay.py`（`--gameplay-v5`）執行，不受影響。

## 02b：計時器晚醒分布

- 新增 `timer_baseline.hpp`：probe 開始時跑 3 秒空的 60 Hz 迴圈，記錄晚醒量與幀間隔的 P50／P99／最大值，以及間隔超過 18 ms 的比例。
  3 秒（180 個樣本）是為了不壓縮 runner 對 probe 啟動的時限（headless 只給 10 秒寫出 ready 檔）。
- 迴圈的睡法必須和 probe 一模一樣，分兩種：
  - GUI probe：每幀開頭起算，用 `SDL_DelayNS` 睡剩餘時間（`frame_relative`）。寫進 `PlatformFingerprint`（JSON 的 `timer` 與文字報告的 `platform_timer_*`）。
  - headless probe（`--gameplay-v5`）：固定截止時間，`deadline += period`，只在睡前已落後時才重新對齊（`absolute`）。寫進 `action-client.json` 的 `timer`。
  - 第一版把 headless 也寫成每次醒來重新對齊，間隔 P50 變成 21.5 ms（誇大）。開發實跑時發現並改正。
- 只供解讀：
  - `presentation_evidence.platform_evidence` 帶出 `timer`；欄位壞掉時只把 `timer` 標為 invalid，平台狀態仍是 recorded。
  - `gameplay_evidence`、`gameplay_soak_evidence` 在結果中帶出 `timer_baseline`。
  - 不依 OS 名稱分支。
- 判定不讀它的證明：
  - 延遲分析器：同一組短測資料，加上極端的或壞掉的計時器欄位，通過與失敗、錯誤訊息都和沒有欄位時相同（突變測試）。
  - `gameplay_evidence`、`gameplay_soak_evidence`、`run_action_short`：原始碼守衛測試，`timer` 只能出現在報告輸出那一行。
    手動突變（在 `gameplay_evidence` 加一條讀 `timer` 的檢查）確認守衛會失敗。
- 開發實跑（headless `clean-60`，不開視窗，不計次）：
  - `pvp-v6-batch02-dev-gameplay-1`：第一版（重新對齊錯誤）。
  - `pvp-v6-batch02-dev-gameplay-2`：改正後通過；180 樣本，晚醒 P50 4.4 ms、P99 8.0 ms，間隔 P50 16.66 ms、P99 24.3 ms，超過 18 ms 的比例 31%。
    與 v5 第 05 批記錄的空迴圈觀察（P99 20.5 ms、約 22～25%）同一量級。

## 02c：pvp 計時判定改為結構條件

開工盤點後確認，有兩處要變成結構條件，必須由產品帶出送出端的序號或時間；本批不改產品。依停止條件停下回報，使用者決定：**做完可行的，其餘記錄**。

| 位置 | 處置 | 誤判情境測試 | 真缺陷突變 |
|---|---|---|---|
| ① `player_presentation_evidence.py` FPS ≥ 名義×0.85 | 判 `invalid_capacity`（D11③）：不計次、不算通過；同跑次其他檢查照判。`run_player_short.py` 不因 invalid 中止其餘案例，摘要列出 `invalid_cases`／`unverified` | `test_cadence_below_85_percent_is_invalid_not_failed` | （依 D11③，FPS 不足屬環境能力，不是產品失敗） |
| ① 同檔劇本時窗 | 改以攻擊方事件**實際觸發**的時間為錨（兩個 probe 共用同一個主機時鐘），宣告的偏移量不變；準時的跑次結果逐位元相同。hold 與 resumed 改由 `holding` 旗標與事件順序決定 | `test_windows_follow_when_the_actor_input_really_fired`（晚 120 ms 的事件） | `test_missing_or_reordered_actor_input_is_still_an_error` |
| ② `worker_main.cpp` 重送 55～65 次、相鄰 ≥14／≥30 ms | **不改，保留原條件**：封包只有 GYOP 的 Seq，沒有送出端時間；用接收時間判節奏，是目前唯一可用的觀測 | — | — |
| ③ 每秒 ≤120 包（relay 接收時間的滑動窗） | **不改**：Gateway 自己的限流器就是以接收時間計數，驗收器照產品語意檢查是對的 | — | — |
| ③' 每秒 ≤31 個動作／結果 | **不改，保留原條件**：理由同 ② | — | — |
| ④ `action_short.hpp` 射擊間隔 0.25 秒、換彈 200 ms 餘裕 | 射擊事件等產品的本機閘門（牆鐘冷卻與 Snapshot Tick ≥ `nextAllowedShotTick`）開了才送；換彈檢查等 `reloading` 結束。延後記錄在 `event_waits`；單一事件延後超過 1 秒就失敗 | 開發實跑（見下） | 閘門 1 秒內沒開就失敗 |
| ⑤ `gui_main.cpp` 命令步數的 1 ms 容差 | 改為括號式上界：產品這次與上次的時鐘取樣，必定落在「上次 Update 開始」到「這次 Update 結束」之間 | 開發實跑 | 重複計入停頓仍會超過上界 |
| ⑤ 穩定幀 ≤40 ms | 改為「連續成功呈現的幀」（frameId 相鄰、未凍結） | 開發實跑 | 移動中的幀占比仍要 ≥80% |
| ⑤ 名目 83 ms 停頓 | 「短停頓不得重設 epoch」改以產品實際取樣到的經過時間下界判斷；下界 ≥100 ms 歸為長停頓。報告新增 `product_elapsed_lower_bound_ms` | 開發實跑：名目 83 ms 的 case 2 下界為 101 ms | 下界 <100 ms 的停頓（case 3 為 87 ms）仍要求不重設 |
| ⑥ `presentation_evidence.py` 遠端交越不得早於本機 20 ms | 改以幀的先後判斷：遠端第一個越過門檻的幀，不得早於本機最後一個未越過的幀 | `test_remote_order_is_judged_by_frames_not_a_time_tolerance`（插值得到 -20.8 ms 的情況） | 同一測試的「遠端已越過、本機尚未」 |
| ⑦ 計次 GUI 輪：任一 OS 視窗事件即無效 | 攻擊方呼叫 `SDL_RaiseWindow` 時，依當下焦點狀態決定是否等待完成事件（攻擊方原本沒有焦點才等 focus_gained；觀察方原本有焦點才等 focus_lost）。第一個完成事件另計為 `raise_completion_events`，不算干擾；其他事件照算 | `test_raise_completion_is_recorded_apart_from_interference` 與開發實跑 | 之後的焦點事件仍算干擾 |
| ⑧ `backpressure_test.go` 的 ticker 節奏 | ticker 屬於測試自己的生產者，不是產品程式。改成確定性步驟：消費端擋住時送出 N 個、只留最新一個；釋放後第一個收到最新值；之後一送一收都是當前值；再加一段並行檢查單調性 | 不再依賴 ticker 與 100 ms 間隔 | 手動突變：通道保留最舊值、送出時阻塞，兩者都失敗 |
| ⑨ 「≥100 ms 停頓」約 83 ms 即觸發 | `acceptance_util.STALL_RULE`，寫進 `gameplay_evidence` 與 `gameplay_soak_evidence` 的報告 | — | — |

⑦ 的第一版會在「攻擊方本來就有焦點」時一直等著完成事件，可能誤吞之後真正的干擾。開發實跑時發現並改正。
