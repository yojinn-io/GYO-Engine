## 1. 已觀察到的事實與上限

下表是現在程式裡的上限，以及推到 1 km²（0.5 m 一格＝2000×2000 格）時的估計。
**估計欄都是推算，沒有量測**；它們的用途是決定 `ve-scale-measure` 要量什麼，不是結論。

| 項目 | 現況（出處） | 768 區塊的合成圖（已量） | 1 km² 的推算（未量） |
|---|---|---|---|
| 格子檔大小上限 | 16 MiB，超過就拒讀（`MaxGridTextBytes`，`GridDocument.cpp`） | 3.83 MB（約 5.0 KB／區塊） | 只有地面一層：約 15,625 區塊，約 1 MB。和合成圖一樣密（48 格高）：約 46,875 區塊，約 230 MB，**超過上限** |
| 記憶體中的格子 | 每區塊 4096 格 × 4 bytes＝16 KiB（`ChunkCellsArray`） | 約 12 MiB | 46,875 區塊時約 730 MiB |
| 拖曳開始時的複製 | 按下滑鼠時複製整份文件給拾取用（`Drag::base`） | 量到的 P1 是每幀編輯，不含這一下 | 每次按下複製約 730 MiB |
| 調色盤／形狀的 undo | 前後兩份完整文件（`DocumentStep`） | 約 24 MiB／步 | 約 1.5 GiB／步 |
| 整張重烘（調色盤、形狀變更時） | `RebakeChunks` 全部重烘 | 578 ms | 約 0.75 ms／區塊 × 46,875 ≈ 35 s |
| 預覽畫幾個區塊 | 全部，沒有視錐剔除（`PreviewScene`） | P1 p95 7.48 ms | 未知；畫的 mesh 數約 60 倍 |
| 一次編輯的格數 | Shape、Extrude、Laser 最多 2^20 格（`MaxBoxCells`）；Brush 最大 16（8 m） | — | 1 km² 的地面約 4M 格，一次填不完 |
| 拾取的距離 | 光線最多走 1024 格（512 m）（`Pick` 的 `maxCells`） | 足夠 | 從遠處看整張地圖時點不到 |
| 編輯平面的格線 | 只畫游標附近 ±16 格 | — | 遠景沒有參考格線 |

**結論只有一句**：區塊化讓**烘焙後的地圖**沒有大小上限，但**格子檔、記憶體、undo 與預覽**還有上限；TODO #9 的「邊界可以長」在格式上成立，在規模上沒有驗證。所以 #9 的第 1 項不是「已經可以」，而是「要先量」。

## 2. 文件模型

### 2.1 格子（v1，現況）

格式見 [architecture.md](architecture.md)「The grid」。編輯模型 `EditSession` 持有一份 `GridDocument`：
- 區塊以座標為鍵（`std::map`），空區塊不存；
- 格子的值是「方塊＋朝向」；
- 編輯只經 `SetCell`／`PaintCell`／`FillBox`，以及調色盤與形狀庫的編輯。

下面的設計都以「只有這一份格子會被烘焙」為前提（DI 7：看到的就是遊戲讀的）。

### 2.2 選取集合

- **是什麼**：一組格子座標，屬於編輯器的狀態，**不寫進格子檔**，也不進烘焙。
- **表示**：區塊稀疏的位元集合（每區塊 4096 bit＝512 bytes；整區塊全選時只記一個旗標）。理由：大面積選取（整片地面）不能逐格存。
- **進不進 undo**：Goxel 把選取放在歷史快照裡。建議：選取的變更**不單獨成為一步**，但每一步記下「當時的選取」，undo 時一起還原。這樣「選取 → 移動 → undo」回到的是移動前、仍然選著的狀態。
- **選取的形狀**：盒（Goxel 的 Selection 工具）與「依方塊種類相連」（Goxel 的 Fuzzy Select，把「顏色差在門檻內」換成「同一種方塊」）。§3.7。
- **其他工具怎麼看選取**：照 Goxel，有選取時 Extrude 只推選取範圍內的面、Delete 清掉選取的格、Move 移動選取的格；Brush 等繪圖工具可以用「只畫在選取內」的開關（Goxel 的 snap 有 Selection 項；我們先只做「限制在選取內」，列為 `ve-select-move` 的範圍內選項）。

### 2.3 prefab（可重用的格子片段）

**格式（Q5 建議 (a)）**：一個 prefab 就是一個 `gyo.voxel_grid` v1 檔。

- 錨點是 origin（相對座標 (0, 0, 0) 那一格）。存 prefab 時，錨點取選取範圍的最小角，y 取選取的最低層。
  - v1 規定 origin 的 y 是 0。prefab 的格子仍可在 y ≥ 0 的任何位置，錨點取最低層就不違反。
- `cell_size` 必須和目標地圖相同，否則拒絕（不做重採樣，TODO #9 已定）。
- 方塊與形狀庫隨 prefab 一起存（它是完整的格子檔）。
- 好處：同一個解析器 `ParseGrid`、同一套規則；CLI 的 `build-map` 也能直接烘焙一個 prefab 來看。
- 代價：prefab 檔帶著自己的調色盤，貼上時要對應（下面）。

**貼上時的方塊對應（Q6 建議 (a)）**：
- 依方塊名字對應；目標沒有的方塊，連同它的形狀加進目標的調色盤與形狀庫（加入是一次調色盤編輯，會整張重烘，§1）。
- 同名但形狀或顏色不同：拒絕整次貼上，列出衝突的名字。
- 形狀依名字對應，規則相同。

**放置的變換**：平移、繞錨點的 90° 旋轉、鏡像。

- **旋轉**：24 個朝向本身就是方塊的旋轉群（architecture.md「Orientations」）。把整個 prefab 轉 R（24 個之一）時：
  - 每格的位置 p 變成 R·p；
  - 每格的朝向 o 變成 o′，o′ 是使 `OrientationMatrix(o′) = R · OrientationMatrix(o)` 的那一個。
  - 因為 24 個旋轉對乘法封閉，o′ 一定存在且唯一，可以事先算成 24×24 的表（測試：表的每一格乘回去相等）。
  - UI 上只給繞 Y 轉（Q／E 已用於方塊朝向，放置模式中沿用同一組鍵），加 Shift 換軸，和現在的朝向操作一致。
- **鏡像**（既定的 (c)：只有對稱的形狀可以鏡像，其餘拒絕；格式不變）：
  - 鏡像 F（沿 X、Y 或 Z 翻轉）不是旋轉，所以不能直接換成朝向。但若某格的形狀 S 對某個鏡面 G 對稱（G·S＝S），則 F·M(o)·S＝(F·M(o)·G)·S，而 F·M(o)·G 是旋轉，所以一定有對應的 o′。
  - 判定方法（可計算、不必人工列表）：對每個（形狀、朝向、鏡像軸），在 1/16 格的解析度上比較「鏡像後的占用」與 24 個朝向各自的占用，相等者就是 o′；都不相等就是「不能鏡像」。結果可以快取成表。
  - 預設形狀庫中，cube、slab 對任何軸都能鏡像；stair 的兩個 box 在 x 方向占滿，對 X 鏡面對稱，所以沿任何軸鏡像都找得到 o′。使用者自訂的不對稱形狀才會被拒。
  - 拒絕的單位：一次放置中只要有一格不能鏡像，就整次拒絕並標出那些格（和 Q8 的 (c1) 一致）。
- **`.vox` 匯入**（原 TODO #5，併入 #9 第 2 項）：
  - `.vox` → 一個記憶體中的 prefab，參數是比例（每個 vox 體素是 k×k×k 格，k 是正整數；參照門高 2 m＝4 格）。不支援縮小（那是重採樣）。
  - 調色盤：每個用到的 vox 顏色變成一種 cube 方塊，名字由索引產生（例如 `vox_017`），之後照一般貼上對應。
  - 現有的 `vox_to_grid.py`（主 checkout 證據夾）是手動階段的腳本；升成工具命令符合 AGENTS §5 的「手動 → Script → Tool」，且壓力已出現（已用兩次）。
- **貼放是「蓋章」，不是「實例」**：貼上後的格子就是地圖的格子，和 prefab 檔沒有連結；改 prefab 檔不會更新已貼的位置。
  - 理由：若要保留連結，地圖就得在烘焙時讀 prefab 檔或另存「放置表」，那是場景（放置）的職責；依 `v8-arch-map-scene-split`，這個編輯器只編幾何。
  - 若之後場景編輯器想「放置 voxel prefab 的實例」，格子就有了第二個讀者，觸發 RC 1（格子要搬進 Engine）。本頁不做，列在 §5。

**放置模式（剪貼簿、prefab、`.vox` 共用）**：

- 進入方式：Ctrl＋V（剪貼簿）、開 prefab 檔、匯入 `.vox`。三者都產生同一種「待放置的片段」。
- 顯示：片段跟著游標，以 snap 規則決定錨點的位置（Add 的規則：放在被指的面外側）；用線框顯示外框，並顯示片段本身的預覽（見 §3.3 的 ghost 預覽，和 `ve-feel-1` 共用）。
- 操作：Q／E 旋轉（Shift 換軸）、X／Y／Z 鍵鏡像（Shift＋鍵，避免和視角鍵衝突；鍵位在宣告時定）、左鍵放下（一步 undo）、Esc 取消。放下後可以留在放置模式連續貼。
- Goxel 的貼上是「貼到目前選取框的位置」，沒有跟隨游標的放置模式；這裡偏離 Goxel，理由是地圖上同一棟建築要貼很多次（#9 的用途），跟隨游標比先拉選取框快。這一點請在 L3 確認。

### 2.4 Layers

**Goxel 的做法**（行為）：
- 每個圖層有自己的體素、名字、可見、合成模式（加、減、交集、塗色）、可選的邊界框、變換矩陣；另有「複製連結」圖層與「形狀」圖層。
- 畫面與匯出看的是所有**可見**圖層依序合成的結果；編輯只作用在目前的圖層。
- 圖層可以上下移動、向下合併、合併所有可見圖層。
- undo 快照包含全部圖層。

**對我們的意義**：Layers 會改格子格式（v2），並碰到幾個本工具特有的問題。

| 問題 | 說明 | 可能的規則 |
|---|---|---|
| 圖層怎麼存 | v2 的 `layers` 陣列，每層有 `name`、`chunks`（和 v1 的 chunks 相同的 run 編碼）、`mode` | 調色盤與形狀庫全格子共用，不分層 |
| 合成規則 | 同一格多層都有值時誰贏 | 依序覆蓋：後面的層的非空格蓋掉前面；`mode: sub` 的層把它的非空格變成空。不做交集與塗色模式（用途少） |
| 可見與烘焙 | Goxel 匯出只看可見層。若「可見」存進檔案又影響烘焙，就把編輯器的檢視狀態變成了烘焙輸入 | 分成兩個欄位：`bake`（存檔、影響烘焙）與「可見」（只在編輯器，不存檔）。DI 3 的決定性只依檔案 |
| 對區塊化烘焙的影響 | 烘焙先合成再烘，合成是逐格的 | `BakeMap` 的輸入改成「合成後的格子」。`ChunksTouchedBy` 不變（只看哪些格改了）；切換一層的 `bake` 會改到那一層有格子的全部區塊 |
| 拾取與編輯 | 拾取看合成結果還是目前層 | 照 Goxel：拾取看所有可見層的合成，編輯寫目前層 |
| v1 → v2 遷移 | 舊檔怎麼讀 | 讀 v1 時成為只有一層的 v2；寫出一律 v2（或保留「沒有多層時寫 v1」，要在宣告時二選一）。golden 檔要新增，§14.4 |
| 大小 | 多層會讓格子檔更大，和 §1 的 16 MiB 上限疊加 | 若同時需要分檔（Q3），一起設計（Q4） |

**建議（Q2 (b)）**：先不做 Layers，先做兩個不改格式的功能，再看是否還需要 Layers：

1. **剖切顯示**：只畫某高度（或某平面）以下的格子，拾取也忽略被剖掉的部分。解決「看不到室內、二樓」。
   - 但這必須遵守 DI 7：預覽畫的是 Engine 展開的區塊。剖切若在區塊內部切開，就不是「遊戲讀的那份」；做法只能是「不畫高於剖切面的區塊」（以區塊為單位），或另加一個明確標示為「剖切檢視」的模式並改寫 DI 7 的字句。前者不改 DI；後者是 Architecture Delta。**這一點要在 `ve-feel-1` 的宣告中選。**
2. **選取＋隱藏**：把選取的格暫時從顯示中移除，同樣受 DI 7 約束，問題與 1 相同。

如果你仍想要 Layers（例如想分開「地形」與「建築」各自編輯、各自開關），就照上表做 `ve-layers`，屬上段，事前宣告要包含 v2 的 golden、遷移與 §14.4。

### 2.5 undo／redo 的粒度

- **現況**：一次操作一步。格子的步存「每格的前後值」（`CellStep`）；調色盤與形狀的步存「前後兩份完整文件」（`DocumentStep`）。Goxel 則是每步存整份影像的快照，靠體素 tile 的 copy-on-write 讓快照便宜。
- **建議（Q7 (a)）**：使用者看到的粒度維持「一次操作一步」（一次拖曳、一次放置、一次填充、一次調色盤編輯）。改的是**儲存方式**：
  - 小操作：維持每格前後值。
  - 大操作（超過某格數，例如一個區塊的格數）：存「被改到的區塊的前像」；原本不存在的區塊只記「不存在」，所以在空地上大面積填充的 undo 幾乎不占空間。
  - 調色盤與形狀的步：只存調色盤與形狀庫的前後，**不存區塊**（調色盤編輯不改格子；刪除方塊時已規定「有格子在用就拒絕」）。§1 的 1.5 GiB／步就消失了。
  - 歷史總量設上限，超過就丟掉最舊的步（Goxel 也有歷史大小的設定）。上限的數值在宣告時給。
- **相機不進 undo**：照 Goxel，undo 不移動相機。現況已是如此。
- **判定**（給宣告用）：200 組隨機操作序列（含大操作、undo、redo），每一步後的文件與「從頭重放到該步」的文件相等；undo 後預覽的區塊等於整張重烘（沿用 W7 的方法）。

### 2.6 大地圖下的格子檔

只有在 `ve-scale-measure` 量到 v1 撐不住時才需要。可能的方向（不在本頁決定）：

- **(i) 提高上限**：16 MiB 是格子檔自己的規則，提高它是格式規則的變更，但讀寫路徑不變。代價是讀檔、`WriteGrid` 與記憶體都跟著變大。
- **(ii) 格子分檔**：仿照區塊化地圖，`grid.json` 當索引，區塊寫在多個檔。存檔時只寫改過的檔（目前每次存檔都寫整份格子）。
- **(iii) 換成二進位編碼**：檔案變小，但失去「文字、可 diff」的性質。

建議在量測後用 ultracode 規劃（上段，§6）。

### 3.2 snap

- **Goxel**：每個手勢有自己的 snap 遮罩；可選的目標有 Volume（體素表面）、Plane（全域編輯平面）、選取框的內／外、影像框、自訂平面／直線、相機光線；取**離相機最近**的。另有「位移」（Brush 用，可以把落點往法線推半格或一個筆刷半徑）與「四捨五入到格子中心」。
- **現況**：Volume、Plane，取先碰到的（審查 B1 修過）；拖曳中拾取看拖曳開始時的地圖。
- **要補的**（依批）：
  - 選取框的內／外（`ve-select-move`）：Brush 等工具可以只吸到選取框上。
  - 自訂直線：Extrude 開始拖曳後吸到法線方向的直線（Goxel 的做法）。現況是用螢幕上的移動量換算，概念相同；手感調查時比較。
  - Brush 的 snap 位移（Goxel 有一個 -1～+1 的位移值）：對 voxel 地圖的用處不明，列入 H2 的問題，不預先做。

### 3.3 拖曳與預覽

- **Goxel**：
  - 懸停時就算出「如果現在按下會變成什麼」，直接以體素畫出來（不是只有外框）。
  - 拖曳中，Brush 把路徑畫在一個暫存體素上，再和原本的體素合成顯示；放開才寫入圖層並推一步歷史。
  - 選取類工具有「移動一點才開始拖曳」的延遲，避免點擊被當成拖曳。
- **現況**：懸停只畫線框外框；拖曳中直接寫進文件（開著一個 stroke）並重烘顯示；放開成為一步，Esc 取消。
- **ghost 預覽（候選，屬 `ve-feel-1`）**：懸停時就顯示會放的方塊（含形狀與朝向）。
  - DI 7 的限制：畫面上的方塊必須是 Engine 展開的區塊。所以 ghost 不能由編輯器自己做三角形；做法是把懸停的結果套在一份暫存文件上、重烘那幾個區塊、畫它們，就像拖曳中的做法（DI 7 已允許「拖曳中的預覽走同一條路徑」）。
  - 成本：懸停每換一格就要重烘碰到的區塊（每區塊約 1 ms），放開滑鼠時要還原。要在宣告中寫判定：懸停預覽不進 undo、不留在文件、預覽等於「真的按下去」的結果（逐位元）。
  - 只畫線框的替代方案：在線框上加「朝向箭頭」（例如 stair 的上方向與正面），不重烘。成本低，但看不到形狀。兩者由手感調查決定。
- **拖曳開始的延遲**：`Drag::base` 在按下時複製整份文件（§1）。大地圖上會在按下的那一幀卡住。建議改成「拾取時忽略本次 stroke 改過的格」（stroke 已記下改過的格與它們的前值），不複製文件。這是 `ve-scale-measure` 先量、`ve-feel-1` 或 `ve-big-fill` 修。

### 3.4 相機

| 項目 | Goxel | 現況 | 差異 |
|---|---|---|---|
| 旋轉 | 中鍵拖曳；轉盤式（繞垂直軸＋俯仰）；拖滿整個畫面寬＝轉一圈 | 中鍵拖曳；每像素 0.01 rad | 速度與視窗大小的關係不同（畫面越大，我們轉得越多） |
| 平移 | 右鍵拖曳（另有 Shift＋中鍵） | 右鍵拖曳 | Shift＋中鍵沒有 |
| 縮放 | 滾輪（另有 Ctrl＋中鍵拖曳）；**縮放時把旋轉中心移到游標下的體素** | 滾輪，朝固定的中心 | **差異大**：Goxel 是「往游標縮放」 |
| 左鍵點在空白處 | 拖曳就旋轉相機 | 若平面 snap 開著就落在平面上；否則沒有反應 | 不同 |
| 視角鍵 | 1、3、7、0；5 切換正交；Ctrl＋3 左視 | 1、3、7、0 | 沒有正交（window-1 決定 5 延後）與左視 |
| undo 時相機 | 不動 | 不動 | 相同 |

- 「往游標縮放」與「左鍵空白處旋轉」都只改視窗程式（相機的中心與距離是視窗自己設的），不必改 framework。
- **大地圖**（Q12）：Goxel 的相機繞一個中心點，適合小模型。在 km² 的地圖上，要從一端到另一端，只能靠平移與縮放。是否加飛行相機（WASD＋滑鼠視角）超出「照 Goxel」，需要你決定。
- **正交投影**：仍延後（要改 framework 或 Engine 的相機，window-1 決定 5）。若手感調查顯示它是主要問題，另開 framework 的卡（owner 是架構會話）。

### 3.5 快捷鍵約定

- **Goxel 的預設**（摘要）：工具 B、S、L、F、P、C、M、Shift＋R（Selection）；模式 T、R、G；視角 0、1、3、5、7；Ctrl＋Z／Y、Ctrl＋C／V、Delete（有選取時清掉選取的部分，否則清掉整個圖層）；快捷鍵可以在設定中改。
- **我們的約定**（建議寫進 architecture.md 的 The window，成為一張表，每批更新）：
  - 照 Goxel 的鍵優先；Goxel 沒有的功能才用其他鍵。
  - 現有的自訂鍵：Q／E 朝向（Shift 換軸）、`[`／`]` 筆刷大小、PgUp／PgDn 編輯平面、N（Line，Goxel 的 Line 沒有預設鍵）。
  - 新增：M（Move）、Shift＋R（Selection）、Ctrl＋C／V、Delete（清選取）、Ctrl＋A（全選？要在宣告中確認範圍：全選一張大地圖的代價）。
  - macOS 上 Ctrl 與 Cmd 都當成命令鍵（現況已如此）。
  - 不做快捷鍵自訂（Goxel 有）；若手感調查顯示需要，再說。
- **衝突檢查**：放置模式中的鏡像鍵、對稱面的開關鍵，要和視角鍵 1、3、7 分開；宣告時列出完整鍵表，並加一個 CPU 測試「鍵表沒有重複」。

### 3.6 對稱

- **Goxel 的行為**：X、Y、Z 三個開關，各有一個對稱面的位置（可在半格上），可以「置中到體積／圖層／影像」；開啟時畫面上以有色平面顯示；所有繪圖操作（Brush、Shape、Line 等）都同時套到鏡像的位置，多軸時遞迴（X 和 Z 都開就是四份）。
- **我們的版本**：
  - 繪圖操作算出格子集合後，對每個開啟的軸各鏡像一次（集合的聯集）；鏡像後的格子用 §2.3 的規則換朝向。
  - 對稱面在格界或格中心（座標以半格為單位）。
  - Add 時遇到不能鏡像的形狀：Q8 建議 (c1) 整筆拒絕並提示是哪一種方塊。
  - Sub 不管形狀，鏡像位置直接清空（不需要換朝向）。Paint 保留原本的朝向，只換方塊；換上的方塊不能鏡像時同樣拒絕。
  - 顯示：對稱面以 ImGui 的線畫出（和編輯平面的格線一樣，不是區塊幾何，符合 DI 7）。
- **判定**：每個工具在 X、Y、Z 各開一個、和三個全開時，結果等於「原操作的格子集合 ∪ 其鏡像」；朝向逐格符合鏡像表；不能鏡像時文件不變。

### 3.7 選取（框選與擴展）

- **盒選**（Goxel 的 Selection）：在面上按下拖曳，拉出一個盒；盒是平的時往法線方向長一格（Goxel 的做法）。Shift 加入、Ctrl 減去、沒有修飾鍵就取代。拉完之後盒有把手可以拖動每一面（Goxel 的 box edit）；面板可以輸入位置與大小。
- **依方塊相連**（Fuzzy 的改裝）：點一格，選取「同一種方塊、面相連」的所有格；上限與 Extrude 相同，超過就停並提示。
- **擴展**：選取後可以「長大一格」「縮小一格」「只留表面」（Goxel 沒有，候選，手感調查時問）。
- **清除選取**：點空白處（Goxel 的做法）或 Esc。
- **顯示**：選取的格子以線框盒（盒選）或每格的外框（相連選取；格數多時只畫外接盒）表示。

- **大號筆刷**：Brush 的上限 16 格（8 m）改為可設定（例如 64），大筆刷沿路徑蓋章的格數成長很快（64³ 是 26 萬格），要和上面的分區塊提交共用機制。
- **平面填充**（Goxel 沒有；候選）：點一個面，把「同一平面上、被已有方塊圍住的空格」填滿（2D flood fill），用於地板。要有上限（不封閉時會漫出去）。手感調查時問是否需要。
- **判定**：填充的結果等於逐格 `SetCell` 的結果；分幀重烘完成後，預覽等於整張重烘（W7 的方法）；中途 Esc 的行為（取消已套用的部分，或不允許中途取消）在宣告時定。

### 3.9 邊界延伸（在現有範圍外落筆）

- 格式上已經可以：區塊是稀疏的，沒有固定的地圖尺寸。
- 實際上妨礙的是：
  1. **沒有東西可以點**：Volume snap 要有方塊，Plane snap 要編輯平面。編輯平面是無限大的，所以在平面 snap 開著時，地圖外的任何地方都能落筆；但格線只畫游標附近 ±16 格，看不出來。建議：格線改成隨相機距離調整間距（例如每 16 格一條粗線，即區塊邊界），並顯示目前的地圖範圍外框。
  2. **拾取距離 1024 格**：從遠處看大地圖時，超過的部分點不到。建議改成依相機的遠裁切面決定。
  3. **origin 不是 16 的倍數時，邊緣的區塊會超出 Engine 的範圍（M6）**，`build-map` 拒收（已記錄於 architecture.md「Range」）。延伸到很遠時才會碰到，記錄即可。
- **判定**：在地圖範圍外 1 km 處落筆、存檔、`verify-map` 一致；拾取在相機能看到的距離內都成立。

## 4. 手感

使用者 2026-11-07 的評價是「這次的合格是基礎功能，編輯手感和操作差的很遠」。
本節**不推斷使用者指的是哪一項**；只把「手感」可能涉及的面向拆開，每一項給一個可量的判定或一個要在 L3 問的問題。結論由 `ve-feel-survey` 的結果與使用者的回答決定。

| 代號 | 面向 | 可能的原因（本頁從程式與 Goxel 的比較觀察到的，未經使用者確認） | 可量的判定（候選） | L3 要問使用者的問題 |
|---|---|---|---|---|
| H1 | **延遲** | 按下滑鼠時複製整份文件；每次編輯重烘並上傳區塊；P1 只量了「每幀改一格」 | 從輸入到畫面更新的時間：按下、拖曳中、放開、undo 各自的 p95，用像建築的合成圖與 1 km² 的合成圖量。候選門檻：拖曳中 ≤ 2 幀（33 ms）、按下 ≤ 50 ms | 有沒有「按下去頓一下」「拖快了跟不上」「放開後等一下才出現」？在哪個工具、多大的地圖？ |
| H2 | **游標命中的面與方向** | 拾取把任何形狀當成整格：游標指著 slab 上方的空半格時，命中的是 slab 那一格；Add 放在它旁邊，可能和你預期的不同。平面和方塊重疊時取先碰到的 | 測試案例：slab、stair 的空的部分被指到時，命中與落點是什麼（逐案列出，讓你選期望的行為） | 有沒有「放的位置不是我指的那格」？在 slab、stair 上，還是一般方塊上？什麼角度？ |
| H3 | **預覽** | 懸停只有線框，看不到形狀與朝向；Goxel 懸停時就顯示結果 | 判定 ghost 預覽的正確性（§3.3）；不是手感本身的量測 | 放之前看得出「會放什麼、朝哪邊」嗎？線框加朝向箭頭夠嗎，還是要看到方塊本身？ |
| H4 | **撤銷** | 粒度是一次操作；Line 是兩次點擊，第一次不留步；調色盤編輯也是一步 | undo／redo 的回應時間（同 H1）；每種操作 undo 一次回到的狀態（測試表） | undo 一次回到的地方符合預期嗎？有沒有「undo 了不該 undo 的」或「要按很多次」？ |
| H5 | **相機** | 縮放朝固定中心而不是游標；旋轉速度和視窗大小有關；左鍵點空白不會旋轉；沒有正交；大地圖只能靠平移 | 量不出「好不好」；可以量「從一點移到地圖另一端要幾個操作」 | 最常卡住的相機操作是哪個？要不要「往游標縮放」「左鍵空白旋轉」？大地圖要不要飛行相機？要不要正交？ |
| H6 | **快捷鍵與操作流程** | Line 是點兩下（Goxel 是拖曳）；朝向用 Q／E；工具與方塊的切換要點面板 | 鍵表無重複（CPU 測試）；完成一個固定任務（例如蓋 4×4 的房間加門）要的按鍵與點擊數 | 哪個操作要點太多次？選方塊要不要像 Minecraft 的快捷列（數字鍵）？Line 用拖曳還是點兩下？ |
| H7 | **尺度** | 一格 0.5 m，筆刷最大 8 m；格線只畫 ±16 格 | — | 蓋牆、鋪地時覺得「一次只能做一點點」嗎？需要多大的筆刷或填充？ |
| H8 | **回饋** | 沒有游標座標、沒有格數、狀態列只有存檔訊息；Goxel 顯示游標座標與操作提示 | — | 想看到哪些資訊（座標、選取大小、方塊名）？ |

**`ve-feel-survey` 的做法**：
1. 加量測（H1）：在 `measure-preview` 加「按下、拖曳、放開、undo」的計時情境，用兩張合成圖量（工具只加量測，不改操作）。
2. 做一張「Goxel 與我們的差異表」（本節與 §3 的內容），在你試用時一起看。
3. 請你照 H1～H8 的問題，各選「是問題／不是／不確定」，並指出最痛的三個。
4. 依結果寫 `ve-feel-1` 的宣告（項目、判定）。沒被你選中的候選不做。

## 5. 契約影響

### 5.1 分類

| 範圍 | 項目 |
|---|---|
| **只動工具的程式**（大多數） | 選取、Move、剪貼簿、放置模式、對稱、ghost 預覽（走 Engine 展開的路徑）、相機、快捷鍵、格線、拾取距離、大面積填充、undo 的儲存方式、`.vox` 匯入命令、量測命令 |
| **動工具的檔案** | prefab 檔：格式不變（v1 格子），但視窗會**寫**新的檔（prefab），DI 5 的「只寫命令列指定的檔」要擴充；格子 v2（`ve-grid-v2`、`ve-layers`，條件批） |
| **碰 Engine 契約** | **預期沒有**。逐項檢查過：烘焙輸出仍是 `gyo.voxel_map`／`gyo.voxel_region`，由 Engine 驗證；Layers 在烘焙前合成，Engine 看不到；prefab 是蓋章，Engine 看不到。正交投影若要做，會碰 framework 或 Engine 的相機（本頁不做） |
| **碰 framework** | 預期沒有。相機的中心與距離由視窗設定；若要正交，另案 |

### 5.2 Design Invariants 逐條

| DI | 會不會違反 | 說明 |
|---|---|---|
| 1 依賴 | 不會 | 新功能都在核心（CPU 可測）或視窗；不加新的 Engine 模組或第三方庫。`.vox` 的讀取是工具自己的二進位解析，在核心 |
| 2 一個驗證者 | 不會 | 烘焙輸出仍經 Engine 驗證。prefab 是格子檔，由 `ParseGrid` 讀，屬工具自己的格式 |
| 3 決定性 | 不會（v2 時要新 golden） | 分幀重烘的結果必須等於整張重烘（判定已列）。Layers 的「可見」不存檔、不影響烘焙。v2 會新增 golden，舊 golden 不變，§14.4 照規則處理 |
| 4 無損 | 不會 | 烘焙不變 |
| 5 只寫自己做的 | **會擴充**（`ve-prefab`） | 視窗多寫 prefab 檔；`import-vox` 寫命令列指定的格子。照現有的寫法：只寫使用者指定的路徑、原子替換、被外部改過不覆寫。字句變更要你核准 |
| 6 格子是工具的 | 不會；**但要守住** | prefab 若變成場景編輯器放置的「實例」，格子會有第二個讀者，觸發 RC 1。本頁把 prefab 定為蓋章 |
| 7 看到的就是遊戲讀的 | 不會，**但兩處要選** | ghost 預覽與分幀填充都走 Engine 展開的路徑；剖切顯示若在區塊內部切開，就要改寫 DI 7（§2.4）。對稱面、選取框、格線都是 ImGui 的線，和現在的疊加線一樣 |

### 5.4 Architecture Delta 的草稿

只列會成立的兩件；細節在各批的宣告中補完。

**A. `ve-prefab`：視窗寫 prefab 檔、`import-vox` 命令**

2. 現在的問題：一棟建築要在大地圖上重複出現，只能逐格重畫；`.vox` 匯入是手動腳本，已用兩次。

4. 受影響：`tools/voxel_map_editor`（核心：變換表、方塊對應、`.vox` 解析；視窗：放置模式）、`tests/voxel_map_editor`、`docs/voxel_map_editor/architecture.md`。Engine、framework、產品不改。
5. 依賴方向：不變。
6. Ownership：不變（prefab 是工具的格子檔；不是場景的資料）。
7. 為何不能更小：貼放需要讀寫一個片段；用既有的格子格式已是最小（不新增 schema）。

**B. `ve-grid-v2`：格子格式 v2（條件批）**

1. Feature：TODO #9 的第 1 項（大地圖），以及 Q2 若選做 Layers。
2. 現在的問題：（待量測）格子檔 16 MiB、記憶體、整份存檔。
3. 變化的邊界：`gyo.voxel_grid` 的格式（版本、分檔或圖層）；讀 v1 的遷移。
4. 受影響：工具的核心（`ParseGrid`、`WriteGrid`、存檔）、golden、CLI 的 `inspect`、視窗的開檔與存檔。Engine 不改（格子只有工具讀，DI 6）。
5. 依賴方向：不變。
6. Ownership：不變。
7. 為何不能更小：待量測。若提高上限就夠，就不做 v2（Contract 先於 Architecture）。
