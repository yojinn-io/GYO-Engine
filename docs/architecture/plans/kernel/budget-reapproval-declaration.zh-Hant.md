## 2. 先讀：要使用者定的事（各項細節在 §3、§4）

照計畫候選的形式把今天的值代進去，會出現三件計畫寫成時看不到的事。我把它們寫成提案，請使用者定：

1. **BU-1 的倍數項實際上不起作用**（§3 BU-1）。今天一個 tick 約 2 µs，`max(基線 ×1.25, 基線 ＋0.25 ms)` 由＋0.25 ms 決定（容許約 252 µs，是基線的 128 倍）；×1.25 只有在基線超過 1 ms 時才會生效。所以 G2a 實際判的是「Kernel 讓一個 tick 多花的時間 ≤0.25 ms」，不是「慢 25% 以內」。Kernel 的派發本身（§6 BU-2：每次 System 呼叫 ≤2 µs）就會讓 tick 變成今天的好幾倍，所以 ×1.25 本來就不可能成立。**提案**：保留這個形式，計畫裡寫明「基線 ≪1 ms 時由絕對項決定」；把 ×1.25 改寫成倍數判不到的事實說明，不當護欄。
2. **BU-6 真實行程的「絕對 ≤1 s」今天的程式就不過**（§3 BU-6）。LD 冷啟動 1.317 s 已經超過 1 s。這個 1 s 是沒有分母時寫的推定。**提案**：絕對 1 s 只套重放值（今天 1.6 ms），真實行程只用相對項。這是對候選數字的**放寬**，在看新路徑結果之前提出，交使用者決定。
3. **10% 的「先停下判環境」規則換成看散佈寬度**（§4）。計畫的「同機 5 次 p95 散佈（全距比）>10% 先停」在四環境報告裡被證明不穩健：一次偏離就讓 LN 的全距比到 35～44%，排除那次後只有約 1%。**提案**：改成 10 次；先決條件改為「四分位距或去極值全距的絕對寬度 ≤ 該項容許增量的一半」，再加一條「舊二進位重量的中位數離 U12 寫入值不超過 5%（載入 10%）」。改規則要使用者核准（§14.1）。

另有兩點偏小，也請一起看：BU-4 RSS 由 ×1.10 決定（容許約 3.0 MiB），新加的程式碼（kernel、plugins、yyjson）夠不夠沒有根據（§3 BU-4）；計畫寫的「8 人長情境」做不到（`MaxPlayers = 4`），改寫成 long4（§3 BU-1）。

## 3. 各項提案（BU-1～BU-8）

讀法：「今天」＝§1 的 Dn；「容許增量」＝預算 − 今天的值；「起作用的項」＝max／min 裡決定數字的那一項。數字都是 LD、容器內。倍數與絕對項的根據寫在每項的「根據」；沒有根據的照舊標**推定**。

### BU-1 Match tick 的工作（重放 host；G2a）

| | 計畫候選 | 提案 |
|---|---|---|
| 情境 | 37 golden＋**8 人**長情境 ≥3,600 tick | 37 golden（golden-all）＋**long4（4 人，3,600 tick，前 600 不計）**；`MaxPlayers = 4`（`Movement.hpp:21`、Gateway 也是 4），pvp-baseline 報告「計畫的 8 人長情境做不到」 |
| 判定量 | 「同機 5 次取每次 p95 的中位數」 | golden-all 與 long4 **各自**判：10 次，每次 p95（另記 p99）取中位數 |
| 驗證關 p95 | ≤ max(基線 ×1.25, 基線 ＋0.25 ms)，且 ≤2.0 ms | 形式不變。golden-all：max(2.455, 251.96) ＝ **≤251.96 µs**；long4：max(3.131, 252.51) ＝ **≤252.51 µs**；絕對 ≤2.0 ms 保留（不起作用） |
| 驗證關 p99 | ≤4.17 ms | 不變（今天 D2 2.66 µs、D4 3.35 µs，不起作用） |
| 驗證開 | ≤ 驗證關 ×3 且 ≤8.33 ms | 不變（今天沒有驗證開的路徑，無分母） |

- **根據**：起作用的是＋0.25 ms＝tick（16.67 ms，60 Hz）的 1.5%，**推定**（三案折衷，§6 取捨）。×1.25 在基線 <1 ms 時不起作用，寫明為事實說明（§2 第 1 點）。
- **與 BU-2 的關係**：§6 BU-2 的「以 PvP 的 System 數換算不得超過 BU-1 允許增量的一半」換算後＝**≤125 µs**（0.25 ms 的一半）。這條原文就有，只是現在才有具體數字。
- **替代**（不建議）：把＋0.25 ms 換成由 BU-2 推出的值（System 數 × 2 µs＋同步點數 × 5 µs）。比較有道理，但 System 數要等 dryrun（G1）才知道，而 U12 的時點只要求 match-sim 宣告之前；那樣要再核准一次。
- **口徑提醒**（寫進 first-host-cost 的限界）：舊的 golden-all 裡，35 個情境只計 `PvpMatch::Tick`、2 個計 `MatchRuntimeHost::Advance` 全段；新路徑計 FixedUpdate 的一次 `Run`。新路徑多計的部分對新路徑不利，量級是 µs，遠小於容許增量。重放用合成內容（pvp-baseline 報告限界 10），新的重放 host 要用同一份合成內容。

## 4. 統計量、量法、判定方式（G2a、G2b 共用）

### 4.1 統計量與次數

- **次數**：每個判定項 **10 次**（計畫原寫 5 次；分母本身就是 10 次的統計）。重放：10 個行程。真實行程：10 場。載入、冷啟動：各 10 次。
- **判定值**：10 次的中位數（重放是每次 p95 的中位數）。分母照 §1 同樣算。
- **不用全距比當判定**：四環境報告 §4，10 次的全距比會被單次偏離拉大（LN 第 0 次：35～44%），四分位距比與去極值全距比約 1%。

### 4.2 量測有效的先決條件（取代「同機 5 次 p95 散佈 >10% 先停」）

兩條都成立，量測才有效；任一不成立就**停下判環境，不改門檻**（§14.1）：

1. **散佈寬度**：新舊兩路的每個判定項，`max(Q3−Q1, 去極值全距)` 的**絕對寬度 ≤ 容許增量的一半**。
   - 根據：四環境報告 §5 的推法「r ≤ d／2 才算可做」，改成用絕對寬度，這樣絕對項起作用的項也能套。
   - 用今天的 LD 試算（只是說明這條在今天的雜訊下可以滿足，**不是**判定）：BU-1 寬度約 0.01～0.06 µs，容許增量的一半約 125 µs；BU-6 重放寬度約 0.12 ms，一半是 50 ms；冷啟動約 8 ms，一半約 66 ms；RSS 約 170 KiB，一半約 1,510 KiB。
2. **舊二進位的漂移**：閘門那一批用同一映像、同一份 `eb018478` ELF 重量舊路徑；**它的中位數與 U12 寫入的值相差 ≤5%**（D5 載入用 ≤10%）。超過就停下（機器、kernel、Docker 版本可能變了），交使用者決定要不要重量分母。
   - 根據：LN↔LD 的容器化本身讓中位數偏移 ≤3%（四環境報告 §2.2）；載入在 LD 分兩群、相差約 ±6%。5%、10% 是**推定**。
   - 這一條的用意：分母是 U12 現在寫死的數字（「今天的值 × 倍數」照字面），閘門時不會因為重量而移動；重量只用來證明環境沒變。

### 4.3 頻率跳動的處理

四環境報告「先讀」第 2 點：Linux 實機在量測開頭約 1～2 秒偏快（推測是短暫的 boost）。提案：

- **(a) 暖機**：每個計時項目開始前，在釘住的核上跑 ≥10 s 不計時的持續負載（例：重複跑 long4）。根據：偏快的狀態只持續約 1～2 s；10 s 是**推定**。
- **(b) 記頻率**：每個項目前後與暖機前後，記錄核 8～15 的 `scaling_cur_freq`、governor、boost 狀態，進報告。
- **(c) 統計量**：§4.1、§4.2 的中位數與四分位距本來就不受單次偏離影響。
- **(d) 新舊交錯**：舊、新、舊、新…逐項交錯（照四環境報告 LN／LD 的做法），時段造成的偏移會平均分到兩路。
- **不建議固定頻率**（governor `performance`、關 boost）：這要改系統設定（使用者定），而且分母 D1～D11 是在 `powersave`＋boost 開的設定下量的，固定頻率後分母就要重量，U12 的數字跟著失效。若使用者仍要固定，分母要在同樣設定下重量，再走一次 U12。

### 4.4 判定方式

- 每項：比值＝新路徑判定值 ÷ 預算。**≤1.0＝過**；**1.0～1.5＝報告，使用者決定**；**≥1.5＝停、重排**（§8 RC-1，不變）。
- G2a 集合（BU-1 golden-all、BU-1 long4、BU-2、BU-4 World、BU-6 重放）與 G2b 集合（BU-1′、BU-4 RSS、BU-6 真實行程）不變，只是 BU-1 拆成兩個判定量。
