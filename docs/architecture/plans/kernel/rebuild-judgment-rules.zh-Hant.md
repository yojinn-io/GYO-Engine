之前犯過的兩種錯，這個機制都要擋：
- **正向偏差**：因為「已驗證」「與舊的一致」「改動少」就留下舊形狀。例：World 重用 entity_store，理由是它的突變一覽不必重列。
- **反向偏差**：因為「追得到舊程式」或「用了舊詞」就判成錯。例：把「Host 剩下五項職責」因為用了 Host 這個詞判成舊說法。

## 1. 定義（要你確認）

### 1.1 判斷的單位：設計元素

一個設計元素＝一個可以單獨說對或錯的主張。四種：
- **機制**：例「結構變更延後到同步點套用」。
- **契約**：例「System 回傳 Result」。
- **不變量**：例「欄依 id 升冪」。
- **取捨的結論**：例「事件不用游標」。

一份文件、一條 DI、一個模組都可能含多個元素，要拆開判。程式、測試、守衛不是判斷的單位：它們跟著自己實作或守護的設計元素走。

### 1.2 三類產品與「作者」

| 類 | 定義 | 現況 |
|---|---|---|
| ①PvP | 有權威端與預測端、要兩端結果一致的多人遊戲 | object_fps_pvp（在 master） |
| ②單機遊戲 | 沒有 Match 與 Client 之分的遊戲。代表：2D 橫版通關 | 沒有產品；用架構師自建的樣本代表 |
| ③工具 | Editor 與四個工具這類沒有固定步模擬的應用 | 四個工具（在 master） |

「作者」＝用 Engine 寫產品的人。判斷時問的是作者，不是 Engine 的實作者。

### 1.3 兩種成本

- **作者成本**（不可接受，除非那一類產品自己需要）：
  - 多寫的宣告
  - 多懂的概念
  - 多遇到的啟動錯誤
  - 被禁止的寫法
- **性能成本**（可以接受）：執行期多花的時間與記憶體。前提是作者與玩家感受不到差異。

### 1.4 什麼算理由

| 可以當決勝理由 | 只能當系譜或成本，不能決勝 |
|---|---|
| 名指的 Feature，並寫出是哪一類產品的 | 「今天就是這樣」「與舊的一致」「延伸舊的」 |
| 由 Feature 推出的 Contract | 「已驗證」「已核准」「測試或守衛依賴它」 |
| 與產品類別無關的性質：資料競爭、可重現、錯誤不靜默、可刪除性（AGENTS §3、§6、§7） | 「改動少」「不必重列突變或 golden」 |
| 使用者明說的決定（要寫出原話與日期） | 「參考實作這樣做」單獨一條（AGENTS §2：要配 Feature 或規模） |

「使用者的決定」分兩種，要標明：
- **主動定的**：使用者自己提出或改了規格。可以當決勝理由。
- **採規格通過的**：選項由舊規格框好、使用者照建議選。不能單獨當決勝理由，要重新過第 2 節。

## 2. 三題（每個設計元素都分開問）

### 第 1 題　內容：這個主張成不成立

四個小問，都要寫出答案：

- (a) **誰需要**：哪一類產品的哪個 Feature 需要它。
- (b) **替代案**：至少一個不同的做法。Bevy 有對應做法時必列。
- (c) **決勝**：只用 1.4 左欄的理由，寫出它為什麼贏替代案。
- (d) **別人付什麼**：不需要它的那幾類產品，作者成本是什麼。

判定：

| 情形 | 第 1 題的結果 |
|---|---|
| (a)(c) 寫得出，(d) 是零 | 成立 |
| (a)(c) 寫得出，(d) 不是零 | 成立，但第 3 題一定要答「住在哪裡」 |
| (a) 寫得出，(c) 只能用右欄的理由 | 未判：要補比較、量測，或請使用者定 |
| (a) 寫不出 | 不成立 |
| 拿掉舊理由後，替代案明顯較好 | 不成立 |

### 第 2 題　名字：詞變了沒有

查同詞異義表。詞變了只改名字，不影響第 1 題的結果。

### 第 3 題　歸屬：誰持有、住在哪一層

| 第 1 題 (a)(d) 的結果 | 住在哪裡 |
|---|---|
| 三類都需要，作者成本是零 | 通用機制 |
| 三類都需要，但形式不同 | 通用機制提供擴充點，形式由各類自己給 |
| 只有一類需要，對其他類的作者成本是零（只有性能成本） | 可以留在通用機制，要標明系譜 |
| 只有一類需要，對其他類有作者成本 | 移到那一類選用的 plugin 或產品；通用機制只留它需要的擴充點 |

層的名字（Kernel、plugin、產品等）這裡不先定，由 R1 定；這一題只判「通用」還是「某一類專用」。

## 3. 六種結論

| 結論 | 條件 | 之後怎麼處理 |
|---|---|---|
| **照帶** | 第 1 題成立；名字與歸屬都沒變 | 進 R1 的設計，附上新寫的理由 |
| **照帶、換名字** | 第 1 題成立；第 2 題變了 | 同上，用新詞 |
| **照帶、換位置** | 第 1 題成立；第 3 題變了 | 進對應的 plugin 或產品的設計；列出通用機制要留的擴充點 |
| **照帶、換理由** | 結論成立，但原文的理由是 1.4 右欄的 | 用 (c) 的新理由重寫 |
| **不帶** | 第 1 題不成立 | 不進 gyo2；寫明原因。需要這個功能的話由 R1 重新推導 |
| **未判** | 缺量測、缺名指的 Feature，或要使用者在選項中選 | 列出缺什麼。未判的不得當任何設計的前提，也不得靜默變成照帶或不帶 |

一個元素可以同時換名字、換位置、換理由。

## 4. 把關：誰判、誰查、誰定

1. **提案**：agent 對每個元素寫第 2 節的答案與第 3 節的結論。
2. **檢查**：作者以外的模型逐項否定（AGENTS §4）。兩個方向都要查：
   - 有沒有用右欄的理由讓它過關。
   - 有沒有只因為舊詞或舊出處就判不帶。
3. **確認**：使用者分組確認。確認之前，任何結論都只是提案。
4. **登記**：確認過的結論寫進一張登記表（第 5 節）。gyo2 的設計與程式只能引用登記表裡「已確認」的列。

## 5. 登記表

放在 `docs/architecture/plans/rebuild/`，是舊設計去留的唯一來源。每列：

| 欄 | 內容 |
|---|---|
| 編號、元素 | 一句話；舊出處（`master@08566260:<檔>:<行>` 或條文代號） |
| (a) 誰需要 | 產品類別與 Feature |
| (b) 替代案 | 含 Bevy 的對應做法與出處 |
| (c) 決勝理由 | 只用 1.4 左欄 |
| (d) 別人付什麼 | 作者成本、性能成本分開寫 |
| 名字 | 沿用，或新詞 |
| 歸屬 | 通用，或某一類專用與它要的擴充點 |
| 結論 | 第 3 節的六種 |
| 狀態 | 提案／已檢查／已確認（日期與原話） |

底稿是盤點 (c1) 的 319 個設計元素與 118 列條文。它們已有結論的提案，但缺 (b)(c) 兩欄，而且結論是用舊的五種分類寫的；要照這份機制重做，不能直接當已確認。

## 6. 用兩個例子檢驗這個機制

| | 例一：欄依 EntityId 排序（容器順序） | 例二：Host 的五項職責 |
|---|---|---|
| (a) 誰需要 | ①需要「兩端的查詢順序相同」。容器本身有序：寫不出需要它的 Feature | ①②③：任何應用都要建 World、選 schedule、列 plugin、接外部服務、跑迴圈 |
| (b) 替代案 | Bevy：archetype 儲存，順序不保證；需要順序的查詢自己排序 | 全部交給 Scheduler |
| (c) 決勝 | 原文的理由是「與 entity-store 一致」「舊 `std::map` 的順序」：右欄 | 這五項不是「排 System 的順序」，Scheduler 做不了；Bevy 也放在 World 外 |
| (d) 別人付什麼 | ②③的作者成本是零，性能成本是插入要保序 | 零 |
| 名字 | — | Host 改成 main 加 runner |
| 歸屬 | 「查詢順序是鍵的函數」只有①需要 | 不再由一個物件全部持有，分給 main、runner、各 plugin |
| 結論 | 容器有序：**未判**（寫不出 Feature，但拿掉它的替代案還沒比較過性能與複雜度）。「兩端查詢順序相同」：**照帶、換位置** | **照帶、換名字、換位置**。其中「固定步累加器放在 Host」與「白名單寫死 `FixedTickRuntime`」是另外兩個元素，各自判 |

例一說明不因為「舊的」就直接判不帶：它是未判，要補比較。例二說明不因為用了舊詞就判錯。

## 9. 範囲の限界

- 這份機制判的是設計元素。帶過去的 engine 模組（base、math、os 等）是程式；它們的去留已由 R0 清單核准，重審點在清單附錄。它們的 Design Invariants 要不要也逐條過這份機制，是步驟 3 的一組。
- ②類沒有真實產品，(a)(d) 對②的答案是推定，要標明。
- 判斷有主觀成分；機制靠「寫出來、別的模型查、使用者確認」降低它，不能消除它。
