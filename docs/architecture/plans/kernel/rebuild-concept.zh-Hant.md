**(3) C2 的作者成本與缺的東西**

從簽名推存取，作者要付的不只是「普通函式」。照 SP 的原型：
- 不能用泛型 lambda 與多載的函式。
- 參數只能以值接收規定的型別。
- 不能回傳值，所以 System 出錯怎麼回報沒有定義。
- 不能拿整個 World，所以沒有「獨占整個 World 的 System」。
- 不能在執行期才決定要存取什麼。Inspector、通用的序列化、復原用的快照、存讀檔都需要這個。
- System 自己的狀態放哪裡沒有定義。
- 不能在同一個 System 裡讀又寫同一種事件。

Bevy 同樣從簽名推存取，但留了出口：拿整個 World 的獨占 System、`Local` 放私有狀態、System 可以回傳結果、動態的查詢。v1 的替代案只列「手寫清單」，漏了這個。

這幾項原文的概念層都沒有答案，列進未判（U10～U12）。③的主要功能靠它們。

**(4) 還沒做的檢查：②與③需要什麼**

v1 只做了一個方向：把只有①需要的東西篩出去。反方向沒做：②與③需要、原文因為是從 netcode 倒推而沒有的東西。已經看到的候選：
- 快照與還原：②存讀檔、關卡重開；③復原。v1 把它放在「預測與回滾」底下，不對。
- 從外面重跑一個 schedule：②的固定步。
- 獨占整個 World 的存取、執行期才決定的存取：③。
- 階層與關係、狀態的轉換、欄位的描述（反射）：②③。

這一輪要從②與③的 Feature 出發，等於 R1 的前半。這裡先列為洞，不在這份稿裡補。

**(5) 理由要重寫或標明系譜的列**

| 階段清單（BP 的 K1） | schedule 的清單 | Schedule 沿用 |
| 階段（schedule 裡的一段） | stage（舊） | Stage 加限定詞 |
| change tick | stamp | Tick 加限定詞 |
| 受限句柄 | System 參數 | Handle 加限定詞 |
| Link（當通用概念） | external Resource（舊） | Link 加限定詞 |
| (c) 區 | 決定性區 | Zone 加限定詞 |
| 外部服務 | World 外的 IO | Service 加限定詞 |
| Kernel、核心 | 通用機制 | Kernel 只指舊的 |
| 多個時鐘 | 多個 clock domain（舊） | Clock 被 time 先占 |
| 欄 | ECS 元件；講儲存時寫「儲存」 | 「欄」不用 |
| Ingress、Egress | 輸入的交換點、輸出的交換點；名字 R1 定 | 表裡沒有 |

第一部分的表（1.1～1.5）是 v1 寫的，裡面還有「核心」「欄」「main」這些舊寫法；意思照上表讀。

## 第三部分　暫定稿：目前站得住的部分

**這不是基準。** 它只列出通過第一部分、而且不依賴任何未判項的內容。有洞的地方直接寫「未判」，不先替它選答案。

### 3.1 目的

讓需要被排程的工作都遵守一套可驗證的共同契約（C9）。三類產品用同一套通用機制。只有一類產品需要、而且會讓別的產品的作者多寫或多懂的東西，不放在通用機制裡。

### 3.2 推導鏈（C1～C5）

```text
型別 ──登記──▶ id
System 的函式簽名 ──編譯期──▶ 存取集合
存取集合 ＋ 顯式的約束 ──分析──▶ 衝突邊、順序邊（分開存）
邊 ＋ 執行策略 ──▶ 執行計畫（每個 schedule 一張）
計畫 ──Executor──▶ 呼叫 System、交給它 System 參數、記 stamp
```

每一環都不含業務。

### 3.3 組成

| 組成 | 已經站得住的 | 還沒判的 |
|---|---|---|
| World | 存資料：id 對應到有搬移與解構規則的位元組；有 stamp、延後的變更、事件緩衝、時間（C6） | 儲存的做法（U20）；疊代順序與 id 的配發（E1、E2，待你確認） |
| 型別與 System 的 Registry | plugin 套件在 build 時登記；id 依登記的先後（C1、K3、D3a） | 凍結之後能不能再加（U13） |
| Scheduler | 只看存取集合與顯式的約束，算出計畫；不打開函式體（C3、C4、C7） | stage（舊）還在不在（U18） |
| Executor | 照計畫執行；第一版只有 Serial（C5、D1d） | — |
| App | 名字是你定的 | 它含幾個 World、和 runner 的關係（U8） |
| `Plugin` 型別與 plugin 套件 | 登記的單位；擁有它登記的東西，可以整個拿掉（X12） | — |
| 組裝（setup）與 runner | 舊 Host 的五件事都還要有人做（M12）；runner 可以替換（E10b） | 五件事各自歸誰；schedule 清單由誰給（U17）；固定步在哪裡累加（U7） |

### 3.4 契約

- **從簽名推出的一半**：讀寫哪些 ECS 元件與 Resource、讀寫哪些事件、會不會記延後的變更（C2）。有核對攔。
- **顯式宣告的一半**：掛在哪個 schedule、run 條件、before／after、執行緒親和（M4）。都有預設。只靠審查，宣告錯了不會報錯（E4）。
- **資料的契約**：ECS 元件可以宣告獨占寫入（M1）。預設值未判（U1）。
- **作者要付的**：見 1.6 的 (3)。獨占整個 World 的存取、System 的錯誤、System 的狀態都還沒有答案（U10～U12）。

### 3.5 分析的結果

| 情形 | 處置 | 元素 |
|---|---|---|
| 兩個 System 的存取有衝突 | 不是錯誤。不同時跑；先後看順序邊 | M2 |
| 有衝突又沒寫順序 | 依登記的先後穩定平手；要讓人看得到。選用嚴格的模式時是啟動錯誤 | M3、M3b |
| 順序成環、獨占的元件有第二個寫者、讀的 Resource 沒人登記、掛到不存在的 schedule | 啟動錯誤，一次報完 | K2、M1 |

同一份登記得到同一張計畫（D1b、D3a）。

### 3.6 結構變更、同步點、hook、stamp、事件

- 生成、刪除、加減元件都先記下，在同步點套用（K4）。套用的順序未判（U2）。
- 同步點之後，之前拿到的參考全部失效（M6a）。
- 同步點在哪裡：未判（U5）。
- 元件被加上或移除時可以有 hook（K6）。種類與生效的時機未判（U3）。
- 每個 ECS 元件每個實體有 stamp；值是依計畫位置取的單調計數（K7、E3）。
- World 的事件緩衝：寫入者之後的 System 當步就能讀（M8）。游標與保留期未判（U4）。

### 3.7 邊界

- 外部（OS 事件、檔案 IO、網路）不持有、不修改 World；只在交換點交換資料（M11、D6b）。
- 通用機制不含 OS；OS 只經帶過來的 os（D6a）。
- 模擬與渲染分成兩個 World，只在 Extract 交會；渲染不回寫（D7a、D7b）。它們在不在同一個 App、各在哪條執行緒：未判（U8）。
- 時間是 Resource，可以替換（K8a）。帶過來的 time 與 audio 直接讀真實時鐘，和這一條不合，要處理（2.1）。

### 3.8 從通用機制移出去的東西

| 移出去的 | 由誰選用 |
|---|---|
| 決定性區與它的規則（M4c、M6）；它管的元件必須獨占（M1b、X6）；step 是純函式、時間只來自 tick（D5）；平行的條件（M7）；stamp 換算成 tick、決定性區不准用變更過濾（E3 的後半） | 需要決定性的產品，①是其一 |
| wire 上的 id（D3b 的一半）；收包的時間（D6c 的一半）；Ledger、Visibility、N1～N12（X4、X5） | 連網的產品 |
| Match 與 Client 共用同一份 System；Peer 與 Player | PvP 產品自己 |

它們怎麼掛上通用機制，也就是擴充點的形式，未判（U19）。v1 在這裡列了「屬性袋、finish 時的驗證、匯出計畫、快照與還原、重跑 schedule」，那些沒有經過第一部分，v2 拿掉。其中快照與還原、重跑 schedule 可能本來就是通用的（U9）。

移出去的代價，全局審計已經指出，一併列在這裡：
- 擴充點本身是新的基盤介面，設計錯了一樣難改。
- 產品忘了選用決定性的 plugin 套件時，那些檢查會整個消失，要有別的辦法讓人發現。
- 未查證的反例：有的多人引擎把決定性放在核心。

### 3.9 已知的限界（M10、X18、E5）

- 從簽名推存取：做得到，三個編譯器都成立。
- 擋住繞路：做不到絕對。攔不到的形狀有八種，例如：
  - 寫了又寫回原值
  - 經存下的參考讀沒宣告的元件
  - 元件裡堆積上的成員被改
  - 全域變數
  - 其他執行緒的存取
- System 執行中不能再跑 System。
- 核對只在 debug 建置還是可以開關：未判（U14）。

### 3.10 它不解決什麼（X9）

- 不會自動給出業務的順序。
- 不會自動給出決定性。
- 不會把外部 IO 變成 System。
- 不會消掉組裝與 runner 的職責。
- 「統一契約省多少整合成本」還是假說（E7）。

### 3.11 檢驗的場景

| # | 場景 | 通過的樣子 |
|---|---|---|
| 1 | 加一個新的 plugin 套件 | 通用機制與 runner 不必改 |
| 2 | 刪掉一個產品 | 其餘照樣建置 |
| 3 | 沒有畫面的 App | 用同一套通用機制 |
| 4 | 換遊戲規則 | 和規則無關的 plugin 套件不動 |
| 5 | 寫一個 2D 橫版的樣本 | 作者不必寫任何決定性、回滾、網路的宣告，也不必懂這些概念。另外要量通用機制本身讓作者多寫多少：登記、System 的寫法限制、兩個 World 與 Extract、同步點。比較的基準與門檻在看結果前由你定 |
| 6 | 寫一個小工具的樣本 | 工具的主要功能寫得出來：一份文件、幾個面板、復原。若寫不出來或只是多出儀式，E7 的假說就不成立 |

失敗的條件：
- 接第一個能力還要改通用機制或 runner。
- 要引入第二種排序機制才能表達需求。
- 宣告與實作脫節到抓不住的情形反覆出現。
- 場景 5 或場景 6 不通過。
