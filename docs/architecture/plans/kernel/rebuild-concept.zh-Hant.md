## 第三部分　重構後的概念層

這一部分只寫通過第一部分的內容，用新的詞。每一段後面的括號是它對應的元素編號。

### 3.1 目的

讓需要被排程的工作都遵守一套可驗證的共同契約（C9）。三類產品用同一套通用機制；一類產品專用的需求住在它選用的那一層，不讓別的產品的作者多寫、多懂。

### 3.2 推導鏈（C1～C5）

```text
型別 ──登記──▶ id
System 的函式簽名 ──編譯期──▶ 存取集合
存取集合 ＋ 顯式的約束 ──分析──▶ 衝突邊、順序邊（分開存）
邊 ＋ 執行策略 ──▶ 執行計畫（每個 schedule 一張）
計畫 ──Executor──▶ 在對的執行緒呼叫 System、交給它 System 參數、記 stamp
```

每一環都不含業務。

### 3.3 組成

| 組成 | 做什麼 | 元素 |
|---|---|---|
| World | 存資料：id 對應到有搬移與解構規則的位元組；另有 stamp、延後佇列、事件緩衝、時間 | C6 |
| Registry | plugin 在 build 時登記型別、System、schedule；finish 時凍結。id 依登記順序 | C1、K3、K5、D3a |
| Scheduler | 只看存取集合與顯式的約束，算出計畫；不打開函式體 | C3、C4、C7 |
| Executor | 照計畫執行；第一版只有 Serial | C5、C8、D1d |
| App | 一個 World、它的 Registry、它的 schedule 清單 | — |
| Plugin | 登記的單位；擁有它登記的東西，可以整個拿掉 | K5、X12 |
| main 與 runner | main 組裝：建 App、列 plugin、接外部工作者。runner 跑迴圈：決定哪個 schedule 何時跑、協調時鐘、啟停 | M12、M13 |

### 3.4 契約

- **從簽名推出的一半**：讀寫哪些元件與 Resource、讀寫哪些事件、會不會記延後的結構變更（C2）。
- **顯式宣告的一半**：掛在哪個 schedule、run 條件、before／after、執行緒親和。都有預設，不寫也能跑（M4）。
- **資料的契約**：欄可以宣告獨占寫入（M1）。
- **錯誤**：照 base 的契約。寫錯程式是 Programmer Error，不靜默。

### 3.5 分析的結果

| 情形 | 處置 | 元素 |
|---|---|---|
| 兩個 System 的存取有衝突 | 不是錯誤。不同時跑；先後看順序邊 | M2 |
| 有衝突又沒寫順序 | 依登記順序穩定平手，並列進診斷 | M3 |
| 順序成環、獨占的欄有第二個寫者、讀的 Resource 沒人登記、掛到不存在的 schedule | 啟動錯誤，一次報完 | K2、M1 |
| 選用了嚴格模式的範圍內，有衝突又沒寫順序 | 啟動錯誤 | M3b |

同一份登記得到同一張計畫（D1b、D3a、D3c）。

### 3.6 結構變更、同步點、hook、stamp、事件

- 生成、刪除、加減元件都先記下，在同步點套用；套用的順序有定義（K4）。
- 同步點之後，之前拿到的參考全部失效（M6a）。
- 同步點的位置寫在 schedule 的定義裡（M9）。
- 元件被加上或移除時，可以登記 hook（K6）。
- 每個元件每個實體有 stamp，記它最後被改的時刻（K7）。
- 事件：寫入者之後的 System 當步就能讀（M8）。

### 3.7 邊界

- 一個 World 由一條執行緒擁有；World 內不上鎖（M11、D6b）。
- 外部（OS 事件、檔案 IO、網路）不碰 World，只在交換點經交換 Resource 交換資料；交換點由 runner 安排（M11、X3、M13）。
- 核心不含 OS；OS 只經帶過來的 os（D6a）。
- 模擬與渲染是兩個 World，只在 Extract 交會；渲染不回寫（D7a、D7b）。
- 時間是 Resource，可以替換（K8a）。

### 3.8 不在通用機制裡的東西，以及通用機制要為它們留什麼

| 專用的一層 | 住在裡面的 | 通用機制要留的 |
|---|---|---|
| 決定性 | 決定性區與它的規則（M4c、M6）；嚴格模式的選用（M3b）；管的欄必須獨占（M1b）；step 是純函式、時間只來自 tick（D5）；平行的條件（M7） | 型別與 System 可以掛別人定義的屬性；finish 時別人可以加檢查，結果併進同一份啟動報告；計畫與存取集合可以匯出 |
| 預測與回滾 | 固定步的重入（K8b） | 可以從外面重跑一個 schedule；可以對宣告的一組欄做快照與還原 |
| 網路與複製 | wire id（D3b）；收包時間（D6c）；Ledger、Visibility、N1～N12（X4、X5） | 交換 Resource；stamp；hook |
| PvP 產品 | Match 與 Client 共用同一份 System（X4）；Peer 與 Player | 同上 |

右欄是需求的來源，不是設計。每個擴充點長什麼樣，由 R1 推導，並照 AGENTS §4 寫系譜與被否決的替代案。

### 3.9 已知的限界（M10、X18）

- 從簽名推存取：做得到，三個編譯器都成立。
- 擋住繞路：做不到絕對。攔不到的形狀有八種，例如：
  - 寫了又寫回原值
  - 經存下的參考讀沒宣告的元件
  - 元件裡堆積上的成員被改
  - 全域變數
  - 其他執行緒的存取
- 對策三層：API 讓繞路難寫；可開關的存取核對；審查。

### 3.10 它不解決什麼（X9）

- 不會自動給出業務的順序。
- 不會自動給出決定性：那要決定性那一層加上數值的規則。
- 不會把外部 IO 變成 System。
- 不會消掉 main 與 runner 的職責。

### 3.11 檢驗的場景（X13、X15，加一個新的）

| # | 場景 | 通過的樣子 |
|---|---|---|
| 1 | 加一個新的 plugin | 核心與 runner 不必改 |
| 2 | 刪掉一個產品 | 其餘照樣建置（AGENTS §7） |
| 3 | 沒有畫面的 App | 用同一個核心，schedule 清單裡沒有渲染 |
| 4 | 換遊戲規則 | 通用的 plugin 不動 |
| 5（新） | 寫一個 2D 橫版樣本 | 作者不必寫任何決定性、回滾、網路的宣告，也不必懂這些概念 |

場景 5 來自你 11 月 14 日的決定，原文沒有。

這張設計圖算失敗的條件：
- 接第一個能力還要改核心或 runner。
- 要引入第二種排序機制才能表達需求。
- 宣告與實作脫節到抓不住的情形反覆出現。
- 場景 5 做不到。
