1. 規格否決甲的第一個理由（entity-store DI 4、E-12）是系譜，不能決勝。

1. 和 entity-store 的一句話一致。那句話屬於已撤回、從未實作的一節，原意是套用期間不可重入的斷言（主 checkout `build/evidence/kernel-hook-window-review/sources.md`）。這是系譜，不能決勝。
2. 避免連鎖和輪數的設定。這是「會不會停」的問題，和產品無關，可以當理由。

| 選項 | 系譜 | 作者付什麼 | 其他代價 |
|---|---|---|---|
| 子：當場連鎖（深度優先）。hook 記的變更緊接著套用 | Bevy（沒有輪數上限） | 有：hook 是在套用到一半時執行的，看到的是套到一半的狀態；它記的變更會插到後面的記錄之前（5.2） | 不保證會停 |
| 丑：下一個同步點 | 規格 F.4 | 有：兩個同步點之間，System 看得到半成品。例：加上 A 的 hook 會補上 B；在下一個同步點之前，別的 System 看到有 A 沒有 B 的實體 | hook 的佇列會跨 schedule 開著；①的回滾快照要多存它 |
| 寅：同一個同步點裡分輪（廣度優先）。這一輪的變更全部套完，再套 hook 記的，最多 N 輪 | 規格當時的提案 3，被否決 | System 看不到半成品；hook 看到的是套完一整輪的狀態 | 要定 N；超過 N 怎麼辦 |

v1 說「子的作者成本是零」，不對。v1 也漏了寅。

子與寅都要回答「怎麼保證會停」。hook 重審留下三個辦法：

| 辦法 | 作者付什麼 | 保證到什麼程度 |
|---|---|---|
| (i) hook 不准刪除實體 | 有。「父節點被移除時刪掉子節點」做不了；②③的階層（U16）會碰到 | 還要配 (ii) 才完整 |
| (ii) 啟動時檢查：hook 會加、會移的元件型別不能成環 | 有。看起來成環但其實會停的設計，啟動時被拒。刪除等於移除全部元件，所以會刪除實體的 hook 幾乎一定成環，結果接近 (i) | 啟動時就保證 |
| (iii) 執行期的上限（深度或輪數），超過就是 Programmer Error | 正常情形是零 | 跑到那個情形才會報 |

v1 引了你一句話「這是底層機制，不能放鬆」，拿來問「(iii) 算不算放鬆」。我查了原話，是 11 月 14 日你在 hook 重審的會話裡說的：「去看下源碼，這個是底層機制，不能放鬆的。」意思是審查要去讀原始碼、不能馬虎，不是在說哪一個辦法可以選。v1 用錯了，撤回。

hook 的種類（只有加上與移除，還是更多）仍未判。

### 5.4 固定步在哪裡累加（U7）：未判

圖上有兩句話：
- 圖一 World 裡：「Time：resource，可替換」。
- 圖一底部與圖二：「多時鐘、啟停、IO 同步點仍是 Host 的」。出自 v0.2 §10.1：「跨時間域的資料同步仍然需要明確設計，不能只靠 Scheduler 自動解決。」

原架構師會話已更正：偏離的不是「Host 協調時鐘」，而是把舊的 `FixedTickRuntime` 的型別和語義原樣帶進來、還寫進白名單。R0 已經不帶 `engine/runtime`、不帶那張白名單。

| 選項 | 系譜 | 代價 |
|---|---|---|
| A：累加的狀態與驅動都在 runner | 規格 G-6、H.2；舊的 `FixedTickRuntime` | 累加的狀態不在 World 裡。暫停、慢動作、測試用的手動時間要另外開路 |
| B：都在 World 裡。一個獨占整個 World 的 System 累加，並重跑固定步的 schedule | Bevy（`bevy_time/src/fixed.rs:243`） | 需要「獨占整個 World 的 System」（U10）。有了它，②的作者什麼都不用寫 |
| C：狀態在 World 的 Resource，驅動在 runner | A 的驅動加 B 的狀態 | 見下 |

v1 提議 C，說它是「新導的」，並用 E5 退掉 B。這三點都不對：
- C 不是新導的。驅動那一半就是規格 H.2 的形狀（runner 呼叫 k 次），也就是舊累加器的迴圈；只是把它的狀態搬進 World。
- E5 是 spike 自己選的斷言。有了 U10，B 就沒有這個問題。v1 把「需要 U10」和「違反 E5」當成兩個缺點，是同一件事算了兩次。
- C 有 v1 沒寫的代價：
  - Time 會有兩種寫者：runner 在 System 之外寫，System（例如對時）也寫。「獨占寫入」的檢查看不到 runner 那一邊。
  - 規格把累加器放在 runner 有它的理由（G-6）：它來自真實時鐘，不該進決定性的資料。搬進 World 之後，①的回滾、digest 與存檔都要把它排除。
  - runner 要知道哪一個 schedule 是固定步的（U17）。
  - 舊的做法在追不上時會丟掉時間；這和「時間被截斷時不可以讓時間消失」（E9b）衝突，要另外定。

這一項跟著 U10 走：如果通用機制要有「獨占整個 World 的 System」（③的 Inspector、復原很可能需要），B 就可行；沒有的話在 A 與 C 之間選。

另外，帶過來的 time 模組的 `Now()` 是全域函式，audio 用真實時間排程（重構稿 2.1）。這兩處和「時間是可替換的 Resource」不合，另列。

## 6. 評審帶出的更正

### 6.1 「Entity：index＋generation」和我提的 E2

圖一寫「Entity：index＋generation」。規格 A.8 取捨 1 記載為「使用者 2026-11-11 決定」（K.3 第 1 項，側邊會話轉述；repo 裡沒有你的原話）：

- 鍵的格式是機制的：64 位元，低 32 位 index、高 32 位 generation。機制不看兩段的意義。
- 配發的策略是產品的 Resource。PvP 選單調、不重用、generation 恆為 0。
- World 自己不配發。

我在[實體的疊代順序](rebuild-entity-order.zh-Hant.md)提的 E2 是「id 單調配發、不重用，當通用機制的預設」。它會改到第三點。R0 的帶過去清單（你 11 月 14 日核准）在擴充點裡列了「可替換的預設配發器」，所以方向你看過；但 E2 那份文件沒有寫明這是在改 11 月 11 日的決定。這裡補上。

提議的方向不變：通用機制附一個預設的配發器，產品可以換。理由：②③的作者不該為了生成實體先寫一個配發器。

**v1 說「格式不變、兩者可以並存」，說得太簡單。還有兩個問題沒解：**

1. **格式和預設的策略互相矛盾，要選一邊。**
   - 照格式，只在 32 位的 index 段裡單調配發：一個 World 一生最多生成 2³² 次，用完就報錯。每秒 1 萬次約 5 天。
   - 跨整個 64 位元一直數：不會用完，但 generation 那一段就沒有意義了。
   - Bevy 是另一種：回收 index、靠 generation 分辨。那樣「順序＝生成的先後」不成立。
2. **配發器會讓會生成實體的 System 兩兩衝突。** 配發器是一個會被寫的 Resource，所以任兩個生成實體的 System 都衝突（規格就是這樣推的）。照「歧義要讓人看得到」，②③的作者每一對都會看到一則提示。只有 Serial 時，可以不把配發器算成衝突；這要定。
