# 架構師複核：`v8-arch-adapter-plugins-plan`（PR #212）的壞味道

更新：2026-11-13。Owner：架構（架構師會話，Opus 5.5）。**狀態：給使用者決定的複核意見；未改規劃稿與計畫。**

出處：使用者的疑慮（kernel HANDOFF 現況「使用者對 #212 的方向性疑慮」）；盤點 `build/evidence/adapter-plugins-plan/review-inventory.md`（主 checkout，Opus／high 只讀盤點，74 條，每條附兩問的試答）；規劃稿與計畫修訂（本分支）。盤點的 74 條我沒有逐條重驗原始碼；下面的判斷以盤點的出處欄與我讀過的段落為準。

## 1. 診斷：規則放錯了地方

使用者的原意是「產品能自由使用 Engine 的能力」，規則只該守 Engine 與 adapter 之間的邊界。#212 把邊界的守法延伸到了產品、工具、測試與每一批的流程上：

| 盤點的數字 | 值 |
|---|---|
| 新增或加嚴的規範性條目 | 74 |
| 規劃稿自己加的（不是使用者定的） | 40（另 13 條性質是使用者定、機制是規劃稿加） |
| 往產品或工具的日常開發加步驟或限制 | 23（其中 2 條是 Feature 本身要求的） |
| 答不出「不守的話誰會壞」 | 4 |
| 只能對到 AGENTS 通則、流程或訊息品質 | 17 |
| configure 錯誤代號 | 1 → 9 |
| 新的常駐守衛 | +7（N1～N7），其中 4 份是「只減不增」的白名單 |

最大的一個張力：規劃稿 §0 自己寫「升級靠型別隔離今天已大致成立」。也就是說，使用者的 Feature 1（升級一個外部組件只改對接它的那一塊）今天大部分已經成立；#212 新增的大多數東西守的是「位置」與「流程」，不是 Feature。

第二個張力：使用者在未決 10 選了 (iii)——adapter plugin 可以對依賴它的產品與 plugin 露出第三方型別，原則 3 是對 Engine 說的。但規劃稿在 (iii) 之前寫的幾條產品側的守衛與限制（`*Native` 歸零、工具只准呼叫 ImGui widget、asio 連結的白名單、imgui 自己重寫 SDL 那一半）都還以「產品不得碰第三方型別」為前提，沒有隨 (iii) 重看。

## 2. 建議的判準

每一條只在下面兩種情況之一保留：

- **守 Engine 與 adapter 的邊界**：Engine 不連、不含入外部組件；Engine 的標頭只有 Engine 的詞；adapter 實作 Engine 介面的部分只用 Engine 的詞；一個外部組件一個 adapter。
- **Feature 2、3 本身要求的**：產品在一個欄裡選能力與後端；缺後端或多個後端在 configure 指名報錯。

其餘的刪掉、或降為該批的實作細節（不寫成計畫層的規則、不成為常駐守衛）。產品與工具的日常開發不因這次改造多一個步驟——除了「在選擇欄寫要用的 plugin」這一個 Feature 2 本身的步驟。

## 3. 逐組的建議

### 3.1 保留（守邊界或 Feature 本身）

- 使用者已定的原則與歸屬：判斷順序、三原則（只對 Engine 側）、兩類 plugin、SDL 家族、對外介面的讀法、P2、shader 工具搬進 SDL plugin（未決 2 B）、(iii)、DI 5（已改窄）、DI 6、兩條 RC、SDL 2D renderer 退役。
- 選擇欄：同一個欄（每個可執行單位一份）；Engine 的能力在各能力模組的 CMake 宣告「需要一個後端」；configure 錯誤只留三種——缺後端、多個後端、選了不存在的 plugin。
- 守衛：Engine 側的含入與連結檢查（只掃 `engine/`）、Engine 標頭衛生、搬家後的含入根不沿用 `engine/` 前綴、中性 platform 契約的合成實作測試、搬家的 byte 級等價（golden、內容身分 digest）、搬家前後 ctest 名單相同、修既有 SDL link guard 漏掉 `SDL3_ttf` 的缺陷。
- 新批 adapters-relocate：理由是位置不是 Feature，但使用者明說要「SDL 的部分全部在 plugin」，保留，範圍限於機械搬動。

### 3.3 要回到使用者的已定項（附證據，照使用者的要求「若發現強行外移降低效率或膠水過多，停下附證據回報」）

1. **未決 3：model 取樣規則與 audio core 做成 plugin。** 盤點答不出「不守的話誰會壞」：三份提案都寫「沒有點名的 Feature」。做了反而要新增一個跨 plugin 的契約——Match 與 Client 必須選同一個取樣 plugin，否則命中判定不同（決定性）——外加守它的守衛。這正是使用者說的「膠水過多」的訊號，而且是事前就看得到的。**建議**：方向照記錄保留（Engine 只提供機制），但這次改造不搬；等出現第二種取樣規則或第二個音訊實作（有 Feature）時再搬。
2. **未決 7：工具只准呼叫 ImGui 的 widget。** 在 (iii) 之下，工具依賴 imgui plugin、使用它露出的 ImGui 型別本來就被允許，C 的限制與它的工具守衛變成多餘。**建議**：取消這條限制；「GYO 自己的 UI API」仍是未來目標。
3. **未決 6 的補充：「產品獨有的需求先做成該產品的 plugin」。** 若讀成「產品每個獨有功能都要包成 plugin」，就是往產品的日常開發加步驟。**建議的讀法**：只在產品要用到一個外部組件時（例：PvP 的 Gateway 連線），把對接那個組件的部分做成產品目錄下的 plugin；產品自己的功能程式照常寫在產品裡。
4. **未決 8：手寫程式不含 protobuf、解碼檔要列名。** 照第 3 點的讀法，產品的 wire 編解碼檔就是產品對接 protobuf 的 plugin；不需要另設列名清單。**建議**：刪列名機制。

### 3.4 (iii) 帶來的一筆節省

規劃稿為了讓 imgui plugin 不碰 SDL，計畫自己重寫 ImGui 的平台與繪製那一半（+8～16 h）。在 (iii) 之下，imgui plugin 可以依賴 SDL plugin。SDL 2D renderer 退役後（未決 9），imgui 可以用它官方的 SDL3 平台後端加 SDL_GPU 繪製後端。**建議**：不自己重寫，改用官方後端；`IRenderDevice` 的擴充是否還需要由 plugins-editor 的宣告確認。這一筆未經查證，plugins-editor 開工時先驗。
