# 實體的疊代順序：是特性還是舊設計的污染（`v8-arch-rebuild`）

更新：2026-11-14。Owner：架構（架構師會話）。**狀態：分析與提案，待使用者確認。沒有量測；代價只寫到複雜度，數字要等樣本量。**

使用者（2026-11-14）：
> 這裡面有一個點，有可能是會被你排除掉的，就是 entity ID、在 bevy 的設計裡，那個調度是無序的，但是在 GYO 裡，則被改成了有序。這個點你可以考慮一下如何做。看下這樣做的代價是什麼，在單機遊戲和聯機遊戲中是否都成立。（這個如果成立就是特性，我怕被你當成舊設計的污染）

## 0. 結論

1. **它成立，是特性，三類產品都受益，作者不必多寫任何東西。** 我先前把它分成兩半，其中「兩端查詢順序相同」判成「只有 PvP 需要、換位置」。那個判斷錯了，在這裡更正。
2. **要分清楚的是兩件事**：
   - **契約**：查詢疊代實體的順序，只由「現在有哪些實體」決定，依 EntityId 由小到大。這是特性。
   - **做法**：把每個元件的儲存依 id 排好。這是實現契約的一種做法，不是唯一的一種。
3. **舊設計的問題不在這個特性，在它的理由與附帶的東西**：
   - 理由寫的是「和 entity-store 一致」。
   - 置換條件把做法鎖死，連換儲存都不准。
   - 門檻借自 PvP 的實測。

   這些要換；特性本身留下。
4. **代價是性能，不是作者成本。** 另有一個前提：實體的 id 不能回收重用。

## 1. Bevy 怎麼做（本機 6a911653f，路徑從 `crates/bevy_ecs/src/` 起算）

| 事實 | 出處 |
|---|---|
| 查詢的疊代順序不保證。同一句註解在兩個檔出現十多次 | `system/query.rs:655`、`query/state.rs:1230` |
| 刪除時把最後一列搬來補洞，所以順序隨增刪的歷史改變 | `storage/table/mod.rs:227` 的 `swap_remove_unchecked` |
| 實體的 index 會回收重用，靠 generation 分辨 | `entity/mod.rs:648`、`:801` 的 `free` |
| 需要順序時，作者自己在查詢上排序 | `query/iter.rs:614` 的 `sort`，以及 `sort_by`、`sort_by_key` 等 |
| System 之間沒寫順序的衝突，預設忽略 | `schedule/schedule.rs:1954` 的 `ambiguity_detection: LogLevel::Ignore` |

所以在 Bevy 裡，「這一幀先處理哪個實體」取決於之前生成與刪除的歷史。同一段歷史會得到同一個順序；歷史不同、內容相同的兩個 World，順序不同。

## 2. 特性的定義

> 查詢疊代實體的順序是 EntityId 由小到大。兩個 World 只要現在的實體集合相同，疊代順序就相同，不論它們是怎麼走到這個狀態的。

它和「System 的執行順序可重現」是兩回事。後者已在概念層重構稿判為照帶。

## 3. 什麼時候順序會影響結果

只要 System 處理實體的結果和先後有關，順序就會影響結果：
- 兩個實體搶同一個東西：先到的拿到。
- 浮點數逐個累加：加的順序不同，結果差一點。
- 邊疊代邊生成新實體：新實體的 id 跟著順序走。
- 邊疊代邊發事件、取亂數：事件的順序、每個實體拿到的亂數跟著順序走。

這些寫法在遊戲裡很常見。作者通常不會意識到它們依賴順序。

## 4. 對三類產品各自成不成立

| 產品 | 有了這個特性，得到什麼 | 沒有的話 |
|---|---|---|
| ①PvP | Match 與 Client 的歷史一定不同（Client 晚加入；實體進出它看得到的範圍；狀態從權威端還原）。有這個特性，兩端對同一組實體的處理順序相同，共用的模擬才會算出同樣的結果 | 每個和順序有關的 System 都要自己排序；漏一個就是很難找的不一致 |
| ②單機遊戲 | **重來一次的行為和第一次相同**：關卡重開、讀檔之後，實體是重新生成的，歷史和第一次不同。有這個特性，敵人的處理順序和第一次一樣。**從存檔重現問題**：拿玩家的存檔重跑，會走到同一個結果。倒帶、重播這類功能也靠它 | 讀檔後或重開後行為有細微差異，例如哪個敵人先動、誰先撿到東西；問題只在某些遊玩歷史下出現，很難重現 |
| ③工具 | **復原再重做之後，順序和原來一樣**。**存檔的內容順序穩定**：同一份文件不論怎麼編輯出來，寫出的順序相同，版本控制的差異乾淨。測試可以直接擺好狀態，不必重演一段操作 | 存檔時要另外排序；測試要重演歷史才能得到和實際相同的順序 |

②與③的好處不靠 PvP 的理由。它們是「結果只取決於現在的狀態，不取決於怎麼走到這裡」這個性質，和產品類別無關。

作者成本：零。作者反而少懂一件事：不必知道「疊代順序不保證」這個坑，也不必記得哪裡要排序。

所以照判斷機制的第 3 題：三類都受益、作者成本是零，屬於通用機制。

## 5. 前提：id 不能回收重用

這個特性要有意義，id 本身必須是穩定的：
- **新生成的實體拿到比現有都大的 id**（單調配發、不重用）。這樣「依 id 排序」就等於「依生成的先後」，作者很容易懂：先生成的先處理。
- **可以用指定的 id 生成**：讀檔時用存檔裡的 id；Client 用權威端給的 id。
- 若像 Bevy 那樣回收 index，新實體會填進舊的空位，「依 id 排序」又變成取決於歷史，特性就失效。

影響：
- 我先前把「單調、不重用」判成 PvP 的配發策略、要移到產品。**這一點也要改**：它是這個特性的前提，應該是通用機制預設的配發方式。
- 不重用還有一個好處：刪掉的 id 永遠不會再出現，舊的 id 查不到東西就是查不到，不需要 generation 來分辨。
- 代價：id 不能直接當陣列的索引用，查一個實體在哪裡要多一次查找。
- id 用 64 位元的計數就不會用完。舊設計的格式是低 32 位 index 加高 32 位 generation；單調配發時只用到 32 位，每秒生成一萬個實體約五天用完。格式要不要改成整個 64 位計數，是設計題。

## 6. 做法與代價

n 是實體數，k 是一次同步點要加或刪的數量，m 是一個查詢涉及的元件數。

| 做法 | 怎麼做 | 生成與刪除 | 多元件的查詢 | 作者成本 | 評語 |
|---|---|---|---|---|---|
| A 每個元件一欄，欄內依 id 排好 | 舊設計的做法 | 每一欄搬動後面的資料，O(n)；在同步點成批合併是 O(n＋k log k) | 幾個排好的欄做合併，O(各欄長度的和) | 零 | 最簡單。加減一個元件不必搬整個實體。實體多、元件多的查詢比 Bevy 的做法慢 |
| B 照元件組合分表（Bevy 的 archetype），表內依 id 排好 | 查詢跨多張表時再合併 | 表內所有欄都要搬，O(n)；加減元件要換表 | 單張表很快；跨表要做多路合併 | 零 | 查詢最快，實作最複雜 |
| C 不排序的儲存，另外維護一份依 id 排好的索引 | 疊代時照索引去取 | 索引 O(n)；儲存本身 O(1) | 照索引跳著讀，對快取不友善 | 零 | 生成與刪除便宜，疊代較慢 |
| D 不排序，查詢預設先排序再給 | 每次疊代排一次 | O(1) | 每次 O(n log n) | 零 | 實作最省事，每幀都付排序的錢 |
| E 不排序，作者需要時自己排（Bevy 的做法） | — | O(1) | 快 | **有**：作者要知道哪裡依賴順序，漏了不會報錯 | 不提供這個特性 |

- A 到 D 都實現第 2 節的契約，差別只在性能與實作的複雜度。E 沒有實現。
- 你說性能開銷可以接受，作者成本不行。所以 E 排除；A 到 D 之間的選擇是設計時用量測決定的事。
- 大量、生命短、彼此不互動的東西（粒子、彈幕的子彈）可以不當實體，放在它們自己的緩衝裡。這是一般引擎的做法，不影響這個特性。
- 平行疊代時順序本來就沒有意義；第一版沒有平行。

**還沒有的證據**：沒有任何一種做法在 GYO 的規模上量過查詢的時間。卡 07 也指出舊設計說「在預算內」沒有根據。選做法之前要量：1 千、1 萬、10 萬個實體時，生成與刪除的時間，以及兩個、四個元件的查詢時間。

## 7. 舊設計裡要換掉的部分

| 舊設計寫的 | 問題 | 處置 |
|---|---|---|
| 理由：「和 entity-store 的 DI 2 一致」；系譜追到 PvP 最早的 `std::map` | 理由是「舊的就是這樣」 | 換理由：第 4 節 |
| 不變量寫成「每個欄依 id 嚴格升冪」 | 把做法 A 寫成了不變量 | 不變量只寫第 2 節的契約；做法是設計 |
| 置換條件：換儲存時「順序不變、不在上面加 archetype」 | 「順序不變」是對的（那是契約）；「不加 archetype」把做法 B 預先排除 | 只留「契約不變」 |
| 換儲存的門檻：4,000 個實體、1 ms，取自 PvP 的實測 | 借用一個產品的數字 | 用樣本重新量，門檻另定 |
| 守衛：測「容器的內容是排好的」 | 守的是做法 | 守契約：兩個歷史不同、內容相同的 World，疊代序列相同 |
| 配發寫成「World 不配發，產品自己寫配發器」 | ②③的作者要多寫一個配發器 | 通用機制給預設的配發（單調、不重用）；產品可以換，也可以指定 id |

## 8. 提議

1. **去留登記表加一列**：「查詢的疊代順序依 EntityId 由小到大，只取決於現在的實體集合」。結論：照帶、換理由，屬通用機制。
2. **再加一列**：「實體的 id 單調配發、不重用；可以用指定的 id 生成」。結論：照帶、換理由、換位置（從產品的策略移回通用機制的預設）。
3. **儲存的做法**（A 到 D）列為設計題，用樣本量過再選。先用最簡單的 A 做樣本沒有問題，前提是不把它寫成不變量。
4. **更正兩份文件**：

## 9. 要你確認的事

1. 這個特性照第 2 節的定義，列為通用機制的契約。
2. id 單調配發、不重用，列為通用機制的預設（第 5 節）。
3. 儲存的做法不寫成不變量，量過再選。

## 10. 範囲の限界

- 沒有量測。第 6 節只有複雜度。
- ②沒有真實產品；第 4 節②的好處是從「關卡重開、讀檔、倒帶」這些常見功能推出來的。
- Bevy 的事實只查了第 1 節列的幾處。Bevy 的生態怎麼處理需要決定性的情形（例如網路套件自己排序），沒有查。
- 做法 B、C 的複雜度是分析，沒有實作過。
