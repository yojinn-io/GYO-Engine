## 1. 這一批做什麼

### 1.1 用例子講

這個測試案例有兩條執行緒：

- **waiter**：每回合先看旗標，沒設就呼叫 `Block` 睡著。
- **signaller**：看到回合開始，就設旗標再 `Signal`。

如果 `WakeSignal` 有 bug，在「看旗標」和「睡著」之間到的訊號會丟掉，waiter 會一直睡到 2 秒的逾時。為了抓這個 bug，案例讓 waiter 每回合晚一點點才看旗標（0～63 次讀時鐘），讓「看旗標」的時間點掃過訊號到達的那一刻。兩條執行緒必須**同時在跑**，訊號才會落在那個縫裡。

signaller 等對方的時候先自旋 4096 次，等不到就 `yield`。4096 次自旋大約只有 1～9 µs，跟 WakeSignal 的喚醒延遲（平均 4.5～10.7 µs）同一個量級，所以每個進了 `Block` 的回合，signaller 都會走到 `yield`。結果在兩個平台上不一樣：

- **macOS 有負載時**：每次 `yield` 讓出 CPU 最多一個時間片（約 10 ms）。signaller 讓出後，下一回合 waiter 一定進 `Block`，所以一旦進入這個狀態就會一直持續下去。案例因此拖到幾十秒（#289 第 3～5 節）。
- **Linux 有負載時**：時間不會拖長（最多 0.6 s），但兩條執行緒常常輪流跑，不再同時跑。2 萬回合全部進 `Block`，訊號落在 waiter 看旗標前後 0.5 µs 內的回合變成 0，掃描完全沒掃到縫（第 2.2 節）。

這兩個問題的根是同一個：signaller 在對方很快就會回應的時候，太早讓出 CPU。

### 1.3 改成什麼（建議：選項 B）

`tests/common/os/WakeSignalTests.cpp`「loses no signal」案例：

- `SpinsBeforeYield` 從 4096 改成 65536。三個等待的迴圈（signaller 等回合開始、signaller 等 `consumed`、waiter 等 `signalled`）都用這個值，維持現狀。
- 改寫案例前的註解：說明自旋要比對方的喚醒久，`yield` 只在對方真的沒在跑時才發生；單核時仍然靠 `yield` 前進。
- 拿掉 #289 加的進度 `Note`（`CaseTiming.hpp` 寫明「使用者對這個案例的決定落地後拿掉」，這一批就是那個決定）。驗收量測用的是還帶著 `Note` 的版本；`Note` 每 2000 回合才在回合開頭寫一次檔案，不在掃描的縫裡。拿掉後再跑一次閒置的 ow-x1、ow-x19 與 L1（第 5.4 節）。listener（`CaseTiming.cpp`）留著，照 #289 的條件由主會話拿掉。

判定不改：`Rounds = 20000`、`StopAfterLost = 3`、1500 ms 的遺失線、2 s 的 `Block` 逾時、`CHECK_MESSAGE(lost == 0, …)`、案例名都照舊。

## 3. 選項比較

| | 現狀 | A：多核只自旋 | B：自旋 65536 次（建議） |
|---|---|---|---|
| 系譜 | `756073aa`（D71）：自旋後 `yield`，為了單核前進；4096 沒有寫理由 | 新導出：「掃描需要兩條執行緒同時跑，所以多核時讓 CPU 一直被占著」 | 現狀的形狀，只改數字：讓自旋比對方的喚醒（平均約 10 µs）久 5～20 倍，`yield` 只在對方真的沒在跑時發生 |
| macOS 負載下的時間 | 拖到幾十秒（#289） | 未量；推論不會（不 `yield`） | 未量；推論不會（喚醒通常在自旋內完成） |
| Linux 負載下的近縫回合 | 會塌到 0 | `yes` 32 時塌到 0 一次 | 每次都 ≥ 5096 |
| Linux 負載下的突變遺失 | 28 | 52 | 42 |
| 單核 | 靠 `yield` 前進 | 靠 `yield` 前進（`hardware_concurrency() == 1`） | 每次交手最多多花一次自旋（約 0.02～0.2 ms）再 `yield`；Linux 綁 1 顆 CPU 時 0.15 s |
| 有 CPU 限制但看得到很多核的環境（容器、affinity） | 不受影響 | `hardware_concurrency()` 回報的是硬體數，只自旋，靠排程器搶占才前進。Linux 綁 1 顆 CPU 時仍是 0.25 s（喚醒會搶占）。macOS、Windows 沒量 | 同單核 |
| 改動 | — | 加一個條件分支，三個迴圈都要用 | 改一個常數 |

**建議 B**，決定的理由：

1. 在量過的條件中，只有 B 從來沒有塌掉（Linux 每次近縫回合都 ≥ 5096）。A 在 `yes` 32 時塌過一次。推測原因：兩條執行緒被排到同一顆 CPU 時，A 的 signaller 會一直占著 CPU，對方只能等搶占；B 自旋一段後會 `yield`，正好讓出去。這是推測，沒有驗證。
2. 突變的遺失數 A（52）比 B（42）多，但兩者都遠高於現狀（28），而且抓到的次數相近（19 對 18，總共 20）。B 的弱點比 A 的塌陷小。
3. B 沒有依賴 `hardware_concurrency()` 的條件，也不會在有 CPU 限制的環境裡一直占著 CPU。

B 的代價：65536 是以「比喚醒延遲長」為根據選的數字，不是推導出的界限；CPU 越快，自旋時間越短。B 只把 4096 換成另一個大一點的數字，形狀沒變。

退掉的選項：

- **時間制的自旋**（自旋到經過 N µs 才 `yield`）：要在自旋裡讀時鐘，會改變 signaller 的反應時間，也就是掃描的相位。
- **自旋 262144 次**：只在 Linux 單核量過。比 65536 多出來的長度，沒有看到需要它的條件。

## 4. §14.4 的 1～5

這個案例是 Design Invariant 8 的守衛測試。判定本身不改，但改了它的機制，所以照 §14.4 交使用者核准。

1. **它守的性質**：在 waiter 看旗標與進 `Block` 之間送出的訊號不會丟（Invariant 8：pending 的訊號是 primitive 自己的狀態，後備實作在 mutex 下設定與讀取）。判定是「2 萬回合內沒有任何一回合等超過 1500 ms」。
2. **緩める面**（以前判定失敗、改了以後會通過的情況）：判定的條件沒變，所以只可能來自「掃到縫的機會變少」。
   - 量過的條件下沒有看到：Linux 閒置與 `yes` 16～32、Mac 環境負載 4～17，B 的近縫回合都不少於現狀；突變的遺失數與抓到數，閒置時一樣，負載下 B 比較多（第 2.1 節）。
   - 沒量過的條件：macOS 加負載、Windows。macOS 排在驗收（第 5.1 節）。Windows 只看 L1（第 5.5 節）。
   - 單核時現狀與 B 的近縫回合都是 0，一樣測不到。
3. **締める面**（以前通過、改了以後會失敗的情況）：
   - 負載下掃描不再塌掉，以前在負載下會「沒掃到縫而通過」的 bug，改了以後比較容易抓到。
   - 負載下不再因為拖到幾十秒而逾時。這不是締める面，是少了一種跟缺陷無關的失敗；不過它也沒有放過任何遺失（遺失的判定在逾時之前）。
4. **守住的性質還有誰守**：這個競爭只有這個案例在測。`ow-x1`、`ow-x19` 只有它能抓（`mutations.json` 的 what）。其他 Invariant 8 的案例（「stays pending」等）守的是不同的面向，不能代替。所以這一批不能有緩める面，驗收（第 5 節）要直接示範。
5. **根據與證據**：第 2 節；PR #289 的 dev_log 第 3～5 節。證據在主 checkout 的 `build/evidence/gyo2-os-wake-test-backoff/`（Linux 的輸出在 `linux/`）與 `build/evidence/gyo2-os-test-timeout/`（這台 macOS Intel 機器，git 不追蹤）。
