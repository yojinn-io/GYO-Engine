# 用 stamp 分先後：試做的統合（`v8-arch-gyo2-stamp-order-spike`）

更新：2026-11-15。Owner：架構（GYO2 重建會話）。**狀態：統合的草稿，待對抗檢查；結論待使用者判。這份文件不改任何已定的決定。**

## 0. 起因與使用者的話

對象是 [K0 事前宣告](kernel-nested-schedule-declaration.zh-Hant.md)第 10 節第 16 條：外層的 System 記了「刪除 5 號」，裡面那張 schedule 用指定的編號生成 5 號。

- 舊的 5 號本來就不在：裡面生成的新 5 號，回到外層的同步點被那筆刪除靜默刪掉。
- 舊的 5 號還在：裡面生成時撞上斷言，程式終止。
- 不巢狀時這兩筆在同一個同步點，先刪舊的、再生成新的，是合法而且被支援的寫法（同一個編號重新加入）。

主會話原本的收法是「撞到時回報錯誤」。使用者（2026-11-15，分支會話，原話記在 HANDOFF `v8-arch-gyo2-stamp-order-spike`）：「這額感覺就是數據庫的那種髒讀問題。」「有沒有漂亮一些的解法，Bevy如何處理的？」「能不能像stamp那樣在建一個編號？」「現在就試做。」

使用者的判準（同日）：「同樣的操作，每次不能不一樣，但是這個標準是單執行緒。」「我們不能保證的得提前說。並且提供解決方案（當然會有代價）」；以及先前問的「這些觀察是有必要的嗎……這個問題的核心是是否過度設計」。

## 1. 做了什麼

三個探索（都是 Opus／high），並行：

| 名稱 | 做什麼 | 結果 |

| 資料試做 | 其他幾種成對的情形（移除對插入、插入對插入等）也照先後 | 有條件可行，每種做法都有硬傷 |

## 2. 事實

### 2.1 成熟的做法（影響掃描，讀原始碼）

- **Bevy** 把「第幾輩子」放進編號：編號＝位置＋世代，實體被刪掉世代就加一。指令在記下的當下綁定整個編號，套用時比對，世代不對就不會落到新的實體上。比對失敗時怎麼處理可以設定（警告、不出聲、或交給錯誤處理）。
- Bevy 不鼓勵用指定的編號生成：`insert_or_spawn` 一族已在 2025 年刪除，官方說明稱它是容易誤用的寫法；`spawn_at` 還在，文件標了風險，往活著的編號生成是回報錯誤，不是斷言。
- **網路複製**（bevy_replicon、lightyear）兩端的實體用對照表對應，不指定編號；斷線時整張表清掉，重新加入拿到新的實體；跨重連的身分另外用一個持久的編號。
- **GYO 已定而會擋住照搬的**：編號就是網路上的編號、也是摘要的鍵，不另設對照表；自動配發的編號不重用，所以當初判定世代沒有工作可做；用指定的編號生成是特意留的。World 的 Replacement Criteria 明寫：需要 World 拒絕過期的鍵、或需要對照表時，鍵的形狀要重新設計。
- 掃描提的一個沒有人試做過的變體：指令記下時綁定「目標當時的出生 stamp」，套用時要求相同。等於不改編號的世代。

### 2.2 實體試做跑出來的

- **舊的 5 號不在**：規則讓外層那筆刪除作廢，新 5 號留下，和不巢狀時相同。
- **舊的 5 號還在**：光靠 stamp 解不了，裡面仍然要去看外層還等著的那筆刪除。兩個變體都做了：
  - 回報錯誤：舊的留著，什麼都不套用。
  - 當場先刪舊的、再生成新的：最後的結果、hook 的次數與先後都和不巢狀時相同；不同的只有 hook 觸發的時機（在裡面那張的同步點）。
- **「出生的 stamp」要用「記下生成的那一步」**，不能用「套用生成的同步點」：後者會改變不巢狀時既有的結果，上一輪的一個案例因此失敗。
- 比較要寫成「出生晚於紀錄才作廢」；兩者相等的情形會發生，必須算有效（否則守衛 J-32、J-7 會失敗——掃描從程式推的）。
- 既有的正式測試在規則打開時全過（93/93），包括 J-32 的固定值。
- 成本：每筆紀錄多 8 個位元組，每個實體多 8 個位元組；時間量不出差異。
- **規則一開，管的是所有刪除，不巢狀時也會改變結果**：hook 記的刪除留在佇列裡跨到下一次執行，中間那個編號被別的 schedule 或外面的程式建出來——現在的結果是死，規則下是活。（hook 那一批做完之後，hook 的紀錄在每次跑完時清空，這種跨執行的情形就不存在了；這一句是統合的推論。）
- **它不管移除**：外層記了「拿掉 5 號的 Tag」（5 號不在），裡面生成帶 Tag 的 5 號，回到外層 Tag 被拿掉。不巢狀時 Tag 留著。要一致得對移除加同樣的規則。插入不需要：不巢狀時插入本來就落到新的實體上。
- **和守衛 Z5 互相牽動**：作廢的刪除如果仍然做 Z5 的檢查，會對一筆根本不會生效的刪除報錯；跳過的話，巢狀時成功、不巢狀時報 Z5。兩種都和不巢狀不完全一致。
- **出生的 stamp 是新的 World 狀態，而且會影響結果**：它不在摘要裡（摘要相同的兩個 World 之後可能走出不同結果）；之後的快照與還原要帶上它。

### 2.3 資料試做跑出來的

- 先後的記號用「呼叫的序號」而不是 stamp（同一個同步點的 hook 共用一個 stamp，分不出先後）。
- 兩個目標都做出來了，都有硬傷：
  - **「結果和同一個同步點一樣」**：要四條規則加例外，而且自相矛盾——排在驅動的 System 後面的外層 System 讀到裡面加上的元件、決定拿掉，結果拿不掉。
  - **「照記下的先後，晚記的勝」**：一句話，但變成兩套規則（同一個同步點看階段，跨層看先後）；要只留一套就得改掉 DI-KS 9「結果不依記錄順序」。
- **結果開始隨這一輪跑幾步而變**：現在那幾種情形的結果不管跑 0 步或 3 步都一樣；照先後之後，跑 0 步和跑 1 步以上不同。
- 漏斗修不好（要修得讓漏斗覆寫已經存在的值，和 #229 的原則衝突）。
- 成本：外層一萬筆變更時每輪多 40～80%，沒有任何衝突時也一樣。
- 可以單獨拿出來的一項：「往外層已經記了生成、但還沒生效的實體插入」現在是丟掉並計數；把這筆轉回外層、等實體生效後套用，做得出來，結果正確。

### 2.4 對決定性的影響（影響掃描，從程式推的）

- 規則比的兩個 stamp 屬於同一個 World，所以 Match 與 Client 的 stamp 值不同不會讓 (c) 區的結果分歧——前提是出生的 stamp 一律用本 World 的，還原時不照抄別端的。
- 但它直接碰到 world 的 Design Invariant 3「stamp 不進 (c)」：刪除有沒有效改由 stamp 的比較決定之後，(c) 的結果就依賴 stamp。這是要使用者同意的變更。
- 同一個同步點裡，舊的被刪、新的出生拿到同一個 stamp；這時 hook 記的指令分不出針對哪一個。這是現在就有的行為，規則沒有讓它變糟，也沒有修好。

### 2.5 對應到資料庫的做法（影響掃描）

這裡不完全是髒讀：裡面那張看不到外層還沒套用的東西，那是隔離。出事的是兩邊各自延後寫、套用的順序和下指令的順序相反（寫寫衝突），而且刪除用的是一個會被重用的鍵。

| 資料庫的做法 | 對應到這裡 |
|---|---|
| 多版本：每筆資料記是誰建立的，刪除只作用在自己看得到的版本 | 用 stamp 分先後；世代；綁定記下當時的出生 stamp |
| 提交時檢查，不符就失敗 | 撞到時回報錯誤 |
| 先上鎖 | 啟動時就不准那樣排 |
| 內部用永不重用的鍵，外部的鍵另存對照 | 對照表 |

## 3. 選項（給使用者選的形狀；待對抗檢查）

問題限定在「外層還等著一筆刪除（或移除），裡面用同一個編號生成」。它要同時滿足：有人用指定的編號重用一個編號；刪除記在外層、而且那一輪固定步有跑；外層那筆在裡面生成時還沒套用。照說明頁建議的排法（驅動的 System 自己佔一個 stage）外層的佇列是空的，只剩「外層的 hook 記的」這一條路。

| | 回報錯誤 | 用 stamp 分先後（實體） | 綁定記下當時的出生 stamp |
|---|---|---|---|
| 做法 | 裡面那張要生成時，看外層還等著的刪除；有就回 Err、World 中斷。兩種情形（舊的在、不在）都報 | 每筆刪除帶記它那一步的 stamp，每個實體記出生的 stamp；出生晚於紀錄的刪除作廢。舊的還在時，當場先刪舊的、再生成新的。移除照同一條規則 | 每筆指令記下時綁定目標當時的出生 stamp（不在就記「無」），套用時要求相同 |
| 結果和不巢狀時 | 不同：不巢狀合法的「同一個編號重新加入」，巢狀時是錯誤 | 相同（刪除、試做驗過；移除要另外補，沒試做） | 推論上相同，而且涵蓋 hook 同一個 stamp 的盲點 |
| 同樣的輸入每次結果相同 | 是 | 是 | 是（推論） |
| 試做過嗎 | 上一輪兩個試做都做過 | 做過（移除那一半沒有） | 沒有 |
| 新增的狀態 | 無 | 每個實體 8 個位元組、每筆紀錄 8 個位元組 | 同左，每筆指令都要帶 |
| 要改的既有條文 | 無（新增一條錯誤） | 規格 F.2 第 2 步（刪除）、第 3 步（移除）；world 的 DI 3（stamp 不進 (c)）；Z5 對作廢的刪除做不做要定；快照之後要帶出生的 stamp | 同左，範圍更大（每一種指令） |
| 作者要多知道什麼 | 巢狀時不能在外層刪、裡面用同一個編號生成；撞到會報錯 | 刪除與移除針對的是「記它的時候那個實體」 | 所有指令針對的都是「記它的時候那個實體」 |
| 系譜 | 資料庫的提交時檢查；Bevy 往活著的編號生成也是回報錯誤 | 新導出的（使用者提的方向）；想法近似多版本 | Bevy 的世代，改成不動編號 |
| 需要它的 Feature | 巢狀執行不能讓程式終止或靜默刪錯 | 巢狀時用同一個編號重新加入。PvP 的正式環境由 Gateway 配發不重用的編號，同一個編號重新加入是測試情境；單機讀檔回到同一個 World 是否會這樣用，還沒有設計 | 同左 |

資料那一半（移除對插入、插入對插入等也照先後）不列成選項：兩種做法各有硬傷，而且會讓結果開始隨那一輪跑幾步而變，正好違反使用者的判準。它們維持「每次結果相同、事前講明」（已定寫進說明頁的那條規則）。

「把往外層還沒生效的實體的插入轉回外層」可以單獨做，和上面三個選項互不相干。照建議的排法不會碰到；不做的話維持「丟掉並計數」並在說明頁講明。

## 4. 架構師暫定的看法（待對抗檢查、待使用者判）

1. 資料那一半不做。
2. 實體這一半，三個選項都說得通；差別是「現在付多少、換到什麼」：
   - 回報錯誤最小，但它讓一個不巢狀時合法的寫法在巢狀時變成錯誤，而且照使用者的通用考量，先報錯、之後再改，上面蓋了東西就不會有人回頭改。
   - 用 stamp 分先後做得出來、結果和不巢狀一致、成本小；代價是動到一條 Design Invariant，並且要再定三件事（移除照不照、Z5 對作廢的刪除做不做、出生的 stamp 進不進摘要與快照）。
   - 綁定出生 stamp 最完整，但沒有試做過，範圍也最大。
3. 架構師傾向「用 stamp 分先後」，移除照同一條規則，作廢的刪除不做 Z5 的檢查（它不會刪掉任何東西，Z5 要守的性質沒有被破壞）。這個傾向的把握不高：需要它的 Feature 目前只有測試情境。
4. 不論選哪一個，「舊的還在時裡面生成會讓程式終止」都要消掉。

## 5. 範圍的限界

- 兩個試做都沒有突變、沒有換模型檢查；成本是粗估。
- 「綁定記下當時的出生 stamp」沒有試做。移除照同一條規則沒有試做。
- 對決定性的影響、J-32／J-7 需要「相等算有效」、hook 清空之後跨執行的情形消失，都是從程式或文件推的。
- 回滾、快照、讀檔在 gyo2 上還沒有設計；出生的 stamp 和它們的關係只能列成待定。
- 平行執行器沒有考慮。
