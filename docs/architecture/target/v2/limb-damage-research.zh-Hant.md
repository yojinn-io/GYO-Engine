## 1. 部位清單要不要資料化

**前提**：這是**作者（遊戲）能處理的**。部位是遊戲的列舉或資料，交換時是遊戲自己的 component 和 Codec；Engine 的網路只搬 bytes、管版本號（`Codec.hpp:104-112`），不認得部位。所以這一題**不產生 Engine 的批次**。

### 1.1 現況：`HitPart` 寫死時，加一個部位要動哪裡

| # | 位置 | 加 `Arm` 要做的 |
|---|---|---|
| 1 | `CombatRules.hpp:16` | enum 加值 |
| 2 | `CombatRules.hpp:25-27` | 加 `armPermille` |
| 3 | `CombatRules.cpp:13-24`、`39-47` | `ShotDamage`、`PartRank` 的 `switch` 各加一個 case |
| 4 | `CharacterRig.cpp:219-220` | 認得 `arm` |
| 5 | `PvpWorld.cpp:169-192` | `ShotCodec`、`HitCodec` 的版本號 1→2（bytes 沒變，意思變了：舊 Client 收到 4 會照 `Codec.hpp:57-61` 直接 cast） |
| 6 | 測試、突變 | `tests/object_fps_pvp/RulesTests.cpp:140-197`、`world/WorldTests.cpp:183,492`；`games/object_fps_pvp/docs/mutations.json:64,182,2878` 的 find 字串 |
| — | `PlayerAnimation.cpp:171`、`ClientWorld.cpp:972` | 不必改（`Arm` 走「其他」） |

**代價本身不大**（約 6 處）。問題在「部位數與規則由作者定」：

- 路線 (A) 下，**同一份角色資料要在不同模式下有不同的部位切法**：核心 PvP 是頭、軀幹、腿（手臂不判）；別的模式可能是 CS 型（加手臂、倍率和胸一樣），也可能把軀幹、手腳再拆細。部位數由模式定，enum 定不了。
- 每換一種切法，上表 1～6 就要再走一遍；而且 enum 會同時裝著「群組值」（`Body`、`Leg`）和「細的值」，意思靠程式約定。
- **被打的不只是人形**：最終產品有怪物。四足、有尾巴、有弱點的怪物，部位清單和人不同；寫死的人形 enum 每加一種怪物就要改程式。
- **部位不只來自射線**：side chat 的說明裡，近戰由攻擊資料指定部位、爆炸與墜落按規則分攤。這些資料要能用**名字**指到部位，enum 的整數值不適合寫在資料裡。

### 1.2 別家怎麼做

| 誰 | 做法 | 查證 |
|---|---|---|
| **lightyear**（avian 整合） | 框架不定義部位。回溯的單位是「一個 collider entity」：每個要回溯的 collider 有自己的 `LagCompensationHistory`，查詢回傳被打中的 entity（`crates/integration/avian/src/lag_compensation/history.rs:69-72`、`query.rs:212-243`）。要分部位，就是每個部位一個 collider entity，部位是掛在那個 entity 上的 component（作者的資料） | 源碼 |
| **avian**（Bevy 生態的物理） | 子 collider 用 `ColliderOf` 關聯到同一個 rigid body（`avian/src/collision/collider/collider_hierarchy/mod.rs:41-53`）。一個角色多個子 collider，部位資訊放在子 entity 上 | 源碼 |
| **Unity Netcode for Entities** | 回溯整個 `CollisionWorld`（`Runtime/Physics/PhysicsWorldHistory.cs:41-57,118`）；官方範例打到的是 `Entity`，沒有部位的概念（`Tests/Editor/DocCodeSamples/server-rewind.cs`）。部位要作者自己從 collider entity 推 | 源碼、官方文件 |
| **bevy_replicon**、**Bevy** | 沒有 hitbox 或部位的機制；replicon 的 README 只指向第三方的 `bevy_rewind`（`bevy_replicon/README.md:58-60`） | 源碼 |
| **Source 引擎**（CS、TF2、Garry's Mod） | **固定的部位列舉**（hitgroup：generic 0、head 1、chest 2、stomach 3、左右手 4/5、左右腳 6/7、gear 10）；**模型資料**把每個 hitbox 指到一個 hitgroup；**遊戲規則**決定每個 hitgroup 的倍率（Garry's Mod 的 `ScalePlayerDamage` hook）。列舉是人形的；非人形的 NPC 也只能借用這幾個值 | 官方文件（https://developer.valvesoftware.com/wiki/Team_Fortress_2/Scripting/Script_Functions/Constants）、△ 社群 wiki（https://wiki.facepunch.com/gmod/Enums/HITGROUP）；SDK 原始檔本卡沒在本機查；「非人形借用」是推論 |

共同點：

1. **框架都不定義部位**；部位是作者的資料（三個網路框架、avian）。
2. 有部位的遊戲裡，Source 把「形狀屬於哪個部位」（模型資料）和「部位的倍率」（規則）分開；但部位清單本身是固定的人形列舉。

### 1.3 選項

把「部位」拆成兩件事來看：

- **形狀標籤**：這個形狀是什麼（頭、胸、左上臂…；怪物可以是尾巴、弱點）。屬於**角色**（`hitbox.json`），和模式無關。
- **規則部位**：這一發算哪個部位、乘多少、扣哪一格血、會不會死、擋不擋後面。屬於**模式**。

| | 做法 | 好處 | 代價 |
|---|---|---|---|
| (1a) | **維持寫死的 enum，加 `Arm`**；模式只決定「手臂形狀判不判」 | 改動最少（1.1 節的 6 處）；Client 照舊 | 部位數、倍率、血量都寫在程式裡；換切法、加怪物都要改程式；**退回 CS 方式也要改程式**（CS 的手臂倍率、「不擋」都不是資料） |
| (1b) | **固定的人形標籤 enum（Source 的 hitgroup 形狀）＋模式資料的規則表** | 標籤的意思兩端都編進程式；人形角色的部位切法、倍率、血量都由資料定；CS 方式是一份規則表 | 非人形怪物的部位要改程式（或借用人形的值）；近戰、爆炸的資料要用 enum 的名字指部位，名字清單由程式定 |
| (1c) | **全部資料化**：每個角色的 `hitbox.json` 宣告自己的形狀標籤（字串）；模式的規則表用標籤名對到規則部位；交換內容傳「規則部位在模式表裡的索引」 | 部位數、名字、規則全由作者定；人和怪物同一套；近戰、爆炸的資料直接寫部位名；核心 PvP 可以保留現在的 `head`／`body`／`leg` 標籤，不必改 `hitbox.json` | 索引的意思由資料決定：**Client 和 Match 的模式表必須相同**（要放進內容比對，見 1.4）；解碼不檢查範圍（`Codec.hpp:57-61`），Client 要把超出表的索引當「其他」；Client 的受擊片段、命中標記改成看表裡的表現標籤 |

各選項的影響點：

| 影響點 | (1a) | (1b) | (1c) |
|---|---|---|---|
| `ShotRecord`／`HitRecord` 的 Codec | bytes 不變（u8），版本號升 | bytes 不變（u8），版本號升一次 | bytes 不變（u8），版本號升一次；意思隨模式表變 |
| `Replicate` 登記（`PvpWorld.cpp:1124-1128`） | 不變 | 部位血量另加 `LimbHealth`（第 3 題）。**登記要固定、掛不掛由模式定**：protocol hash 由登記的名字與順序組成（`Replication.hpp:13,160`），依模式登記會讓不同模式的 protocol hash 不同 | 同 (1b) |
| 權威 hash（`PvpWorld.cpp:81,89`） | 不變（仍 hash u8） | 不變；沒掛 `LimbHealth` 的實體不 hash 它 | 同 (1b)；兩端的表不同時 hash 照樣一致、意思卻不同，所以要靠內容比對擋 |
| Client 受擊片段（`PlayerAnimation.cpp:171`）、命中標記（`ClientWorld.cpp:972`） | 不必改 | 改成看規則表的表現標籤，或維持「是不是頭」 | 必須改成看表的表現標籤 |
| 內容比對 | 不必 | Client 顯示部位血量時要知道血池清單 → 模式要比 | **必須**把模式表放進比對 |

(1b) 和 (1c) 在內容比對上的差距，比第一版估的小：**只要有部位血量的 UI，兩者都要比模式**（1.4 第 1 點）。(1c) 多出的只有「範圍外的索引當其他」與 Client 改看表現標籤。

### 1.4 和「模式資料開關」的銜接

批次表〈後續小事〉的「模式資料開關」（`rebuild-batch-plan.zh-Hant.md:88`）還沒設計。這一題給它的需求：

1. **模式要有身分，兩端要一致**：模式 id＋規則 digest 放進 `MatchInfo`（和 `wallsDigest` 同一種做法，`Components.hpp:148-155`），不一致就當內容不符（`PvpWorld.cpp:810-820`）。角色的 `hitbox.json` 也要進 digest（(1c) 下標籤名由它宣告）。
2. **模式帶一張傷害規則表**：每個規則部位的欄位見第 3.3 節，加上第 4 題的「擋不擋」；模式層級另有「有沒有總血量」。現在寫死在 `CombatRules` 裡的數字（`CombatRules.hpp:25-27`）就是核心模式的表。
3. **模式決定掛哪些 component**：`LimbHealth` 只在有部位血量的模式掛；登記固定（protocol hash，見上表）。
4. **核心 PvP 模式的規則表＝現在的數字**，S5 的結果要一致。

順序照批次表：模式資料開關先，肢體傷害（G6）後。

### 1.5 推薦：(1c)

1. 「部位數與規則由作者定」是前提；(1a) 把部位數釘在程式裡，(1b) 把部位**清單**釘成人形。最終產品有怪物、近戰與爆炸要用名字指部位，兩者都會在第一種怪物時碰到限制。
2. 三個網路框架、avian 都把部位留給作者的資料（1.2），(1c) 和它們一致；Source 的固定列舉是單一類型遊戲（人形對人形）的選擇，不是 GYO 的前提。
3. (1c) 比 (1b) 多的代價很小（1.3 末段）：內容比對兩者都要；多的是範圍檢查與 Client 看表現標籤。
4. 核心 PvP 的結果留得住：核心模式的表把標籤對到 `head`／`body`／`leg` 三個規則部位；手臂形狀加進角色資料後，核心模式的表不列它們＝不判。標籤可以先維持現在的 `head`／`body`／`leg`，也可以照形狀切細（第 3.8 節第 4 點的建議），由核心模式的表合回三個。

（第一版推薦 (1b)，理由是「人形的部位很少變」。那是用「塔科夫要 7 個」在想；換成「作者定、有怪物、部位也來自非射線的傷害」之後，這條理由不成立。）

## 2. 延遲補償（PV3）的時機

**前提**：這是**作者（遊戲）能處理的**。Engine 已經給了機制：Client 每格輸入帶畫面的時間 `ViewTime`（`engine/modules/net/include/engine/net/Replication.hpp:396-404`），Match 消耗輸入時把它寫進 `PeerInput<T>::lastView`（`Replication.hpp:559`）。存什麼歷史、怎麼插值、回溯多久，是遊戲的規則（port 宣告 PV3：「之後做回溯時不用改 wire」，`games/object_fps_pvp/docs/port-declaration.zh-Hant.md:53`）。所以這一題**不產生 Engine 的批次**。

### 2.1 現況

- Match 用**當 tick** 的位置與姿勢判（`PvpWorld.cpp:495-521`）；`ViewTime` 有送，Match 沒讀（`port-declaration.zh-Hant.md:134`）。
- Client 看到的對手落後。落後量（推論，沒量）：
  - 對手的畫面時間＝Match 現在的 tick 估計 − 半個 RTT − 內插延遲（`ClientWorld.cpp` 的 `InterpolateRemotes` 註解，約 `1582-1588` 行）。
  - 內插延遲＝max(送出間隔 1 tick × 1.2, 5 ms)＋jitter × 4＋1 tick（`games/object_fps_pvp/include/object_fps_pvp/present/Interpolation.hpp:26-33`）；64 Hz、jitter 0 時約 2.2 tick ≈ 34 ms。
  - 自己的輸入要提前送到 Match（約半個 RTT＋輸入的餘裕）。
  - 合起來，判定時的對手和畫面上的對手差 ≈ **RTT＋內插延遲＋輸入餘裕**。LAN（RTT 幾 ms）約 50 ms；RTT 60 ms 約 110 ms（輸入餘裕當 1 tick，未確認）。
- 對手橫移的速度上限是 3 m/s（各 arena 的 `movement_speed`，例 `assets/object_fps_pvp/maps/pvp_arena.json:7`），所以畫面和判定差 **LAN 約 0.15 m、RTT 60 ms 約 0.33 m**（推論）。
- 對照形狀的大小：頭的球半徑 0.184、軀幹膠囊 0.18、小腿 0.105（`hitbox.json`）；手臂膠囊的半徑還沒量（G5），以人體比例推約 0.05～0.08（推論）。**在 LAN 上，橫移中的手臂（直徑約 0.1～0.16 m）就已經小於落差**：沒有提前量就打不到；頭（直徑 0.37 m）還容得下。
- 站著不動的目標沒有這個落差，只剩姿勢的跨平台差（PV6）；但 PV6 在 LAN 上比 0.15 m 小得多（推論：PV6 是浮點差，不是幾個 tick 的位移）。**所以「看到打中卻沒算」在手臂上的主因是沒有回溯，不是 PV6**。

## 3. 傷害模型

**前提**：這是**作者（遊戲）能處理的**。部位血量、倍率、歸零後果全是遊戲規則；同步用的是遊戲自己的 component＋`Replicate`（HANDOFF `v8-arch-gyo2-limb-damage`）。**不產生 Engine 的批次**。這一題要回答的不是「選哪一家的規則」，而是**程式要提供哪些欄位，才能讓作者用資料寫出各家的規則**（含退回 CS）。

### 3.1 現況

- 一個總血量 `PlayerCombat::hp`；傷害＝`shotDamage × 部位倍率`、封頂、不超過剩下的血；歸零就死（`CombatRules.cpp:13-24`、`PvpWorld.cpp:530-541`）。
- 墜落傷害直接扣總血量（`Arena.hpp:21-25`）。
- 沒有部位血量、沒有傷害轉移、沒有斷肢的狀態效果。

### 3.2 別家怎麼做（都是二手資料，各自是一個參考點）

| 遊戲 | 血量 | 部位的作用 | 歸零之後 | 查證 |
|---|---|---|---|---|
| CS:GO／CS2 | 只有總血量 | 只影響倍率；手臂和胸同為 1×；2016 起打到手臂、射線繼續進頭算頭 | 無部位後果 | △ 社群 wiki、報導（#363 第 10.3 節）；CS2 是否保留 2016 的規則，未確認 |
| Valorant | 只有總血量 | 倍率分頭、身、腿；早期數值表把手臂和腿列同一級 | 無 | △ 報導（#363 第 10.3 節，1.03 版）；現行版本未確認 |
| Overwatch | 只有總血量 | 只有頭有暴擊倍率 | 無 | 未確認（憑記憶，本卡沒查來源） |
| DayZ | — | 打不同部位的傷害不同；護甲以部位為單位，不是自己的 hitbox | — | △ 社群 wiki（https://dayz.gamepedia.com/Weapons,_damage_and_armor ） |
| 塔科夫 | 部位各有血量（常見說法：7 個部位，總和 440） | 頭、胸致命 | 非致命部位歸零後，再打到那裡的傷害乘係數、分給其他部位（社群 wiki 寫腹 1.05、手 0.49、腳 0.7）；斷手斷腳有狀態效果 | △ 社群 wiki（https://wikiwiki.jp/eft/%E4%BD%93%E5%8A%9B ，沒標資料版本）、△ 報導（https://www.gamepressure.com/escape-from-tarkov/health-and-injuries/z1cf2f ）；各部位的血量數字未確認 |

這些做法的差別可以歸成幾個獨立的自由度：有沒有總血量、部位有沒有自己的血量、哪些部位致命、歸零後傷害往哪去、有沒有狀態效果、手臂擋不擋。下一節把它們寫成欄位。

### 3.3 欄位模型（驗證 side chat 的說法）

side chat 的說法：「CS 方式是部位血量的特例；每個部位三個欄位：倍率、有沒有自己的血量、是不是致命部位」。

**驗證結果：方向成立，但三個欄位不夠**，要再加三個：

| 層級 | 欄位 | 用途 | side chat 有沒有 |
|---|---|---|---|
| 規則部位 | 倍率 | 傷害乘多少 | 有 |
| 規則部位 | 自己的血量（最大值；無＝沒有） | 部位血池 | 有 |
| 規則部位 | 致命 | 只對有自己血量的部位有意義：歸零即死 | 有 |
| 規則部位 | 歸零後的轉移係數 | 非致命、有自己血量的部位歸零後，再打到它的傷害怎麼分出去 | **沒有**：少了它寫不出塔科夫型 |
| 規則部位 | 擋不擋後面的部位 | 第 4 題（D10） | side chat 已指出要是欄位 |
| 規則部位 | 表現標籤 | Client 的受擊片段、命中標記（第 1 題） | — |
| 模式 | 總血量（有／無；最大值），以及「有自己血量的部位被打時，要不要也扣總血量」 | **沒有**：少了它分不出「只有部位血量」和「總血量＋部位血量」 | **沒有** |

用這些欄位寫各家（例子，不是建議值）：

| 設定 | 總血量 | 部位的自己血量 | 致命 | 轉移 | 手臂擋不擋 |
|---|---|---|---|---|---|
| 核心 PvP（現在） | 有 | 無 | — | — | （不判手臂） |
| CS 型 | 有 | 無 | — | — | 不擋 |
| Valorant／Overwatch 型 | 有 | 無 | — | — | 未確認 |
| 混合（總＋部位） | 有，部位被打也扣 | 手腳等有 | 可選 | 可選 | 作者選 |
| 塔科夫型 | 無 | 每個部位有 | 頭、胸 | 有 | 擋（△） |

所以 **CS 方式確實是特例**（「每個部位都沒有自己的血量、只有倍率、總血量有」），退回 CS 只是換一份表。side chat 另一個說法「不用部位血量的模式不掛 `LimbHealth`，不同步也不算 hash」：**掛與不掛成立**（沒掛的實體沒有那個 component 可以 hash 或複製）；但**登記要固定**，不能依模式登記，否則 protocol hash 會隨模式不同（`Replication.hpp:13,160`）。

### 3.4 選項：程式要提供到哪裡

| | 做法 | 好處 | 代價 |
|---|---|---|---|
| (H1) | 維持一個總血量，只把倍率變成資料 | 最小 | 寫不出部位血量；不符合 (3) |
| (H2) | 寫死某一家的形狀（例如塔科夫型：只有部位血量＋致命部位） | 一種規則做得最直接 | 退回 CS 要改程式；違反「規則由作者選」 |
| (H3) | **欄位模型**（3.3）：程式只實作欄位的語意，各家的規則都是資料 | 核心 PvP、CS 型、混合、塔科夫型都是同一套程式；退回 CS 只換表 | 程式多一層「部位→血池→死亡條件」；核心模式要確認和現在逐位元一樣（S5、權威 hash） |

### 3.5 歸零的後果

| | 後果 | 欄位 | 代價與注意 |
|---|---|---|---|
| (Z1) | 只記錄（UI 顯示歸零） | 自己的血量 | 最小 |
| (Z2) | 傷害轉移 | 轉移係數 | 只動 Match 的傷害計算；同步的只有結果（`LimbHealth`）。分法（平均、按最大血量比例、只分給還沒歸零的部位）要寫成資料；塔科夫型的分法連社群 wiki 也只有推測 |
| (Z3) | 致命部位歸零即死 | 致命 | 只動 Match |
| (Z4) | 狀態效果：手（換彈、瞄準變慢）、腳（不能跑、變慢） | 另一張「部位狀態→效果」表 | **會進預測**：自己的移動和換彈是 Client 預測、會回滾的 sim；`LimbHealth` 要登記成 authority component＋`Replicate`（和 `PlayerCombat` 一樣，`PvpWorld.cpp:1092-1095,1124-1128`），`MovePlayers`、換彈的時間要讀它，兩端要逐位元一致。代價比 (Z1)～(Z3) 大一級 |

### 3.6 傷害的來源：統一成「(部位, 數值)」

side chat 的說明：射擊類怪物走 hitbox；近戰由攻擊資料指定部位，或按面積權重隨機；爆炸、墜落照規則分攤；可以統一成「(部位, 數值)」交給同一個扣血規則。

| 來源 | 部位從哪來 | 現況 | 注意 |
|---|---|---|---|
| 射擊 | hitbox 射線（`PvpWorld.cpp:495-521`） | 有 | — |
| 近戰 | 攻擊資料寫部位名，或按形狀面積的權重抽 | 沒有 | 抽籤只在 Match 做（傷害只在 Match 算，`ShotRecord` 的註解寫「written only at the Match」，`Components.hpp:69`）；仍建議用決定性的亂數（tick＋實體當種子），重播才可重現 |

### 3.8 推薦

1. **(H3) 欄位模型**，欄位照 3.3（side chat 的三個＋轉移係數、模式的總血量設定、擋不擋）。核心 PvP 的表＝現在的數字；CS 型是另一份表。
2. **後果的程式先做 (Z1)～(Z3)**（都只動 Match、成本小）；(Z4) 另成一批（進預測與回滾）。

## 4. D10：手臂擋不擋後面的部位

**前提**：這是**作者（遊戲）能處理的**。同一目標內取哪個形狀是遊戲的判定規則（`PvpWorld.cpp:513-519`）。**不產生 Engine 的批次**。

### 4.1 現況

- 對每個目標，取射線上**最近**的形狀；同距看 `PartRank`（`PvpWorld.cpp:513-519`、`CombatRules.cpp:39-47`）。現在沒有手臂，所以舉槍時手臂擋在胸前的情形，算的是胸。
- #363 第 7 節的 D10 推薦 (a) 擋，理由是手臂有血量，不擋會讓手臂很少扣血。
- side chat 指出：CS 方式（2016 起）是不擋，所以「擋不擋」要是模式資料的欄位，不寫死在判定程式裡。

### 4.2 和設定的關係

| 設定 | 擋 | 不擋 |
|---|---|---|
| CS 型（只有總血量） | 只換倍率：手臂倍率比頭低時，擋＝對被打的人有利 | CS 2016 的做法（△）：射手看到打頭就算頭 |
| 有部位血量的設定 | 手臂替後面的部位吸收傷害；塔科夫型下，替致命的胸擋子彈是部位血量的主要作用之一（△） | 手臂只在「只中手臂」時扣血，部位血量很少動（#363 的理由） |

兩種做法**在不同設定下各自合理**；所以它不是一個全域的決定，是規則表的一個欄位。

### 4.3 別家怎麼做

| 遊戲 | 做法 | 查證 |
|---|---|---|
| CS:GO（2016 起） | 不擋：射線打到手臂後繼續進頭，算頭 | △（#363 第 10.3 節） |
| 塔科夫 | 手臂會擋；手臂護甲能防止子彈穿過肩膀進胸；玩家說法：子彈可以穿過手臂再進胸、穿過時損失傷害與穿透 | △ 攻略站（3.7 的連結）；穿透的細節只有玩家討論，**未確認** |

### 4.4 選項

| | 做法 | 好處 | 代價 |
|---|---|---|---|
| (a) | **寫死擋**：照現行規則取最近 | 判定規則不用改 | CS 型寫不出來 |
| (b) | **寫死不擋**：同目標的其他形狀有中就算那個；只中手臂才算手臂 | CS 型 | 有部位血量的設定裡手臂很少扣血 |
| (c) | **穿透**：先扣手臂，再照穿透量進後面的部位 | 最接近塔科夫（△） | 要武器有穿透數值，現在沒有；判定要沿射線收集多個形狀 |
| (d) | **規則部位的欄位**：每個規則部位標「擋／不擋」；判定取最近的「擋」形狀，沒有中任何「擋」形狀時才取最近的「不擋」形狀 | (a)、(b) 都是資料；核心 PvP 不受影響（它不判手臂）；之後加 (c) 時欄位可以多一個值 | 判定迴圈（`PvpWorld.cpp:513-519`）的取法要改成上面的兩級；成本是同一次走過形狀時多一個比較，可以忽略 |

### 4.5 推薦：(d)

1. 擋與不擋在不同設定下各自合理（4.2），寫死哪一個都會讓另一種設定寫不出來；side chat 的方向成立。
2. (d) 的實作只是把「取最近」改成兩級，不必收集多個形狀；(c) 要等武器有穿透數值再議，到時欄位加一個值即可。
3. 各設定的預設值是表的事，不在本卡定。

### 4.6 決策點

- **L5**（＝D10）：用 (a)、(b)、(c)、(d) 哪一個？（推薦 (d)）

## 5. Match 的成本

**前提**：這是**作者（遊戲）能處理的**。成本來自遊戲自己的判定迴圈；用到的 Engine 部分（model 的取樣、E2 的 two-bone IK、物理的射線對膠囊）都是已定的純函式。量測若發現 model 的取樣本身是瓶頸，才會回到 Engine（那時另開）。

### 5.1 現在一發的工作量（從程式推，沒量）

對**每個射手、每個活著的其他目標**（`PvpWorld.cpp:495-521`）：

| 步驟 | 工作 | 位置 |
|---|---|---|
| 1 | `AnimationInputOf` | `PvpWorld.cpp:505-506` |
| 2 | `ComposeBody`：站姿時 `SampleClip` 6～7 次（Idle、Walk、Jog、AimNeutral、Aim 上或下、動作片段 2 次）＋2～3 次 `Blend`＋上半身逐骨合成；每次都走過**整副骨架的所有 node**；函式裡新配置 4 個 vector | `CharacterRig.cpp:244-316` |
| 3 | `ModelSpace`：整副骨架 | `CharacterRig.cpp:318-321` |
| 4 | `PlaceHitShapes`：7 個形狀 | `CharacterRig.cpp:329-347` |
| 5 | 射線對膠囊 7 次 | `PvpWorld.cpp:514-519` |

注意兩件事：

- **沒有 broadphase**：每個目標都先擺好整副姿勢再測，不管射線離他多遠。
- **同一 tick 多個射手時，每個射手都重算每個目標的姿勢**（沒有每 tick 的快取）。

4 人、射速上限 6 發／秒（`cooldownSeconds = 1/6`，`CombatRules.hpp:30`）時，最壞每秒 4×6×3＝72 次姿勢；平常遠少於此。

### 5.2 加手臂之後（推論）

| 項目 | 增加 | 相對大小 |
|---|---|---|
| IK（D5 (b)，G3） | 每次姿勢多一次 two-bone IK（左手；右手握槍是片段本身）＋手臂鏈的模型空間重算 | 小：幾次向量運算與一段鏈；和 6～7 次整副取樣相比應可忽略（推論） |
| 形狀 7→11 | `PlaceHitShapes` 多 4 個、射線測試多 4 次（＋57%） | 小：射線對膠囊是常數時間的幾何 |
| 再拆部位 | (1b) 下解剖標籤 11 個＝形狀 11 個；規則部位怎麼合併不加形狀 | 0 |

結論（推論）：**加手臂本身不改變 Match 的成本級別**；成本由「每次判定要擺幾次整副姿勢」決定。

### 5.3 做 PV3 之後（推論）

| | 現在（當 tick） | PV3 (b)（存擺好的形狀） |
|---|---|---|
| 擺姿勢的次數 | 開槍時，射手數×目標數 | **每 tick 每個玩家 1 次**：64 Hz × N（4 人＝256 次／秒，比現在最壞的 72 次多） |
| 記憶體 | 0 | 11 形狀 × 7 float × 4 B ＝ 308 B／人／tick；回溯 250～500 ms（16～32 tick）≈ 5～10 KB／人 |
| 每發的查詢 | 7→11 個形狀 × 目標數 | 同左，加兩 tick 間的插值；配 broadphase 可只測射線附近的目標 |

撤離模式人數多、還有怪物時，(b) 的成本隨「有判定形狀的實體數 × tick 率」線性增加。怪物要不要用同一套形狀與回溯，是怪物線的事，這裡只點出。

### 5.4 可以先做的省法（別家做法，不是本卡的決定）

1. **broadphase**：lightyear 先打「歷史 AABB 的包絡」，中了才做精確測試（`history.rs:121-145`、`query.rs:181-212`）。gyo2 可以先用「身體的包圍膠囊」測，中了才擺姿勢。這在 PV3 之前也有效。
2. **每 tick 的姿勢快取**：同一 tick 多個射手共用目標的姿勢；PV3 (b) 本身就是這件事。

### 5.5 量測項（本卡不跑；都是小的 micro benchmark，不是重量測）

| # | 量什麼 | 在哪 | 給誰用 |
|---|---|---|---|
| M1 | `ComposeBody`＋`ModelSpace` 一次的時間（Release，Linux） | Match 的機器 | 5.1、5.3 的乘數 |
| M2 | two-bone IK 一次（含鏈的模型空間重算） | 同上 | G3 |
| M3 | 射線對 7／11 個膠囊 | 同上 | G6 |
| M4 | `JudgeShots` 一 tick 的最壞情形（4 人同 tick 開槍），手臂有／無 | 同上 | G6 的回歸 |
| M5 | PV3 (b) 每 tick 擺所有玩家：N＝4、8、16 | 同上 | L2 的排程、撤離模式的人數上限 |
| M6 | LAN 場次的實際落差（RTT、內插延遲、輸入餘裕） | LAN 場次 | 2.1 的推論、回溯上限（L2'） |
| M7 | 手臂膠囊的半徑與包覆（D9）、Client 與 Match 的手臂形狀差（PV6） | G5 | 倍率與半徑 |

M1～M5 都是 CPU 的短時間量測，不需要 GPU 或大記憶體；排在 G5 或 G6 裡一起做即可。

### 5.6 決策點

這一題沒有要使用者定的；量測項排進哪一批照批次表的順序由主會話排。broadphase 要不要和 G6 一起做，屬於實作細節，開 G6 時由那張卡判斷。
