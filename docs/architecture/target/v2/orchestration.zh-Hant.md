編排層在 Kernel 之上、各 Module 之下：它把登記單位（`Module`、`Plugin`）與產品自己的遊戲程式接進每個 World，排遊戲初始化與每幀的流程，替換 World，記自己的警告。Kernel 不認得它（統合 L16、`v8-arch-gyo2-two-layers-like-bevy`）。

## Design Invariants

守衛欄：行為的測試照常是守衛；綁實作方式的掃描守衛延後（`v8-arch-gyo2-guards-after-mechanism-stable`；宣告第 7.4 節），延後的那幾條寫「延後」，這段期間靠本頁與審查守。

<a id="o-1"></a>
**O-1 遊戲初始化。** 一個 `Product` 一份遊戲初始化清單（schedule 名），行程一次、在所有 World 的第一幀與任何 `RunSchedule` 之前跑完、跑在第一個 World（描述的第一個；使用者 `v8-arch-gyo2-game-init-list`）。`RunFrame`、`RunSchedule` 在它還沒跑時先跑它；明確呼叫 `RunGameInit` 只准一次。清單的順序照插入（`Append`、`InsertBefore`、`InsertAfter`；插入當下解析錨點，錨點不在是啟動錯誤 O-E5；同名可以出現兩次）。任何一張回錯誤：停下、回傳、記為已跑（Product 就此結束，O-11）；有 World 壞了時不跑、不記為已跑。〔草稿，D10〕`BuildNewFirst` 替換第一個 World、遊戲初始化在還沒交出去的新 World 上失敗時，不算跑過（新 World 丟掉、舊 World 照跑、回 E2）；下一個入口照本條在舊的第一個 World 上跑。直接呼叫 `WorldExecutor::Run` 是繞過編排層，不先跑遊戲初始化。（「遊戲初始化的 schedule 要屬於一個 domain」的過渡句隨 Kernel 的 D-E12 拿掉，`v8-arch-gyo2-time-events` G2。）守衛：`orchestration.O-1` 各案（J-58 改寫）；scenario 第一段。（取代 Kernel 的 DI-KS 22）

<a id="o-2"></a>
**O-2 登記單位與生命週期。** 〔第 5 批，`v8-arch-gyo2-world-gen`；使用者 2026-11-22 合併前核准〕每個 World 在任何登記單位的 `Build` 之前，編排層登記 `WorldGeneration`（骨架開關都一樣，owner `orchestration`；O-14）。產品層一次 `Configure`（登記單位依序，產品自己的最後）；每個 World：用到的登記單位依序 `Build`（Module 先、各自照登記檔的順序；產品自己的 `build` 最後、而且一定經過一次 `Register`）→ Kernel `BuildPlans` → 依序 `Finish`（讀到版本 1 與 Plan）→ 依序 `Check`。Kernel 有啟動錯誤的 World 不跑 `Finish`、`Check` 與清單檢查。出錯的登記單位不用、其餘照做，錯誤一起收齊；有任何錯誤就不建任何 World。替換 World 時對那個 World 重走 `Build`～`Check`（`Configure` 不重跑），登記單位以 World 名為鍵記的資料在 `Build` 時重設（不含 [O-15](#o-15) 共用處裡跨 World 的物件——它們比每個 World 活得久，例：照 World 名沿用的提交口；〔使用者 2026-11-22「O-2 照建議補」，`v8-arch-gyo2-o2-shared-note`〕）。動態插入只走 Kernel 的兩步，不重跑 `Finish`、`Check`、也不通知——它們屬於登記單位自己的生命週期，System 不能重置它（使用者 `v8-arch-gyo2-dynamic-insert-no-lifecycle-rerun`）。World 描述的選項包只轉交、不解讀。**Module 的 buffer**（`v8-arch-gyo2-authority-rollback`；使用者 2026-11-20 選 (a) 並要求共用要有機制）：每次建 World（啟動與每次替換）有一份新的、以型別為鍵的 `ModuleBuffer`。每種型別只由擁有它的登記單位建（`Create<T>`），別人用 `Find<T>`（找不到回 `nullptr`、不代建）；先後由登記檔的依賴與 O-E3 保證，產品自己的 `build` 在最後。登記單位與產品自己的 `build` 在 `Build` 經 `WorldSetup::Buffer()` 拿到可寫的 `ModuleBuffer&`；所有 `Build` 跑完時編排層凍結它（`Frozen()` 之後為 true），之後 `Finish`、`Check` 經 `WorldFinish::Buffer()`、`WorldCheck::Buffer()` 只拿到 `const ModuleBuffer&`（`Find<T>` 回 `const T*`）。`Build` 階段的寫入只追加、帶來源（作者或代為）；進 Kernel 的副作用在登記當下做、不取決於裁決；裁決是擁有者對紀錄的純函式，在凍結後經擁有者的讀取介面取得，結果和呼叫順序無關（例：回滾 Module 的 `Resolve`）。編排層不解讀 `ModuleBuffer` 裡的型別。照 CCR-5 在一條執行緒上，不加鎖。`ModuleBuffer` 和那一次建 World 的準備函式放在一起，活到準備函式跑完；要留到執行時的內容，由 Module 在準備函式裡凍結進 World 的 Resource（例：回滾 Module 的 `RollbackRegistry`）。錯誤的形式（都是 Programmer Error，斷言，不新增 O-E 碼）：兩個登記單位 `Create<T>` 同一型別；凍結後呼叫 `Create<T>` 或可寫的 `Find<T>`；Module 的 `Build` 或產品自己的 `build` 找不到依賴的登記（由呼叫 `Find<T>` 的一方斷言）。經 `Build` 時留下的 `T&` 在凍結後寫入，編排層看不到，由擁有者的介面拒絕。守衛：`orchestration.O-2`、`O-5`、`O-E1`～`O-E7` 各案；`orchestration.module-buffer`「the owner creates, a later unit and the product's build write; Finish, Check and prepare read」「Find of a type nobody created is nullptr, and makes nothing」「two units creating one type is a Programmer Error」「a Create or a writable Find after Build is a Programmer Error」「each build of the World has a buffer of its own」（`ModuleBufferTests.cpp`）與突變 `or-buffer-`；裁決和登記的先後無關、同一來源兩筆 options 不同是錯誤：`rollback.rollback_registrations`「the author's registration counts over one made on behalf, whatever the order」「two of the author's with different options are RB-E1; with the same, one」「two made on behalf with different options are RB-E1」；`Finish`／`Check` 只能讀由型別保證（沒有編譯期的反向測試）。（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）Product 一份的共用處、Product 層的選項、`Configure` 的回報、`OnDestroy` 與 `~Product` 的順序在 [O-15](#o-15)。

<a id="o-3"></a>
**O-3 runner。** 一個 `Product` 至多一個 runner（第二個是 O-E4），由登記單位或產品在 `Configure` 裝；沒有時用只跑一次的 runner（`RunFrame` 一次）。〔第 5 批，`v8-arch-gyo2-world-gen`；使用者 2026-11-22 合併前核准〕有人 `Hold()` 時只跑一次的 runner 照樣回 Success，那個 World 仍在生成中（O-14）。runner 擁有迴圈與執行緒的安排，只呼叫 `Product` 的執行入口（`RunGameInit`、`RunFrame`、`RunSchedule`、`ReplaceWorld`、`InsertSystems`）與 Module 給的函式，不排 System 的先後；〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕runner 在兩次入口之間讀寫 World、呼叫 Module 給的函式是交換點的「runner 直接讀寫」（O-12），只做屬於 runner 的事，Module 的資料走套用點或交換函式；〔`v8-arch-gyo2-kernel-diagnostics-exchange` 修訂 1〕交換函式負責、但「出」不會再被呼叫的那部分由 runner 取（有 World 壞掉、Product 結束之後，或替換那個 World、銷毀 Product 之前；O-12）。例：Kernel 的診斷紀錄誰取，規則只寫在 LG-1；Product 結束（O-11）之後，關掉程式或回主選單（另建一個 Product）由它決定。〔草稿，target/error-handling「Error levels」〕入口回的錯誤帶 `failure` 就是 E1（這個 Product 有 World 壞了，不能再跑）；不帶就是 E2（這次請求沒做成）。〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕`RunFrame` 回的 `ExchangeFailed` 是第一個「做了一部分」的 E2：失敗那個 World 之前的 World 已跑了這一輪（O-12）。接下來怎麼辦由 runner 決定。〔草稿，退出流程（使用者 2026-11-21「照這個流程改。④ 也要在這一批補一個標準的 main 範例或輔助函式」、「記日誌和處理異常不在同一層」）〕Engine 自己的程式這樣用：預設 runner 跑一幀，失敗時回 `RunnerExit` `Failure` 與原因（E1 是 `WorldFailure` 的完整文字），自己不寫。接下來記不記、結束還是回主選單另建 `Product`，由產品自己的 main 決定；Engine 不給標準 main（使用者 2026-11-21：`RunProduct`、`ExitCode` 刪掉）。產品的 main 怎麼接 runner 的結果，例子在頂層 `examples/orchestration/product_main.cpp`（例子程式，不屬於 Engine，也不是測試；使用者 2026-11-21「加，這tmd是你的職責」）。守衛：`orchestration.O-3` 各案；「不讀 Plan 的步驟、不呼叫 System」的掃描（`orchestration.guard`，`v8-arch-gyo2-time-events` 第 1 步立）。

<a id="o-4"></a>
**O-4 職責。** **編排層的職責是組裝與流程**（統合 L17）。職責清單：登記單位與生命週期（含產品自己的登記）；依賴的讀取與檢查；`Product`（World 群、runner、World 的準備與替換，含帶過去）；遊戲初始化與每幀的清單；生成世界的流程（O-14）；交換點、extract 的時機、執行緒的安排（第 5 條）；啟動錯誤的彙整〔草稿，D2：拿掉「與編排層自己的警告」——編排層不寫日誌（O-11），清單少一項〕。（「World 的準備與替換」「帶過去」算原有的項目，不算多一項：使用者 2026-11-18「照建議」。）**編排層給 schedule 的預設骨架**（名字與段落順序；作者可換或關）並經 Kernel 執行它；不認得時間，也不認得任何 Module 掛進去的是什麼（`v8-arch-gyo2-orchestration-gives-schedule-skeleton`；這是「每幀的清單」那一項的預設值，**不算職責清單多一項，使用者 2026-11-19 核准**，`v8-arch-gyo2-time-events-declaration-approved`）。做法：每個 World 在任何登記單位的 `Build` 之前，由編排層（owner `orchestration`）宣告每幀一張 `Main`（stage 依序 `First`、`PreUpdate`、`FixedMainLoop`、`Update`、`PostUpdate`、`Last`）與固定步一張 `FixedUpdate`（stage 依序 `First`、`PreUpdate`、`Update`、`PostUpdate`、`Last`），名字在 `ScheduleSkeleton.hpp` 的 `DefaultSchedules`；每幀的清單沒寫 `Main` 時把它放在最前面，`FixedUpdate` 不進清單（由掛進去的 System 巢狀跑，沒人跑就不跑）；替換 World 時照樣再宣告。作者可以在 `Build` 裡往骨架插 stage；要換掉骨架，在 `WorldDescription::skeleton` 選 `ScheduleSkeleton::Off`（編排層不宣告 schedule，作者自己宣告；`WorldGeneration` 照登記，O-2）——開著骨架時作者再宣告 `Main` 是 Kernel 的 R-E2。Module 在登記時把 System 掛進去（O-3、RC-O8）。不帶任何第三方能力；不認得產品、策略的語意、時鐘、回滾。守衛：依賴只有 Kernel 與 Base；`orchestration.O-4` 各案（`SkeletonTests.cpp`，預設骨架）與突變 `or-skeleton-`；include 掃描（`orchestration.guard`）、`naming_guard` 的目錄對應、依賴的連結檢查（`gyo_expect_links(gyo_orchestration GYO::Base GYO::Kernel)`）已立（`v8-arch-gyo2-time-events` 第 1 步）；三條掃描（O3、O4、O6）與 `naming_guard` 的目錄對應各有實際程式碼樹上的陽性對照，O0（掃不到東西不放行）兩處各有突變（第 7 步依敵對式檢查補：`or-guard-real-*`、`or-guard-o0-*`、`or-guard-o4-dropped`、`or-guard-o4-unreadable-silent`）。

<a id="o-5"></a>
**O-5 啟動錯誤一次收齊。** Kernel 的 `StartupReport`（每個 World 一份，原封不動；Kernel 的 `StartupCode` 不擴充）、編排層的 `OrchestrationCode`（O-E1～O-E7、O-E9；O-E8 不用）、各登記單位在 `Finish`／`Check` 回報的錯誤（它自己的碼）收成一份 `ProductStartupReport`；準備函式的錯誤（O-E7）在建好的 World 上才會出現，另成一份。執行時的錯誤 `OrchestrationError` 是另一組碼，準備函式回報的碼原樣帶出（存檔版本 Module 的拒絕靠它分辨）。〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕`ProductSetup::Report` 的錯誤也收進 `ProductStartupReport`，有它就不建任何 World（O-2「出錯的登記單位不用、其餘照做」不及於 `Build`）；交換函式的失敗是執行時的 E2 `ExchangeFailed`（O-12）。〔`v8-arch-gyo2-sdl-extract`，使用者 2026-11-23 Q1＝(a)〕Extract 的來源沒登記成（Kernel 的錯、被 O-E6 丟掉，或讀者自己的 `extractFrom` 是 O-E9）時，讀者不登記、標沒檢查，只報擋住它的那一個錯——和 O-15「有 `Configure` 回報就不跑 World 的 `Build`」同類，是「一次收齊」的例外：讀者自己和來源無關的錯要等下一次啟動才看得到。守衛：`orchestration.O-5` 各案；`orchestration.extract`「a source that did not register leaves the reader unchecked …」；`orchestration.product-buffer` P-7；`orchestration.exchange` X-3。

<a id="o-6"></a>
**O-6 依賴只在登記檔。** Module／Plugin 之間的依賴只寫在 `config/modules.csv`、`plugins.csv`（使用者 `v8-arch-gyo2-module-deps-in-registers`）；Module 的子目錄（`dir` 欄：`modules/<名>`）、Module 與 Plugin 之間的 link 與產品的登記單位表由它產生。core、ecs、orchestration 不是 Module、不登記：`engine/CMakeLists.txt` 直接加它們，它們彼此的 link、以及 Module 對它們的 link，寫在各自的 CMakeLists（使用者 2026-11-21，`v8-arch-gyo2-core-not-registered`）；編排層建立 `Product` 時檢查（缺、在後、Module 依賴 Plugin 是 O-E3，不重排）。進 World 的 Module 照 `default` 欄預設帶、產品可以關；`default=no` 的與 Plugin 由產品列出。Plugin 的目錄（`plugins/<名>`）只在被選時加入建置：設定中的產品列出的、快取變數 `GYO_PLUGINS` 點名的（`ALL`＝全部），連同它們依賴的 Plugin，在所有產品之後照登記順序加入；沒被選的不 configure，它抓的外部組件不下載（`v8-arch-gyo2-sdl-p`；SDL-2，`sdl.zh-Hant.md`）。守衛：`cmake.UnitRegistry`（登記檔的讀取與驗證、產品帶哪些單位、產生的表與 link、加入哪些 Plugin，`cmake -P`）、`cmake.PluginSelection`（整個 repo 什麼都沒選時不加 Plugin）、`orchestration.units`（產生的表建得起 `Product`）、`orchestration.O-E3` 的依賴各案；引擎 CMakeLists 不手寫登記單位的 link 的掃描（`orchestration.guard`，`v8-arch-gyo2-time-events` 第 1 步立；2026-11-21 起只看登記檔裡的 target）。

<a id="o-7"></a>
**O-7 準備時機。** 每個 World 建好之後（啟動與每次替換）、第一次 Run 之前，照「帶過去 → 登記單位的準備 → 描述的準備 → 替換帶的 `extra`」的順序呼叫；準備放預設值時不蓋掉已經在的值；失敗時這個 World 不用。〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕交換函式和準備函式一樣在 `Build` 登記、隨替換重新登記，但存在 World 槽、活到那個 World 被替換或銷毀（O-12）。守衛：`orchestration.O-8` 的準備各案；讀檔案例；`orchestration.exchange` X-6。

**O-12 交換點。**〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准，[事前宣告](exchange-declaration.zh-Hant.md)第 5.1、5.4 節〕資料進出 World 有四種形，World 的資料都不上鎖（M11、D6b 與其加註）：

- **Extract**：渲染一類的 World 在來源跑完之後唯讀地讀來源，不寫回（DI-KS 13，使用者 11-11）；兩個 World 都不在 Run 裡；來源被替換後讀者不得讀舊來源（O-8）。〔`v8-arch-gyo2-sdl-extract`，草案；最終文字合併前核准〕讀者的描述 `extractFrom` 指名一個排在它前面的 World；指名不存在的、自己、排在後面的，或每幀清單有 extract schedule 而 World 沒有 `extractFrom`、開局清單有 extract schedule，都是 O-E9。編排層在讀者第一次 `BuildPlans` 之前把來源的 Registry 設成讀者的 extract 來源；每幀清單、`RunSchedule`、`beforeSwap` 遇到 extract schedule 經 Kernel 的 `RunExtract` 跑、給來源 World（DI-KS 35），沒有來源的 World 跑 extract schedule 是斷言。讀到的是來源這一輪與它的交換函式「出」之後的狀態（`RunSchedule` 讀當下的）；讀者的交換函式「進」在它之前。extract schedule 不在清單最前面不算錯，在它之前跑的 schedule 讀到上一輪抽的資料。一個來源可以有多個讀者，讀者也可以當別人的來源。守衛：`orchestration.extract` 各案與突變 `or-ex-`。系譜與比過的在[事前宣告](sdl-extract-declaration.zh-Hant.md)第 3 節（Bevy `SubApp::extract`）。

**O-15 Product 一份的共用處。**〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准；使用者 2026-11-22 選「Product 一份的共用處」，[事前宣告](exchange-declaration.zh-Hant.md)第 5.2 節〕
- **共用處**：`Product` 另持有一份 `ModuleBuffer`，規則同 O-2 的每 World 那一份（一方 `Create<T>`、別人 `Find<T>`、一個型別一個擁有者），但**不凍結**。拿得到它的地方：`ProductSetup::Buffer()`（`Configure`）、`WorldSetup`／`WorldFinish`／`WorldCheck::ProductBuffer()`（都可寫）、`Product::Buffer()`（runner 與 Product 的持有者）；交換函式、準備函式在 `Build` 時捕參照，System 要用的由擁有的 Module 在準備函式放一個指向它的 World Resource。表只在擁有 Product 的執行緒上碰（CCR-5）；放進去的物件若會被別的執行緒用，同步是物件自己的事（CCR-6）。物件照 `Create` 的反序解構。
- **Product 層的選項**：`ProductDescription::options`（`OptionBag`）從第一個單位的 `Configure` 起經 `ProductSetup::Options<T>()` 讀得到，只轉交、不解讀；產品或測試給單位的物件一律走這裡（產品自己的 `configure` 在所有單位之後），介面放進持有者的小結構。
- **`Configure` 的回報**：`ProductSetup::Report` 收進 `ProductStartupReport::unitErrors`（`world` 空；`unit` 是登記列名，產品自己的是產品名）；有任何 `Configure` 回報就不跑任何 World 的 `Build`～`Check`（每個 World 標沒檢查），其餘單位的 `Configure` 照跑完；單位在 `Configure` 找不到依賴的物件時自己回報後返回、不斷言。
- **`OnDestroy`**：`ProductSetup::OnDestroy(fn)` 的回呼在 Product 銷毀時、照登記的反序各跑恰好一次（`Build` 失敗、`Configure` 丟例外時已登記的也照跑），跑完就放掉閉包；回呼跑時共用處的物件都還在，回呼返回時它負責的工作必須已停、不再碰共用處；回呼不回錯誤、不丟例外。系譜：Unity Entities 的 System 照建立的反序「停 → `OnDestroy` → 銷毀」、flecs 的 `ecs_atfini`。
- **誰比誰活得久**（`~Product` 照這些關係寫成明確的步驟，`Build` 失敗的路徑也一樣；步驟本身在 `Product.cpp` 的註解）：每個 World 都比共用處先銷毀；`OnDestroy` 的回呼在所有 World 之後、共用處之前；runner 在回呼之後、共用處之前；描述的閉包與選項在共用處之後；登記單位最後；World 之間照描述的反序（讀者先於 Extract 的來源；讀者的 Registry 也先於來源的 Registry，`Build` 失敗時還沒成 World 的登記也照反序丟，DI-KS 37）。

守衛：`orchestration.product-buffer` 各案（P-1～P-9，`ProductBufferTests.cpp`）與突變 `or-pbuf-`。

### Replacement Criteria

符合任一條時，停下來交使用者「修還是重建」（L17 的形式：不數次數，出現就停）。

- **RC-O1**（原 Kernel RC 7「Host 又長回來」，主詞改成編排層）：第一個真實能力接進機制時仍要改編排層的迴圈或 Kernel 本體；或編排層以外的協調邏輯在兩個以上產品中重複。
- **RC-O2**：每加一種產品或 World 的組法都要改編排層的程式。
- **RC-O3**：runner 需要排 System 的先後才做得出某個 Feature。
- **RC-O4**：編排層開始 include 某個第三方或某個 Module 的內部。
- **RC-O5**：編排層的職責清單（O-4）要多加一項，或判不出某樣東西屬於哪一層。
- **RC-O6**：登記檔的欄位不夠用、需要第二份描述同一件事的檔，或 CMake 與編排層讀出的依賴不一致；或「只用函式庫、不要登記單位」的 World 被 O-E3 擋到。
- **RC-O7**：替換 World 的某個用途需要「不重建 World 就換掉內容」。
- **RC-O8**：scenario 的某一段為了通過，必須讓編排層知道某個 Module 或產品的語意。
- **RC-O9**：讀檔（替換 World）重跑登記的時間成為讀取時間的主要部分，或第 5 條的 extract 為了它要改 Kernel。
- **RC-O10**：CCR-5 放寬時（建 World 要並行，或一個 World 的登記單位並行 `Build`），`ModuleBuffer` 需要加鎖或改成別的同步方式。（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕CCR-5 的放寬也包括 World 交出到別的執行緒（O-13）；Product 一份的共用處同樣適用；或整個交出保不住 O-11、做不出點名的 Feature。
- **RC-O11**〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕：交換函式的登記沒有點名的使用者了（例：診斷紀錄改成別的形），或某個點名的 Feature 需要進、出之外的呼叫點（例：每張 schedule 之間），或需要編排層傳這一輪的資訊（時間設計 5.3 原形有的取樣時刻、第幾輪）才做得出。
- **RC-O12**〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕：Product 一份的共用處需要知道放進去的物件是什麼（例：要依型別做不同的收尾）、`OnDestroy` 的反序排不出某個收尾的先後，或兩個單位需要共同擁有一個型別。
- **RC-O13**〔`v8-arch-gyo2-exchange`，使用者 2026-11-22 合併前核准〕：Extract 的來源替換（O-8）讓讀者的重建成為替換時間的主要部分，或讀者有不能重建的狀態（和 RC-O9 第二句一起看）。
- **RC-O14**〔第 5 批，`v8-arch-gyo2-world-gen`；使用者 2026-11-22 合併前核准〕：有點名的 Feature 需要「新 World 生成期間舊 World 照跑、生成完才換上」（無縫轉場），或需要「跨幀的讀檔放回途中失敗也保留舊 World」（宣告 8.1「旁邊生成再換上」）。
- **RC-O15**：兩個以上的產品為了「生成中」另寫自己的旗標或狀態，因為 `WorldGeneration` 與兩個條件不夠用。
- **RC-O16**：生成要做得出來，必須讓 Kernel 認得生成（任何階段的欄位、分支）。
- **RC-O17**：兩個以上的產品各自寫「逐項做完才下一項」的游標，考慮由編排層提供。
- **RC-O18**：兩個以上的 Module 為了生成各開條件選項，或作者要擋某個 Module 的 System 而擋不到——看要不要讓 Kernel 能給既有的 set 加條件（Bevy `configure_sets`；改 Engine，先問使用者；使用者 2026-11-22 定現在不做）。
- **RC-O19**：不能暫停的 World 用條件寫法時，生成期間每幀一筆 `TimeDiscarded` 在有名字的產品上成為問題。
