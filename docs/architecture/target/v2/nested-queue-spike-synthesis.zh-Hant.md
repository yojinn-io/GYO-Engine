架構師對最後一句的第一個理解：同一條基礎規則不應該因為有沒有巢狀而給出不同的答案。**使用者否定了這個理解**（2026-11-15）：「不，我是說，你加上C之後，不能，這個 tick 裡面有C。下次做同樣的操作時，C在下一個tick裡面才會出現。而且我剛才if的例子是單執行緒下，多執行緒是另一種思考模式。我們不能保證的得提前說。並且提供解決方案（當然會有代價）」

所以「一致」指的是：**同樣的操作，每一次的結果（包括變更在哪個 tick 生效）都一樣**。做不到的地方要事前講明，並提供有代價的解法。單執行緒下的要求；多執行緒另外想。

**第 3、4 節是照第一個（錯的）理解寫的**：它們比的是「巢狀對不巢狀」，據此提出「不讓多個佇列同時存在」。照使用者真正的意思，要比的是「每一次是否相同」。第 3、4 節留作紀錄，結論作廢；對抗檢查已經收到這個更正，照新的讀法查。

## 2. 事實

### 2.1 兩種存放形式幾乎等價

- 兩者都做得出來。既有的 94 項測試在兩邊都全過，指紋的 golden 不變，沒有改任何既有測試。
- **層的標記是多餘的**（甲）：目前這一層的紀錄一定排在佇列的尾端。理由是只有正在跑的 System 會記進佇列、獨占的 System 沒有記延後變更的路、每張執行計畫都以同步點收尾。甲加了全掃描的斷言，跑完全部案例都成立。所以「一個佇列」實際上就是「各層疊在同一個容器裡」。
- 差別只剩這些：

| | 一個容器（甲） | 另外存的堆疊（乙） |
|---|---|---|
| 進出巢狀 | 不用存與還原 | 存與還原約 15 行 |
| 中斷時丟棄 | 現有的程式不用改 | 要另外清每一層 |
| 新加一條要看外層的檢查 | 外層的紀錄就在同一個容器 | 要自己去翻堆疊；忘了就靜默漏掉（乙用突變驗過） |
| 標記用在 hook 的佇列 | 會過時，不能用（甲踩到，誤擋了一個正當的情形） | 沒有標記，沒有這個問題 |
| 成本（外層 10000 筆時，一次巢狀執行，粗估） | 14～38 µs | 約 1 µs；裡面有一筆刪除時約 13 µs |

### 2.2 會讓程式壞掉、或讓既有的守衛失效的（兩個試做都重現了）

| 情形 | 什麼都不做時 | 兩個試做補上之後 |
|---|---|---|
| 外層 (c) 區記了往 E 插入或用指定的 id 生成，裡面 (b) 區刪 E（第 1、18 條） | 守衛 Z5 不出聲，E 被刪 | 裡面那張的同步點回報 Z5，E 沒被刪。三層、外層的 hook 佇列也一樣 |
| 外層刪除 E，裡面用同一個 id 生成（第 16 條） | E 還在時撞斷言；**E 本來就不在時，生成的實體被外層靜默刪掉**（新發現） | 加一個檢查後兩種都回 Err |
| 外層與裡面的紀錄位置剛好相同 | 一個佇列不分層時撞斷言 | 不會撞 |

### 2.3 結果和「同一個同步點」不同、而且沒有訊息的（兩個試做的實際結果一致）

| 情形 | 巢狀時 | 同一個同步點時 |
|---|---|---|
| 外層移除 E 的 C，裡面往 E 插入 C | 沒有 C；hook 只觸發移除 | 有 C；hook 先移除再加上 |
| 外層插入 C=1，裡面插入 C=2 | C=1 | C=2 |
| 外層生成 N（還沒套用），裡面往 N 插入 V | N 在、沒有 V、丟棄的計數加一 | 有 V |
| 外層刪除 E，裡面往 E 插入（都是 (b) 區） | E 沒了；多觸發一次加上與一次移除的 hook；丟棄的計數是 0 | E 沒了；沒有 hook；計數是 1 |
| 漏斗：外層放請求 R=a，裡面放 R=b | R 是 a，目標卻是照 b 算的 | R 與目標一致 |
| 漏斗：外層放請求 R1，裡面放 R2，都是同一個目標的請求 | 目標由 R2 決定 | 目標由先登記的 R1 決定 |

**這些不是存放形式造成的**，兩種形式都一樣。原因是「各層的紀錄各自套用」本身：外層先記的，比裡面後記的晚套用。

### 2.4 「一個檢查處理所有成對的情形」試過了（甲）

- 寫得成一個函式（58 行），在裡面那張的同步點套用之前，把「正要套用的」和「外層留著的」成對比過，認到就回 Err。
- **它會誤擋正當的寫法**：
  - 外層放請求、裡面明寫目標——巢狀與同一個同步點的結果完全相同，卻被擋。
  - 兩邊插入相同的值——任何順序結果都一樣，卻被擋。
  - 外層刪除、裡面插入——最後的狀態相同，只有 hook 的次數不同。
- 它只抓得到「裡面先套用」這一邊；外層套用時裡面的紀錄已經不在了。
- 成本：外層 10000 筆時每個同步點多 40～50 µs。

### 2.5 試做時才發現、正式實作要處理的

- 巢狀時 Z5 的錯誤訊息寫「同一個窗」，其實那筆在外層。
- 外層吞掉錯誤之後，如果執行器不停下來，下一個同步點會把中斷的 World 改回執行中（乙從程式推的，沒有寫案例）。
- 「只給測試用的讀法」不能放在 `tests/` 底下（命名的守衛不准測試打開 Kernel 的命名空間），要放在 Kernel 的標頭。
- hook 的佇列每張 schedule 一個、壽命比一次執行長：裡面那張最後一個同步點的 hook 記下的紀錄，要等那張 schedule 下一次被跑才套用。這是巢狀以前就有的行為；固定步一輪跑 0 到 k 次時，它什麼時候套用就不固定。只跑一次的 schedule（Startup）最後一個同步點的 hook 紀錄永遠不會套用（丙從程式推的）。

### 2.6 寫入的關口與「誰寫的」（丙）

- 每個元件的格子與每個 Resource 都存著最後一次寫入的記號；每一步（System 或同步點）一個記號。現在沒有任何「記號 → 哪張 schedule 的哪個 System」的對照。
- 加一張有上限的對照表（每一步一筆）就查得出**當場寫入**是誰寫的，每種建置都開得起。
- 查不到的：延後的變更在同步點套用之後，格子上只留同步點的記號，記錄者的身分已經丟掉；漏斗補出來的值、hook 的寫入同樣；外面程式在兩次執行之間的寫入會被算到下一個 System 頭上；刪除與移除不留痕跡。要補齊得在套用時另外留一筆紀錄。
- 巢狀以前就有的一個無聲問題：hook 寫的事件，位置用的是觸發它的那張 schedule 的，和事件所屬的時鐘對不上時，那筆事件可能永遠讀不到。

## 3. 分析（架構師的；待對抗檢查）

### 3.1 這些問題的同一個根

使用者指出的是對的：以前同一時間只有一個還沒套用的佇列，所有延後變更的規則（一個同步點裡先刪除、再移除、再生成、再插入；同一格由後面的 System 勝；Z5；漏斗同一輪的選法）都建立在這個前提上。「各層各自套用」讓外層與裡面的佇列同時存在，第 2.2、2.3 節的每一列都是這個前提不成立時，某一條既有規則給出不同答案的例子。

### 3.2 兩條路

- **路一：維持多個佇列，補一個東西讓它們互相看得到。** 第 2.4 節就是它的樣子：要對每一種成對的情形決定怎麼辦，會誤擋正當的寫法，而且只蓋得住一邊。只補「會壞掉的」（第 2.2 節）是做得到的，但第 2.3 節的不一致會留著。
- **路二：不讓多個佇列同時存在。** 進入裡面那張之前，外層已經沒有還等著的紀錄。這時每個同步點都是普通的同步點。

**待檢查的主張**：在路二的前提下，第 2.2、2.3 節的每一列都不會發生，Z5、漏斗、刪除後再生成都走和現在完全相同的程式；剩下的只有第 2.5 節最後一點（hook 的佇列，巢狀以前就有的行為）與執行器本身要改的項目（狀態、成員檢查、存取驗證、句柄、stamp、出錯的處置）。

### 3.3 路二的三個做法（宣告第 3.1 節當時的選項，重新比）

| | 排程時在獨占的 System 前面固定加一個同步點 | 呼叫「跑一張 schedule」時先套用外層還等著的 | 佇列不是空的就回 Err |
|---|---|---|---|
| 同步點在哪裡是什麼時候決定的 | 啟動時，寫在執行計畫裡 | 執行時，看那一輪有沒有呼叫 | 不加同步點 |
| 裡面那張看不看得到外層剛記的變更 | 看得到 | 看得到 | 不會有（作者要先排好） |
| 影響到誰 | 每一個獨占的 System，包括不跑 schedule 的。除非讓「會跑 schedule」出現在簽名上，只對那些加 | 只有真的跑了 schedule 的那一次 | 只有佇列不空時去跑的 |
| 對決定性的區 | 執行計畫與 C 指紋多一個同步點；兩端要一致，不一致在連線時被擋下 | 同步點出不出現取決於執行期（例如這一輪固定步跑 0 次還是 1 次）；同一個 stage 前面有 (c) 區的 System 記了變更時，它什麼時候套用就跟著 (b) 區的時間走 | 無 |
| 錯了會怎樣 | 不會錯 | 不會錯 | World 中斷；只有那一輪前面真的記了變更才發生，受登記順序影響 |
| 加了這個獨占的 System，同一個 stage 其他 System 的結果會不會變 | 會：它前後的 System 被分到兩個同步點（等於它們在不同的 stage） | 會，而且只在有呼叫的那一輪 | 不會 |
| 系譜 | 比 Bevy 強（Bevy 只在寫了先後、而且前一個有延後寫入時加） | 新導出的 | 新導出的 |
| 需要它的 Feature | 固定步（驅動的 System 自己佔一個 stage 時，三個做法的行為相同） | 同左 | 同左 |

宣告第 3.1 節當時把「一律自動加同步點」的代價列了四點（同一輪的結果會變、Z5 被繞過、hook 提早、C 指紋會變）。照第 2.3 節的事實，「各層各自套用」也有同一類的代價，方向相反，當時沒有列；那張表在這一點上不公平。

### 3.4 第 3、4 條與「觀察者」

- 第 3 條（寫 Resource 要列）已定。它補的是「預設只有一個寫者」這個啟動檢查的洞，在編譯期擋。
- 第 4 條（元件要不要也列）掛起。獨占的 System 本來就寫不到單一寫者的元件，啟動檢查沒有洞；要列的理由只剩「查得出是誰寫的」。
- 「查得出實際是誰寫的」（第 2.6 節）是另一件事：它需要對照表加上套用時的紀錄，和巢狀沒有直接關係，路一、路二都一樣要另外做。

## 4. 架構師暫定的看法（**作廢**：照錯的理解寫的，見第 0 節；留作紀錄）

1. 如果使用者要的是「基礎規則不因巢狀而變」，路二比路一直接：它恢復原本的前提，而不是在新的前提上把規則重新補回來。
2. 這等於重新打開使用者已定的「各層各自的佇列」（`v8-arch-gyo2-nested-apply-per-level`）。要不要重開由使用者定。
3. 路二的三個做法之間，架構師沒有結論：固定加同步點是靜態的、不會錯，但會影響同一個 stage 的其他 System；呼叫時才套用的時機不固定；回 Err 最小，但錯誤看當輪的資料。
4. 不論走哪一條路，第 2.5 節的項目與「會壞掉的」都要處理。
5. 「誰寫的」的對照表不在這一批；要不要做、什麼時候做，另外定。

## 4b. 對抗檢查之後（2026-11-15）

對抗檢查（Opus／xhigh，唯讀）：blocker 3、should 11、nit 6。報告：`build/evidence/gyo2-nested-queue-spike/adversary-synthesis-opus.md`。反例都是它讀程式推的，沒有執行。

- **第 3.2 節的主張不成立。** 「先套用」只清得掉外層的佇列，清不掉外層 schedule 的 hook 佇列：先套用本身會觸發 hook，hook 記下的變更要等外層下一個同步點才套用。所以不論哪一個做法，進入裡面那張時都可能還有等著的紀錄；Z5 被繞過、刪除後用同一個 id 生成撞斷言，經由 hook 佇列照樣會發生。也就是說 hook 的佇列本來就是第二個佇列，巢狀以前就是。
- **第 3.3 節「呼叫時先套用：不會錯」是錯的。** 同步點出不出現取決於這一輪固定步跑 0 次還是至少 1 次，同一個 stage 裡其他 System 的結果與 Z5 報不報錯都會跟著變。
- **照使用者更正後的讀法（同樣的操作每次結果與生效的 tick 相同）**：

| 情形 | 各層各自套用（已定） | 驅動的 System 前面有同步點（自己佔一個 stage、宣告一個、或固定加） | 呼叫時先套用 | 不空就回 Err |
|---|---|---|---|---|
| 和驅動的 System 同一個 stage、排在它前面的 System 記的變更，固定步幾步之後看得到 | 那一輪跑了幾步就晚幾步，每次不同 | 下一步就看得到，每次一樣 | 下一步就看得到；但同一個 stage 其他 System 的結果隨那一輪有沒有跑而變 | 那一輪有跑、前面又有記時 World 中斷 |
| 上面那種變更觸發的 hook 再記的變更 | 晚幾步不固定 | **仍然**晚幾步不固定 | 不固定 | 不固定 |
| 排在驅動的 System 後面、或在前面的 stage 記的變更 | 下一步就看得到 | 同左 | 同左 | 同左 |
| 固定步裡面自己記的變更 | 下一個 stage 就看得到 | 同左 | 同左 | 同左 |
| 第 2.3 節那六種成對的情形（真的落在同一輪時） | 每次結果相同，可以寫成一條規則：排在驅動的 System 前面的外層紀錄，在裡面那張全部的紀錄之後套用 | 不會發生（外層已經先套用） | 隨那一輪有沒有跑而變 | 不會發生（先回 Err） |

- 「驅動的 System 前面有同步點」不必改 Kernel：現有的機制就能由登記那張 schedule 的人宣告一個具名的同步點，讓驅動的 System 排在它後面。
- 所有做法共同的限界：每幀與固定步的對應本身取決於真實時間。要以固定步精確一致，每幀那一側的變更得帶著「在第幾個固定步生效」的標記交過去（像網路遊戲的輸入緩衝），那是另一套機制。
- hook 記的變更要做到每次一樣，三個方向都有代價：每個同步點把 hook 的連鎖當場做完（Bevy 的做法；要全面改 hook 現在的規則）；每次跑完一張 schedule 就把它的 hook 佇列清空（也順便解決只跑一次的 schedule 的 hook 永遠不套用）；禁止 hook 記延後的變更。
- 其他更正：第 2.1 節「新加的檢查看不到外層」兩個試做都一樣（甲的突變也是同一種漏法），差別只在預設有沒有把外層的清單傳進去；成本的數字兩邊量法不同，不能直接比。第 2.4 節的「誤擋」寫過頭：那幾種最後的值相同，但 hook 的時機與次數不同。第 3.4 節「和巢狀沒有直接關係」不對：巢狀之後每一輪跑幾次會變，「誰寫的」更推不回去。

## 5. 範圍的限界

- 兩個試做都沒有做出錯的處置、Startup、Resource 介面、閉包介面；沒有驗可回滾的 schedule、tick 的推進（乙）、漏斗的鏈。
- 路二沒有試做。第 3.2 節的主張是從第 2 節的事實與丙的掃描推的。
- 成本都是粗估（這台 Mac，同時有別的建置在跑）。
- 丙的掃描沒有讀 `Fingerprint.cpp`、`SystemTraits.hpp`，`Scheduler.cpp` 只讀了一部分。
