## 1. 先用遊戲講：三個後果

規則（現在的，【程式】`World.cpp:373-385`、`:1042-1053`、`Executor.cpp:327-358`）：每個讀者一個游標；被 run 條件跳過、或所在 schedule 沒跑，游標不動，下次補讀；**第一次跑才開始拉住**，第一次從還留著的最舊一筆讀起；每次最外層 Run 結束修剪到「拉住的游標」的最小值；滿了（預設 1024）丟最舊，記一筆 `DroppedMessages`（列出還沒讀到的讀者）。

**後果 1：停跑的讀者一直拉住保留，記錄失去警報作用。**
網路對戰裡，暫停選單不會停模擬（對手還在打你）。「播命中特效」帶 `InState<Playing>`，讀 `Hit`。開了選單，它被條件跳過，可是它跑過，所以拉住全部 `Hit`。一直開著，`Hit` 堆到 1024 筆之後，每次有人寫，那次 Run 就記一筆 `DroppedMessages`（「讀者：播命中特效」）。記錄每幀都報，真正的漏讀反而看不出來。
同型：主選單的「處理按鈕」帶 `InState<MainMenu>`，進關卡後它不跑卻拉住 `ButtonPressed`；生成世界裡帶 `WhileGenerating()` 的讀者，生成完永遠不跑、永遠拉住（world-gen 宣告第 5.11 節已記）。

**後果 2：恢復時補讀舊的——玩家看得到的錯。**
同一個「播命中特效」，關掉選單的那一幀，一次讀到暫停期間的全部 `Hit`（上限內最多 1024 筆），一口氣播出幾百個特效。主選單的「處理按鈕」回到主選單那一幀，把關卡裡暫停選單寫的 `ButtonPressed` 全部當成主選單的按鈕處理。

**後果 3：進入那張第一次讀不到，之後每次讀到上次以來的全部。**
`Flow.Enter.InLevel` 裡的 System 讀 `LevelSelected`。第一次進關卡時它從沒跑過、不拉住，選關那一幀的 Run 結束，`LevelSelected` 就被修剪，它讀到空的。
同型而且和狀態機無關：每幀清單是 `[Main, Render]`，`Main` 寫、`Render` 讀；第一幀 `Main` 結束就修剪，`Render` 的讀者還沒跑過、沒拉住，第一幀的訊息就丟了。固定步第一幀跑 0 次時，固定步裡的讀者同樣丟掉第一幀的輸入。**這一型已經有 Module 在繞**：日誌 Module 把它寫成「不保證」——LG-1「讀者第一次跑之前，別張最外層 schedule 寫的、那次 Run 結束就被修剪的訊息」（`logging.zh-Hant.md:33`；【程式】`Forward.hpp:44-46`）。

## 2. 假設 → 查證 → 對比 → 推斷 → 總結

### 2.1 假設

**H1**：三個後果不是「照游標修剪」（你定的）本身造成的，而是統合在推導時多加的兩個前提（1+1=3）造成的：
- **前提 X**：「被 run 條件跳過」和「所在 schedule 這次沒跑」當成同一件事，都要補讀。
- **前提 Y**：「第一次跑才開始拉住，第一次從還留著的最舊一筆讀起」。

**H2**：只改這兩個前提，就能解掉後果 1、2 與 3 的第一次讀不到，而且不必改 Kernel 公開介面的形狀（不加函式、不加選項）、Kernel 不必知道 schedule 的語意。

### 2.2 查證：前提表

| # | 前提 | 誰定的／出處 | 掛在它上面的 |
|---|---|---|---|

**「不漏讀」原本指什麼**：U1 的理由寫的是「不必依賴編排層**排得對**」，比過的另一個選項是 Bevy「由編排層或時間排的更新事件 System、忘了排會一直累積」。也就是說，你要的保證是：**修剪的時機不必有人排對，讀者在節奏不同時（固定步這幀跑 0 次）也不會漏**——對象是「排程與節奏造成的漏讀」。
「作者自己用條件把讀者關掉的那段時間，回來要補讀」不在 U1、U2、U3 的任何一句裡；它是 X，由統合把「不漏讀」讀成「任何原因沒跑都要補」推出來的。Y 也不在你的話裡：U2 說的是「每個讀者一個游標、留到讀過」，沒有說「跑過才算讀者」。

**H1 的查證結果：成立。**三個後果的成因逐一對回前提：後果 1、2 ← X（加上 U2 的「留到讀過」，讓關掉的讀者也算在「讀過」的條件裡）；後果 3 的第一次讀不到、`[Main, Render]` 第一幀丟訊息、日誌 Module LG-1 的「不保證」← Y；後果 3 的「之後每次讀到上次以來的全部」← U3 本身（進入那張是「schedule 沒跑」，Kernel 分不出它和固定步跑 0 次），不是多加的前提。

### 2.4 推斷

**D1（X 是多的）**：把 X 拿掉、換成「被條件跳過＝讀過了」，後果 1、2 就沒有了；「不漏讀」的保證（U1、U3）不受影響，因為固定步跑 0 次是「schedule 沒跑」，不是條件。Kernel 判斷「被條件跳過」用的是自己的條件求值（`Executor.cpp:334-350`），不必知道哪張是固定步、哪張會暫停——不碰游標宣告 RC 2（「游標或修剪要知道 schedule 的語意才做得對」）。

**D2（Y 是多的）**：把 Y 換成「讀者一出生就拉住」，`[Main, Render]` 與固定步第一幀的丟失、進入那張的第一次讀不到就沒有了；而且**一個讀者讀到什麼，只看它自己**（出生、上一次跑或被跳過之後寫的，上限內），不再取決於別的讀者有沒有拉住（現在的 Y 下，新讀者第一次讀到的是「別人還拉住的最舊一筆」以後的全部，見 J-36 `msg-new-reader-oldest`：`later:2 3 4` 的 2、3 是另一個讀者拉住才留下的）。
上限內獨立：緩衝永遠留「最小游標之後最新的 ≤ 上限筆」，所以讀者 R 讀得到它游標之後的全部，當且僅當它游標之後寫的不超過上限——和別的讀者無關。

**D3（D2 不能單獨做）**：只做 D2、不做 D1，帶 `AfterGenerating()` 的讀者從 World 一建好就拉住，生成完一次補讀生成期間的全部——更糟。所以 D2 只和 D1 一起做。

**D4（留下的、Kernel 分不出來的）**：「schedule 沒跑」的讀者照舊拉住、補讀（這是 U3 要的）。因此：
- 時間暫停（固定步跑 0 次）時，每幀寫、固定步讀的訊息照舊留著，恢復時補讀（上限內）。**這和 Bevy 同型**（Bevy 更是無上限），作者的寫法是在暫停時擋住寫者（例：讀手把的 System 帶 `InState<Playing>`）。
- 進入／離開那兩張、observer 裡的讀者，兩次執行之間照舊拉住，下次讀到上次以來的全部。說明頁照狀態機 (A) 寫：要帶進「進入」的放 Resource。
- 轉換那一幀的殘留：讀者在這一幀被跳過之後、下一幀變成要跑之前寫的訊息，它下一幀會讀到（最多一幀）。這是 Bevy #15072 的同型、範圍比 Bevy（兩次 update）小；Bevy 用 Plugin 層的清除補。GYO 先不做（沒有點名的 Feature）；作者若開始寫補償，照第 6 節 RC 停下來問。

**H2 的查證結果：成立。** D1、D2 都只改 Kernel 內部的游標規則，`MessageReader`、`MessageWriter`、`MessageOptions`、`DroppedMessages`、唯讀登記表的形狀都不變。

### 2.5 總結

- 三個後果的主因是統合多加的 X、Y，不是你定的「照游標修剪」。
- 別家沒有一家讓作者關掉的讀者回來補讀；Bevy 的寬限能力 GYO 可以用游標拿到、不必取它的時間窗。
- 建議：D1＋D2 一起做（第 3 節的 (R)），不加介面、不加選項；留下 D4 的三個情形寫進說明頁。

| 讀到什麼取決於別的讀者 | **是** | 否 | 否 | 是（寬限內） |
| 代價 | — | 從沒跑過的讀者也拉住（例：一張從沒跑過的 schedule 裡的讀者；滿了每次 Run 記一筆丟棄——這時記錄是真的：它真的會漏） | 第一幀丟 | 第二種保留規則（RC 1） |
| Kernel 公開介面 | 不變 | 形狀不變，契約改 | 不變 | 不變 |

**建議 (R2)**，和 (R1) 一起（D3）。若你只想動最少，(R1) 可以單獨做，題目二留 (K)；那樣後果 3 的第一次讀不到與 `[Main, Render]` 第一幀丟失照舊，說明頁寫明。

### 3.3 (R1)＋(R2) 之後，一句話的契約

> **一個讀者讀到的，是它出生、上一次被執行、或上一次被條件跳過之後寫的全部（上限內）；和別的讀者無關。被條件跳過不拉住；所在 schedule 沒跑的照舊拉住、下次補讀。**

（「被執行但沒呼叫 `Read()`」照舊不推游標、下次補讀，和 Bevy 相同；本頁不改。）

## 5. Architecture Delta（AGENTS §3 的七項）

1. **Feature**：游標宣告第 2 節的射擊例子（固定步不漏讀，照舊）；狀態機的四個點名 Feature 用狀態條件時不出現後果 1、2；生成世界的 `WhileGenerating()`／`AfterGenerating()` 分段；網路對戰暫停選單不停模擬時的命中特效（第 1 節）。
2. **現在的問題**：第 1 節三個後果；新讀者讀到什麼取決於別的讀者（D2）。
3. **變化的邊界**：Kernel 保留式訊息的讀者契約（DI-KS 10）。介面形狀不變。
4. **影響**：`engine/ecs/kernel`（`Executor.cpp`、`World.cpp`、`World.hpp`、`Params.hpp` 註解）；`tests/common/kernel/MessageCursorTests.cpp`（J-36）與用「被條件跳過的讀者」當拉住者的其他案例（實作批逐案查：`HookFlushTests.cpp`、`ImmediateChangeTests.cpp`、`ObserverTests.cpp`、`NestedRunTests.cpp`）；World 摘要（游標出生得早，摘要的值變；有 golden 的重產）；突變 `msg-` 系列；文件見 4.2（含日誌 Module 的 LG-1）。Module 的程式沒有用到「跳過補讀」（`git grep MessageReader` 掃 `engine/modules`、`engine/orchestration`：只有 `world_logging` 的轉送 System（`Forward` 的選項只有 schedule 與 stage，不帶條件）；`rollback` 只讀登記表的讀者名單）。
5. **Dependency Direction**：不變。
6. **Ownership**：不變（訊息留多久仍是 Kernel 照游標與上限）。
7. **為什麼不能更小**：只寫說明頁（(A)）留著玩家看得到的錯（後果 2）與失效的警報（後果 1），而且作者的補償會積在上層（RC 7 的觸發條件）；(E)、(F)、(B／G) 都要加介面，(B／G) 還把機制散到每個 Module。(R1) 單獨做是更小的選擇，代價寫在 3.2。

## 6. 基盤的根據（AGENTS §2）

- **為什麼算基盤**：讀訊息的行為在每個讀 `Message` 的 System 裡；狀態機、生成世界、時間 Module、網路轉送、音效都積在上面。現在狀態機正要積上去（它的說明頁要寫這三個後果的寫法），越晚改，要改的說明頁與補償越多——這就是使用者「保守的選項會被上層蓋住」的情形。
- **予見的根據**：(1) 名指的 Feature——狀態機的四個點名 Feature、生成世界的兩段、`time-plan-two` 的暫停；(2) 參考實作——第 2.3 節；(3) 規模——上限 1024 筆、每幀寫入的 UI 與命中訊息幾秒到十幾秒就填滿（60 fps、每幀一筆約 17 秒）。

**Design Invariants（改寫 DI-KS 10 保留式那一段；核准後在實作批寫進 `target/kernel.zh-Hant.md`）**：
- 每個讀者一個游標，在 World，以（掛載點、訊息種類）為鍵；System 掛載、run 條件、observer 都是讀者（hook 不能帶 `MessageReader`）。
- **讀者一出生就有游標**（建 Plan 時、observer 登記時），起點是當時最新。
- **讀者讀到的，是它出生、上一次被執行、或上一次被條件跳過之後寫的（上限內），和別的讀者無關。**
- **被 run 條件跳過的 System，它的所有游標推到當時最新**（不拉住、回來不補讀）；所在 schedule 沒跑的讀者游標不動、下次補讀（Kernel 自己保證，不靠人排對）。
- 其餘照舊：寫入序號、修剪（每次最外層 Run 結束，修到全部游標的最小值）、上限丟最舊並按種類聚合記錄、修剪不在 Plan 裡、推游標不算寫入、只有游標一種讀法、訊息不回滾。

**Replacement Criteria（加進 Kernel 的 RC）**：
- 作者開始為「schedule 沒跑的讀者」寫補償（暫停後清掉、進入時推到最新），而且出現在兩個以上的 Module 或產品——表示 Kernel 需要分辨 schedule 的語意，觸發游標宣告 RC 2，停下來問。
- 為了某一種訊息要第二種保留規則（時間窗、固定 N 次）——游標宣告 RC 1，停下來問。
