## 1. 這一批做什麼

### 1.1 用遊戲講

一個單機遊戲：

1. 遊戲一啟動，畫面是**主選單**。主選單的按鈕用開局放的設定（按鍵對應、UI 設定）生成。
2. 玩家按「開始」，遊戲**進關卡**：主選單的按鈕拿掉，顯示關卡的介面，關卡開始載入（地圖、敵人、玩家都走 Loading），好了開始跑。
3. 玩家按暫停，遊戲**進暫停**：跳出暫停選單，遊戲邏輯不跑；再按一次，回到原來的關卡——**關卡不重載**。

這三件事有共同的形狀：

| 形狀 | 例子 | 機制的詞 |
|---|---|---|
| 遊戲現在在哪一段 | 主選單、關卡中；暫停、進行中 | 狀態的值 |
| 進入某一段時做一次 | 進主選單時生成按鈕；進暫停時跳出選單 | 進入時跑一次的 schedule |
| 離開某一段時做一次 | 離開主選單時拿掉按鈕 | 離開時跑一次的 schedule |
| 只在某一段才做 | 只在關卡中移動角色；只在主選單處理「按開始」 | 只在某個狀態下才跑的 System（run 條件讀狀態） |
| 要求換到另一段 | 按「開始」→ 要求進關卡 | 換狀態的要求，與套用要求的那一步 |

GYO2 現在沒有這個形狀。作者要自己寫一個 Resource 記「在哪一段」、自己寫 run 條件、自己做「進入時做一次」——最後一件在 K0 之前做不到乾淨的版本。

主選單的按鈕、關卡的介面是「進入」那張 schedule 裡生成的實體，不算組合頁 DI 3 說的「世界內容」（地圖、場景、可互動物件、敵人、玩家）；世界內容照舊只經 Loading。這句是我的讀法，DI 3 沒有寫 UI 實體。

### 1.4 為什麼當基盤處理（AGENTS §2）

每一個有選單、有暫停的產品都會照它寫：作者的 System 掛在哪張「進入」的 schedule、run 條件怎麼寫、什麼時候要求換狀態。之後要改「轉換在一幀的哪裡發生」或「進入時看得到什麼」，上面積多少就要改多少。

它**不一定是 Kernel 的基盤**：照第 5 節的形狀，Kernel 不為它加任何東西（兩輪檢查都確認在現有程式與 K0 的介面下做得出來）。

成熟方案裡另一個主流是**引擎不提供流程的狀態機**，只給切換場景與暫停的原語（Godot、Unity、flecs、EnTT；設計模式報告第 6.4 節）。你已經把狀態機排上日程，所以它不是選項；記在這裡讓你知道。

### 1.5 這一批不做的

### 3.1 暫停怎麼表達

**已定（2026-11-15，`v8-arch-gyo2-state-machine-pause-as-substate`）：子狀態**——照 Bevy 改裝，不移除 Resource、改在現在的值裡記「不存在」，不動 Kernel；父子的先後照 Bevy。使用者的理由：暫停的特殊性；能換來一些作者的自由度。下面的選項表留作紀錄；套用的細節在第 5.1 節。

### 3.2 進關卡和 Loading 的關係

**已定：照 Bevy，狀態機不管 Loading。**

例子：玩家在主選單按「開始」，關卡要先載入，好了才開始跑固定步。世界內容一律走 Loading（DI 3）。

| | 狀態機不管 Loading | 狀態機不擁有 Loading，由「只在載入中才跑」的獨占 System 巢狀跑 | Loading 是狀態機內建的一個狀態 |
|---|---|---|---|
| 做法 | 「進入關卡中」裡寫「要載入哪一關」的請求；Loading 怎麼跑由 T3 定（時間設計:344：好之前每輪跑一批、由驅動固定步的 System 判斷）；好了之後產品自己決定要不要換 | 產品自己加一個值「載入中」；一個帶「在載入中」條件的獨占 System 每輪 `RunSchedule` Loading 一批，好了就要求「關卡中」 | 狀態機內建「載入中」：外層每輪跑 Loading，好了自動換到下一個狀態 |
| 系譜 | DI 3 原本的形狀；Godot、Unity 的切換場景與背景載入是兩套 | Bevy 生態的「載入中」慣例（bevy_asset_loader，憑記憶，沒有讀原始碼） | Unreal `AGameMode` 的 `EnteringMap`；沒有它的 `AGameModeBase` 後來成為新專案的預設 |
| 依賴方向 | 狀態機與 Loading 互不依賴 | 狀態機不依賴 Loading；產品用兩者 | runner 或狀態機要互相認識——狀態機若是 plugin 就不行 |
| 代價 | 「進入關卡中」一跑完，現在的值就是「關卡中」，但關卡還在載入：帶「在關卡中」條件的**每幀** System 在載入期間就會跑（固定步因為時間設計的規則還沒開始），作者要另外看「載入好了沒」，或自己加「載入中」這個值（那就是第二欄的寫法） | 「Loading 由誰跑」多了一個答案，和 T3 那一題重疊 | 狀態機要懂 Loading 的 ready；沒有選單的產品也有 Loading |
| 需要它的 Feature | 從主選單進關卡 | 同左 | 同左 |
| Kernel 要加什麼 | 不加 | 不加 | 不加（runner 的事在 T3） |

**我的建議：狀態機不管 Loading。** 「Loading 由誰跑」是 T3 的題目；選這一欄之後，T3 那一題剩下「驅動固定步的 System 巢狀跑」「runner 先跑」兩個可能。第二欄是產品用這一批的工具自己寫得出來的寫法，不必由機制規定。

### 3.3 放在哪一層

**已定：Engine 的 Module（`engine/state_machine`）。** 使用者：「狀態機是內化模組，放Module沒有問題。」判準怎麼並用那一問，使用者沒有另外回答。

### 3.4b (c) 區的狀態怎麼做（修訂 3 新增）

**已定**：(c) 區兩種形狀都支援；「兩端在同一個 tick 自己換」那一種改 Kernel（另開一批，排在狀態機這一批之後）；這一批只定介面，見本節最後的「(c) 區的介面」。下面的表與建議留作紀錄。

例子（你舉的）：聯機遊戲的天氣 `Weather { Clear, Rain, Fog }`。規則的 System 在第 3600 個 tick 要求「起霧」；Server 與 Client 在**同一個 tick** 跑「進入起霧」（例：把能見度設成 30 公尺），結果逐位元相同。玩家打開選單不會讓 Server 停下來，Server 也沒有暫停——所以這種狀態不碰暫停，只要「在固定步裡、每一端一樣」。時段（上午、下午、夜晚）、地圖中的全局事件同一類。

side chat 的複述（**不是你的原話**；你看過後說「轉過去」，沒有逐字確認）：作者登記一種狀態時選等級，Engine 照那個等級保證；同一套機制，不是兩套。

從這個 Feature 導出的要求：
- 現在的值與要求都是 (c) 區的 Resource；套用在固定步裡、對準 tick。
- 進入／離開裡做的事是 (c) 區的 System，結果每一端逐位元相同。
- 結構（哪個套用的 System、可能跑哪幾張進入／離開）要進 C 指紋；**執行期**「哪個 tick 換成了什麼」靠狀態的值本身是 (c) 資料、進產品逐 tick 的狀態紀錄（舊 PvP 的權威 digest）來比對。修訂 3 寫「要讓 C 指紋看得到」是錯的：查過 `Fingerprint.cpp:335-400`，C 指紋只收登記與執行計畫的結構，不收執行期的值（PvP 偵察報告第 6 節第 8 條提醒的）。
- 要求來自 (c) 區的規則 System；(b) 區（UI、除錯台）不能直接寫 (c) 區（Z2），要經 ingress 的 Input（Z3）。
- 回滾來了之後，重跑固定步要能重跑轉換（現在 `gyo2` 上沒有回滾，這一條只寫形狀）。

**卡在哪裡**：照修訂 2 的形狀，套用的是一個獨占的 System——而獨占的 System 只能是 (b) 區、寫不了 (c) 區（DI-KS 2、Z2、K0 宣告第 2 節第 1 點），它跑的巢狀 schedule 也不在 C 指紋裡（K0 宣告第 9 節）。所以要嘛改 Kernel，要嘛 (c) 區不用巢狀的 schedule。這是底層機制，要不要改 Kernel 由你判（`v8-arch-gyo2-solve-real-problems` 的但書）。

- 教訓：「偵測到換的 tick」與「動畫的零點」兩端各自詮釋，曾經差 6 個 tick（`protocol-v9:80-84`），後來改成 Match 權威、上 wire。

### 3.6 一次套用換幾次

**已定（2026-11-15）：照 Bevy，一次只換一次。** 使用者：「照用，這個沒關係，讓作者在實作中優化。我們提供的是機制」。下面的表與「跟著連鎖的細節」留作紀錄，連鎖、上限都不做。

| 需要它的 Feature | 沒有點名 | 沒有點名 |

**我的建議：換到沒有要求為止，有上限。** 理由是上面那一幀：照「保守的機制會被蓋住」，一次一換的延遲一旦有產品照它寫，之後很難再改。

**我補的、跟著連鎖的細節（還沒經你判，請一併看）**：
- **離開裡提出的要求**：這次的換照常做完（跑完進入），再換那個要求。例：「離開主選單」裡要求回主選單——會先進關卡中（「進入關卡中」整張跑一次），再馬上離開。另一個做法是「離開裡的要求取消這次的換」，那要多一條規則。
- **第一次執行之後也連鎖**：初始的進入裡提出的要求，同一次接著處理。
- **上限算的是什麼**：一次套用裡「換」的次數，第一次執行的初始進入算一次。剛好等於上限不報，多一次才報。
- **上限放在哪**：兩種——特性裡每種狀態一個值（編譯期，產品改不了預設）；或產品的一個設定加每種狀態可以另外指定（和 hook 那一批「產品可以改預設、每張可以另外指定」同形）。我的建議是後者，但它要多一個放設定的地方（`InstallStateMachine` 的參數）。
- **超過上限時**：現在的值停在最後一次換完的值，待處理的要求留著（World 已中斷，只影響診斷）。

**我補的細節（還沒經你判）**：

### 3.9 「進入／離開時跑一次」用什麼做

**已定：改裝，每個值一張 schedule。**

### 3.10 「只在某個狀態下才跑」與暫停的權威

**已定（2026-11-16 改定）：暫停要不要停時間由作者決定，狀態機不碰 `TimeControl`。** 下面「暫停的權威與時間」那張表與我的建議，降成說明頁裡範例產品的寫法比較（取代 2026-11-15 定的「狀態是權威，進入與離開暫停時寫 `TimeControl`」）。條件的部分不變。

例子：「移動角色」只在關卡中、而且 `Pause` 是「進行中」時才跑。暫停時，冷卻的倒數停不停？

**條件**（Kernel 不加東西）：條件不能捕獲值，所以不能像 Bevy 的 `in_state(值)` 那樣放進閉包；改成樣板參數帶值，名字從特性組：

```cpp
// The module's helpers: conditions named "InState.Pause.Running" / "NotInState.Pause.Paused".
.conditions = {InState<Flow, Flow::InLevel>(), InState<Pause, Pause::Running>()}
// Each reads Res<StateMachine<S>> and compares; "not entered yet" or "no value" makes both kinds false.
```

套件提供「在某個值」與「不在某個值」兩種。也可以用 `SetOptions` 的條件一次給一整組 System（`Registry.hpp:260`；成熟方案裡的對應是 flecs 停用整個 phase）。用在含驅動固定步的那一組上要小心：時間還在累積，恢復時會補跑。

**暫停的權威與時間**（只在第 3.1 節選「暫停是另一種狀態」或「子狀態」時要定；選「只有 `TimeControl`」就不用）：

| | 只用 run 條件，時間不停 | 狀態是權威，進入與離開暫停時寫 `TimeControl` |
|---|---|---|
| 做法 | 遊戲邏輯的 System（含固定步裡的）都帶「在進行中」的條件，或放進帶這個條件的組 | 「進入暫停」那張裡的 System 把 `TimeControl` 設成暫停，「離開暫停」設回來；`TimeControl` 的暫停**只由這兩處寫**（說明頁的規則）；每幀那張裡屬於遊戲邏輯的另外帶條件 |
| 系譜 | Bevy 的狀態範例（不碰 `Time<Virtual>`）；Amethyst 的 `pausable` | Unity 的慣例（`timeScale = 0` 加自己的旗標）；Bevy 實務上常見的「狀態＋暫停虛擬時鐘」（憑記憶） |
| 和你核准的範圍 | 就是原文的字面 | 多用了時間的機制；這是我的延伸 |
| 「是不是暫停」記在幾處 | 一處 | 兩處，靠進入／離開同步。`TimeControl` 標成可以多寫，別的 System（例：除錯工具、視窗失焦）直接寫它時兩邊會不一致，Kernel 擋不住 |
| 漏標條件的 System | 暫停時照跑 | 固定步裡的不必標，一定停；每幀那張裡漏標的照跑 |
| 用 tick 或遊戲時間記的東西（冷卻、計時器） | tick 與 `VirtualTime` 照走，暫停期間會到期 | 不走 |
| 有 (c) 區的產品 | 固定步裡的 (c) 區邏輯帶不了 (b) 區暫停的條件（Z1）；但你說過聯機的 Server 沒有暫停、Client 開選單也不停模擬，所以這一列只對「有 (c) 區又要暫停」的單機產品有差別——那種產品沒有人點名 | 固定步整張不跑 |
| 什麼時候真的停 | 套用的 System 之後的同一幀 | 時間的 System 下一輪才套用（時間設計:175）；同一幀還是下一幀看 T3 的排法 |
| 需要它的 Feature | 暫停時不跑遊戲邏輯 | 同左 |

對照：Godot 與 Unreal 只記一處，而且漏標的預設是**停**（錯的方向是「暫停選單不動」，比較容易發現）；Unity 的慣例記兩處，是它出名的坑。

**我的建議：狀態是權威，進入與離開暫停時寫 `TimeControl`。** 理由：暫停回來，冷卻與計時器不該跳一大段。（修訂 2 的第二個理由「有 (c) 區的產品只有這一欄停得下來」，照你說的「Server 沒有暫停」已經撤回：聯機用不到，只剩沒有人點名的單機情形。）代價是兩處記，我用「`TimeControl` 的暫停只由進入／離開暫停寫」這條說明頁的規則守，Kernel 擋不住；你若更看重「只記一處」，第 3.1 節的「只有 `TimeControl`」或這一節的「只用 run 條件」是兩個方向相反的單一來源。

## 4. 照既有規則推出來的（照寫，不再問）

1. 進入／離開那兩張不帶時鐘，**裡面不能讀寫事件**（F-9）。例：「進入關卡時送一個『關卡開始』的事件」現在做不到，要用 Resource 或元件。T4 改事件的規則時再看。
2. 開局執行中不能跑別的 schedule（K0），開局裡不會發生轉換。套用的 System 若被插在開局那張，第一次跑就被 K0 拒絕、World 中斷。帶狀態條件的 System 掛在開局那張，條件永遠是否（開局時還沒進入任何狀態），永遠不跑——說明頁講明。
3. 套用的 System 是獨占的，和同一個 stage 的每個 System 都算衝突；照第 3.5 節的建議它自己佔一個 stage。
4. 套用的 System 讀現在的值與要求、寫現在的值（列在宣告裡）、清掉要求（`Shared`，不用列），都是 K0 已定的讀寫規則。閉包裡回傳「要求的值或沒有」用套件自己的小結構，不用 `std::optional`（K0 宣告第 9 節，:383 一帶）。
5. 「進入主選單」那張裡生成的按鈕，在那張的同步點就套用（`v8-arch-gyo2-nested-apply-per-level`）；排在套用的 System 後面的 System 同一幀看得到。
6. (c) 區的 System 不能帶 **(b) 區**狀態的條件、不能寫 (b) 區的要求（Z1）；(b) 區的 System 不能寫 (c) 區狀態的要求（Z2），要經 ingress 的 Input（Z3）。(b) 區狀態的進入／離開那兩張裡放 (c) 區的 System，Kernel 不擋，但它讀不到 (b) 區的現在的值，什麼時候跑由 (b) 區的狀態決定、不在 C 指紋裡——要讓 (c) 區的事跟著狀態換，就用 (c) 區的狀態（第 3.4b 節）。
7. 現在的值除了套件以外沒有人改得了（第 3.4 節的型別設計）：別的 System 拿 `ResMut` 只能讀，外面的 `SetResource` 造不出值。

## 5. 要改的程式（照第 0 節的決定；(b) 區的實作）

### 5.1 子狀態怎麼套用

**使用者定的**（2026-11-16）：
- 一棵狀態樹一個套用的 System；先子後父離開、先父後子進入；子不存在時對它的要求丟掉；子每次重新出現都從初始值開始；同一幀父與子都有要求時，先換父、子從初始值開始，再在同一次套用裡換子（分出會話列的規則，使用者：「可以，而且順序非常有有邏輯性。」）。比過、沒選的是「子不存在時把要求存著、等子出現再套用」（玩家一進關卡就是暫停，較怪）。
- 同一個父底下多個子，子與子的離開、進入照登記的順序（「是的。」）。
- 父換成**同一個值**時（例：暫停中選「重新開始這一關」），**默認**照我們的寫法：子先離開、回到初始值、再進入（重開之後是「進行中」）；作者可以在子的特性裡打開 `KeepOnParentReenter`（暫名），改成保留子的值、不跑子的離開與進入（Bevy 的行為）。使用者：「這個也是狀態機是提供默認機制，但是依然可以讓作者修改呀。」「用我們自己的寫法。」
- 兩棵互不相干的狀態樹之間（例：遊戲流程與天氣）不歸狀態機管、不當規則承諾；實際先後由插入的位置決定，每次一樣；說明頁講明。
- 暫停要不要停時間由作者決定，狀態機不碰 `TimeControl`。範例產品的一種寫法：「進入暫停」寫 `TimeControl` 暫停、「離開暫停」設回來。（分出會話補的看法，不是你的話，你聽完沒有異議：時間不停的遊戲，例如開背包不停時間，「背包開著角色不動」靠條件 `InState<Inventory, Closed>`。）

**我補的細節**（照上面的規則與現有程式接起來；修訂 5 的檢查找到的洞照這裡補；還沒經你判，核准整份時一併看）：
- **寫入**：`ApplyStateMachine.Flow` 一併處理 `Flow` 與它的子，寫入宣告列父與每個子（`ExclusiveWorld<Writes<StateMachine<Flow>, StateMachine<Pause>, StateMachine<Inventory>>>`）。理由：子的離開要排在父的離開前面，只有父的套用 System 做得到；兩個套用 System 寫同一個子會是 D-E2。
- **子的清單寫在父的特性裡**：`StateMachineTraits<Flow>` 寫 `using SubStates = TypeList<Pause, Inventory>;`；子的特性寫父與父的值（`using Parent = Flow; static constexpr Flow kParentValue = Flow::InLevel;`）。`RegisterStateMachine<Flow>` 與 `InstallStateMachine<Flow>` 都從父的特性讀子的清單，所以放第一個值時不會漏子。對照放在三個地方，都用約束（`requires` 子句），測試用 `requires` 運算式驗接不接受：登記父與 `InstallStateMachine`——父列的每個子，特性都寫這個父；用到子的型別（`StateMachine<Pause>`、`StateMachineRequest<Pause>`、`InState<Pause, …>`）——子寫的父有列它（C++ 沒辦法從父反查誰把它當父，所以這一邊在用到子的地方擋）；列在清單裡的子自己不能再有 `SubStates`（只做一層），子也不能單獨登記成一棵樹。修訂 5 寫「登記父的時候列出子」，放第一個值的函式拿不到那份清單（檢查的 blocker），改成這個形狀。
- **取走要求的時機**：第一次以外的每次套用，一開始就把父與每個子的待處理要求**一起取走、一起驗**（任一個值不在對照表就回 Err，什麼都不跑；子存不存在都驗，因為那是程式的錯）；這一次套用裡（離開、進入的 schedule 裡）新提出的要求，留到下一次。第一次套用不取走任何要求（第 3.8 節）。所以一次套用對每種狀態最多處理一個要求——子可能因為父換了而重設一次、再處理自己的要求一次（同一幀父子都有要求那一條），但不會連鎖。
- **子什麼時候記成「不存在」**：每個子的離開一跑完就記（不是全部離開完才一起記），所以後面的子的離開、父的離開與新父值的進入裡，讀那個子都是「不存在」（例：「進入主選單」裡看不到「主選單＋暫停」）。
- **一次套用的順序**：
  1. 取走父與子的要求。
  2. 父有要求：每個存在的子照**登記的順序**跑離開、每個一離開完就記成不存在 → 父的離開 → 改父的值 → 父的進入 → 在新的父值底下該存在的子，照登記順序先設成初始值、再跑進入。父換成同一個值、子設了 `KeepOnParentReenter`：那個子不離開、不重設、不進入（只對同一個值；父換到別的值時照常）。修訂 6 曾經把子的離開寫成登記的反序，那是我自行改的、和你定的「照登記的順序」不合，修訂 7 改回。
  3. 每個子照登記順序，有要求就處理：子存在 → 子的離開、改值、子的進入；子不存在 → 丟掉。
- **兩種要求**（第 3.4b 節）：`Request(值)` 照上面的規則跑離開與進入；`RequestSilent(值)`（暫名）在同一個時機換值，不跑這個狀態、也不跑跟著它出現或消失的子的離開與進入（父 silent 換到別的值：子照新的父值靜靜地出現成初始值或消失）。**父 silent 換成同一個值時：子不動**（不重設、不跑任何離開與進入；使用者 2026-11-16「照建議」）。建議的理由（卡片的）：Client 每收到一筆快照就用 silent 寫一次同一個值時，子才不會一直被悄悄重設；`KeepOnParentReenter` 只管一般的 `Request`。兩種寫進同一個待處理的格子，後寫蓋前寫（值與種類一起蓋），計數照算，套用後格子清空。用了 silent 之後，離開與進入不保證成對（例：silent 進關卡中之後，一般的要求回主選單會跑一張沒有進入過的「離開進行中」），說明頁講明。
- **第一次套用**：不取走任何要求；父進初始值、跑父的進入；初始的父值底下該存在的子，進子的初始值、跑子的進入。開局裡提出的要求（父的、子的）都留到下一次套用。
- **條件**：子不存在時，`InState<Pause, …>` 與 `NotInState<Pause, …>` 都是否（和「還沒進入」相同）。

**和 Bevy 的差別**（Bevy 的行為照 `state_set.rs:161-214`）：

| 情形 | Bevy | GYO |
|---|---|---|
| 同一幀父與子都有要求、子原本不存在 | 子直接進要求的值（跑一次進入） | 子先進初始值、再換到要求的值（你定的順序） |
| 父換成同一個值、子仍該存在 | 子保留原本的值，不跑子的離開與進入 | 默認重設成初始值（跑子的離開與進入）；`KeepOnParentReenter` 時同 Bevy |

## 7. 判定（先宣告，結果出來之後不放寬）

測試用的產品：`Flow`（主選單／關卡中，初始值主選單），它的子狀態 `Pause`（進行中／暫停，初始值進行中）與 `Inventory`（關閉／開啟，初始值關閉），兩個子都只在關卡中存在，登記順序 `Pause`、`Inventory`；另有一種互不相干的狀態 `Weather`（晴／雨，(b) 區，只用在組合的案例）。套用的 System 插在一張每幀的帶時鐘 schedule（Frame）裡；runner 用一個不是預設的名字。下面寫「各一次」「沒有跑」時，指的是案例點名的那幾張；子跟著父出現或消失時跑的子的離開與進入另外列。

**判定 1：行為。**

| 案例 | 驗什麼 |
|---|---|
| 初始的進入 | 開局放一個設定 Resource；第一次跑每幀那張：開局先跑完，「進入主選單」跑一次，裡面讀得到開局的設定、讀到的現在的值是主選單；兩個子不存在、沒有任何子的進入；第二幀不再跑 |
| 開局裡的要求留到下一次 | 開局裡要求「關卡中」：第一次套用只進主選單；第二次套用才離開主選單、進關卡中 |
| 初始之前條件為否 | 第一幀排在套用的 System 前面、帶 `InState<Flow, MainMenu>` 與 `NotInState<Flow, InLevel>` 的兩個 System 都沒有執行；排在後面的有執行 |
| 換狀態 | 要求「關卡中」：同一次套用裡「離開主選單」先、「進入關卡中」後，各一次；之後 `InState<Flow, InLevel>` 為真、`InState<Flow, MainMenu>` 為否、`NotInState<Flow, InLevel>` 為否、`NotInState<Flow, MainMenu>` 為真 |
| 跑對那一張 | 換狀態時，父跑的離開是舊值那張、進入是新值那張；父的其他值的離開與進入都沒有跑 |
| 離開時的值 | 「離開主選單」裡讀到主選單；「進入關卡中」裡讀到關卡中 |
| 換完不再換 | 換到關卡中之後，下一次套用沒有新要求：不跑任何離開與進入 |
| 一次只處理一個要求 | 「進入關卡中」裡要求「主選單」：這次套用不再換；下一次才換回主選單。「離開主選單」裡提出的要求也一樣。「進入進行中」裡要求「暫停」：這次套用不換，下一次才換 |
| 一個子的進入裡對另一個子提要求 | 進關卡中時「進入進行中」裡要求「開啟（背包）」：這次套用 `Inventory` 不換，下一次才換 |
| 第一次套用時子的要求 | 開局裡對 `Pause` 要求暫停：第一次套用進主選單、不取走這個要求；第二次套用時 `Pause` 不存在，要求被丟掉 |
| 子狀態跟著出現 | 進關卡中的那一次套用：「進入關卡中」→「進入進行中」→「進入關閉（背包）」；`InState<Pause, Running>` 為真 |
| 子進入時讀到的值 | 「進入進行中」裡讀 `Pause` 是進行中（不是不存在） |
| 子在父的進入裡還不存在 | 進關卡中時，「進入關卡中」裡讀 `Pause` 是不存在 |
| 暫停時遊戲邏輯不跑 | 關卡中、進行中時，帶 `InState<Pause, Running>` 的 System 執行；要求暫停後，套用的 System 之後的同一幀起不執行；要求進行中後又執行 |
| 子換時父不動 | 在關卡中要求暫停、再要求進行中：`Pause` 的離開與進入照跑；「離開關卡中」「進入關卡中」與 `Inventory` 的離開與進入都沒有跑 |
| 子狀態跟著消失 | 暫停中要求「主選單」：同一次套用裡依序「離開暫停」→「離開關閉（背包）」→「離開關卡中」→「進入主選單」（子照登記的順序離開）；「離開關卡中」與「進入主選單」裡讀 `Pause` 都是不存在；之後 `InState<Pause, Paused>` 與 `NotInState<Pause, Paused>` 都是否 |
| 多個子一個一個消失 | 上一案裡，「離開關閉（背包）」執行時讀 `Pause` 已經是不存在 |
| 子狀態重新出現時回到初始值 | 上一案之後再進關卡中：`Pause` 是進行中（不是上次的暫停） |
| 子狀態不存在時的要求 | 在主選單要求暫停：丟掉，不跑任何 `Pause` 的離開與進入；之後進關卡中，`Pause` 是進行中 |
| 父與子同一次都有要求 | 主選單時要求「關卡中」、同一幀也要求「暫停」：這次套用進關卡中、`Pause` 先進進行中，接著「離開進行中」「進入暫停」 |
| 兩個子同一次都有要求 | 關卡中時同一幀要求「暫停」與「開啟（背包）」：`Pause` 的離開與進入先、`Inventory` 的後 |
| 父換成同一個值（默認） | 暫停中要求「關卡中」：依序「離開暫停」「離開關閉」「離開關卡中」「進入關卡中」「進入進行中」「進入關閉」；之後 `Pause` 是進行中 |
| 父換成同一個值（保留） | `Pause` 的特性打開 `KeepOnParentReenter`：暫停中要求「關卡中」：「離開關卡中」「進入關卡中」照跑；`Pause` 不離開、不進入，仍是暫停；`Inventory`（沒打開）照默認重設。同一組型別再要求「主選單」：`Pause` 照常離開、變成不存在（保留只對同一個值） |
| 不跑離開與進入的要求 | 主選單時 `RequestSilent(關卡中)`：值換成關卡中，「離開主選單」「進入關卡中」與子的進入都沒有跑；子照新的父值存在（是初始值） |
| silent 讓子消失 | 關卡中、暫停時 `RequestSilent(主選單)`：子的離開、父的離開與進入都沒有跑；兩個子變成不存在 |
| silent 換成同一個值 | 關卡中、暫停時 `RequestSilent(關卡中)`：子不動，仍是暫停；沒有任何離開與進入 |
| 子的 silent | 關卡中時對 `Pause` `RequestSilent(暫停)`：值換成暫停，`Pause` 的離開與進入都沒有跑；主選單時對 `Pause` `RequestSilent(暫停)`：丟掉 |
| 兩個要求 | 同一次套用前對 `Flow` 寫兩次要求：後寫的生效；被蓋掉的次數是 1；只寫一次時是 0；下一次套用前再蓋一次，次數變成 2（累計）；`Request` 被 `RequestSilent` 蓋掉也算，而且套用時照後寫的那一種（不跑離開與進入）；套用之後下一個 `Request` 照常跑離開與進入 |
| 不在對照表的值 | 在關卡中、暫停時要求一個沒有登記的 `Flow` 值：回 Err，規則字串是這個 Module 的那一條；沒有任何離開（子的也沒有），現在的值沒有變。用 `RequestSilent` 提出同樣回 Err |
| 子的值不在對照表 | 主選單時要求「關卡中」、同一幀對 `Pause` 要求一個沒有登記的值：回 Err，「離開主選單」沒有跑；`Pause` 不存在也一樣驗 |
| 離開出錯 | 「離開主選單」裡的 System 回 Err：World 中斷；現在的值仍是主選單；「進入關卡中」沒有跑 |
| 進入出錯 | 「進入關卡中」裡的 System 回 Err：World 中斷；現在的值是關卡中；兩個子仍是不存在、沒有進入 |
| 子的離開出錯 | 暫停中要求主選單，「離開暫停」裡的 System 回 Err：World 中斷；`Flow` 仍是關卡中，「離開關卡中」沒有跑 |
| 子的進入出錯 | 進關卡中時「進入進行中」裡的 System 回 Err：World 中斷；`Inventory` 沒有設值、沒有進入 |
| 沒放第一個值 | 組裝的程式沒有呼叫 `InstallStateMachine`、也沒有 System 寫要求：條件回否；套用的 System 斷言，訊息有函式名（照 K0 的斷言案例的做法驗） |

| 特性對不上 | 用 `requires` 運算式驗下面這些函式與型別**接不接受**（不是驗一個獨立的布林）：登記父與 `InstallStateMachine`——父列了子、子沒寫這個父，不接受；用到子的型別（`StateMachine<Pause>`、`StateMachineRequest<Pause>`、`InState<Pause, …>`）——子寫了父、父沒列它，不接受；列在清單裡的子自己又有 `SubStates`，不接受；子單獨登記成一棵樹，不接受 |
| 寫者 | 另一個每幀的 System 用 `ResMut<StateMachine<Flow>>`：啟動時報 D-E2 |

| runner 與時鐘 | 進入／離開的 schedule 用的是登記時給的時鐘與 runner |

| (c) 區還不支援 | 用 `requires` 運算式確認：`RegisterStateMachine<Weather, Zone::C>` 不接受 |
| 不碰時間 | 掃描：`engine/state_machine` 的檔案裡沒有 include `engine/time`（引號與角括號的寫法都算）；目錄不存在或是空的算失敗。配一個自我測試，在合成的目錄上跑：一個會命中的引號寫法、一個角括號寫法、一個空目錄，都要判為違規（照 Kernel 文字守衛的做法，`tests/common/kernel/CMakeLists.txt:80-104`） |

**組合的案例**（驗的是 K0、Kernel 或產品寫法與這個 Module 接起來的行為；不算進判定 2 的檢出力）：進入裡生成的實體，排在後面的 System 同一幀看得到；同一種狀態登記兩次報 R-E2；作者另外登記套用的函式報 D-E2；兩棵樹的實際先後（`Weather` 與 `Flow` 插在同一個錨點之前、`Flow` 先登記 → `Flow` 先套用，「進入關卡中」裡對 `Weather` 提的要求同一幀生效）——固定實際的行為，不是這個 Module 承諾的規則。

## 8. Architecture Delta、Design Invariants、Replacement Criteria

### 8.1 Architecture Delta（AGENTS §3 的七項）

1. **需要它的 Feature**：啟動後進主選單、從主選單進關卡、暫停時不跑遊戲邏輯（(b) 區，這一批實作）；遊戲中的全局狀態（(c) 區，這一批只定介面）。
2. **現在的問題**：沒有狀態切換的形狀；「進入時做一次」在 K0 之前做不到乾淨的版本，每個產品會各寫一套。
3. **變動的邊界**：Engine 多一個 Module `engine/state_machine`（新目錄、CMake target、測試目錄、它的條文頁）。Kernel 的邊界不變。
4. **影響**：`engine/state_machine`、它的測試、CMake 的建置圖；說明頁、用詞表、命名守衛（第 3.13 節）。`gyo2` 上沒有產品。
5. **依賴方向**：`engine/state_machine` → `engine/kernel`。Kernel、`engine/time`、runner 都不依賴它；它也不依賴 `engine/time`。
6. **Ownership**：這個 Module 的 owner 是架構（Engine）。「現在在哪一段、什麼時候換」歸它的 Resource 與套用的 System；狀態的列舉、名字表、子的清單、「什麼時候要求換、跑不跑離開與進入」歸產品；「套用的 System 插在哪」歸產品的登記（錨點的名字來自 T3 的骨架）；「第一個值與初始值」歸組裝的程式；「暫停時時間停不停」歸作者（時間的機制是 `TimeControl`），狀態機不碰它；「從第幾個 tick 起」「淡入多久」這類資料歸遊戲；兩棵狀態樹之間的先後歸產品的插入位置。
7. **為什麼不能更小**：比它小的有兩種——只給說明頁的範本（每個產品各寫一套；Godot、Unity 走這一條）；每種狀態只有一對 schedule（第 3.9 節，代價在表裡）。

### 8.2 Design Invariants（新；要你同意。每條附守它的案例）

1. 一種狀態的現在的值只有這個 Module 改得了：型別沒有公開的建構與改值；套用的 System 把它列在寫入宣告裡，別的 System 用 `ResMut` 寫是 D-E2。守衛：「型別不給改」「寫者」。
2. 一次套用的順序：取走要求 →（子照登記的順序離開、每個一離開就記成不存在）→ 父的離開（現在的值仍是舊的）→ 改值 → 父的進入 →（子照登記順序設初始值、進入）→ 子各自處理自己的要求。守衛：「換狀態」「跑對那一張」「離開時的值」「子狀態跟著出現」「子狀態跟著消失」「兩個子同一次都有要求」「離開出錯」「進入出錯」。
3. 一次套用對每種狀態最多處理一個要求，要求在套用一開始就取走；離開或進入裡提出的要求留到下一次。子因為父換了而離開、重設、進入，不算處理子的要求。守衛：「一次只處理一個要求」「換完不再換」「父與子同一次都有要求」。
4. 第一次套用一律先進初始值（開局之後、套用的 System 第一次執行時）；開局裡提出的要求留到下一次；在那之前兩種條件都回否。守衛：「初始的進入」「開局裡的要求留到下一次」「初始之前條件為否」「指定初始值」。
5. 子只在父的指定值底下存在；不存在時兩種條件都回否、對它的要求丟掉；每次重新出現從初始值開始；父換成同一個值時默認重設，`KeepOnParentReenter` 時保留。守衛：「子狀態跟著消失」「子狀態重新出現時回到初始值」「子狀態不存在時的要求」「父換成同一個值（默認）」「父換成同一個值（保留）」。
6. `RequestSilent` 換值，但不跑這個狀態、也不跑跟著它出現或消失的子的離開與進入；其餘規則（時機、驗值、蓋寫、計數、子的存在跟著父的值）和 `Request` 相同。父 silent 換成同一個值時子不動。守衛：「不跑離開與進入的要求」「silent 讓子消失」「silent 換成同一個值」「子的 silent」「兩個要求」。
7. 同一種狀態只在一處套用。守衛：Kernel 的 R-E2（登記函式呼叫兩次）與 D-E2（作者另外登記套用的函式），在組合的案例固定；子不能另外單獨登記（「特性對不上」）。
8. 狀態機不碰時間：這個 Module 不讀寫 `TimeControl` 與任何時間的 Resource，不依賴 `engine/time`。前提：時間的型別都在 `engine/time`（時間設計:512）；T3 若把它們放到別處，守衛的掃描範圍跟著改。守衛：「不碰時間」的掃描與它的自我測試。
9. Kernel 不知道狀態機：這個 Module 只用 Kernel 的公開介面。守衛：既有的 Kernel 守衛的 include 白名單（`tests/common/kernel/kernel_guard.py:45-47`），Kernel 一 include `engine/state_machine` 就失敗。

### 8.3 Replacement Criteria（新）

符合任一條時，停下來向你提出「修還是重建」：

1. (c) 區的狀態因為這個 Module 的形狀，出現「兩端不一致而逐 tick 的比對看不到」的情形。
2. 一個點名的 Feature 需要同一種狀態在每幀與固定步兩處換。
3. 為了狀態機要在 Kernel 加型別、分支或介面（第 9 條被打破；(c) 區的獨占套用是已定的另一批，不算）。
4. Engine 的另一個 Module 需要讀狀態（例：Loading 改成綁在狀態機上），而這個 Module 的形狀接不上。
5. 作者為了繞過「一次只處理一個要求」「進入在套用處跑」「第一次一律進初始值」，在兩處以上寫了同樣的補償（例：自己再跑一次套用、自己存「上一個狀態」）。gyo2 上還沒有產品，要等產品回來才觀測得到；「兩處以上」沒有根據，是我給的。
6. 子狀態要第二層（子的子），或一個子要掛在兩個父值底下，而這個形狀接不上。
7. 事件的規則在 T4 之後仍然不讓進入／離開的 schedule 讀寫事件，而點名的 Feature 需要它。

## 10. 範圍的限界

- 這份宣告是照讀程式、Bevy 的原始碼與公開文件寫的，沒有試做。K0 還沒實作，第 5 節依賴 K0 宣告寫的介面；K0 實作時若改了介面，這裡跟著改。**修訂 5、6 送過檢查；修訂 7 照修訂 6 的檢查改完沒有再送**；修訂 0、1 都曾在修改時引入新的錯，這一份也可能有。
- T3 還沒宣告：錨點的名字、每幀那張的形狀、`TimeControl` 的實際介面、「暫停這一幀固定步跑不跑」，寫不準。
- **套用的 System 掛在固定步那張**：修訂 3 起支援（(c) 區的狀態一定掛在那裡，第 3.4b 節）。但作者若把 (b) 區的「暫停」掛在固定步，又照範例在「進入暫停」時寫 `TimeControl`，會永遠離不開暫停：暫停時固定步不跑，套用的 System 也就不跑（時間設計:189、:506）。說明頁講明；Kernel 擋不住。
- 第 7 節的判定、第 8.2 節的 Design Invariants 只寫了 (b) 區；(c) 區的先後：Kernel 的「(c) 區獨占套用」一批，之後另一批做狀態機 Module 這一側的 (c) 區；(c) 區的案例、突變與條文寫在後一批的事前宣告裡。`Change` 這個參數在 `RequestSilent` 定了之後還要不要、另一個值叫什麼，到後一批再請你判（原本的理由「Engine 守不住快照蓋進來時不跑進入」，已經由遊戲用兩種要求自己選來處理）。
