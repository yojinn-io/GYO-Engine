## 閘口 1：第 4 步，模擬又回滾的 Client（K3）要改的回滾文字

**前提：Engine 要解決的。** 權威值怎麼進回滾、確認點怎麼前進，是回滾 Module 入口的語意（R-8）。作者改不了，也不該各自補（機制不分散在各實作）。

### 1.1 用遊戲講

PvP 的 Client（K3）預測第 100 步。這時伺服器在第 96 步生成一扇門、在第 98 步刪掉一個小怪：

- 門是網路生成的，不是 Client 的步生成的。回滾到第 96 步之前時，現在的規則（存活集合整份放回）會把它刪掉，而且不會再生。
- 小怪：權威要刪掉整個實體，目前沒有入口，Client 預測出來的小怪會一直留著。
- 計分放在 Resource，伺服器的值目前進不了回滾（入口只有元件）。
- 伺服器一幀跑了第 97～99 三步，只送第 99 步的值（你已定 U4）。Client 的確認點直接從 96 跳到 99。

### 1.2 要改的文字（`rollback.zh-Hant.md`）

### 1.4 「一幀跑多步、中間的 tick 沒有值訊息」：別家怎麼做

| | 怎麼做 | 出處 |
|---|---|---|
| bevy_replicon | `ServerTick` 每個固定步加 1（預設在 `FixedPostUpdate`）。送件的 System 掛在 `PostUpdate`，條件是 `resource_changed::<ServerTick>`，**一幀只送一次**。一幀跑三步時，只送第三步的狀態 | `src/server.rs:67-73`、`:195-200` |
| lightyear | 用 replicon 的送件，所以同上。它另外把 replicon 的「送件序號」對到自己的模擬 tick：送件時把當下的模擬 tick 寫進 userdata，Client 收到時記下對應。預測的回滾只在「已完成的確認點」比，確認點就是這些送過的 tick | `crates/replication/replication/src/checkpoint.rs:1-30`；`crates/replication/prediction/src/rollback.rs:313-316`（不變式：確認點 C 對每個實體都有完整資訊，沒收到的＝上次確認的值）、`:360-372`（用 ≤ 當下的最後一個已完成確認點） |
| Unity Netcode | `NetworkTickRate` 可以低於 `SimulationTickRate`，伺服器輪流送，快照不是每個 tick 都有；預測從最新快照的 tick 重跑 | 偵察原文：`D~/client-server-worlds.md:85-86`、`D~/intro-to-prediction.md:113-115` |

**和我們的相似點**：網路 PR-1 已經是「每幀送一次、送最後一個 tick」（U4），和 replicon 相同。確認點只在送了值的 tick，和 lightyear 的已完成確認點相同。

**要改的**：只有 R-8 的「前提」那一句（改後的 B），以及限界補一句「作者覆寫判斷時看不到中間 tick」。回滾 Module 的程式不用為缺 tick 改：官方策略本來就只在 C 比，用的是「C 當時或之前最後的值」。

## 閘口 2：第 5 步，頻寬預算的典型情境與候選（量之前先定）

**前提：Engine 要解決的機制，數字是驗收用的。** 送什麼、送多少（相關性、元件範圍、優先度）是網路 Module 的機制，作者改不了；作者只給可見性的規則。預算的數字用來驗收這個機制，取點名產品的典型情境。各產品要自己的上限時，是產品的設定，不是這裡的事。

### 2.1 典型情境（**要你確認**；來源多半是研究卡整理的，不是你的話）

| 項 | 值 | 來源 |
|---|---|---|
| 玩家 | 8 | 你說 4 人（`-budget-scale-depth`）；研究卡：之後可能 8 人（`-vision-scale`，master `entity-requirements.md`，11-01） |
| Match 上的實體 | 約 400（AI 20、Boss 1、物品 200、門 50，其餘約 129） | 研究卡（同上） |
| 地圖 | 500 m × 500 m，地面與地下兩層 | 你（`-map-500-two-layers`） |
| 可見範圍 | 半徑 100 m，只看同一層 | 研究卡（視距 100 m）；分層是本卡的推法 |
| 一個 Client 看得到的實體 | **約 50** | 本卡推的。每層約 200 個；半徑 100 m 的圓佔一層面積的 12.6%，均勻分佈約 25 個；玩家扎堆，取兩倍 |
| 每 tick 會變的（看得到的裡面） | **約 14** | 本卡推的。玩家 8 個都在附近，加看得到的 AI 約 5 個、Boss 1 個；物品、門平常不變（變的時候走事件） |
| 局部密集（Boss 房、撤離點） | 看得到 50 個，全部每 tick 都變 | 研究卡提到的「局部密集處」 |

**推出來的大小**：每個實體的值約 23 bytes（step3c 量的：值 8 bytes＋編號與欄位標頭 15 bytes），每則訊息另加標頭約 60 bytes。

| 情境 | 每 tick 每 Client | 64 Hz 換算 |
|---|---|---|
| 典型 | 14 × 23 ＋ 60 ≈ 380 B | 約 195 kbps |
| 局部密集 | 50 × 23 ＋ 60 ≈ 1 210 B | 約 620 kbps |
| 參考：G-12（沒有相關性、400 個全變） | 9 743 B | 約 5.0 Mbps |

### 2.2 預算的候選（判定：典型情境的平均 ≤ 預算）

| 候選 | 每 Client 下行 | 推法 | 局部密集時 |
|---|---|---|---|
| (a) | ≤ 256 kbps | 典型 × 約 1.3 的餘量 | 超過，只記錄 |
| (b) | ≤ 512 kbps | 接近 lightyear 預設 token bucket 56 KB/s（約 450 kbps，預設不開，`crates/transport/transport/src/packet/priority_manager.rs:31-32`） | 超過，只記錄 |
| (c) | ≤ 1 Mbps | 局部密集 × 約 1.6 也放得進 | 放得進 |
| (d) | 你另給 | — | — |

**建議 (b)**：典型情境有兩倍以上的餘量；局部密集時靠優先度（第 5 步）分到後面的 tick。數字有參考實作的系譜可以對照。

### 2.3 判定怎麼量（先宣告；結果出來後不放寬）

- **情境產生**：用固定的種子，把 400 個實體放進 500 × 500 × 2 層。8 個玩家在同一層扎堆移動，AI 巡邏，Boss 在一個房間；可見性規則是「同層、半徑 100 m」。
- **量什麼**：確定的位元組數（不靠計時）：MemoryLink 不掉包，2 000 tick，每 Client 每 tick 的下行位元組。
- **判定**：
  - 8 個 Client 各自的平均都 ≤ 選定的預算；
  - 兩次執行逐位元組相同。
  - 最大值、局部密集的情境只記錄。
- **限界**：情境是合成的，沒有實際玩家的移動資料；之後有產品時要換成實際的情境再量（AGENTS §2）。
