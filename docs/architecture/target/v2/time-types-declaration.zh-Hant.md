## 1. 這一批做什麼

在 `engine/time` 加上純資料的型別與純算術，全部不碰 Kernel、不讀時間基準：

| 東西 | 是什麼 |
|---|---|
| `RealTime` | 真實時間：這一輪取樣的時間點、和上一輪的差、累計。附一個更新它的純函式 |
| `VirtualTime` | 可暫停、可縮放的時間：這一輪的量、累計、這一輪乘上去的倍率、這一輪有沒有暫停、累計扣掉的量 |
| `FixedTime` | 固定步：步長、離上一個固定步過了多久（內插用）。**沒有累計，也沒有 tick**（設計第 3.1 節） |
| 通用的時間 `ActiveTime` | 這一輪的量與累計。平常等於 `VirtualTime` 的值，固定步裡是固定步的值 |
| `TimeControl` | 想要的暫停與倍率（產品寫它，時間的 System 下一次執行時套用） |
| `TickAccumulator` | 累加器：加進一段時間，回傳這一輪跑幾步，留下不足一步的餘數。整數奈秒，不記 tick |
| `AdvanceVirtual(…)` | 一個純函式：給這一輪的真實經過時間、`TimeControl`、上限、累加器現在的餘數，算出 `VirtualTime` 這一輪該前進多少、扣掉多少 |

**需要它的 Feature 與 Product**（AGENTS §2，設計第 1 節點名的）：固定步（①PvP、②單機）、暫停與慢動作（②單機、③工具的預覽）、UI 讀真實時間（②③）。

**為什麼是基盤**：每個讀時間的 System 都會照這些型別的欄位寫。

**這一批不做的**（後面的批次）：把它們登記成 World 的 Resource；時間的 System 與驅動固定步的 System；進出固定步時換通用的時間的值；runner；取樣；「追不上時記一筆診斷」。這一批做完，World 裡還沒有時間。

## 2. 行為

### 2.1 已定的（設計第 0 節、第 3.1 節、第 4.3 節）

1. **整數奈秒**；倍率是浮點數，只在算「這一輪前進多少」時乘一次（取整數的方式見第 3 節第 3 條）。
2. **累加器**（設計第 4.3 節的介面）：
   - `Add(量, 上限)`：把量加進餘數，取走所有的整步，回傳步數。回傳之後餘數一定不足一步。步數超過上限是斷言（正常情況下 `AdvanceVirtual` 已經先扣掉了，這條斷言是它沒有被正確使用時的保險）。
   - `Overstep()`：餘數。`UntilNextStep()`：步長減餘數。`Reset()`：餘數歸零，回傳被清掉的量。
   - 它不丟時間，也不記 tick。tick 只在 World。
3. **追不上時**（你定的：超過上限的整步從可縮放的時間扣掉，丟了多少有記錄）：`AdvanceVirtual` 先算「把這一輪的量加進餘數之後會有幾個整步」；超過上限 N 的那幾個**整步**從這一輪的量扣掉，加進 `discarded`。扣的是整步，所以餘數和不扣時相同。
4. **暫停**：這一輪的量是 0，累加器不前進。
5. **`VirtualTime` 上的倍率是這一輪乘上去的那個值**（來自 `TimeControl`），不是想要的值，也不是被上限扣過之後的有效值；被扣掉多少看 `discarded`。
6. **`RealTime`** 第一輪的差是 0；不受暫停、倍率、上限影響。

### 2.2 從上面推出來的（不是新的決定，寫出來是因為可以測）

- 取消暫停後第一輪的量＝那一輪的真實經過時間×倍率，再過上限。暫停期間如果 runner 很久沒有跑（視窗最小化、系統休眠），擋住那一大段時間的是**上限**，不是暫停。
- 有固定步時，`VirtualTime` 這一輪的量＝這一輪的步數×步長＋餘數的變化。前提是驅動固定步的 System 每一輪都把這個量完整地 `Add` 進去；Loading 期間或它被跳過時不成立，那是 T3 的事。

## 3. 要你定的（四條，第 1 條已定）與要你知道的（五條）

### 要你定的

1. **【已定：`ActiveTime`，使用者 2026-11-16，`v8-arch-gyo2-active-time-name`】通用的時間叫什麼。** 使用者對分支會話的提案 `ActiveTime` 回「可以。一併記錄到文檔中。」命名對照的規範用 v2 那一份（[rebuild-naming.zh-Hant.md](rebuild-naming.zh-Hant.md)）。
   - 比過的：`CurrentTime`（初稿；和 Kernel 的 `CurrentTick` 成對會誤導——`CurrentTick` 由 Kernel 依正在跑的 schedule 給值、(c) 區讀得到；通用的時間是 Resource，值靠驅動固定步的 System 切換、(c) 區讀不到）、`ScheduleTime`、`CommonTime`、`StepTime`（`Step` 在 Kernel 已指執行計畫的一步）。不能叫 `Time`（和 `GYO::Time` 這個 Module 撞名）。
   - 使用者沒有另外說理由。分支會話照規範給的理由（不是使用者的話）：形狀是「限定詞＋Time」，和 `RealTime`、`VirtualTime`、`FixedTime` 並排（N19）；`Current` 與 `Schedule` 是 Kernel 的概念標籤，而這個值不是 Kernel 給的（N5）；`ActiveTime` 的限定詞說的是「正在作用的那一種」。
2. **沒有固定步的 World，一輪的量要不要設上限。** 你定的「扣整步」講的是有固定步的情形。沒有固定步時：
   - 設上限（Bevy 的做法，預設 250 ms）：超過的部分扣掉，記進 `discarded`。卡住之後不會一輪跳一大段。
   - 不設：卡住多久就前進多久。
   
   我建議設，並且記進 `discarded`（和有固定步時一致：丟了多少查得到）。兩個上限不會同時作用：有固定步只扣整步，沒有固定步只用時間長度的上限。
3. **乘完倍率怎麼取整數。**
   - 四捨五入：每一輪最多差半奈秒，但會累積（極端的例子：每輪 1 奈秒、倍率 0.5，每輪都被進位成 1 奈秒，變成想要的兩倍）。
   - 無條件捨去：同樣會累積，方向固定是變慢。
   - 把不到 1 奈秒的部分留到下一輪：累計的量和「真實時間×倍率」永遠差不到 1 奈秒。多一個欄位。
   
   我建議第三個。
4. **步長怎麼表示。** 60 Hz 的一步是 16,666,666.67 奈秒，不是整數。
   - 整數奈秒（設計第 3.1 節與 PvP 的 `FixedStep{stepNs}` 現在的寫法）：取 16,666,667 就是每秒 59.9999988 步，一小時比真正的 60 Hz 少跑約 0.26 步。Match 與 Client 用同一個整數，彼此一致；差的只是對牆上時鐘的漂移。
   - 頻率（每秒幾步）加上進位：累加時用「奈秒×頻率」當單位，滿十億就是一步。整數、不漂移。代價是「一步多長」不再是整數奈秒，`FixedTime` 給作者的步長要另外表示（例如分子與分母，或取整數的近似值加一個精確的版本）；PvP 的 `FixedStep` 也要照改。
   
   這一條碰到 PvP 的契約（`stepNs`），我沒有把握，兩個選項都做得出來。不決定的話照設計現在的寫法（整數奈秒）做，並在文件寫明漂移的量。

### 要你知道的

5. **我對設計做的調整（共四處，請你確認）**：
   - 扣整步的算術從「時間的 System」抽成 `engine/time` 的純函式 `AdvanceVirtual`。理由：這條規則可以不經 Kernel 單獨測；Bevy 的截斷也是放在時間型別自己的函式裡（`Time<Virtual>` 的 `advance_with_raw_delta`）。核准的話，設計第 547、552 行「扣整步是時間的 System 的事」要跟著改寫。
   - `FixedTime` 這個 Resource 裡面裝著累加器，作者經它的函式讀步長與餘數。理由：獨占的 System 不能有自己的狀態，累加的狀態一定要在 Resource 裡；放兩份就有兩個來源。
   - `Add` 多一個「上限」的參數（設計只寫 `Add(delta)`），用來做設計第 4.3 節說的那條斷言。
   - `Reset()` 回傳被清掉的餘數。這個量要不要記進 `discarded`，由呼叫它的 System（T3）決定；照你說的「丟了多少有記錄」，我傾向要記。
6. **上限的預設值**：固定步一輪最多 5 步（舊的預設）。Bevy 沒有步數的上限，它靠 250 ms 的時間上限間接限制。兩個都是組裝時可以給的設定。
7. **通用的時間在固定步裡的「累計」從哪來，這一批不定。** `FixedTime` 不放累計（否則回滾時 tick 被還原、它不會，兩者對不上）。固定步裡的累計只能是「tick×步長」，由誰算、怎麼寫進通用的時間是 T3 的事。
8. **和舊的 `FixedTickRuntime` 的關係，初稿說得太滿。** 能保證的是：對同一個整數步長、同一串整數輸入，哪幾輪跑幾步、餘數、扣掉的量，和舊的邏輯相同。舊版用 `double` 秒，步長是 1/60 秒；新版步長取成整數奈秒之後，格點會慢慢和舊版錯開（見第 4 條）。
9. **放進 World 之後的兩件事，留給 T3**：Kernel 的存取驗證與摘要是照 Resource 的原始位元組比的，所以這些型別要沒有 padding、沒有指標；`RealTime` 的時間點每次都不同，摘要要怎麼排除它現在沒有機制。

## 6. Architecture Delta

設計第 8 節已經列了七項。這一批的差分：

- **邊界**：`engine/time` 原本只有時間基準、等待器、統計；之後多了「時間的型別與算術」。它仍然是只靠作業系統與 `GYO::Base` 的葉子。
- **依賴方向、Ownership**：不變。型別屬於 `engine/time`；World 裡的值由之後的 System 寫（T3）。
- **為什麼不能更小**：只做累加器、不做型別的話，T3 會自己定一套欄位；型別就是這一批要先定的契約。
- **有沒有在替舊的形狀找位置**（架構 README 的檢查）：累加器是你指定帶過來的（改名、改成整數、拿掉 tick 與自己丟步）；介面 `Add` 回傳步數是舊的形狀，Bevy 的做法是一次取走一步（`expend`）。兩者算出來的結果相同；我照設計第 4.3 節用舊的形狀，因為取走之後餘數一定不足一步，內插與 `UntilNextStep` 不會讀到中間狀態。5 步的預設上限也是舊的；Bevy 沒有步數的上限（第 3 節第 6 條）。比過但沒採的：不另外定義 `TickAccumulator`、讓 `FixedTime` 自己就是累加器——名字是你指定要留的，而且算術和 Resource 的欄位分開，T3 以外的地方（測試、工具）也能用。

**Design Invariants**（實作時用英文加進 `docs/architecture/time.md`，附守衛）：

1. 累加器只做整數的算術：不讀時間基準、不記 tick、不丟時間。從上一次 `Reset` 起，加進去的總量恆等於步數乘步長加上餘數；`Add` 回傳之後餘數不足一步。守衛：「不丟時間」「沒有 tick」「累加」。
2. 超過上限的量只在 `AdvanceVirtual` 一處扣；有固定步時扣的一定是整步；扣掉的一定累計進 `discarded`。守衛：「扣整步」「步數不超過上限」。（「`VirtualTime` 的量＝步數×步長＋餘數的變化」是設計放在 runner 那一批的 DI 5，它還需要 System 那一側的前提；這一批的「量與步數的關係」只驗算術這一半。）
3. 這些型別不引用 Kernel。守衛：測試只連 `GYO::Time` 與 `GYO::Base` 而能編譯。

**Replacement Criteria**：時間的 System（T3）要正確，必須知道累加器內部的狀態（而不是經它的函式）；或通用的時間需要第三種來源（不是可縮放的、也不是固定步的）。碰到就停下來重看型別的切法。
