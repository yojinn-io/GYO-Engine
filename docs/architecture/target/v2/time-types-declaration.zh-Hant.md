## 1. 這一批做什麼

在 `engine/time` 加上純資料的型別與純算術，全部不碰 Kernel、不讀時間基準：

| 東西 | 是什麼 |
|---|---|
| `RealTime` | 真實時間：這一輪取樣的時間點、和上一輪的差、累計。附一個更新它的純函式 |
| `VirtualTime` | 可暫停、可縮放的時間：這一輪的量、累計、這一輪乘上去的倍率、這一輪有沒有暫停、累計扣掉的量 |
| `FixedTime` | 固定步：步長、離上一個固定步過了多久（內插用）。**沒有累計，也沒有 tick**（設計第 3.1 節） |
| 通用的時間 `ActiveTime` | 這一輪的量與累計。平常等於 `VirtualTime` 的值，固定步裡是固定步的值 |
| `TimeControl` | 想要的暫停與倍率（產品寫它，時間的 System 下一次執行時套用） |
| `TickAccumulator` | 累加器：加進一段時間，回傳這一輪跑幾步，留下不足一步的餘數。整數奈秒，不記 tick |
| `AdvanceVirtual(…)` | 一個純函式：給這一輪的真實經過時間、`TimeControl`、上限、累加器現在的餘數，算出 `VirtualTime` 這一輪該前進多少、扣掉多少 |

**需要它的 Feature 與 Product**（AGENTS §2，設計第 1 節點名的）：固定步（①PvP、②單機）、暫停與慢動作（②單機、③工具的預覽）、UI 讀真實時間（②③）。

**為什麼是基盤**：每個讀時間的 System 都會照這些型別的欄位寫。

**這一批不做的**（後面的批次）：把它們登記成 World 的 Resource；時間的 System 與驅動固定步的 System；進出固定步時換通用的時間的值；runner；取樣；「追不上時記一筆診斷」。這一批做完，World 裡還沒有時間。

## 2. 行為

### 2.1 已定的（設計第 0 節、第 3.1 節、第 4.3 節）

1. **整數奈秒**；倍率是浮點數，只在算「這一輪前進多少」時乘一次。乘完不到 1 奈秒的零頭不丟、不進位，留到下一輪（多一個欄位存它）；累計的量和「真實時間×倍率」永遠差不到 1 奈秒（`v8-arch-gyo2-t1-three-items`）。
2. **累加器**（設計第 4.3 節的介面）：
   - `Add(量, 上限)`：把量加進餘數，取走所有的整步，回傳步數。回傳之後餘數一定不足一步。步數超過上限是斷言（正常情況下 `AdvanceVirtual` 已經先扣掉了，這條斷言是它沒有被正確使用時的保險）。
   - `Overstep()`：餘數。`UntilNextStep()`：步長減餘數。`Reset()`：餘數歸零，回傳被清掉的量。
   - 它不丟時間，也不記 tick。tick 只在 World。（**2026-11-17 改**：時鐘與 tick 移出 Kernel、到時間的 Module，作者可選，`v8-arch-gyo2-clock-out-of-kernel`；tick 在時間 Module 裡存在哪裡、和回滾怎麼一起還原，待時間 Module 那一批重新定）。
3. **追不上時**（你定的：超過上限的整步從可縮放的時間扣掉，丟了多少有記錄）：`AdvanceVirtual` 先算「把這一輪的量加進餘數之後會有幾個整步」；超過上限 N 的那幾個**整步**從這一輪的量扣掉，加進 `discarded`。扣的是整步，所以餘數和不扣時相同。
4. **暫停**：這一輪的量是 0，累加器不前進。
5. **`VirtualTime` 上的倍率是這一輪乘上去的那個值**（來自 `TimeControl`），不是想要的值，也不是被上限扣過之後的有效值；被扣掉多少看 `discarded`。
6. **`RealTime`** 第一輪的差是 0；不受暫停、倍率、上限影響。
7. **沒有固定步的 World**：一輪的量有時間長度的上限，預設 250 毫秒，組裝的人可以改；超過的部分扣掉，記進 `discarded`。兩個上限不同時作用：有固定步的只扣整步，沒有固定步的只用時間長度的上限（`v8-arch-gyo2-t1-three-items`）。
8. **步長的設定**：內部存成整數奈秒。組裝的人可以用頻率設定，也可以直接給時間長度；用頻率時當場換算成整數奈秒存起來，之後只用那個整數。**預設是 64 Hz**（一步 15,625,000 奈秒，除得盡，對牆上時鐘不漂移）。用除不盡的頻率（例如 60 Hz → 16,666,667 奈秒）可以，說明頁寫明那時的漂移量（60 Hz 時每秒 59.9999988 步，一小時少約 0.26 步）。不做「頻率加進位」（`v8-arch-gyo2-t1-three-items`）。

### 2.2 從上面推出來的（不是新的決定，寫出來是因為可以測）

- 取消暫停後第一輪的量＝那一輪的真實經過時間×倍率，再過上限。暫停期間如果 runner 很久沒有跑（視窗最小化、系統休眠），擋住那一大段時間的是**上限**，不是暫停。
- 有固定步時，`VirtualTime` 這一輪的量＝這一輪的步數×步長＋餘數的變化。前提是驅動固定步的 System 每一輪都把這個量完整地 `Add` 進去；Loading 期間或它被跳過時不成立，那是 T3 的事。

## 3. 已定的四條、還要你看的、要你知道的

### 已定的四條（2026-11-16）

1. **【已定：`ActiveTime`，使用者 2026-11-16，`v8-arch-gyo2-active-time-name`】通用的時間叫什麼。** 使用者對分支會話的提案 `ActiveTime` 回「可以。一併記錄到文檔中。」命名對照的規範用 v2 那一份（[rebuild-naming.zh-Hant.md](rebuild-naming.zh-Hant.md)）。
   - 比過的：`CurrentTime`（初稿；和 Kernel 的 `CurrentTick` 成對會誤導——`CurrentTick` 由 Kernel 依正在跑的 schedule 給值、(c) 區讀得到；通用的時間是 Resource，值靠驅動固定步的 System 切換、(c) 區讀不到）、`ScheduleTime`、`CommonTime`、`StepTime`（`Step` 在 Kernel 已指執行計畫的一步）。不能叫 `Time`（和 `GYO::Time` 這個 Module 撞名）。
   - 使用者沒有另外說理由。分支會話照規範給的理由（不是使用者的話）：形狀是「限定詞＋Time」，和 `RealTime`、`VirtualTime`、`FixedTime` 並排（N19）；`Current` 與 `Schedule` 是 Kernel 的概念標籤，而這個值不是 Kernel 給的（N5）；`ActiveTime` 的限定詞說的是「正在作用的那一種」。
2. **【已定：設上限，`v8-arch-gyo2-t1-three-items`】沒有固定步的 World，一輪的量要不要設上限。** 使用者：「照建議」。設上限，預設 250 毫秒，組裝的人可以改；超過的部分扣掉並記進 `discarded`。比過的：設上限（Bevy 的做法，預設 250 ms）／不設（卡住多久就前進多久，防呆落在每個讀時間的 System）。使用者沒有另外說理由。
3. **【已定：零頭留到下一輪，`v8-arch-gyo2-t1-three-items`】乘完倍率怎麼取整數。** 使用者：「照建議」。比過的：四捨五入（誤差累積、方向不固定；極端的例子：每輪 1 奈秒、倍率 0.5，每輪都被進位成 1 奈秒，變成想要的兩倍）／無條件捨去（誤差累積、固定變慢）／零頭留到下一輪。使用者沒有另外說理由。
4. **【已定：整數奈秒、可以用頻率設定、預設 64 Hz，`v8-arch-gyo2-t1-three-items`】步長怎麼表示。** 使用者的話（依序）：「之前的PvP的做法呢？」「另外參考一下Bevy的網絡Plugin」「改64Hz。並且提供作者寫頻率。我認為可以參考Bevy的做法。」「預設值是64，pvp也改成64」。
   - 定下的：照 Bevy——步長在內部存成整數奈秒，作者可以用頻率或時間長度設定，Engine 當場換算；不做「頻率加進位」。Engine 固定步的預設是 64 Hz。PvP 也改成 64 Hz，那是產品移植時的事，這一批不做，記成方向。
   - 用除不盡的頻率仍然可以、說明頁寫明漂移量——這一點是分支會話複述裡的，使用者沒有逐字確認。
   - 比過的：整數奈秒、作者可以用頻率設定（Bevy、lightyear、bevy_replicon 的做法；也是規格 G-6 的設計）／頻率加整數的進位（不漂移，但「一步多長」不是整數、沒有參考實作）。理由（使用者的）：「我認為可以參考Bevy的做法」。
   - **更正修訂 1 的一句**：我寫「PvP 的 `FixedStep{stepNs}` 現在的寫法」，不準。分支會話讀了程式：舊 PvP（master）實際跑的是頻率加浮點——`AuthorityTickRate = 60`；Match 把 `tick_rate` 放進歡迎訊息、Client 比對不合就拒絕，協議上沒有「一步幾奈秒」的欄位；累加器 `FixedTickRuntime` 把一步記成 `1.0 / tickRate` 秒的浮點數，帶一個步長十億分之一的容許值，最多補跑 5 步。「整數奈秒」來自規格 G-6，是設計、沒有程式在跑。
   - 參考實作（分支會話讀了原始碼）：Bevy `bevy_time/src/fixed.rs`——步長與餘數都是時間長度，`from_duration`／`from_seconds`／`from_hz` 三種寫法，預設 `Duration::from_micros(15625)`（64 Hz）；bevy_replicon 自己不管步長；lightyear 的設定欄位是 `tick_duration`，範例用 64 Hz。

### 還要你看的（我補的細節，沒有經你判）

4b. **用頻率設定時，頻率是整數還是小數。** 你定的是「提供作者寫頻率」。
   - 整數（每秒幾步）：換算用整數的算術，四捨五入到奈秒，沒有浮點；要 59.94 這種頻率就直接給時間長度。系譜：新導出的。
   - 小數（Bevy 的 `from_hz` 收浮點）：什麼頻率都寫得出來；換算過一次浮點的除法。系譜：Bevy。
   兩者存進去的都是整數奈秒，之後的行為相同；Match 與 Client 比對的是那個整數。需要它的 Feature：固定步（①PvP、②單機）。我的建議：整數。這只是建議。

### 要你知道的

5. **我對設計做的調整（共四處，請你確認）**：
   - 扣整步的算術從「時間的 System」抽成 `engine/time` 的純函式 `AdvanceVirtual`。理由：這條規則可以不經 Kernel 單獨測；Bevy 的截斷也是放在時間型別自己的函式裡（`Time<Virtual>` 的 `advance_with_raw_delta`）。核准的話，設計第 547、552 行「扣整步是時間的 System 的事」要跟著改寫。
   - `FixedTime` 這個 Resource 裡面裝著累加器，作者經它的函式讀步長與餘數。理由：獨占的 System 不能有自己的狀態，累加的狀態一定要在 Resource 裡；放兩份就有兩個來源。
   - `Add` 多一個「上限」的參數（設計只寫 `Add(delta)`），用來做設計第 4.3 節說的那條斷言。
   - `Reset()` 回傳被清掉的餘數。這個量要不要記進 `discarded`，由呼叫它的 System（T3）決定；照你說的「丟了多少有記錄」，我傾向要記。
6. **上限的預設值**：有固定步時一輪最多 5 步（舊的預設）；沒有固定步時一輪最多 250 毫秒（已定，第 2 條）。Bevy 沒有步數的上限，它靠 250 ms 的時間上限間接限制。兩個都是組裝時可以給的設定。
7. **通用的時間在固定步裡的「累計」從哪來，這一批不定。** `FixedTime` 不放累計（否則回滾時 tick 被還原、它不會，兩者對不上）。固定步裡的累計只能是「tick×步長」，由誰算、怎麼寫進通用的時間是 T3 的事。
8. **和舊的 `FixedTickRuntime` 的關係，初稿說得太滿。** 能保證的是：對同一個整數步長、同一串整數輸入，哪幾輪跑幾步、餘數、扣掉的量，和舊的邏輯相同。舊版用 `double` 秒，步長是 1/60 秒；新版的預設是 64 Hz（除得盡），舊 PvP 的 60 Hz 取成整數奈秒之後格點會慢慢和舊版錯開——PvP 移植時改成 64 Hz（第 4 條），舊的驗收紀錄不能直接比。
9. **放進 World 之後的兩件事，留給 T3**：Kernel 的存取驗證與摘要是照 Resource 的原始位元組比的，所以這些型別要沒有 padding、沒有指標；`RealTime` 的時間點每次都不同，摘要要怎麼排除它現在沒有機制。

## 5. 判定（先宣告，結果出來之後不放寬）

下面的「餘數」都是 `Add` 回傳之後量的。

**判定 1：行為。** `TimeTypesTests.cpp` 全部通過：

| 案例 | 驗什麼 |
|---|---|
| 累加 | 加 2.3 步的量：`Add` 回 2；餘數是 0.3 步；`UntilNextStep` 是 0.7 步 |
| 餘數跨輪保留 | 每輪加 0.4 步，連續 10 輪：一共跑 4 步，哪幾輪跑的和手算一致 |
| 不丟時間 | 任意序列（固定種子）：從上一次 `Reset` 起，加進去的總量＝步數×步長＋餘數。`Reset` 回傳被清掉的量 |
| 沒有 tick | 編譯期檢查：累加器與 `FixedTime` 上沒有 tick 的成員 |
| 扣整步 | 上限 5、上一輪的餘數 0.6 步、這一輪 7.7 步的量（合計 8.3 步）：`AdvanceVirtual` 扣掉 3 個整步，`discarded` 從原本已有的值再增加 3 步的量，之後 `Add` 回 5，餘數是 0.3 步 |
| 步數不超過上限 | 隨機的序列（固定種子，含卡住）：經 `AdvanceVirtual` 之後每一輪 `Add` 回傳的步數都不超過上限 |
| 上限的斷言 | 不經 `AdvanceVirtual`、直接 `Add` 超過上限的量：斷言 |
| 量與步數的關係 | 同一個隨機序列：每一輪「`VirtualTime` 的量」＝「步數×步長＋餘數的變化」；`VirtualTime` 的累計加的是扣之後的量 |
| 舊測試的期待值 | 把 `master` 的 `tests/common/core/runtime/FixedTickRuntimeTests.cpp` 裡手算的案例搬過來（步長改成它們用的頻率對應的整數奈秒；因為取整數而對不上的案例列出來並說明，不默默改期待值） |
| 和舊版逐點比 | 步長 15,625,000 奈秒（1/64 秒，`double` 可以精確表示）：同一串輸入（含卡住 2 秒、連續小步、剛好整步）餵給新的組合與**逐字複製進測試的舊 `double` 版**，每一輪的步數、餘數、扣掉的量相同 |
| 暫停 | 暫停的每一輪量是 0、累加器不前進；取消後第一輪的量＝那一輪的真實經過時間×倍率 |
| 暫停中隔很久才有一輪 | 取消暫停的那一輪真實經過時間是 10 秒：量被上限擋住，多的記進 `discarded` |
| 倍率 | 0.5 倍、2 倍、0 倍；`VirtualTime` 上記的是乘上去的倍率；2 倍而且超過上限時，多的記進 `discarded` |
| 零頭留到下一輪 | 每輪 1 奈秒、倍率 0.5：兩輪前進 1 奈秒，不是每輪 1 奈秒也不是永遠 0。隨機的序列（固定種子，倍率中途改變、含暫停）：每一輪之後，累計的量和「到目前為止每輪真實經過時間×當輪倍率的總和」差不到 1 奈秒。暫停與改倍率都不清掉零頭 |
| 沒有固定步 | 預設的上限是 250 ms：這一輪 400 ms，量是 250 ms，`discarded` 增加 150 ms。把上限改成 100 ms：量是 100 ms。有固定步時時間長度的上限不作用（這一輪 400 ms、步數上限夠大：不扣） |
| 步長的設定 | 預設是 64 Hz：15,625,000 奈秒。用頻率 60 設定：16,666,667 奈秒（四捨五入）。用時間長度設定：原樣。頻率是 0：斷言 |
| `RealTime` | 第一輪的差是 0；之後是兩次取樣的差；不受暫停、倍率、上限影響 |
| 前置條件 | 負的量、步長是 0、上限是 0、倍率是負數或不是有限的數、倍率大到乘出來會超過整數的範圍、加進去會溢位：斷言 |

**判定 2：檢出力。** 突變清單在實作前由實作者（Opus）定案，交別的模型（Fable）檢查。至少包含：`Add` 把餘數清掉；`UntilNextStep` 回傳餘數；扣的不是整步（改成夾總量）；扣整步時不看上一輪的餘數；扣了卻不記 `discarded`；`discarded` 每輪覆寫而不是累計；累計加的是扣之前的量；`Add` 不斷言上限；`Reset` 沒有歸零；暫停時仍然前進；取消暫停後把暫停期間的量補回來；倍率乘兩次；零頭每輪丟掉（改成捨去）；零頭每輪進位；暫停時把零頭清掉；`VirtualTime` 上的倍率記成別的值；沒有固定步時不設上限；時間長度的上限預設不是 250 ms；有固定步時時間長度的上限也作用；預設的步長不是 64 Hz；頻率換算用捨去而不是四捨五入；`RealTime` 跟著暫停。只有預期的那個案例失敗才算抓到；建置失敗不算。

**判定 3：沒有回歸。** 本機完整 ctest 全過；三平台 L1 全過；`GYO::Time` 的連結檢查照過。既有測試一個判定都不改。

## 6. Architecture Delta

設計第 8 節已經列了七項。這一批的差分：

- **邊界**：`engine/time` 原本只有時間基準、等待器、統計；之後多了「時間的型別與算術」。它仍然是只靠作業系統與 `GYO::Base` 的葉子。
- **依賴方向、Ownership**：不變。型別屬於 `engine/time`；World 裡的值由之後的 System 寫（T3）。
- **為什麼不能更小**：只做累加器、不做型別的話，T3 會自己定一套欄位；型別就是這一批要先定的契約。
- **有沒有在替舊的形狀找位置**（架構 README 的檢查）：累加器是你指定帶過來的（改名、改成整數、拿掉 tick 與自己丟步）；介面 `Add` 回傳步數是舊的形狀，Bevy 的做法是一次取走一步（`expend`）。兩者算出來的結果相同；我照設計第 4.3 節用舊的形狀，因為取走之後餘數一定不足一步，內插與 `UntilNextStep` 不會讀到中間狀態。5 步的預設上限也是舊的；Bevy 沒有步數的上限（第 3 節第 6 條）。比過但沒採的：不另外定義 `TickAccumulator`、讓 `FixedTime` 自己就是累加器——名字是你指定要留的，而且算術和 Resource 的欄位分開，T3 以外的地方（測試、工具）也能用。

**Design Invariants**（實作時用英文加進 `docs/architecture/time.md`，附守衛）：

1. 累加器只做整數的算術：不讀時間基準、不記 tick、不丟時間。從上一次 `Reset` 起，加進去的總量恆等於步數乘步長加上餘數；`Add` 回傳之後餘數不足一步。守衛：「不丟時間」「沒有 tick」「累加」。
2. 超過上限的量只在 `AdvanceVirtual` 一處扣；有固定步時扣的一定是整步；扣掉的一定累計進 `discarded`。守衛：「扣整步」「步數不超過上限」。（「`VirtualTime` 的量＝步數×步長＋餘數的變化」是設計放在 runner 那一批的 DI 5，它還需要 System 那一側的前提；這一批的「量與步數的關係」只驗算術這一半。）
3. 這些型別不引用 Kernel。守衛：測試只連 `GYO::Time` 與 `GYO::Base` 而能編譯。

**Replacement Criteria**：時間的 System（T3）要正確，必須知道累加器內部的狀態（而不是經它的函式）；或通用的時間需要第三種來源（不是可縮放的、也不是固定步的）。碰到就停下來重看型別的切法。

## 8. 範圍的限界

- 這份宣告是照設計與舊的 `FixedTickRuntime`（`master` 的 `engine/runtime/include/engine/runtime/FixedTickRuntime.hpp`）寫的，沒有試做。
- 修訂 1、修訂 2 都沒有再送檢查。
- 零頭那個欄位的確切型別（浮點的零頭）實作時定；倍率是浮點數，同一串輸入在三個平台算出同樣的結果靠的是 IEEE 的乘法，判定 1 的案例在 L1 三平台都跑。
- Bevy 的做法：截斷那一部分只根據偵察報告（`build/evidence/gyo2-time-v2/scout-c-bevy-eight-items.md`）；固定步的步長那一部分分支會話讀了原始碼（`bevy_time/src/fixed.rs`）。
- PvP 改成 64 Hz 是移植時的事，會動到權威的 tick 頻率、快照的頻率、所有用 tick 數寫的時間長度（重生、換彈、射擊間隔），舊的驗收紀錄不能直接比；不在這一批。
- 通用的時間會有兩個寫者（時間的 System、驅動固定步的 System），要不要標成可多寫是設計第 0 節列的未定事項，T3 的事。
- 舊的 `double` 版有一個相對的容差（步長的十億分之一），整數版沒有；「和舊版逐點比」選的步長與輸入避開了它。
