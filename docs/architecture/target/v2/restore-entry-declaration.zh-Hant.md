**第三條的內容**（卡片的複述，使用者回「對就是這個。」）：存什麼、存檔格式、玩家出現在哪裡、要不要留相機和 HUD，都是作者的事；作者想把每個物件都存下來，就自己掃描、自己寫，用 Engine 現有的機制。Engine 保護的是機制，並提供一條**預設支持的路**：建一個新的 World，經開局與 Loading，由作者的讀檔 System 把存檔的內容放回。比過的選項：一律在新的 World 裡讀 ← 選／在現在的 World 裡讀／兩種都支援由產品選。理由（使用者的）：存檔的核心是玩家當前的狀態（物品、任務進度、觸發條件），不用 100% 還原世界；各類遊戲的存檔條件不同，應由作者確定。

## 1. 這一批做什麼

### 1.1 用遊戲講

RPG：玩家在第 3 關存檔，身上有 3 瓶藥水、一把鑰匙、金幣 120，任務「救出村長」做到第 2 步，觸發過「入口的過場動畫」「拉桿」「Boss 已打倒」。隔天讀檔：建新的 World，Loading 照第 3 關的資產生成地圖、怪物、寶箱（怪物在初始位置、滿血，掉落物不在）；作者的讀檔 System 放回物品、任務進度、觸發條件；關卡裡的東西照觸發條件決定自己的樣子（門是開的、Boss 不生成、過場不再播）；玩家出現在作者決定的地方。遊戲中讀另一個存檔走同一條路。

卡牌遊戲存牌組與對局進度；另一個作者存了每一隻怪物——都走「新 World → Loading → 作者的讀檔 System 放回」。Engine 不認得任何一種存檔。

### 1.2 這一批要確保的

預設的路在機制上走得通，而且行為寫清楚：
- 作者要把實體放回時，編號怎麼處理才不被丟（5.1）；
- Loading 裡放回的元件與 Resource 不撞獨占寫者的檢查（5.2）；
- hook、stamp、tick、診斷紀錄在這條路上的行為（5.3～5.6）；
- 這些保證寫在哪裡、Engine 的「預設支持」具體包含什麼（5.7）；
- 和回滾的關係（第 7 節）。

### 1.3 Derivation Order（AGENTS §2）

| 層 | 內容 |
|---|---|
| Feature | 玩家存檔（使用者 2026-11-16）。Product：單機遊戲 |
| Contract | 存檔檔案是作者的資料契約（AGENTS §8），Engine 不規定。Engine 的契約只有：新 World、開局、Loading 這條路上，放回內容時各機制的行為 |
| Architecture | 現有的 Kernel 機制夠不夠走這條路；不夠的地方要加什麼 |

### 1.4 層的區別

Engine 這一側要確保的是 Kernel 的行為（配發器、丟棄規則、寫者的數法、hook），每個有存檔的產品都會照它寫讀檔，所以照基盤處理。存檔格式與讀檔流程是產品的（應用），這一批不設計。

### 1.5 予見的根據

| 根據 | 推出的要求 |
|---|---|
| 名指的 Feature：玩家存檔（使用者 2026-11-16） | 新 World 裡，作者可以用自己存的編號放回實體，也可以讓配發器重新配號；Loading 裡放回的寫法不撞獨占檢查 |
| 參考實作（偵察報告） | Bevy 讀檔一律重新配號；GYO 的預設路是新 World，所以照存檔編號放回也做得到（5.1），兩種都留給作者 |
| 規模與預算 | 沒有給；存什麼由作者定，Engine 這一側不量效能 |

## 5. 要你判的件

每件先用遊戲講；選項的順序不代表建議；我的建議標在最後。

### 5.1 編號：Engine 要保證什麼

**遊戲**：存了每一隻怪物的作者，存檔裡怪物 57 記著「追的是編號 12（玩家）」。

作者有兩種寫法，Engine 現在都做得到：
- **照存檔編號放回**：組裝在第一次 Run 前，把配發器的範圍訂在存檔記的下一個號之後；讀檔 System 用 `SpawnWithId`。參照不用改寫。
- **重新配號**：讀檔 System 用 `Spawn`，自己記對照表、改寫參照。

| 選項 | 得到什麼 | 代價 |
|---|---|---|
| 兩種都由作者選；Engine 保證「組裝可以在第一次 Run 前設配發器的範圍」「範圍外的 `SpawnWithId` 照常生成」，寫進說明頁與測試 | 存檔格式完全由作者定；Kernel 不變 | 作者照存檔編號放回時，要在存檔裡記「下一個號」並讓組裝在 Run 前設好——這一步在 runner／組裝，不在 World 裡（T3、T5 還沒做） |
| Engine 只支持重新配號 | 規則少一條 | 作者想照存檔編號放回時做不到；每個存了參照的作者都要寫改寫 |
| Engine 提供「從存檔設配發器」的入口 | 組裝不用自己算 | Engine 認得存檔的內容（下一個號），和「不規定格式」衝突 |

**我的建議**：兩種都由作者選，Engine 保證那兩點。來由第 3 件因此有答案（第 8 節）。

### 5.2 Loading 裡放內容的寫者問題（不分讀檔或資產）

**遊戲**：敵人的 `Position` 只有 `Move` 寫（獨占）。Loading 裡要把敵人生成出來——不管是照第 3 關的資產，還是照存檔——生成時就要帶 `Position`，這個 Loading 的 System 就是第二個寫者。RPG 的玩家狀態（物品、金幣這類 Resource）也一樣：放回的 System 和玩法裡改金幣的 System 是兩個寫者。

這是 Loading 本來就有的問題，你 11-14 為它選了漏斗。讀檔沒有帶來新的種類；它讓更多作者會碰到。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 沿用漏斗（現有） | Loading 的 System 生成請求；元件的擁有者宣告從請求取初始值。Resource 由它的唯一寫者讀暫存的資料自己設值 | Kernel 不變；寫者的數法與區規則不動；和資產載入同一套 | 漏斗的優先規則：同一個實體同一個同步點有兩個請求能補同一個元件時，取 ComponentId 小的，**沒有訊息**（例：敵人身上原本的生成請求 `Arrival` 與存檔的請求都在，位置取哪個看登記順序）；串接可能補出存檔沒有的元件；只有擁有者能宣告，可重用 Plugin 的元件要那個 Plugin 提供請求型別；Resource 的寫者要懂存檔裡自己那一塊、要掛在 Loading；請求留在實體上 | 使用者 2026-11-14 |
| 沿用漏斗，並把優先規則的「沒有訊息」改成可見 | 同上；兩個請求補同一個目標時留明細（像 `RejectedSpawn`），或改成啟動時的歧義檢查 | 錯了查得到；漏斗本身變好，資產載入也受益 | 改漏斗的規則（說明頁第 8 節、指紋）；這是漏斗的後續，也可以另開一批 | 使用者「拒絕的話，需要明確給出理由」的同一個精神（#235） |
| Loading 的生成不進獨占寫者的數法 | Kernel 改數法：Loading 裡生成的 bundle（元件）與 Loading 裡對 Resource 的設值不計；存取集合、區規則照算 | 讀檔與資產載入都直接放完整的值；作者不必為每個元件配請求 | 改 DI-KS 6；Loading 的 System 能給任何元件初始值，獨占在 Loading 裡沒有保護（PvP 的 (c) 區載入也是）；和使用者 11-14 選漏斗的方向重疊——「生成不算寫者」那次否決的是 Despawn 類比，這一條算不算同一件事要你判 | 開局不計的現有規則 |
| 要放回的元件標 Shared | 作者自己選 | Kernel 不變 | 失去獨占檢查 | 現有規則 |

**我的建議**：沿用漏斗，並把「兩個請求補同一個目標沒有訊息」列成漏斗的後續（另開一批，不在這一批做）。理由（我的）：你說 Engine 不認得存檔，讀檔就該和資產載入走同一套；那一套你 11-14 已經選了漏斗。我在漏斗上看到的問題（沒有訊息）是漏斗本身的，資產載入也會碰到，改漏斗比為讀檔開例外對。修訂 1 建議的「讀檔專用的生成」撤回：它讓 Kernel 認得讀檔。

### 5.3 hook

**遊戲**：寶箱的 OnAdd 播「寶箱出現」的音效；碰撞體的 OnAdd 加進物理的空間索引；敵人的 OnAdd 生成血條。

| 選項 | 得到什麼 | 代價 |
|---|---|---|
| 照常觸發（預設的路就是一般的生成） | 空間索引這類必須在出現時登記的自然成立；Engine 不認得讀檔 | 作者在意的效果（音效、出生動畫）自己分辨；hook 生成的衍生實體若也存了，讀檔後有兩份（作者的格式決定） |
| hook 看得到這筆變更是誰記的 | 中性的機制；hook 能分辨「讀檔 System 生成的」與「玩法生成的」 | hook 的參數（公開介面）變；資產載入也一樣能用 |
| 讀檔時不觸發 | — | Engine 要認得讀檔，和「不認得存檔」衝突 |

**我的建議**：照常觸發；「hook 看得到記錄者」等有作者在兩處以上重複寫「分辨讀檔」時再提（寫進 Replacement Criteria）。

### 5.4 stamp（確認）

放回的格子取套用那個同步點的 stamp，`Added<T>` 成立。新 World 裡一切都是新的，保留存檔時的 stamp 沒有意義（world §2）。**沒有可選的**。

### 5.5 tick（確認）

新 World 的 tick 從 0 開始，ready 時為 0（DI 3）。遊戲要的「遊戲內時間」由作者放在自己存的 Resource 裡。Engine 不提供設 tick 的入口（「tick 只有一個來源」，DI-KS 12 前半、kernel 頁 `:46`）。**沒有並列選項**——新 World 讓另一個選項（設 tick）沒有需要。

### 5.6 診斷紀錄（確認）

新 World 的 `RejectedSpawn` 總數從 0 開始；讀檔時被丟的生成（例：存檔有兩個實體用同一個編號、或編號落在配發器範圍）照常記明細；`rollbackActive` 是 false。**沒有並列選項**。

### 5.7 「預設支持」具體包含什麼、寫在哪裡

| 選項 | 包含 | 得到什麼 | 代價 |
|---|---|---|---|

## 13. 判定（先宣告，結果出來之後不放寬；照建議的組合）

### 判定 1：行為（新測試 `tests/common/kernel/RestoreEntryTests.cpp`；案例名實作前換成實際的 `TEST_CASE` 名）

1. **照存檔編號放回**：存檔有玩家（12）與 2 隻怪物（57、58，57 的 `ChaseTarget` 是 12），記的下一個號 900；新 World 在第一次 Run 前設配發器 `[900, 上限]`；讀檔前先跑一張每幀的 schedule 生成一個選單實體（開局不載內容，runtime-composition DI 3）；Loading 的讀檔 System 用 `SpawnWithId` 放回請求，`Position` 由漏斗補。讀檔後編號是 12、57、58；`ChaseTarget` 仍是 12；選單實體的編號 ≥ 900；沒有 `RejectedSpawn`。
2. **重新配號**：同一份存檔，讀檔 System 用 `Spawn`；讀檔後三個實體的編號 ≥ 900、依存檔編號的大小順序；`ChaseTarget` 由讀檔 System 改寫後指向玩家的新編號。
3. **範圍沒設好**：配發器範圍是 `[1, 上限]`，照存檔編號 `SpawnWithId`，每一筆以 `IdInAllotterRange` 被丟（記錄來由第 3 件）。
4. **寫者**：`Position` 的唯一寫者是 `Move`；讀檔 System 只寫請求；Registry 完成時沒有 D-E2。
5. **Resource**：金幣由它的唯一寫者在 Loading 讀暫存的存檔資料設值；讀檔後是存檔值；沒有 D-E2。
6. **hook**：每個放回的格子 OnAdd 各一次；`Added<Position>` 在讀檔後第一個讀者成立。
7. **新 World**：第一個 World 跑過 Fixed 的 tick；第二個 World 讀檔，ready 時 Fixed 的 tick 是 0、`RejectedSpawns()` 是 0、沒有第一個 World 的實體。
8. **讀兩次相同**：同一份存檔在兩個新 World 讀，`Summary()` 相同。

案例 1～8 守的是「預設的路」這份契約；它們用到的 Kernel 行為多半已有別的守衛（DI-KS 4、9 的 J-8、J-55，漏斗的 `InitialValueTests`）。
