## 1. 這一批做什麼

### 1.1 用遊戲講

一款 2D 橫版通關遊戲。玩家打到第 3 關的一半：開過一個寶箱、剩 5 隻敵人、金幣 120、一隻敵人正追著玩家（敵人身上記著「追的是誰」）。

- **存檔、關掉遊戲、讀檔**：玩家在暫停選單按「存檔」，關掉遊戲。明天打開遊戲，進主選單，按「繼續」，回到第 3 關的同一個地方：寶箱還是開的、5 隻敵人在原位、金幣 120、那隻敵人還追著玩家。
- **遊戲中讀另一個存檔**（使用者定：同一個機制）：玩家在第 3 關打輸了，從暫停選單讀昨天第 2 關的存檔。第 3 關的東西要消失，第 2 關的東西要回來；主選單、相機這類不屬於關卡的東西留著。

### 1.2 用機制的詞

讀檔＝在一個 World 裡（新的，或已經跑過的）把存檔記下的實體、元件的值、Resource 的值放回去，並且：
- 編號和配發器之間不出錯（#235 之後撞號的生成會被丟掉）；
- 不破壞寫者的數法（元件預設獨占，DI-KS 6）；
- 世界內容照現有條文經 Loading 進來（runtime-composition DI 3）；
- hook、初始值的宣告、stamp、tick、事件、診斷紀錄各有明確的行為。

這一批要定的是**入口的形狀與規則**，不是存檔檔案的格式（第 4.12 件）。

### 1.3 Derivation Order（AGENTS §2）

| 層 | 內容 |
|---|---|
| Feature | 玩家存檔（存與讀成對；遊戲中讀另一個存檔是同一個機制）。Product：單機遊戲。使用者 2026-11-16 點名 |
| Contract | 存檔檔案是資料契約（AGENTS §8）：誰都能產生（遊戲、腳本、工具），讀檔不需要知道是誰寫的。讀檔之後 World 的樣子：哪些東西回來、編號是什麼、哪些副作用發生 |
| Architecture | Kernel 要提供什麼機制，才能讓產品照上面的契約把實體放回去；放在哪一層 |

### 1.4 為什麼是基盤（AGENTS §2 層的區別）

每一個有存檔的產品，它的讀檔 System、每個元件的擁有者（要不要提供「從存檔取值」的規則）、存檔檔案裡編號的意義，都照這一批定的入口寫。之後改入口，這些都要改，而且存檔是保存下來的資料，舊存檔也要能讀（Version，AGENTS §8）。所以照基盤處理：用予見設計，實作薄。

### 1.5 予見的根據（AGENTS §2）

| 根據 | 出處 | 推出的要求 |
|---|---|---|
| 名指的 Feature：玩家存檔 | 使用者 2026-11-16 | 讀檔能在新的 World 與已經跑過的 World 裡用同一個機制（第 4.1、4.6 件）；元件之間的實體參照讀檔後仍指對（4.5）；讀檔後行為和存檔前一致（4.3 的順序） |
| 成熟的參考實作 | Bevy `bevy_world_serialization`（原 `bevy_scene`）、bevy_replicon、lightyear（偵察報告） | 「怎麼做」：重新配號加對照表、實體參照的改寫、hook 照常觸發（4.3、4.5、4.7） |
| 領域的規模與預算 | **沒有給**。存檔裡的實體數、讀檔可以花多久，使用者沒有說 | 未決，第 4.14 件問使用者；沒有預算時不量效能 |

## 3. 現在的程式碰到讀檔時會怎樣（讀程式確認的事實）

| 做法 | 結果 | 出處 |
|---|---|---|
| Loading 裡的 System 用 `SpawnWithId` 照存檔的編號生成 | 存檔的編號都是當時配發器配的，落在範圍內，**整批被丟**（`IdInAllotterRange`） | `World.cpp:642`；#235 宣告 2.3 |
| 同上，但 bundle 直接帶 `Position`、`Health` | `Position` 的寫者變成兩個（玩法的 System 與讀檔的 System），**啟動錯誤 D-E2** | `Registry.cpp:1412-1450` |
| 遊戲中讀檔，World 裡還有主選單的按鈕（編號 1～10）與第 3 關的實體 | 原樣放回時，存檔裡的 1～10 撞上活著的按鈕，被丟（`IdAlive`）；第 3 關的實體要先刪 | `World.cpp:658-664` |
| 外面（runner／組裝）在 Ready 用 `World::Insert` 直接寫 | 做得到：任何編號、不過丟棄規則、不算寫者。但不過 hook 與初始值的宣告；第一次 Run 之後 (c) 區被 W-6b 擋；違反 runtime-composition DI 3 | `World.hpp:164`、`World.cpp:191-200` |
| 用一般的 `Spawn` 生成（配發器給新號） | 做得到，`Spawn` 在記錄當下就回傳編號（`Params.hpp:538`），讀檔的 System 能邊生成邊記對照表 | `Params.hpp:538-550` |

## 4. 要你判的件

每件先用遊戲講，再列選項。選項的順序不代表建議；**我的建議另外標在每件的最後**，你沒有判之前不寫進正文的條文。

### 4.1 放回實體走哪條路

**遊戲**：玩家按「繼續」。存檔檔案已由 IO 讀進來（外部服務，經交換點進 World）。接下來 5 隻敵人、寶箱、玩家要出現在 World 裡。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 讀檔的 System 在 Loading 裡經同步點生成 | 存檔資料經 Loading 的 Ingress stage 進暫存；Loading 裡一個讀檔的 System 用生成的指令放回；同步點照 F.2 套用 | 現有的 Loading 契約（runtime-composition 3a，使用者 2026-11-11）；Bevy 也是一般的 spawn | 要處理寫者的數法（4.2）與編號（4.3）；hook、初始值照常（4.7） | 玩家存檔（新 World 與已經跑過的 World 都能用）／單機 |
| 外面在 Ready 直接寫（現有 `World::Insert`） | runner 或組裝在兩次 `Run` 之間，對每個實體逐一 `Insert` | 舊規格 H.5 的 Restore 也是「外面在 Ready 寫」（DI-KS 12），但它是給回滾的 | 違反 runtime-composition DI 3（要改條文）；不過 hook 與初始值的宣告，產品要自己補；(c) 區被 W-6b 擋；外面要懂存檔格式與元件型別 | 玩家存檔／單機（(b) 區） |
| Kernel 新增一個「還原」動詞 | 經同步點，但記成「還原」：不算寫者、可以用配發器範圍內的編號、hook 可選 | 舊規格的 Restore（不觸發 hook、不算寫者、Z2 的例外）改成經同步點 | 新動詞、新的寫者例外（要改 DI-KS 6、DI-KS 9 的文字）；使用者 2026-11-14 否決過「生成不算寫者」，這是同一類例外 | 玩家存檔；之後回滾可能共用 |

**我的建議**：讀檔的 System 在 Loading 裡經同步點生成。理由（我的）：不改條文就合 DI 3；hook、初始值、`Added` 都照現有機制走；遊戲中讀檔不受 W-6b 影響。

### 4.2 讀檔放回的元件，算不算寫者（4.1 選經同步點時才有這件）

**遊戲**：敵人的 `Position` 只有 `Move` 這個 System 寫（獨占）。讀檔要把敵人放回原位，等於「讀檔的 System 也寫了 `Position`」。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 照算，要存的元件都標 Shared | 讀檔的 System 直接在 bundle 放 `Position` | 現有規則 | 所有要存的元件都失去獨占的檢查；進 digest 的欄不能 Shared（LIM-4），PvP 的存檔（若有）做不到 | 玩家存檔 |
| 漏斗：每個要存的元件配一個「存檔請求」，元件的擁有者宣告「從請求取初始值」 | 讀檔的 System 只生成 `Saved<Position>` 這類請求；`Position` 的擁有者登記 `InitialValue<Position, 從 Saved<Position> 取>`；同步點第 5a 步補上 `Position`。實體存檔裡沒有某個元件，就不給那個請求，元件就不會出現 | 使用者 2026-11-14 選的漏斗（說明頁第 8 節，已實作） | 每個要存的元件多一個請求型別；請求留在實體上（機制不替作者移除，要產品清，或另定「補完就移除」的選項）；擁有者要多寫一個登記 | 玩家存檔 |
| 讀檔的 System 的生成不算寫者 | 登記時把讀檔的 System 標成「還原者」，它在 Loading 裡的生成不進寫者的數法 | 舊規格 Restore 的「不算寫者」 | 使用者 2026-11-14 否決過「生成不算寫者」（「Despawn 是機制，不能當成普通的實作參考」）；開了口子就能被當成繞過獨占的路 | 玩家存檔 |
| Loading 的寫者不計（比照開局） | 改數法：開局與 Loading 的 schedule 都不計 | 開局不計的現有規則 | Loading 在 PvP 是 (c) 區的內容載入，不計寫者等於 (c) 區的載入沒有獨占檢查；改 DI-KS 6 | 玩家存檔 |

**我的建議**：漏斗。理由（我的）：這正是使用者 11-14 為「一個 System 生成、另一個負責」選的工具；Kernel 的寫者數法與區規則都不用改；元件的擁有者寫「怎麼從存檔取值」，知識留在擁有者。附帶一個小題要你判：要不要讓初始值的宣告可以選「補完就移除請求」（不選的話，產品寫一個清請求的 System）。

**Resource（金幣、任務旗標）**：漏斗只對元件。Resource 照說明頁第 8 節已有的寫法——「維持一個寫者，由那個寫者在函式裡讀請求自己套用」：金幣的唯一寫者讀暫存的存檔資料，把值放回。Kernel 不用改。這一點沒有並列的選項，列在這裡讓你確認。

### 4.3 編號：原樣放回，還是重新配號

**遊戲**：存檔裡那隻追玩家的敵人是編號 57，玩家是 12。今天開遊戲，主選單的按鈕已經拿了 1～10。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 原樣放回，配發器跟著還原 | 用 `SpawnWithId(57)`；配發器的「下一個」設回存檔時的值；`SpawnWithId` 對讀檔開例外（不判「落在範圍」） | 舊規格（快照含配發器）；`rebuild-entity-order` 第 5 節（架構師的分析稿）寫「讀檔時用存檔裡的 id」 | 遊戲中讀檔時，存檔的編號會撞上活著的實體（主選單的 1～10、第 3 關的實體），要先全部刪掉；配發器倒退，同一個 World 裡**配發過的編號會再出現**（違反「不重用」），World 外記著舊編號的東西（UI、音效的把手）會指錯；需要 `SpawnWithId` 的例外與「外層刪除、裡面同編號」的檢查（K0 第 9 節） | 玩家存檔 |
| 重新配號，加對照表 | 讀檔的 System 依存檔編號由小到大用一般的 `Spawn` 生成，邊生成邊記「存檔編號→新編號」；元件裡的實體參照照對照表改寫（4.5）；配發器不動 | Bevy（讀檔一律重新配號，`EntityMapper`）；bevy_replicon（Server 編號只當對照表的鍵） | 實體參照要改寫（4.5）；讀檔後編號和存檔不同（存了再讀，存檔檔案裡的編號會變）；每讀一次，配發器多用掉一批編號 | 玩家存檔 |
| 原樣放回，只用在新的 World | 遊戲中讀檔一律先重建 World（DI-KS 14），在新 World 裡原樣放回 | DI-KS 14（世代＝重建 World） | 仍要 `SpawnWithId` 的例外與配發器還原；重建後狀態機先進初始值（主選單）再換（使用者 11-15 的規則），畫面會閃一下主選單；主選單與相機要重建 | 玩家存檔 |

**順序**：選「重新配號」時，依存檔編號由小到大配號，新編號的大小順序就和存檔時一樣（配發器單調），查詢的順序因此和存檔前相同（「從存檔重現問題」照樣成立，`rebuild-entity-order` 第 4 節）。這一句會寫進契約。

**我的建議**：重新配號，加對照表。理由（我的）：遊戲中讀檔（使用者定為同一個機制）時不用先清空、不會撞號；配發的編號永不重用；#235 的丟棄規則與 `SpawnWithId` 都不用動；K0 第 9 節的「外層刪除、裡面同編號」不會發生。Bevy 為了同樣的問題刪掉了「指定編號生成」（#18054）。

### 4.4 配發器的狀態

跟著 4.3：原樣放回要還原配發器（「下一個」設回存檔時的值）；重新配號不還原、也不存。

**我的建議**：跟 4.3 走，不另判。

### 4.5 元件裡指向其他實體的欄位怎麼改寫（4.3 選重新配號時才有這件）

**遊戲**：敵人的 `ChaseTarget{ target = 12 }`。讀檔後玩家的新編號是 803，`target` 要改成 803。

Kernel 沒有反射，不知道哪個欄位是實體參照。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 產品在讀檔的 System 裡自己改 | 讀檔的 System 先把所有實體生成完、拿到對照表，再組每個元件的存檔請求時改寫參照 | 現有機制 | 每個有參照的元件，讀檔的程式要知道怎麼改；漏了一個就指錯 | 玩家存檔 |
| 元件的擁有者登記「參照的改寫函式」，放在一個存檔用的 Plugin | 像 Bevy 的 `MapEntities`：擁有者宣告 `ChaseTarget` 怎麼改；讀檔的 System 對每個請求呼叫它 | Bevy `MapEntities` | 多一個 Plugin 與登記；只有一個產品時是預先一般化（AGENTS §1） | 玩家存檔 |
| Kernel 登記「參照的改寫函式」 | 同上，但登記在 Kernel | Bevy（在 `bevy_ecs`） | Kernel 多一個和存檔有關的概念；沒有反射，仍要擁有者手寫 | 玩家存檔 |

指向存檔外的參照（存檔沒有的實體）：Bevy 換成一個保證不指向活實體的編號（靠 generation，我們沒有）。我們可以換成「沒有」（`0` 或 optional），由改寫函式決定。

**我的建議**：產品自己改，Kernel 與 Plugin 都不登記；第二個產品出現、同樣的改寫寫了兩次時再搬進 Plugin（寫進 Replacement Criteria）。理由（我的）：知識屬於元件的擁有者與存檔格式，現在只有一個 Feature。

### 4.6 遊戲中讀另一個存檔：現在的東西誰清、什麼時候清

**遊戲**：第 3 關打輸，讀第 2 關的存檔。第 3 關的敵人、寶箱要消失；主選單、相機留著。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 同一個同步點先刪再生 | 讀檔的 System 對「屬於關卡」的實體（產品自己標，例如帶 `LevelContent`）記刪除，同時記新實體的生成；同步點照 F.2 先刪、再生 | F.2 的固定順序（使用者 2026-11-11） | 誰屬於關卡由產品標；刪除會觸發 OnRemove（第 3 關的東西「被消滅」的 hook 會跑，產品要分辨） | 玩家存檔 |
| 先跑一張清除的 schedule，再讀 | 狀態機進「讀檔中」時跑清除，下一次再讀 | 狀態機的進入／離開（排程中） | 依賴狀態機那一批；多一幀 | 玩家存檔 |
| 重建 World | 丟掉整個 World，用新的 World 讀 | DI-KS 14 | 見 4.3 第三列：先進主選單再換、主選單與相機重建；一個 Product 一個 World 的現況下，等於重建 Product | 玩家存檔 |

**我的建議**：同一個同步點先刪再生（4.3 選重新配號時沒有撞號的問題）。清除的範圍由產品標，Kernel 不提供「清空關卡」。

### 4.7 hook 與初始值的宣告

**遊戲**：寶箱有 OnAdd hook 播「寶箱出現」的音效；碰撞體有 OnAdd hook 把它加進物理的空間索引。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 照常觸發 | 經同步點生成就照 F.2 第 5a、6 步 | Bevy（讀檔時 hook 與 observer 照常） | 讀檔時會播「寶箱出現」；產品要讓 hook 分辨「讀檔中」（例如讀一個狀態或標記） | 玩家存檔 |
| 不觸發 | 讀檔的生成跳過 hook | 舊規格 Restore（S12）；DI-KS 12 | 物理索引這類「必須在出現時登記」的 hook 不會跑，產品要自己補；要在同步點加分支（新規則） | 玩家存檔 |
| 每個 hook 登記時選 | hook 宣告「讀檔時跑不跑」 | 沒有參考實作 | 新的登記項；讀檔要能被 Kernel 認出來（要有還原動詞，見 4.1 第三列） | 玩家存檔 |

選漏斗（4.2）時，初始值的宣告就是放回的路，一定會跑。

**我的建議**：照常觸發。理由（我的）：對 World 來說，讀檔的實體確實是「出現」；和狀態機「快照蓋值時不自動跑進入／離開、由遊戲決定」（使用者 2026-11-16）是同一個精神——機制照常做，要不要有效果由遊戲決定。

### 4.8 stamp

讀檔放回的格子，`added`／`changed` 取套用那個同步點的 stamp，所以 `Added<T>`、`Changed<T>` 在下一個讀者那裡成立。另一種是「保留存檔時的 stamp」：stamp 不跨世代比較、不進存檔（world §2），存檔時的值在新 World 沒有意義，這一種做不到。**這一件沒有可選的**，列出來讓你確認。

### 4.9 tick

**遊戲**：天氣在「第 3600 個 tick 起霧」。存檔時 tick 是 5000；今天開遊戲、讀檔時 tick 是 300。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 不還原 tick，遊戲自己存遊戲時間 | domain tick 照舊只由時鐘的 schedule 推進；遊戲要的「遊戲內時間」放在一個 Resource 裡存讀 | DI-KS 12 前半（domain tick 只有一個來源）；使用者 2026-11-16「從第幾個 tick 起…是遊戲自己的資料」 | 用 tick 當遊戲時間的寫法讀檔後會錯，說明頁要寫明 | 玩家存檔 |
| Kernel 提供在 Ready 設 domain tick 的入口 | 讀檔前由外面設 tick | 舊規格 Restore（tick 在快照內） | 改「tick 只有一個來源」；遊戲中讀檔時 tick 倒退，`tickStamps` 的換算表要清 | 玩家存檔 |

**我的建議**：不還原 tick。

### 4.10 事件

存檔不存事件；讀檔前還沒讀完的事件照修剪規則消失。Bevy 也不存。**沒有並列選項**，列出來讓你確認。

### 4.11 診斷紀錄（`RejectedSpawn` 的明細與總數）

讀檔時被丟掉的生成（例如產品寫錯，兩筆生成同一個編號）照常記明細、加總數；`rollbackActive` 是 false（讀檔不是重放）。選「重新配號」時，正常的讀檔不會有被丟的生成。**沒有並列選項**，列出來讓你確認。

### 4.12 資料的形狀歸誰

**遊戲**：存檔檔案（JSON 或二進位）裡寫什麼、怎麼寫。

| 選項 | 怎麼做 | 系譜 | 代價 | 需要它的 Feature／Product |
|---|---|---|---|---|
| 產品擁有格式；Kernel 只提供機制 | 存檔格式是產品的資料契約（Version、Validation，AGENTS §8）；IO 讀檔是外部服務；Kernel 只定 4.1～4.11 | AGENTS §8；`engine-not-tool-duties`（Engine 不承擔工具職能） | 每個產品自己寫格式與讀寫的程式 | 玩家存檔 |
| 一個存檔用的 Plugin 擁有通用格式 | Plugin 定格式與每個元件的編解碼登記 | Bevy 的 `bevy_world_serialization`（靠反射） | 沒有反射，元件的擁有者仍要手寫編解碼；只有一個 Feature 時是預先一般化 | 玩家存檔 |
| Kernel 擁有格式 | Kernel 的欄位加「要存」的旗標與編解碼 | 沒有 | 要反射或大量登記；存檔格式進 Kernel，Engine 承擔了產品的資料契約 | 玩家存檔 |

**我的建議**：產品擁有格式；Kernel 只提供機制。照 AGENTS §6 的判斷，少了存檔遊戲仍成立，所以將來的存檔 Plugin 是 Plugin，不是 Module。

### 4.13 和回滾（DI-KS 12）的關係

讀檔和回滾都是「把狀態放回 World」，但目的不同：讀檔是在 World 裡加入新的內容，回滾是把 (c) 區退回過去再重跑。

| 選項 | 怎麼做 | 代價 |
|---|---|---|
| 這一批不碰 DI-KS 12，回滾那一批重審 | 這一批的入口只給讀檔；DI-KS 12 原文不動；範圍的限界寫明「讀檔的路與 DI-KS 12 的 Restore 不同」 | 回滾那一批要看讀檔的入口能不能共用 |
| 這一批在 DI-KS 12 加一句「待回滾那一批重審」 | 條文改一句（Design Invariants 的變更） | 條文的變更要你同意 |
| 這一批改寫 DI-KS 12 | 把回滾的還原一起定 | 超出你定的範圍（第二項） |

**我的建議**：不碰 DI-KS 12，回滾那一批重審，範圍的限界寫明。

### 4.14 規模與預算

存檔裡的實體數上限、讀檔可以花多久（例如「1 萬個實體、讀檔 1 秒內」），使用者沒有給。沒有預算時這一批不量效能，範圍的限界寫明。**要不要現在給一個數字，由你定。**

## 5. 來由的三件（照第 4 節的建議組合；選別的組合時，答案跟著改，見各件）

1. **回滾重放撞上只帶 (b) 區元件的活實體（LIM-7）**：讀檔不經 (c) 區的權威，單機只有一端；重新配號時讀檔的生成不會撞上活實體。LIM-7 與它的解除條件不動，留給回滾那一批。給回滾那一批的要求：若回滾要共用讀檔的入口，要先重看 LIM-7。
2. **`rollbackActive` 固定 false、重放時明細重複計**：讀檔不是重放，`rollbackActive` 是 false 是對的（4.11）。重放時的重複留給回滾那一批；給它的要求：定 `rollbackActive` 由誰、在哪裡設，以及總數要不要扣除重放的部分。
3. **單機用 `SpawnWithId` 放回會整批被丟**：不用 `SpawnWithId` 放回；改用一般的生成重新配號加對照表（4.3）。#235 的規則與配發器都不改。K0 第 9 節的「外層刪除、裡面同編號生成」在讀檔時不會發生（編號都是新的）；K0 那一條的限界可以註明「讀檔已回答」。

## 8. Architecture Delta（AGENTS §3 七項，照建議的組合）

1. 需要的 Feature：玩家存檔（使用者 2026-11-16）。
2. 現在的問題：照字面（`SpawnWithId` 原樣放回、bundle 直接放元件）會整批被丟、撞寫者的檢查；沒有寫明的讀檔方式。
3. 變化的邊界：Kernel 的公開介面不變（若選「補完就移除」，初始值的宣告多一個選項）；新增的是契約（說明頁）：讀檔重新配號、依存檔編號由小到大、元件經漏斗放回、hook 照常。
4. 影響：`engine/kernel` 不變或只加一個選項；說明頁；`rebuild-entity-order`；將來有存檔的產品。
5. 依賴方向：不變。存檔格式在產品，Kernel 不知道存檔。
6. Ownership：存檔格式與實體參照的改寫歸產品；「從存檔取值」歸各元件的擁有者（漏斗的現有規則）。
7. 為什麼不能更小：不寫明的話，產品會照字面用 `SpawnWithId`（`rebuild-entity-order` 第 5 節就這麼寫）而整批被丟；這一批本身已經是「不改 Kernel、寫明用法」的最小形狀。

### 判定 1：行為（新測試 `tests/common/kernel/RestoreEntryTests.cpp`）
