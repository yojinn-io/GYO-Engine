## 1. 這一批做什麼

### 1.1 用遊戲講

一款 2D 橫版通關遊戲。玩家打到第 3 關的一半：開過一個寶箱、剩 5 隻敵人、金幣 120、一隻敵人正追著玩家（敵人身上記著「追的是誰」）。

- **存檔、關掉遊戲、讀檔**：玩家在暫停選單按「存檔」，關掉遊戲。明天打開遊戲，進主選單，按「繼續」，回到第 3 關的同一個地方：寶箱還是開的、5 隻敵人在原位、金幣 120、那隻敵人還追著玩家。
- **遊戲中讀另一個存檔**（使用者定：同一個機制）：玩家在第 3 關打輸了，從暫停選單讀昨天第 2 關的存檔，回到第 2 關存檔時的樣子。

### 1.2 用機制的詞

讀檔＝讓一個 World 的內容變成存檔記下的樣子：實體、元件的值、Resource 的值。要定的是：
- 在哪個 World 裡放回（第 4 節）；
- 實體走哪條路回來、編號是什麼、寫者的數法、hook、初始值的宣告、stamp、tick、事件、診斷紀錄各怎麼處理（第 5、6 節）；
- 存檔檔案的格式歸誰、讀檔的契約寫在哪裡。

### 1.3 Derivation Order（AGENTS §2）

| 層 | 內容 |
|---|---|
| Feature | 玩家存檔（存與讀成對；遊戲中讀另一個存檔是同一個機制）。Product：單機遊戲。使用者 2026-11-16 點名 |
| Contract | 存檔檔案是資料契約（AGENTS §8）：誰都能產生（遊戲、腳本、工具），讀檔不需要知道是誰寫的；要有 Version。讀檔之後 World 的樣子：哪些東西回來、編號是什麼、哪些副作用發生、哪些舊東西不會留下 |
| Architecture | Kernel 要提供什麼機制，產品才能照上面的契約放回；放在哪一層 |

### 1.4 為什麼是基盤（AGENTS §2 層的區別）

每一個有存檔的產品，它的讀檔程式、每個可存元件的擁有者（包含可重用的 Plugin 與 Module）、存檔檔案裡編號的意義，都照這一批定的入口寫；存檔是保存下來的資料，舊存檔也要能讀。之後改入口，這些都要改，而且上面積得越多越貴。所以照基盤處理：用予見設計，實作薄。讀檔所依賴的 Kernel 行為要寫成條文、有守衛（第 12 節），不能只寫在說明頁。

### 1.5 予見的根據（AGENTS §2）

| 根據 | 出處 | 推出的要求 |
|---|---|---|
| 名指的 Feature：玩家存檔 | 使用者 2026-11-16 | 兩種讀檔得到相同的結果（第 4 節）；元件之間、Resource 裡的實體參照讀檔後仍指對（6.2）；讀檔後的行為和存檔前一致——做得到的程度依第 4 節的選擇而不同 |
| 成熟的參考實作 | Bevy `bevy_world_serialization`（原 `bevy_scene`）、bevy_replicon、lightyear（偵察報告） | 「怎麼做」：Bevy 讀檔一律重新配號加對照表，靠反射與 generation 改寫參照，Resource 放在所有實體之後；hook 與 observer 照常，但刻意跳過「關係」的 hook。和 GYO 的不同：GYO 沒有反射、沒有 generation、有固定範圍的配發器與同步點的丟棄規則、有寫者的獨占檢查 |
| 領域的規模與預算 | **沒有給**。存檔裡的實體數、讀檔可以花多久 | 未決，第 5.10 件問使用者；沒有預算時不量效能 |

## 4. 根本的一件：讀檔在哪個 World 裡放回

**遊戲**：玩家在第 3 關，從暫停選單讀第 2 關的存檔。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| **一律在新的 World 裡讀** | 關掉再讀、遊戲中讀都一樣：丟掉現在的 World（現在一個 Product 一個 World，等於重建 Product），建新的，走開局與 Loading，在 Loading 裡把存檔放回 | 兩種讀檔不只走同一條路，**結果也相同**（沒有上一關留下的東西）；可以原樣放回（5.1）：存檔的編號＝World 的編號，元件、Resource、事件、World 外的服務裡記的編號都對得上，**不用寫參照的改寫**；runtime-composition DI 3（ready 時 tick 為 0）、3a、DI-KS 14（世代＝重建 World）照字面成立；查詢順序和存檔前完全相同（編號一樣） | 遊戲中讀檔要重建主選單、相機這類不屬於關卡的東西，讀檔時間包含重建；狀態機第一次套用先進初始值（使用者 11-15），所以要下一次套用才進關卡——會不會畫出一幀主選單由產品與 runner 決定（還沒實作，這裡不斷言）；存檔要記「配發器下一個號」或最大編號；不在 World 裡、但要跨讀檔留下的東西（設定、成就）放在 World 外，或也存讀 | DI-KS 14；舊 `PvpMatch::Reset()`（全局審計判為「結論可能對、理由只剩舊的」） |
| **在現在的 World 裡讀** | 遊戲中讀時，在跑過的 World 裡清掉關卡、放回存檔；關掉再讀時，World 本來就是新的 | 不重建主選單與相機；讀檔不經過開局與狀態機的第一次套用 | **編號只能重新配號**（原樣放回會撞上這個 World 配過的號，見 6.1），所以每個產品都要寫實體參照的改寫，包括 Resource 裡的；清不乾淨的東西會留下（`Local`、沒存的 Resource、上一個 tick 的事件、World 外記的舊編號、刪除時 OnRemove hook 記的變更、巢狀時外層還沒套用的生成，見 6.3、6.4），關掉再讀時沒有、遊戲中讀時有——兩種讀檔結果不同；同一個 World 第二次進 Loading，runtime-composition DI 3「ready 時 tick 為 0」與 3a 的完成旗標要補文字（條文變更）；遊戲中讀檔算不算 DI-KS 14 的「世代切換」要你界定 | Bevy（讀檔寫進現有的 World，重新配號） |
| **兩種都支援，由產品選** | Kernel 兩條路都定 | 產品自己取捨 | 兩套規則、兩套測試；和「是一個機制」的字面有距離 | — |

**我的建議**：一律在新的 World 裡讀。理由（我的，用 Feature 與 Contract 說）：「是一個機制」最強的意思是兩種讀檔結果相同，只有新 World 做得到；存檔的編號就是 World 的編號，存檔這份資料契約才簡單（手寫或工具產生的存檔，參照直接寫編號）；「在現在的 World 裡讀」留下的那一類錯（舊狀態殘留）只在某些遊玩歷史下出現，正是很難重現的那種。代價是重建的時間與「開局→主選單→關卡」的流程，這兩件屬於產品與狀態機，Kernel 不擋。

**你要判的**：選哪一個；選「在現在的 World 裡讀」時，另外判「遊戲中讀檔算不算世代切換」與 DI 3 的補文字。

第 5 節是兩個選項都有的件；第 6 節只在「在現在的 World 裡讀」時才有；只在「新的 World」才有的件併在 5.1。

## 5. 兩個選項都有的件

每件先用遊戲講。選項的順序不代表建議；我的建議標在每件最後，你沒有判之前不寫進條文。

### 5.1 實體走哪條路回來、編號

**遊戲**：按「繼續」。存檔檔案已由 IO 讀進來（外部服務，經交換點進 World）。接下來 5 隻敵人、寶箱、玩家要出現。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| Loading 經同步點，原樣放回（只在新的 World） | 組裝在建 World 後、第一次 Run 前，把配發器的範圍訂成從存檔記的「下一個號」開始；Loading 裡的讀檔 System 用存檔的編號生成；同步點照 F.2 套用 | 編號＝存檔的編號；F-13、DI-KS 9、配發器都不動；`SpawnWithId` 不寫配發器，配發器不必標 Shared；正好是 LIM-7 單機那句「指定編號避開配發器那一段」反過來做 | 只在新 World 成立；存檔要記下一個號；寫者的問題仍在（5.2）；手寫的存檔若編號超過記下的「下一個號」，之後配發器會撞上（被丟、明細查得到） | DI-KS 14；舊規格的快照含配發器（這裡不還原配發器，只訂範圍） |
| Loading 經同步點，重新配號加對照表 | 讀檔的 System 依存檔編號由小到大用 `Spawn` 生成，邊生成邊記對照表，再改寫參照（6.2） | 兩種 World 都能用 | 見 6.1、6.2 | Bevy、bevy_replicon |
| 外面在 Ready 直接寫 | runner 或組裝在兩次 `Run` 之間逐一 `World::Insert`（新 World 時在第一次 Run 前） | 不經同步點，不算寫者，不過丟棄規則；編號照存檔 | 和 runtime-composition DI 3 衝突（條文變更）；不過 hook 與初始值的宣告，產品要自己補；(c) 區在第一次 Run 之後被 W-6b 擋；runner 要懂存檔格式與元件型別 | 舊規格 H.5 Restore（給回滾用） |

**我的建議**：選了第 4 節「新的 World」時，用「Loading 經同步點，原樣放回」；選「現在的 World」時，用「重新配號加對照表」。

### 5.2 讀檔放回的元件，算不算寫者

**遊戲**：敵人的 `Position` 只有 `Move` 這個 System 寫（獨占）。讀檔要把敵人放回原位。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 照算，要存的元件標 Shared | 讀檔的 System 直接在 bundle 放 `Position` | Kernel 不變 | 所有可存的元件失去獨占的檢查，任何 System 都能寫它們；進 digest 的欄不能 Shared（LIM-4） | 現有規則 |
| 漏斗：每個可存元件配一個存檔請求 | 讀檔的 System 只生成 `Saved<Position>` 這類請求；`Position` 的擁有者登記「從請求取初始值」 | 寫者的數法與區規則不變；「怎麼從存檔取值」的知識在擁有者 | **條件**：同一個實體同一個同步點沒有別的請求也能補同一個目標時，存檔值才生效、沒給請求的元件才不出現；否則取 ComponentId 小的那個請求（例：敵人身上原本的生成請求 `Arrival` 先登記，敵人回到出生的位置），串接也可能補出存檔裡沒有的元件——都沒有訊息。只有擁有者能宣告，所以每個擁有可存元件的 Plugin 與 Module 都要提供請求型別與宣告：請求型別放產品，Plugin 引用不了（AGENTS §6）；放一個存檔用的 Plugin，所有這些 Plugin 都依賴它；放 Kernel，介面就變了。這會成為跨部件的規則（AGENTS §1，要查並登記 `docs/cross-component-rules.md`）。請求留在實體上（存兩份，存檔時要排除）。每個產品的每個可存元件都多一個型別與一段宣告——之後覺得重，要改的是所有產品 | 使用者 11-14 選的漏斗（說明頁第 8 節，已實作） |
| 元件的唯一寫者自己放回 | `Move` 也掛在 Loading，讀暫存的存檔資料，用型別化的指令插入自己的 `Position` | 寫者仍是一個；Kernel 不變 | 每個可存元件的寫者都要懂存檔裡自己那一塊、要掛在 Loading；讀檔的 System 先生成只帶標記的實體，寫者在之後的 stage 插入；可重用 Plugin 的寫者要讀產品的暫存（型別放哪裡，同上） | 說明頁第 8 節「維持一個寫者，由它自己套用」的寫法 |
| Kernel 加「讀檔的生成」 | 新的指令參數：只能掛在 Loading；bundle 的元件**不進獨占寫者的數法**；型別寫在簽名上，存取集合與區規則照算；F-13 的丟棄規則照用 | 讀檔的程式直接放完整的 bundle，存檔格式的知識集中在一處；可重用 Plugin 的元件不用各自提供請求；不碰漏斗的優先規則；Resource 也可以用同一種（5.4） | Kernel 多一個動詞與一條寫者數法的例外（DI-KS 6 加一句、D-E2 加一個案例）；「只能掛在 Loading」要有啟動檢查；Loading 裡的讀檔 System 能放任何元件的值——口子限在「Loading、只能生成新實體、不能改已有的」。使用者 11-14 否決過「拿 Despawn 類比，生成不算寫者」這個論證；**讀檔專用的機制算不算同一件事，要你判** | 舊規格 Restore 的「不算寫者」（但它不經同步點） |
| Loading 的寫者不計（比照開局） | 改數法：開局與 Loading 都不計 | 一條規則 | Loading 的所有 System（包括從資產建內容的、PvP 的 (c) 區載入）都失去獨占檢查；改 DI-KS 6 | 開局不計的現有規則 |
| Kernel 提供中性的「帶值的請求」 | Kernel 提供一個通用的請求型別，任何元件都能從它取值 | 擁有者不用各自定請求型別 | 要標 Shared 才有多個來源，等於任何 System 都能經它給任何元件初始值（說明頁第 8 節「只記錄的」那一列的形狀），效果接近「生成不算寫者」 | — |

**我的建議**：Kernel 加「讀檔的生成」。理由（我的，用 Feature 與 Contract 說）：玩家存檔的契約是「存檔記下的值就是讀回來的值」，漏斗的優先規則讓這句話有條件、而且錯了沒有訊息；每個可存元件都配請求型別，會變成所有產品、所有可重用 Plugin 都要遵守的跨部件規則，上面積起來之後就改不掉（`mechanism-not-conservative`）。這和修訂 0 的建議（漏斗）相反；修訂 0 的理由主要是「Kernel 不用改」，照 AGENTS §1、§4 不能當決勝理由。

### 5.3 hook 與初始值的宣告

**遊戲**：寶箱有 OnAdd hook 播「寶箱出現」的音效；碰撞體有 OnAdd hook 把它加進物理的空間索引；敵人有 OnAdd hook 生成血條實體。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 照常觸發 | 經同步點就照 F.2 第 5a、6 步 | 必須在出現時登記的東西（空間索引）自然成立；機制不分辨讀檔 | 會生成東西的 hook：存檔裡也存了血條時，讀檔後有兩個；不存的話，血條的編號順序和存檔前不同（契約要寫「hook 生成的衍生實體不進存檔」）；用 `Added<T>` 做反應的 System（出生動畫）也分不出讀檔；音效要產品分辨 | Bevy（照常，但刻意跳過「關係」的 hook） |
| 不觸發 | 讀檔的生成跳過 hook | 讀檔不會有副作用 | 空間索引這類 hook 不跑，產品要另外補；同步點要認得讀檔（要有 5.2 的「讀檔的生成」才認得出來） | 舊規格 Restore（S12）、DI-KS 12 |
| hook 看得到這筆變更是誰記的 | hook 的參數多一個「記錄者」（名字或記錄者給的標記），hook 自己決定 | 中性的機制，Kernel 不必認得「讀檔」；比讀一個全域旗標準（同一個同步點別的 System 的生成不會被誤判） | hook 的參數變；每個在意讀檔的 hook 要自己判斷 | 沒有參考實作 |
| 每個 hook 登記時選「讀檔時跑不跑」 | hook 的宣告多一個選項 | 宣告集中 | 要有「讀檔的生成」才認得出來；新的登記項 | 沒有參考實作 |

漏斗（若 5.2 選它）：初始值的宣告就是放回的路，一定會跑。選「讀檔的生成」時，bundle 裡已有的元件不會被初始值蓋掉（目標已有就不動），但串接仍會補出存檔裡沒有的元件——契約要寫「存檔的元件集合與初始值的宣告要一致」，或讀檔的生成跳過第 5a 步（另一個小題）。

**我的建議**：照常觸發，契約寫明「hook 生成的衍生實體不進存檔」。理由（我的）：玩家存檔要的是「回到存檔時的樣子」，必須在出現時登記的 hook 不跑就回不去；音效、動畫這類效果是產品的事。（修訂 0 引用使用者 11-16「快照蓋值時狀態機不自己跑進入離開」當理由，方向是反的：那個決定是機制不自己跑。照字面類比，它支持的是「不觸發，由遊戲決定」。這一點列出來讓你看。）

### 5.4 Resource（金幣、任務旗標、「玩家是哪個實體」）怎麼放回

**遊戲**：金幣 120 存在一個 Resource 裡，唯一的寫者是 `Wallet`。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 唯一寫者自己放回 | `Wallet` 也掛在 Loading，讀暫存的存檔資料，自己設值 | 寫者仍是一個；Kernel 不變 | 每個可存 Resource 的寫者都要懂存檔、要掛在 Loading；不能用事件（Loading 的事件到不了別的時鐘，F-9） | 說明頁第 8 節的寫法 |
| 外面在 Ready 寫（`World::SetResource`） | 新 World 時在第一次 Run 前寫 | 不算寫者；Kernel 不變 | 和 DI 3 的精神衝突（世界內容只經 Loading）；runner 要懂存檔 | — |
| 標 Shared | 讀檔的 System 也寫 | Kernel 不變 | 失去獨占檢查 | 現有規則 |
| 「讀檔的生成」擴充到 Resource | 同 5.2 的動詞，Loading 裡可以設 Resource 的值、不進寫者的數法 | 和元件同一套規則 | 同 5.2 | — |

**狀態機的 Resource**：唯一寫者是 Engine 的套用 System，產品寫不到。新 World 時，狀態機第一次套用先進初始值（使用者 11-15）；讀檔要回到「關卡、暫停中」這類狀態，照使用者 11-16 的決定（快照蓋值時不自己跑進入離開、由遊戲決定）有兩種寫法：把存檔的值當成要求寫進去，或直接蓋值、再由遊戲對變化做反應。後者需要一個「蓋值」的入口，這一批不定，列給狀態機那一批。

**Resource 裡的實體編號**（「玩家是哪個實體」）：原樣放回時不用改；重新配號時要改寫，對照表要放進一個 Resource 才給得出去，且要排在各 Resource 的寫者之前（6.2）。

**我的建議**：跟 5.2 走——選「讀檔的生成」就擴充到 Resource；否則唯一寫者自己放回。

### 5.5 stamp

讀檔放回的格子，`added`／`changed` 取套用那個同步點的 stamp，所以 `Added<T>`、`Changed<T>` 在下一個讀者那裡成立。「保留存檔時的 stamp」做不到：stamp 不跨世代比較、不進存檔（world §2）。**沒有可選的**，列出來讓你確認。後果（`Added<T>` 分不出讀檔）在 5.3。

### 5.6 tick

**遊戲**：天氣在「第 3600 個 tick 起霧」。存檔時 tick 是 5000。

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 不還原 tick，遊戲自己存遊戲時間 | domain tick 照舊只由時鐘的 schedule 推進；遊戲要的時間放在一個可存的 Resource | 「tick 只有一個來源」（DI-KS 12 前半、kernel `:46` Host 也不直接寫 tick）不動；新 World 時 DI 3「ready 時為 0」照字面成立 | 用 domain tick 當遊戲時間的寫法讀檔後會錯，說明頁要寫明 | 類比：狀態機那一批使用者說「從第幾個 tick 起…」這類是遊戲自己的資料（那一題講的是狀態機，不是讀檔；不是使用者對本題的話） |
| Kernel 提供在 Ready 設 domain tick 的入口 | 讀檔前由外面設 tick | 用 tick 當遊戲時間的寫法照樣成立 | 改「tick 只有一個來源」與「Host 不直接寫 tick」（DI-KS 12、kernel `:46`、J-39）；同一個 World 裡 tick 倒退，`tickStamps` 的換算要清 | 舊規格 Restore（tick 在快照內） |

**我的建議**：不還原 tick。

### 5.7 診斷紀錄（`RejectedSpawn` 的明細與總數）

讀檔時被丟掉的生成（例：手寫的存檔有兩個實體用同一個編號）照常記明細、加總數；`rollbackActive` 是 false（讀檔不是重放）。新 World 時總數從 0 開始。**沒有並列選項**，列出來讓你確認。

### 5.8 存檔資料的形狀歸誰

| 選項 | 怎麼做 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|---|
| 產品擁有格式；Kernel 只提供機制 | 存檔格式是產品的資料契約（Version、Validation，AGENTS §8）；IO 是外部服務 | 格式隨產品；Engine 不承擔產品的資料契約（使用者 `engine-not-tool-duties`） | 每個產品自己寫格式與讀寫；可重用 Plugin 的元件怎麼進存檔，產品要知道它們的欄位 | AGENTS §8 |
| 一個存檔用的 Plugin 擁有通用格式 | Plugin 定格式與每個元件的編解碼登記 | 產品之間共用；可重用 Plugin 的元件自己登記編解碼 | 沒有反射，擁有者仍要手寫編解碼；只有一個 Feature | Bevy `bevy_world_serialization`（靠反射） |
| Kernel 擁有格式 | Kernel 的欄位加「要存」與編解碼 | 一處 | 要反射或大量登記；存檔格式進 Kernel | 沒有 |

**我的建議**：產品擁有格式；Kernel 只提供機制。存檔用的 Plugin 等它出現時再分類（Module 或 Plugin）。

### 5.9 讀檔的契約寫在哪裡

讀檔依賴的 Kernel 行為（照第 4、5 節的選擇，例如「讀檔的生成只能在 Loading、不進寫者的數法」「配發器範圍由組裝在第一次 Run 前給」「`SpawnWithId` 只在範圍外才生成」「補出的格子照常 OnAdd」）：

| 選項 | 得到什麼 | 代價 |
|---|---|---|
| 寫成 Kernel 的 Design Invariants（kernel 頁加句、守衛測試），用法寫說明頁 | 有人改 Kernel 時會被當成違反條文；合 1.4「基盤」 | 條文的變更要你同意 |
| 只寫說明頁 | 輕 | 之後有人改 Kernel，不會被當成違反；和 1.4 自稱基盤不一致 |

**我的建議**：寫成 Design Invariants（第 12 節的草案）。

### 5.10 規模與預算

存檔裡的實體數上限、讀檔可以花多久（例：「1 萬個實體、1 秒內」），使用者沒有給。沒有預算時不量效能，範圍的限界寫明。**要不要現在給一個數字，由你定。**

## 6. 只在「在現在的 World 裡讀」時才有的件

第 4 節選「新的 World」時，這一節整節不用判。

### 6.1 編號與配發器

原樣放回在同一個 World 裡做不到不改條文：存檔的編號落在現在配發器的範圍會被丟；要放回就得讓配發器倒退（同一個 World 裡配過的號再出現，World 外記著舊編號的東西指錯）並給 `SpawnWithId` 開例外。所以這個選項只能重新配號：

- 讀檔的 System 用 `Spawn` 就是配發器的寫者，有別的生成者時配發器要標 Shared。
- 每讀一次多用一批編號；配發器用完時 `AllotterExhausted`、World 中斷，要重建。契約要寫「讀檔前確認剩下的編號夠」或寫明後果；讀檔的 System 能不能先查剩多少，取決於配發器的型別。
- **順序**：「依存檔編號由小到大配號，讀檔後的順序和存檔時一樣」只在被放回的實體彼此之間、而且配發器單調（E2，待使用者確認）、一次依序配完、中間沒有別的生成者時成立。沒被清掉的實體（例如存檔前才生成的 HUD）穿插的位置會變；依賴編號的值的行為（奇偶錯開、亂數種子、平手判準）會變；hook 在中間生成的衍生實體會排到最後。成立時，存檔裡編號的大小順序就有了意義（決定讀檔後的順序），這是資料契約的一條。

### 6.2 實體參照的改寫

**遊戲**：敵人的 `ChaseTarget{ target = 12 }`；讀檔後玩家的新編號是 803。

初始值的函式只拿得到請求（`Storage.hpp:278-287`），拿不到對照表；所以改寫只能在讀檔的程式組值之前做，讀檔的程式要懂每個帶參照的元件與 Resource 的欄位，包含別的 Plugin 擁有的。分批讀時，指向還沒配號的實體的參照改寫不了（要第一批就配完所有號）。指向存檔外的實體：編號 0 不是保留值（`git grep` 搜 `kInvalidEntity|kNoEntity|InvalidEntity|NullEntity|reserved` 在 `engine/kernel`、`engine/entity_store` 沒有命中），要用 0 當「沒有」得先有保留 0 的規則，否則用 optional。

| 選項 | 得到什麼 | 代價 | 系譜 |
|---|---|---|---|
| 產品在讀檔的程式裡改 | Kernel 不變 | 上面全部；漏一個就指錯，沒有訊息 | — |
| 擁有者登記「參照的改寫函式」，放在存檔用的 Plugin | 知識在擁有者 | 多一個 Plugin 與登記；所有擁有帶參照元件的 Plugin 依賴它 | Bevy `MapEntities` |
| Kernel 登記改寫函式 | 一處 | Kernel 多一個和存檔有關的概念；仍要手寫 | Bevy（在 `bevy_ecs`） |

### 6.3 清除與留下的東西

清除由產品標（例如帶 `LevelContent` 的實體），在同一個同步點先刪再生。（重新配號時新舊編號不重疊，先刪後生只影響 OnRemove 與 OnAdd 誰先跑。）要寫進契約或代價的：
- 刪除時 OnRemove 的 hook 記的變更，在讀檔之後才套用（例：「敵人被消滅就掉寶」的 hook 生成的寶物出現在第 2 關）。
- 存檔的範圍必須等於清除的範圍；存檔含沒被清的實體（相機）時會有兩份；還活著、又在存檔裡的實體放不回值（漏斗不蓋已有的）。
- 有 (c) 區元件的實體：(b) 區的讀檔 System 記刪除就回 Err（Z5，`Params.hpp:597-603`），World 中斷。
- 巢狀（K0）：Loading 若由每幀那張 schedule 裡的獨占 System 巢狀跑，外層這一幀先記下、還沒套用的變更（例：這一幀剛開的一槍的子彈）會在讀檔之後套用。要嘛寫成「讀檔不可以巢狀」，要嘛寫明後果。「進關卡和 Loading 的關係」在狀態機那一批還待判。

**遊戲中讀檔之後什麼會留下**（關掉再讀時都沒有）：

| 東西 | 留下嗎 |
|---|---|
| 沒被清掉的實體 | 留 |
| (b) 區 System 的 `Local` | 留 |
| 沒存的 Resource | 留 |
| 讀檔前最後一個 tick 的事件 | 讀檔後第一個 tick 讀得到（`Params.hpp:419-420`）；例：「玩家死亡」事件讓剛讀回來的第 2 關觸發遊戲結束 |
| OnRemove hook 記的變更 | 讀檔後套用 |
| World 外記的舊編號 | 留，查不到（重新配號下無害） |

### 6.4 事件

| 選項 | 得到什麼 | 代價 |
|---|---|---|
| 寫成作者的規則（讀檔後第一個 tick 自己丟） | Kernel 不變 | 每個讀事件的 System 都要記得 |
| Kernel 在讀檔時清事件緩衝 | 一處 | Kernel 要認得讀檔 |
| 讀檔後多跑一個空 tick | Kernel 不變 | 多一個 tick；遊戲時間要扣 |

## 7. 和回滾的關係（DI-KS 12）

**要判的問題**：已核准的 DI-KS 12（2026-11-13，從舊規格 H.5 來：Restore 由外面在 Ready 呼叫、不經同步點、不觸發 hook、快照含配發器），和使用者在 LIM-7 那次說的「不用帶規格，但是這個點的設計思想可以帶過來（新老架構不同，不能照搬）」是什麼關係？K0 宣告寫「DI-KS 12 不變」。world §3 另有一句「整欄替換（Restore）只用於跨 World 接收權威狀態，不是 World 內的寫法」。

| 選項 | 怎麼做 | 代價 |
|---|---|---|
| DI-KS 12 照舊有效，回滾那一批照它設計 | 不動 | 讀檔與回滾對 hook 的規則相反（讀檔照常、Restore 不觸發），共用入口前要對齊 |

| 這一批不判，列在範圍的限界 | — | 問題延到回滾那一批 |

**我的建議**：這一批不判，列在範圍的限界。理由：你定的範圍不含回滾。

**給回滾那一批的要求**（照使用者定的範圍：回滾只定「不能和讀檔衝突」）：
- 回滾的範圍不能跨過一次讀檔（讀檔之前的快照不能還原到讀檔之後的 World）。
- 讀檔與 Restore 對 hook 的規則若不同，要寫明各自的理由；若要共用「讀檔的生成」，先對齊。
- 重看 LIM-7（重放的生成撞上帶 (b) 區元件的活實體）。
- 定 `RejectedSpawn` 的 `rollbackActive` 由誰、在哪裡設，以及總數要不要扣除重放的部分。

## 11. Architecture Delta（AGENTS §3 七項，照建議的組合）

1. 需要的 Feature：玩家存檔（使用者 2026-11-16）。
2. 現在的問題：沒有讀檔的寫法；照字面（`SpawnWithId` 在原本的範圍、bundle 直接放元件）會整批被丟、撞寫者的檢查；漏斗能做但有沒訊息的優先規則，且會變成所有可存元件擁有者的跨部件規則。
3. 變化的邊界：Kernel 的公開介面多一個指令參數「讀檔的生成」（元件與 Resource）；寫者的數法多一條例外；新的啟動檢查（只能在 Loading）。契約：讀檔＝新 World＋開局＋Loading＋原樣放回；配發器的範圍由組裝在第一次 Run 前從存檔給。
4. 影響：`engine/kernel`（Params、Registry 的數法與檢查、指紋）；說明頁；將來有存檔的產品、擁有可存元件的 Plugin 與 Module（它們不用做任何事——這是選這個做法的理由）；runner 或組裝（重建 World、給配發器的範圍）。
5. 依賴方向：不變。存檔格式在產品，Kernel 不知道存檔的格式。
6. Ownership：存檔格式歸產品；讀檔的生成是 Kernel 的機制；重建 World 的驅動歸 runner／組裝。
7. 為什麼不能更小：更小的做法（漏斗、唯一寫者自己放回、標 Shared）都可行，但各自把代價放到每一個產品與可重用 Plugin 上（5.2 的表）；這一批是基盤，選它們之後要改的是上面所有的產品。

## 12. Design Invariants 與 Replacement Criteria（草案，要你同意）

## 13. 判定（先宣告，結果出來之後不放寬；照建議的組合）

實作時用。案例名在實作前換成實際的 `TEST_CASE` 名（突變的執行器用正規式比對案例名）。

### 判定 1：行為（新測試 `tests/common/kernel/RestoreEntryTests.cpp`）

1. **新 World 原樣放回**：存檔有玩家、5 隻敵人、1 個寶箱（寶箱沒有 `Health`），記的下一個號是 900；組裝把配發器訂成 `[900, 上限]`；Loading 裡的讀檔 System 用讀檔的生成照存檔編號放回。讀檔後實體的編號、每個元件的值與存檔相同；寶箱沒有 `Health`；沒有 `RejectedSpawn`；之後一般的生成拿到 900。
2. **寫者**：`Position` 的寫者是 `Move`，讀檔的 System 也在 bundle 放 `Position`；Registry 完成時沒有 D-E2。
3. **只能在 Loading**：讀檔的生成掛在 FixedUpdate 是啟動錯誤（帶新的錯誤碼或規則代號）。
4. **區規則照算**：(b) 區的讀檔 System 用讀檔的生成放 (c) 區元件，是啟動錯誤 D-E7。
5. **丟棄規則照用**：讀檔的生成用落在配發器範圍的編號，被丟、理由 `IdInAllotterRange`；同一個編號兩筆，照 F-13。
6. **hook**：每個放回的格子 OnAdd 各一次；`Added<Position>` 在讀檔後的第一個讀者成立；補出的格子的 `added` 是那個同步點的記號。
7. **初始值的宣告不蓋存檔值**：實體同時帶原本的生成請求（`Arrival`）與存檔的 `Position`，讀檔後 `Position` 是存檔值。
8. **串接**：存檔沒有 `Health`、但 `Arrival` 有補 `Health` 的宣告時，`Health` 會出現——案例固定實際行為，契約寫「存檔的元件集合與初始值的宣告要一致」（若 5.3 的小題選「讀檔的生成跳過第 5a 步」，期待改成不出現）。
9. **Resource**：金幣與「玩家是哪個實體」經讀檔的生成放回；讀檔後值與存檔相同；`Wallet` 仍是唯一的一般寫者，沒有 D-E2。
10. **遊戲中讀檔＝重建**：第一個 World 跑過、有主選單與第 3 關；建第二個 World 讀第 2 關的存檔；第二個 World 裡沒有第 3 關的實體、沒有上一個 World 的事件、tick 在 ready 時為 0。
11. **連續讀兩次**：同一份存檔讀兩次（兩個新 World），結果逐值相同、`Summary()` 相同。
12. **對照（記錄來由第 3 件）**：配發器範圍和存檔時相同，用 `SpawnWithId` 照存檔編號放回，每一筆都以 `IdInAllotterRange` 被丟。

案例 10、11 驗的是「新 World」這個契約的後果，靠的是 World 建構本身；它們守的是契約，不是讀檔的程式。

## 14. 範圍的限界

- 只定讀檔的入口與規則；存檔格式、IO、狀態機的流程、Loading 的 stage 與分批與驅動、重建 World 的驅動不在這一批。

- 單機、(b) 區為主；(c) 區的產品讀檔沒有分析（6.3 列了 Z5 的硬限制）。
- E2（單調不重用是通用預設）沒有判；6.1 的順序那一句依賴它。
- 分批讀檔時，指向還沒放回的實體的參照：新的 World 原樣放回時不受影響；重新配號時改寫不了（6.2）。
- 參考實作的事實來自偵察報告（讀本機原始碼，issue 原文沒讀）；bevy_ggrs 本機沒有原始碼，沒有讀到。Bevy #18054 的內容是「釋放大量實體後指定任意編號造成極端的效能問題」與「Entity 應該不透明」（偵察報告 1.5），和本題的撞號不是同一個問題，修訂 0 引用錯了，已拿掉。
- 沒有真實的單機產品；判定用測試樣本。
- 沒有建置、沒有試做；「讀檔的生成」的形狀（參數的型別、掛點的檢查）實作時定，先給你看。
- 一個 System 最多 16 個參數（`SystemTraits.hpp:29`）；讀檔的 System 放很多種元件時要用一個帶多個型別的參數。
