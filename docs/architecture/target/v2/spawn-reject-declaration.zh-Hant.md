## 1. 這一批做什麼

### 1.1 用遊戲講

PvP 的對局裡，玩家 7 正在玩（實體 7 還活著）。網路那頭又送來一筆「玩家 7 加入」——可能是重送、可能是 bug、也可能是有人故意送的。同一幀還有一筆正常的「玩家 8 加入」。

- **現在**：負責加入的 System 照收到的編號記「用編號 7 生成玩家」與「用編號 8 生成玩家」。到了同步點，Kernel 看到 7 還活著，**斷言失敗，整個伺服器程式終止**。使用者的話：「我只要發送一個不存在的編號，就能把服務給炸了。」
- **之後**：同步點做到生成這一步時，「用編號 7 生成」那一筆被丟掉：不生成、它帶的元件不寫、不過初始值的宣告（漏斗）、不觸發 OnAdd，原本的玩家 7 原封不動；Kernel 記下一筆紀錄（編號 7、哪個 System 記的、哪張 schedule、為什麼被丟）並把總數加一。玩家 8 照常生成。這一幀照常跑完，`Run` 不回報錯誤，程式不終止。

作者要讓玩家 7 「重新進來」時，照舊在**同一個 System 裡先記刪除 7、再用編號 7 生成**。同一個同步點固定先刪再生（2026-11-11 定的，不動），所以這一對照舊有效。（例外：編號 7 落在配發器的範圍時，刪除照做、生成被丟，7 就消失了——2.3；別的 System 在同一個同步點也生成了 7 時，看 2.2 的規則。）

## 2. 被丟掉的情形

判斷在**每一次套用的第 4 步**做（同步點的兩次、清空輪的每一輪；它們走同一段 `phase`）。被丟掉的那一筆，下面這些**都不發生**：

- 不加入存活的實體清單；
- 它帶的元件（bundle）一個都不寫；活著的那個實體的格子、`added`／`changed` 記號都不動；
- 不進第 5a 步（初始值的宣告只看第 4、5 步**新加**的格子），所以不補值；
- 不觸發 OnAdd（第 6 步只看新加的格子），也就不會因它記下新的 hook 紀錄；
- 不取新的記號（stamp）；`syncEpoch` 照同步點的規則加一，不因它多加；
- 同一步其餘的生成照常（被丟的只有那一筆）。

**不受影響的**（查過程式）：

- **用 `Spawn`（配發器）生成時，編號在記錄時就配掉了**（`Params.hpp:544`；規格 A.1：記錄時配發，同步點才能依編號排序），丟掉那一筆不退回編號。
- **Z5 的重查照舊**：它排在刪除之前、看這次套用的全部紀錄，包括之後會被丟掉的生成（`World.cpp:529-536`）。所以「(b) 區的刪除 X」配上「(c) 區用 X 生成」照舊回 Z5、World 中斷——**即使那筆生成之後會被丟掉，甚至 X 根本不在**。這是既有的規則（K-S10），不是這一批造成的；但它表示外面送來的編號配上同一窗一筆 (b) 區的刪除，仍然能讓 World 中斷。寫進第 9 節。
- **同一個編號上的別的紀錄（插入、移除）**：照舊是獨立的紀錄。移除在第 3 步、插入在第 5 步，看的是「那時誰活著」：生成因「編號還活著」被丟時，它們落在原本活著的那個實體上；生成因「落在配發器的範圍」被丟、編號又不活著時，插入照第 5 步的規則丟掉並計入 `DroppedMissingEntity`。同一次呼叫記的那幾筆要不要跟著丟，列成選項（3.2）。
- **hook 佇列與清空輪**：被丟掉的那一筆不觸發 hook，所以不往 hook 佇列加東西；清空輪每一輪也照同樣的規則丟。
- 被丟掉的紀錄不進 World 的摘要（`World::Summary`，規格 D-9：存活清單、欄、Resource、事件）。

### 2.1 往活著的編號生成（理由「編號還活著」）

第 4 步開始時（這次套用的刪除已經做完），編號活著，而且它不是這個同步點較早生成的（那種歸 2.2）→ 丟掉。

- **重入的一對照舊有效**：同一次套用裡先刪後生——刪除在第 2 步，第 4 步時編號已經不活著。
- 刪除記在**上一窗的 hook**、生成記在**這一窗的 System**：第 0 步那次先刪掉，這一窗那次再生成，也有效。
- 刪除和生成**隔了一個同步點以上**：生成時編號不在，照常生成（`nested-same-id-respawn-not-engine` 第二問的情形）。
- 活著的編號上有兩筆生成、兩筆都不是這個同步點生成的：兩筆都被丟、理由都是「編號還活著」（被丟的那筆不算「生成過」）。

### 2.2 同一個編號在同一個同步點被生成兩次——**使用者 2026-11-15 重判：同一個記錄者留先記的，不同記錄者全部丟掉**

**使用者定的**（`spawn-reject-drop-count-reason` 第 1 件，主會話的建議、使用者「照建議」）：「留排在前面的那筆、丟掉後面的，讓結果固定」。主會話當時給的理由是「緊鄰的兩條同樣能被外面的資料觸發」；「排在前面」怎麼定義當時沒有談。

**檢查找到的問題**（報告 B-1，實驗案例在試做上跑過）：「排在前面」只能用執行計畫的位置 `(planPos, recSeq)` 定。兩個 System 的 bundle 有共同的元件型別時，它們本來就有資料衝突，(c) 區要明寫順序、(b) 區依登記序（規格 A.1、DI-KS 5），先後是作者宣告的。但 **bundle 沒有共同型別時，兩個 System 互不衝突**，執行計畫裡誰在前只取決於**登記順序**：

- 例子：(c) 區的 System「生成玩家」用編號 7 生成 `Bundle<Pos>`，另一個 (c) 區的 System「生成觀戰者」也用 7 生成 `Bundle<Vel>`。兩個不衝突，`Finish` 不報錯。把兩個 plugin 的登記順序對調，留下來的就從玩家變成觀戰者，World 摘要不同（實驗：(b) 區、(c) 區各一組，摘要都不同）。
- 這碰到 **DI-KS 5「(c) 區對登記順序不敏感」**（Design Invariants，守衛 J-44）、規格 D-9（「把同一組 (c) System 的登記順序任意排列……World 摘要相同」）與 F-2／J-32 的第一個子案例（不衝突的 System 重排，World 相同）。以前這種程式在任何順序下都終止，所以條文成立；改成「留前面的」之後第一次出現「不衝突、卻依登記順序」的結果。
- 同一個 System **一次呼叫裡**記兩次（例：同一幀收到兩筆「玩家 7 加入」，負責加入的只有一個 System）：先後是 `recSeq`＝程式的順序，和登記順序無關，沒有這個問題。
- 同一個 hook 被叫兩次（不同實體觸發）：hook 被叫的順序依實體與元件的編號（規格 F.1），和登記順序無關。**兩個不同的** hook 在同一輪生成同一個編號：hook 依登記順序被叫，有同樣的問題。

| 選項 | 系譜 | 行為 | 代價 | 需要它的 Feature |
|---|---|---|---|---|
| **留排在前面的，寫明例外** | 使用者定的規則照原樣 | 依 `(planPos, recSeq)` 留最小的 | DI-KS 5、D-9、F-2 各加一句例外（Design Invariants 的變更）；(c) 區第一次有「不衝突卻依登記順序」的結果，兩端的 plugin 登記順序不同就分岔 | 同一幀重送的加入能進來一筆 |
| **同一個記錄者留先記的，不同記錄者全部丟掉** | 新的；把使用者的「留前面的」限在先後確定的情形 | 同一次套用裡同一個編號的生成：全部來自同一個記錄者（同一個 System，或同一個 hook）→ 依 `recSeq` 留第一筆；來自兩個以上的記錄者 → 全部丟掉（理由「這個同步點生成了兩次」，明細記下另一個記錄者） | 規則多一個條件；兩個 System 撞同一個編號時一個都不生成（這種情形一定是程式或資料的錯：負責加入的通常只有一個 System） | 同上（重送落在同一個 System 裡）；DI-KS 5 不用改 |
| **用指定編號生成的 System 彼此算衝突** | 規格 A.1 對 `Spawn` 的做法：「兩個會生成實體的 System 一定有資料衝突……配發序列化是存取契約推出來的結果」 | `SpawnWithId` 多推出一個共用的存取項；(c) 區沒寫順序就是啟動錯誤 D-E8，(b) 區依登記序；之後依計畫位置留前面的 | 存取集合、Registry／C 指紋的內容都變；既有的測試與 hook 裡同時有兩個 `SpawnWithId` 的要補順序；工作量比這一批大，時間要重估 | 同上；先後永遠是作者宣告的 |
| **重複的全部丟掉** | 新的 | 同一次套用裡同一個編號有兩筆以上，全部丟掉 | 同一個 System 一次呼叫裡的重送也全部丟掉——同一幀送兩次「玩家 7 加入」，7 一筆都進不來；和使用者定的「留前面的」差最多 | 無 |

**使用者選了「同一個記錄者留先記的，不同記錄者全部丟掉」**（我建議的；理由使用者沒有說）。我給的理由： 理由：它保住使用者要的「結果固定」與「留前面的」最常見的用途（一個 System 收到重送），又不改 DI-KS 5；兩個不同的記錄者撞同一個編號，沒有哪一個「本來就該留」，丟掉兩筆、兩筆都進明細，作者看得到是哪兩個。代價是規則多一個條件。「彼此算衝突」最乾淨，但改到存取契約與指紋的內容，超出這一批。

**跨兩次套用**（不管選哪個）：第 0 步（上一窗 hook 記的）先套用，所以它的生成先發生；第 1～7 步裡同一個編號的生成，第 4 步時編號活著 → 丟掉，理由歸「這個同步點已經生成過」，明細記下第 0 步那筆的記錄者。順序是 F.2 固定的，和登記順序無關。但第 1～7 步裡**先刪了再生成**時，第 4 步時編號不活著，照常生成（判斷看「現在活不活著」；記下的編號只用來選理由）。清空輪每一輪是各自一次套用（`hook-flush` 的「跨輪不合併」），上一輪生成的歸「編號還活著」。（分法是我補的。）

**排序鍵**：第 4 步現在只照編號 `std::sort`（`World.cpp:590`），不穩定、不比 `(planPos, recSeq)`。改成照 `(編號, planPos, recSeq)` 排序，排序後斷言相鄰的鍵不相等——**這是規格 F.6 本來就要求的**（「排序後 GYO_ASSERT 相鄰鍵不相等」，`spec.zh-Hant.md:718`；第 5 步插入已經這樣做，`World.cpp:616-618`），修訂 0 漏了。`(planPos, recSeq)` 在一次套用裡唯一（hook 的紀錄 `planPos` 相同、`recSeq` 由 hook 佇列統一計數），所以這條斷言只有 Kernel 自己的錯才會觸發，外面的資料碰不到。

### 2.3 用指定編號生成，編號落在配發器的範圍（理由「落在配發器的範圍」）

`SpawnWithId` 的編號落在本 World 配發器的 `[first, last]` 裡 → 丟掉。不管它現在活不活著、配發器有沒有配到那裡（還沒配到的編號若照收，之後配發器配到它時就撞上）。World 沒有登記配發器、或配發器的 Resource 不在時不查（和現在一樣，`World.cpp:595`、`detail/Storage.hpp:378-381`）。

同一次呼叫裡先刪了再用這個編號生成：刪除照做、生成被丟，編號就消失了。

### 2.4 一筆同時符合幾種時（順序是我補的）

每筆只有一個理由，依這個順序取第一個成立的：**落在配發器的範圍 → 這個同步點生成了兩次 → 編號還活著**。範圍的檢查不看世界的狀態（只看編號與配發器），放最前面，作者一看就知道是「這個編號不該由外面給」。

### 2.5 用配發器生成（`Spawn`）撞上的時候——**使用者 2026-11-15 定：照樣丟掉，加標記**

上面三種情形，使用者說的「外面送一個編號就把服務炸了」只會經 `SpawnWithId` 發生（編號來自外面）。用 `Spawn` 時編號由配發器給，正常的程式不會撞上。會撞上的情形（查過程式；後兩項是檢查者補的）：

- 配發器自己的錯：Kernel 的 `RangeAllotter`，或**產品自己寫的配發器**（規格 A.1：配發策略是產品的 Resource）重複給了編號；
- 組裝或 runner 在 Ready 時用 `World::Insert` 直接放了一個落在配發器範圍裡的編號（`World.hpp:133`），之後配發器配到它；
- **組裝或 runner 重設配發器**：(b) 區的配發器在**任何一次** Ready 都能被 `SetResource` 重設（`World::Access` 的 Ready 分支只擋 (c) 區，`World.cpp:197-201`；實驗：跑過一次之後重設，下一次 `Spawn` 配到活著的 100）；純 (b) 的 World（工具、單機）正是這種；System 也能用 `ResMut` 改配發器；
- **回滾的重放**（規格 H.5，gyo2 還沒實作，照規格推的）：配發器被還原後重放，`Spawn` 再配到同一個編號；如果那個實體還帶著不回滾的 (b) 區元件而活著，就撞上（3.4 也講這件事）。

撞上的那一筆可能來自 System，也可能來自 hook（hook 也能拿 `Spawn`，`CoverageTests.cpp:277-281`），所以可能出在第 0 步或清空輪。

`Spawn::New` 在記錄時就把編號交給記錄者（`Params.hpp:545`），規格明寫「同一次呼叫裡可以立刻拿它來 Insert」（F.1）。丟掉那一筆時，接著記的插入會**落在原本活著的那個實體上**——這和 3.2 的情形相同，差別只在編號是誰給的。

| 選項 | 系譜 | 行為 | 代價 | 需要它的 Feature |
|---|---|---|---|---|
| **照樣丟掉，明細多一個標記** | 這一批的方向直接延伸；使用者的「拒絕的話，需要明確給出理由，否則內部有bug沒發查」 | 和 `SpawnWithId` 一樣依 2.1、2.2 丟掉；明細多一個「用配發器生成」的標記 | 一個 bug 只留下一筆診斷；同一次呼叫接著的插入改到別人的實體（和 3.2 選「照常」的後果一樣），不看診斷就不會發現 | 回滾的重放（計畫中）撞上時不讓 World 中斷 |
| **回報錯誤，World 中斷** | `err-is-bug-world-readable`（到達 Executor 的 Err 代表 bug；中斷後 World 仍可讀） | 新的錯誤碼（暫名 `AllotterIdCollision`，規則 A.1）；先把這次套用的生成全部查完、有一筆撞上就一筆都不套用（比照 Z5 的重查）；Executor 記錄一次、World 中斷、`Run` 回 Err | 多一個錯誤碼（`KernelError.hpp`、`ToString`、規格 E.5 的 Err 來源、說明頁的錯誤表）；同一個編號一筆 `Spawn`、一筆 `SpawnWithId`（產品的配發器 `Owns` 沒涵蓋時）時，誰排在後面決定是「一筆診斷」還是「World 中斷」；回滾的重放撞上時正常的重放會中斷；上層會照「撞上就重建 World」來寫（保守的選項，`mechanism-not-conservative`） | 無點名的 |
| **維持斷言** | 2026-11-11 的規格 A.1、F.2 第 4 步 | 行程終止 | 和現在一樣；外面的資料走不到這條路；但 (b) 區的配發器被組裝或 runner 重設這類程式錯誤會讓整個行程終止 | 無 |

**使用者選了「照樣丟掉，加標記」**（我建議的；修訂 0 建議「回報錯誤」，後來改了）。我給的理由： 理由：使用者對這一類的話是「拒絕、留理由，內部的 bug 才查得到」，沒有區分編號是誰給的；它和 3.2 的處理一致（修訂 0 對 `SpawnWithId` 接受「插入落在活著的那個」、對 `Spawn` 卻要中斷，理由只差在「是不是程式寫錯」，站不住）；回滾的重放（計畫中的 Feature）撞上時不會讓正常運作的 World 中斷；「回報錯誤」是保守的選項，照 `mechanism-not-conservative` 它的代價要算進去。

## 3. 我補的細節與另外的選項

### 3.1 紀錄的形狀（使用者 2026-11-15 核准：「照這個」）

Kernel 自己定義的紀錄型別，放進 World 現有的診斷紀錄（`World::Diagnostics<R>()`、`TakeDiagnostics<R>()` 讀的那一套，`World.hpp:203-229`）。名字照 `naming` 的規則（Kernel 的概念，不指任何產品）：

```cpp
enum class SpawnRejectReason : std::uint8_t {
    IdInAllotterRange,  // 2.3
    IdSpawnedTwice,     // 2.2
    IdAlive,            // 2.1
};

struct RejectedSpawn {
    EntityId entity;
    SpawnRejectReason reason;
    std::string emitter;        // 記錄者（System 或 hook）的名字
    bool emitterIsHook;
    Zone emitterZone;           // 3.4 用得到
    bool fromAllotter;          // 用 Spawn（配發器）記的（2.5）
    std::string schedule;       // 套用它的那張 schedule
    std::uint32_t step;         // 這筆紀錄的 planPos（System：它在計畫裡的位置；hook：觸發它的同步點的位置）
    std::uint32_t appliedAt;    // 丟掉它的那個同步點的位置（清空輪：最後一個同步點的位置）
    std::uint64_t tick;         // 那張 schedule 的 domain tick（沒有時鐘時是 0）
    std::string otherEmitter;   // 只在 IdSpawnedTwice：另一筆（留下的那筆，或 2.2 選「不同記錄者全部丟掉」時的另一個記錄者）是誰記的
};
```

- **總數**：`World::RejectedSpawns()`，一個 64 位元的計數，World 的一生只增不減；`TakeDiagnostics` 不歸零它。
- **怎麼讀**：runner 在兩次 `Run` 之間（World 是 Ready 或 Interrupted 時）讀（現有的規則，`World.hpp:208`）：`Diagnostics<RejectedSpawn>()` 看、`TakeDiagnostics<RejectedSpawn>()` 取走並清空明細。作者（System）讀不到——`DiagnosticsWriter` 只寫不讀（S-8）。遊戲要通知客戶端「加入被拒」時：「編號還活著」「落在範圍」由 System 自己先查（規格 A.1 原本的寫法）；「這個同步點生成了兩次」是別的記錄者造成的，System 查不到，只能由 runner 在兩次 `Run` 之間讀明細。
- **順序**：同一次套用裡依 `(編號, planPos, recSeq)`；一個同步點先第 0 步那次、再第 1～7 步那次；跨同步點依執行順序。所以明細的順序也是「同樣的輸入、同樣的結果」。
- **World 中斷**：明細與總數都留著（診斷紀錄不被 `DiscardDeferred` 清掉，`World.cpp:708-714`；B-13）。
- **World 重建**（世代切換）：新的 World 從 0 開始；runner 要在銷毀前取走。
- **產品的 System 不能寫這個型別**：`DiagnosticsWriter<RejectedSpawn>` 編譯失敗（`static_assert`，訊息帶標記字串；加一個 `compile_fail` 的樣本），避免產品的紀錄混進 Kernel 的明細。
- **不叫 break 掛鉤**：break 掛鉤是給 `KernelError` 的（§2b），丟掉不是錯誤。要找記錄的地方看 `emitter` 與 `step`；要找丟掉的地方看 `appliedAt`。
- **回滾的重放**（計畫中）：現有的診斷緩衝每筆有 `rollbackActive` 欄（`detail/Storage.hpp:229-233`，回滾那一批會設），這一批固定寫 `false`。重放時同一筆會再被丟一次，明細與總數會重複——回滾那一批要重看（第 9 節）。

### 3.2 同一次呼叫裡、同一個編號上的插入與移除——**使用者 2026-11-15 定：照常落在活著的那個**

例子：加入的 System 寫成「用編號 7 生成玩家（帶 `Player`）」接著「往 7 插入 `Name{"新來的"}`」。7 還活著時，生成被丟掉；插入是另一筆紀錄，第 5 步時 7 活著，**插入落在原本的玩家 7 上，把他的名字改掉**。移除也一樣（第 3 步就落在原本的 7 上）。

| 選項 | 系譜 | 行為 | 代價 | 需要它的 Feature |
|---|---|---|---|---|
| **照常落在活著的那個** | 現有的規則（插入、移除看當時誰活著） | 插入、移除照舊是獨立的紀錄 | 上面的例子會改到別人的資料；作者要把生成時的值都放進 bundle 或初始值的宣告（它們本來就是給生成用的地方），說明頁寫明；以前這種程式會終止，現在會改到別人（5.2.1 第 2 點列為放寬的面） | 無額外的 |
| **同一次呼叫記的、同一個編號上的插入與移除一起丟掉** | 新的；比較接近使用者的「這種命令……更本就不會進到流程中」 | 被丟掉的生成「帶走」同一次呼叫在那個編號上記的其他紀錄 | 紀錄要多記「哪一次呼叫」；移除在第 3 步、生成在第 4 步，要先算出哪些生成會被丟才能決定第 3 步（判斷要移到第 2 步之後、第 3 步之前）；插入的規則多一個例外（一筆紀錄套不套用取決於另一筆）；別的記錄者記的照舊落在活著的那個 | 外面的加入照「生成＋插入」寫時也安全 |

**使用者選了「照常落在活著的那個」**（我建議的；說明頁寫明「生成時的值放進 bundle」）。我給的理由： 理由：bundle 與初始值的宣告就是生成時給值的地方，PvP 的 `ApplyMembership` 也是這樣寫；把插入綁到生成上，會讓「插入」這條規則有例外，而且只擋得住同一次呼叫的情形。你覺得「不會進到流程中」該包含同一次呼叫的插入與移除的話，選第二個。

### 3.3 明細會不會無上限地長——**使用者 2026-11-15 定：不設上限，runner 取走**

外面每幀送一筆壞的加入，明細每幀多一筆。runner 每次 `Run` 之後取走就不會長；從來不取，就一直長（一筆約一百位元組加上名字；每秒 60 筆、一小時約 20 MB）。

| 選項 | 系譜 | 行為 | 代價 | 需要它的 Feature |
|---|---|---|---|---|
| **不設上限，runner 取走** | 現有的 `DiagnosticsWriter` 的緩衝（也不設上限） | 每一筆都有完整的理由 | runner 不取就一直長；說明頁寫明 runner 要定期取走 | 使用者的「每筆拒絕要有明確的理由」 |
| **固定上限、留最早的、另計被省略的筆數** | 新的（日誌限流的常見做法） | 明細最多 N 筆（N 沒有根據，例如 1024），之後只加總數與「省略」的計數 | 超過上限的那些沒有編號與記錄者，和「每筆拒絕要有明確的理由」不完全一致；N 是新的常數 | 不取明細的 runner 也有上限 |

**使用者：「不設上限，runner 取走」**（我建議的）。我給的理由： 理由：使用者要每一筆都查得到理由；現有的診斷紀錄也是這個規則；外面的資料要讓它長，每筆都得先變成一筆生成的紀錄，那一筆本身在佇列裡也佔記憶體，所以明細不會放大攻擊的量。

### 3.4 (c) 區的生成被不是 (c) 區的東西擋住——**使用者 2026-11-15 定：照樣丟掉，寫明限制（LIM-7）**

Z1、Z2 讓 (b) 區的 System 只能生成帶 (b) 區元件的實體、(c) 區的只能生成帶 (c) 區的。下面的情形，(c) 區的結果會取決於 (b) 區，或組裝、runner 直接寫進 World 的東西：

- 同一個同步點，(b) 區的 System 和 (c) 區的 System 都生成編號 7（2.2 選「留排在前面的」時，(b) 區那筆在前 → (c) 區那筆被丟；選「不同記錄者全部丟掉」時兩筆都丟，(c) 區照樣沒生成）；
- 編號 7 活著，但只帶 (b) 區的元件（例：客戶端自己做的特效實體），(c) 區用 7 生成 → 被丟掉；
- **回滾的重放**（計畫中，照規格 H.5 推的）：還原後重放 `ApplyMembership` 或 `Spawn`，同一個編號的實體還帶著不回滾的 (b) 區元件（例如 (b) 區 hook 加上去的）而活著 → 重放的生成被丟，(c) 區的格子沒有重建。這是正常運作下就會出現的情形。

(b) 區在兩端可以不同，所以兩端的 (c) 區狀態會分岔。現在這些情形都是斷言（程式終止），所以以前不會悄悄分岔。

| 選項 | 系譜 | 行為 | 代價 | 需要它的 Feature |
|---|---|---|---|---|
| **照樣丟掉，寫明限制** | 這一批的規則照原樣 | 明細帶 `emitterZone`，看得出是哪一區被丟；說明頁寫「有 (c) 區資料的 World，(b) 區生成用的編號不能和 (c) 區的重疊」；回滾那一批重看 | Kernel 不擋；分岔要靠診斷與兩端比對才發現；回滾的重放會撞上，回滾那一批一定要處理 | 無額外的 |
| **(c) 區的生成只看 (c) 區的格子** | 新的；Z1 的精神（(c) 區的結果不取決於 (b) 區）；Z5 的檢查已經在看「實體有沒有 (c) 區的欄」 | 實體活著但沒有任何 (c) 區元件時，(c) 區記錄者的生成照常把 bundle 寫上去（不加入存活清單，它本來就在；寫上的格子算新加，過初始值與 OnAdd） | 「活著」的判斷分區；同一個實體上新舊元件混在一起（舊的 (b) 區元件留著）；2.2 的重複不受影響 | 回滾的重放（計畫中）需要的行為 |
| **(c) 區的生成被 (b) 區擋住時回報錯誤** | 像 Z5 一樣中斷 | — | 外面送一個撞到 (b) 實體的編號就能讓 World 中斷，回到使用者要避免的情形 | 無 |

**使用者 2026-11-15 定：照樣丟掉，寫明限制**（原話：「照樣丟掉，寫明限制。這個就合射擊一樣，之前的權威Match的設計就是為了避免這種情況的。」）。查過舊架構的設計思路（`docs/object_fps_pvp/network-architecture.zh-Hant.md` §1：Match 是唯一的權威；`entity-model.zh-Hant.md` §5.3、E-3、RC-5：客戶端不配編號、本機才有的東西不佔編號空間）之後，使用者：「不用帶規格，但是但是這個點的設計思想可以帶過來。（新老架構不同，不能照搬。）」「對，就這樣寫。但是要記明這個是PVP的形式。」「如果是單機應該會更簡單。」說明頁照下面兩段寫：

- **PvP（有權威端）的形式**：有 (c) 區資料的 World，編號只由權威的一方給。只在本機存在的東西不和權威共用編號空間（怎麼分開由產品決定）；(c) 區的狀態以權威為準。照這樣設計，(b) 區就擋不到 (c) 區的生成；Kernel 不另外擋。
- **單機**：只有一端，不會分岔；同一個 World 的生成都走配發器就好；用指定編號生成時避開配發器的那一段（撞到會被丟掉，明細查得到）。

舊架構的具體做法（暫時鍵、ActionId 等）不帶過來。回滾的重放撞上帶 (b) 區元件的活實體，回滾那一批重看（第 9 節）。這條限制要不要另外登記成 `limits.zh-Hant.md` 的一條 LIM，見 3.6。

`limits.zh-Hant.md` 加一列（實作後狀態改成 `implemented in v8-arch-gyo2-spawn-reject`）：

## 7. Architecture Delta、Design Invariants、要改的程式

### 7.1 Architecture Delta（AGENTS §3 的七項）

1. **Feature**：外面送來的加入（PvP Match，H.2b 第 4 點）不讓伺服器終止。
2. **現在的問題**：外面的資料能讓三條常開的斷言失敗，伺服器程式終止；規格把防守交給每個發出 `SpawnWithId` 的 System（A.1、H.2b 第 4 點），漏一個就終止。
3. **變的邊界**：同步點第 4 步的規則（DI-KS 9 加一句、規格 F-13；2.2 的選擇可能動到 DI-KS 5）；World 的公開介面多一個紀錄型別、一個列舉、一個計數（`World.hpp`）；`Detail::Record` 多兩個欄位；`DiagnosticsWriter` 多一個 `static_assert`；執行計畫指紋與 C 指紋的版本升一。
4. **影響**：只有 `engine/kernel`、`tests/common/kernel`、文件；gyo2 上沒有產品。
5. **依賴方向**：不變。
6. **Ownership**：「外部來的重複編號要拒絕」這件事從發出 `SpawnWithId` 的 System（規格 A.1）移到 Kernel 的同步點（使用者的決定）。存活與否本來就是 World 的狀態（State Authority 不變），沒有新的寫照。
7. **為什麼不能更小**：維持斷言、整次 `Run` 回報錯誤、只丟不留痕跡，使用者都比過、沒選。

### 7.2 新的句子（要你同意）

**DI-KS 9**（target `kernel.zh-Hant.md`）在「結果不依 System 之間的記錄順序。」之後加：

> spawn 階段依 (EntityId, planPos, recSeq) 排序、鍵唯一；下列紀錄被丟掉（不生成、不寫 bundle、不過初始值的宣告、不觸發 OnAdd），留一筆 `RejectedSpawn` 明細與總數，不是錯誤：`SpawnWithId` 的 id 落在本 World 配發器的範圍；同一個同步點裡同一個 id 的第二筆以後的生成（同一個記錄者留第一筆，不同記錄者全部丟掉）；id 還活著。（spec F-13）

守衛加 J-55。

**規格新增 F-13**：「同步點每一次套用的第 4 步，依 (EntityId, planPos, recSeq) 處理生成、排序後斷言相鄰鍵不相等；每筆依『落在配發器的範圍（只對 `SpawnWithId`）→ 這個同步點生成了兩次 → 編號還活著』取第一個成立的理由，成立就丟掉那一筆：不生成、不寫 bundle、不進第 5a 步、不觸發 OnAdd、不取記號。同一次套用裡同一個 id 的生成來自同一個記錄者時留第一筆，來自兩個以上的記錄者時全部丟掉；第 0 步生成過的 id 在第 1～7 步又被生成而且活著時，後者丟掉。World 加一筆 `RejectedSpawn` 明細（編號、理由、記錄者、記錄者是否 hook、記錄者的區、是否用配發器、schedule、記錄的位置、丟掉的位置、domain tick、生成了兩次時的另一個記錄者）與總數，不是錯誤，`Run` 照常。同一個同步點裡先刪後生不被丟掉（id 落在配發器的範圍時除外）。明細與總數在 World 中斷後保留；runner 以 `TakeDiagnostics` 取走明細，總數不歸零。」檢查：J-55、J-32、J-8。

## 9. 範圍的限界

- **不做**：K0（巢狀執行）；`HANDOFF.md`（主會話持有）。K0 宣告第 16 條那個案例的期待會因這一批改變（主會話的理由），由 K0 自己改。「外層記了刪除某個編號，同一幀的固定步裡用同一個編號生成」是 K0 之後才會出現的情形，這一批不寫。
- **讀檔**：還沒設計；照 2.3，用 `SpawnWithId` 把單機存檔的實體放回去會整批被丟（編號都在配發器的範圍）。讀檔設計時要定怎麼放回去（`nested-same-id-respawn-not-engine` 已經這麼寫）。
- **回滾**（還沒實作）：重放時的生成可能撞上帶著 (b) 區元件的活實體（3.4）；明細的 `rollbackActive` 這一批固定 `false`，重放時明細與總數會重複（3.1）。回滾那一批要重看這兩件。
- **Z5**：(b) 區的刪除配上 (c) 區的生成仍會讓 World 中斷（既有規則），所以「外面的編號不讓 World 中斷」不是無條件的（2 節開頭）。
- 3.4 的風險 Kernel 不擋（使用者定的，LIM-7）。
- 目前只有 Serial 執行器；「結果不隨執行順序、登記順序變」用登記順序對調與很多筆的案例檢查，並行執行器還不存在。
- 沒有做成熟方案（其他引擎遇到「往已存在的實體生成」怎麼處理）的對照。
- 條文表（5.1）是用 `git grep` 搜尋「GYO_ASSERT」「活著」「配發」「allotter range」「alive」找的（先命中已知的 `World.cpp:594`、`Params.hpp:572`），加上檢查者補的三處；實作改文件時再逐頁對一次。
