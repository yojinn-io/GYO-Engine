## Design Invariants

正式：使用者 2026-11-13 核准（kernel HANDOFF `v8-arch-target-di-approved`）。本節的變更是 Architecture Delta（AGENTS §3），要使用者同意。

<a id="di-ks-1"></a>
**DI-KS 1.** **描述從簽名推出，一份。** System 的資料存取集合等於其參數型別的 Contribution 聯集（含 bundle 的延後寫、`SetRead` 在 finish 展開的讀；`ExclusiveWorld<…>` 的 Contribution 是所有元件與 Resource 的值的讀寫，不含 `Message` 的讀寫（它可以當場 `Trigger` 推送式事件，DI-KS 10）；`Writes<…>` 是選填的標註，元件與 Resource 都可以列，不改變它的存取、不算寫者，記進登記表的 `annotatedWrites`；它可以在執行中跑 schedule（DI-KS 16～19））；登記 API 不接受手寫的第二份存取宣告；System 是無狀態的可呼叫物，參數只能是 `ParamTraits` 特化過的型別，句柄不可複製、不可移動。守衛：J-10～J-12；J-12「`ExclusiveWorld<Writes<R>>` 不是 R 的寫」「Writes lists a component and a resource in key order and writes neither」；J-59「ExclusiveWorld::Trigger runs the observers now …」。（DI-K2 的推導半；S-1～S-4、S-13；`v8-arch-gyo2-exclusive-writes-optional`；`ExclusiveWorld` 當場觸發：`v8-arch-gyo2-time-events` 10.1；`Writes<…>` 收元件：第 4 批宣告 2.2）（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）
〔併自 system-contract DI 1、DI 3〕可呼叫物是非成員函式或無捕獲 lambda：無捕獲、無 `this`；有捕獲的 lambda、成員函式、泛型 lambda、多載的 `operator()` 編譯失敗。

<a id="di-ks-2"></a>
**DI-KS 2.** **System 回傳 `Result<void, KernelError>`（回傳契約，不是錯誤通道；Ok 是正常路徑）；經 World 的繞路由存取驗證（可關）攔，違規以 Err 回傳、最外層 Run 回傳一次並 Interrupted、Kernel 不寫日誌，任何組態不靜默。**〔草稿，`v8-arch-gyo2-error-levels` D1：原為「Executor 記錄一次」；Kernel 不再有錯誤處理器，Err 一定回到呼叫者，見 target/error-handling DI 1、4；合併前核准定稿〕 System 自己的執行緒上經 World API 存取未宣告的 `(id, mode)`，驗證在存取當下記為違規；未宣告寫入的欄在 System 邊界有淨變化，驗證記為違規；違規由跳板回 Err；驗證是開發工具，關閉（release 預設）時不查、System 回 Ok，寫明且列 LIM-3。記錯當下不斷言，只有會返回的 `breakOnKernelError` 掛鉤（一個事件只有一種性質）。執行期不攔 untyped `Commands`、`Despawn`、`ExclusiveWorld` 對任何資料的寫入（`v8-arch-gyo2-kernel-subtract-structure`：伺服器權威靠 digest 比對與伺服器覆蓋來抓錯；digest 在權威 Module，[DI-A 12](v2/authority.zh-Hant.md#di-a-12)）。守衛：J-5、J-6 的 W-6 那半、J-57 的閉包案；J-32b 留下的那段。（W-5、W-6；修訂：B4／S6／S8；`v8-arch-gyo2-no-runtime-interception`）（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）
〔併自 system-contract DI 2、error-handling DI 1〕`Result<void, KernelError>` 是回傳契約，Ok 是正常路徑；Err 帶完整上下文，逐層包一層（上下文鏈）；存取驗證記下的違規與 System 自己的 Err 是並列清單、不互包；release 目標的測試也要看到 Err 與 Interrupted。補守衛：J-10（回傳型別）、J-35。

<a id="di-ks-3"></a>
**DI-KS 3.** **順序只來自 id 與 Plan；Plan 在兩次成功的 `BuildPlans` 之間不變，同樣的登記得到同樣的 Plan。** 每個欄依 EntityId（u64 的數值，Kernel 不解讀 index／generation 兩段）嚴格升冪，查詢依升冪或交集的升冪產出；World、Scheduler、Executor 不用雜湊順序、指標比較、執行緒完成順序決定任何順序。守衛：J-1、J-2、J-9、J-20；J-18「Registry 指紋看得到 threadBound」「看得到 annotatedWrites」與 Plan 匯出整行 schedule 的檢查（`RegistryTests.cpp`、`SchedulerTests.cpp`）；「DI-KS 3: a second round …」（第二輪只加一個無關的 System，`TieBreaks`、既有的 effects、順序圖、沒動到的 schedule 的 Plan 指紋都不變；`RegistrationRoundTests.cpp`）。（DI-K3 的一部分；W-1、W-2、W-10；`v8-arch-gyo2-kernel-subtract-structure` 3.2）
〔併自 world DI 1、scheduler DI 3〕World 對 `EntityId` 只做 64 位元整數比較；任何疊代、交集、同步點套用的順序都以它為鍵。每個 schedule 的 Plan 唯一，只在 `BuildPlans` 成功時建，衍生的欄位（存取集合、effects、平手、Plan、順序圖、指紋）每次從登記的輸入重算；只取決於登記序與宣告，不依雜湊、位址、執行緒、平台；用這份 Registry 建的 World 在跑時不重建（DI-KS 26）。補守衛：J-20。

<a id="di-ks-4"></a>
**DI-KS 4.** **id 由登記順序或配發器決定；建 Plan 成功的版本發出的 id 在之後的登記與重建中不變，新的往後加；失敗或放棄的那一輪發出的 id 作廢。** ComponentId、ResourceId、EventTypeId、registrationSeq＝登記順序（拿掉的 System 留墓碑，它的 registrationSeq 不重發）；TypeKey 只用於行程內查表；執行期 id 不上 wire、不進 digest；World 不配發實體 id；配發器是產品的 Resource，鍵格式固定為低 32 index、高 32 generation，配發策略（PvP：單調不重用、generation 恆 0）由產品宣告；〔第 5 批，`v8-arch-gyo2-world-gen`；使用者 2026-11-22 合併前核准〕**Kernel 不附任何配發器型別**：預設的範圍配發器 `RangeAllotter` 在 `entity_ids` Module（[entity-ids.zh-Hant.md](v2/entity-ids.zh-Hant.md)，預設帶、可關），Kernel 只留 `EntityAllotter` concept 與配發的機制；stale 句柄的偵測能力取決於策略，Kernel 只保證鍵還活著。守衛：J-8、J-18、J-19；掃描；「DI-KS 4: a failed BuildPlans …」「DI-KS 4: DiscardRegistrations …」（失敗或放棄那一輪的 id 作廢、留下的 id 不變；`RegistrationRoundTests.cpp`）。（DI-K3；R-1～R-3、W-9；使用者 2026-11-11 K.3 第 1 項；`v8-arch-gyo2-kernel-subtract-structure` 3.2 規則 1）
〔併自 world DI 2〕World 內沒有配發、回收、歸零的操作；世代切換＝重建 World。〔第 5 批，`v8-arch-gyo2-world-gen`；使用者 2026-11-22 合併前核准〕預設配發器的單調、不回繞、沒有 `Reset` 由 entity_ids 的 EI-2 守（突變 `we-j8-allotter-wraps`、`we-j8-allotter-reset` 隨型別搬到 `entity_ids_mutations.json`）；Kernel 的 J-8 用測試替身守配發的機制（用完回報 `AllotterExhausted`、範圍內的 `SpawnWithId` 被丟）。

<a id="di-ks-5"></a>
**DI-KS 5.** **衝突與順序分開；沒有先後的衝突對照登記順序平手。** 衝突邊只表示「不能同時」，順序邊表示先後。有衝突且無順序的對照 registrationSeq 平手、列在 `TieBreaks`，不是錯誤；Kernel 不保證結果對登記順序不敏感。守衛：J-20～J-25、J-44 有先後的那半；J-23「宣告的先後消掉平手」「每張 schedule 的平手全部列出、帶 schedule 名」「沒有先後的一對照登記順序平手」。（DI-K1 的修正版；D-1～D-10；`v8-arch-gyo2-no-ambiguity-detection`）（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）
〔併自 scheduler DI 1、DI 2〕衝突邊與順序邊分開存，Plan 的建立只讀這兩種邊，衝突邊不隱含先後。J-44＝System 登記順序的排列測試：有先後的那一組 20 種排列結果都不變。（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）

<a id="di-ks-9"></a>
**DI-KS 9.** **結構變更延後，在宣告的同步點，以及計畫最後一個同步點之後的 hook 清空輪，依「hook 佇列 → despawn → remove → spawn → insert → OnAdd → resource → `Commands` 觸發的推送式事件」套用，每階段依 id，同鍵依 (planPos, recSeq)，鍵唯一。** 一般的 System 執行期間成員不變；`ExclusiveWorld` 可以當場改（DI-KS 18）。記下的變更在記它的那張 schedule 的同步點、用那張的位置套用（DI-KS 19）。hook 的變更屬下一窗——最後一個同步點觸發的，在接下來的清空輪一輪一輪套用到空，每一輪是一次完整的套用，連鎖超過上限是 Err（spec F-12）；例外：`ExclusiveWorld` 當場改觸發的 hook 所記的變更，在那次呼叫回傳前當場套用到空——一輪一輪，每一輪是一次完整的套用、取新的 stamp、同步點序號加一，只套用這次當場改觸發的 hook 所記的（不套用這一層還沒到同步點的紀錄、不碰這張 schedule 的 hook 佇列），上限同清空輪（schedule 宣告的優先，沒宣告用 `KernelSettings` 的），超過是 `HookRoundLimit`、World 中斷；每次 **RC 14.** **hook 的連鎖上限成為負擔**：符合任一條——上限的錯誤出現在正確的內容上（連鎖本來就該那麼長，卻得靠調高上限才跑得過），同一個版本內兩次以上；或為了讓某一張 schedule 的連鎖做完，得把清空的輪改成別的時機（例如中段的同步點也要清空）。→ 停下來重看 hook 的模型：每個同步點把連鎖做完（Bevy 的做法，使用者 2026-11-15 不採），或 hook 不准記延後的變更（使用者比過、沒選）。「兩次以上」沒有根據，是提案者給的。（`v8-arch-gyo2-hook-flush`，使用者 2026-11-15 核准）`ExclusiveWorld` 的當場套用是另一條路，不算把清空輪改成別的時機（`v8-arch-gyo2-kernel-subtract-structure` 第 12 節第 2 件）。

<a id="rc-15"></a>
**RC 15.** **巢狀執行要的特例太多**：實作時發現巢狀執行另外需要的特例，超出 K0 事前宣告第 4 節的清單，累計到三個；或巢狀執行的缺陷在合併後於兩個不同的地方各出現一次。→ 停下來，重新比較「登記式」與「由執行計畫重複執行」兩個做法。（`v8-arch-gyo2-nested-schedule`，使用者 2026-11-15 核准）

<a id="rc-16"></a>
**RC 16.** **Kernel 又長出限制**：Kernel 的職責清單（DI-KS 15）要多加一項，或判不出某樣東西屬不屬 ECS——不數次數，出現就停下來問（L17）。（`v8-arch-gyo2-kernel-subtract-structure`；統合宣告第 9.1 節）

<a id="rc-17"></a>
**RC 17.** **動態登記的接上不夠**（草案）：World 接上新版本時漏了某張表、因此出缺陷兩次以上；或每多一種准登記的東西都要另寫接上的程式；或產品需要准與不准動態插入的 World 共用一份 Registry。→ 停下來比較「每個 World 釘住一個不可變的版本」（事前宣告第 3.2 節退掉的選項 (c)）。「兩次以上」沒有根據，是提案的數字。（`v8-arch-gyo2-kernel-subtract-structure` 第 7 節）

<a id="rc-18"></a>
**RC 18.** **當場套用要第三個例外**（草案）：`ExclusiveWorld` 的當場套用為了某個 Feature，要再破 DI-KS 19 的「每一層的紀錄只在自己的同步點套用」→ 停下來重看當場改的模型。（`v8-arch-gyo2-kernel-subtract-structure` 第 7 節；第 12 節第 2 件選 (a) 時加）

<a id="rc-19"></a>
**RC 19.** **事件機制要多一種**（草案）：為了某一種事件或某一種策略（回滾、網路），事件機制要多一種讀法、多一種保留規則或多一種觸發時機——Kernel 職責清單「事件」那一項要拆成更多項，停下來問（L17，不數次數）。（[游標宣告](v2/event-cursor-declaration.zh-Hant.md)第 9 節；`v8-arch-gyo2-time-events` 10.1）

<a id="rc-20"></a>
**RC 20.** **游標要懂 schedule**（草案）：游標或修剪要知道時鐘、schedule 的語意（哪張是固定步、哪張會暫停）才做得對。（同上）

<a id="rc-21"></a>
**RC 21.** **observer 要進 Plan**（草案）：observer 需要進 Plan 的步驟、或要對作者承諾 observer 的先後，才做得出某個 Feature。（同上）

<a id="rc-22"></a>
**RC 22.** **上限依產品分支**（草案）：訊息上限的預設值或丟棄記錄要依產品分支（共通層出現產品專屬的判斷，AGENTS §9）。（同上）

<a id="rc-23"></a>
**RC 23.** **逐型別雜湊不夠**（草案）：作者的雜湊函式漏寫欄位造成的漏報，在比摘要或 digest 的測試裡出現兩次以上；或作者為了比摘要，產品裡要寫雜湊函式的型別過半 → 停下，提「照位元組加檢查」或「反射」的方案。（第 4 批宣告 11.1；DI-KS 27）（使用者 2026-11-22 核准，`v8-arch-gyo2-authority-rollback`）

<a id="rc-24"></a>
**RC 24.** **帶條件的讀者要補償**（草案）：作者或 Module 為「被 run 條件長期跳過的讀者」寫補償（每幀讀了就丟只為了不拉住、在轉換時清掉、自己記上次讀到哪裡），在產品或 Module 裡反覆出現，或 Engine 的 Module 必須教作者這樣寫才能用——重評 Kernel 是否要提供（候選：[重評宣告](v2/event-cursor-reeval-declaration.zh-Hant.md)修訂 2 的 (C)、(E)，全文在 f957143b）。**基準**：System 契約說明頁第 15 節的寫法（讀者不帶條件、每幀讀了不要的就丟；跨過狀態轉換的資料放 Resource；暫停時擋寫者）是預定的寫法，照它寫、或 Module 的說明頁教它，都不算補償；補償指超出這個寫法的（在轉換時清掉、自己記上次讀到哪裡），或第 15 節的寫法做不到某個 Feature。所在 schedule 很少跑的讀者不在這一條，見 RC 20。現在的寫法在 [System 契約說明頁](v2/system-contract-page.zh-Hant.md)第 15 節。（`v8-arch-gyo2-event-cursor-reeval`；DI-KS 10）（使用者 2026-11-22 核准；「基準」一句是合併前審查 S3 之後加的，使用者「S3 照建議加基準」）

<a id="rc-25"></a>
**RC 25.** **摘要看不見游標**：兩份 World 的摘要相同、之後才分岔，追到原因是游標（有沒有、讀到哪裡），在產品或 Engine 的 Module 的測試裡觀察到兩次以上；或有 Feature 需要「讀者跑過沒有、讀到哪裡」也算進「兩份 World 一樣」——重評摘要收游標的相對位置（[事前宣告](v2/kernel-summary-messages-declaration.zh-Hant.md)第 4 節 (d)；先要讓游標的鍵不跟登記順序走）。（`v8-arch-gyo2-kernel-summary-messages`；DI-KS 10、27）〔`v8-arch-gyo2-kernel-summary-messages`；使用者 2026-11-23 選 (b)，最終文字合併前核准（side chat「核准」）〕

<a id="rc-28"></a>
**RC 28.** **Extract 要寫回、要動兩個 World，或參數不夠**（草案）：(a) 某個點名的 Feature 需要 Extract 寫回來源（GPU 讀回進 World、照 Bevy 把對應實體寫回來源），或同步那一步要同時改兩個 World（渲染 World 的實體對應）——DI-KS 13 要改，停下交使用者；(b) 兩個以上的 Module 或產品為了在 extract 裡過濾、join、知道移除、或記「上次抽到哪」，在渲染 World 抄整份來源或各自寫比對——重評 `Extract<Query<…>>` 與[事前宣告](v2/sdl-extract-declaration.zh-Hant.md)第 2.4 節的候選。（`v8-arch-gyo2-sdl-extract`；DI-KS 13、35、36；最終文字合併前核准）
