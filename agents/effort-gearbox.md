# 作業の分割とギア（ギアボックスの規則）

複数の手順からなる作業では、まず作業をバッチに分け、バッチごとにギア（思考の深さ、effort）を選ぶ。
ギアとは別の軸として、エンジン（どのモデルが処理するか）も選ぶ（「エンジン（モデル）」節）。

## ギア

- low（1 速）：状態の確認、コマンドの実行、ファイルの移動、指示どおりの逐語的な修正。
- medium（3 速）：文書、整理、範囲が明確な小さな修正、受け入れ検証の実行と結果の記録。
- high（4 速、主力）：既存の設計を理解してからの実装、複数ファイルにまたがる修正、code review。
- xhigh（5 速）：局所的にだけ使う。タイミング、プロトコル、決定性など、気づかないうちに誤りやすいロジック。
- max（追い越し）：まれに使う。厳密な論証が必要な問題。反復する失敗は「エンジン（モデル）」節の判定に従う。
- ultracode（四輪駆動）：一段高いギアではなく、別の駆動方式（複数の Agent の協働）。
  用途：バッチの計画、証拠で示す必要があること、高リスクの変更（プロトコル、データ形式、公開インターフェース）、広範囲の走査。
  規模は小さく保つ：案は約 3 つ、審査者 1 人、対抗的な検査 1 回。

## エンジン（モデル）

エンジン（どのモデルが処理するか）とギア（どれだけ徹底するか）は別の軸である。

- 既定：サブ Agent は主会話のエンジンを使う。定型作業（low の作業）は小さいエンジンを使ってよい。
- 難しいと事前に分かっている作業（未知の領域、Architecture の判断）は、最初から大きいエンジンを提案してよい。
- 失敗したときは、ギアやエンジンを変える前に原因を判定する。
  1. 誤りに関わるファイルや出力を読んでいない、または検証を実行していない（transcript の tool call で確認する）→ ギアを上げる。
  2. 欠けていた事実を prompt に明記した再試行で直る → どちらも変えない。
  3. 1 にも 2 にも当たらないのに同じ誤りが残る → エンジンの変更を提案する。
  モデル自身の「確認した」という説明は、判定の根拠にしない。
- 試行の数え方と止め方は AGENTS.md §14 冒頭に従う。エンジンの変更は、その報告の後にユーザーが決める。
- ultracode は同じエンジンの中の編成であり、エンジンの変更の代わりにならない（同じ重みの Agent は盲点を共有しうる）。
  対抗的な検査には、可能なら提案者と別のエンジンを使う。

## ギアの切り替えの原則

1. 要求が大きい、または曖昧なときは、まず ultracode か xhigh で計画し、検収点のあるバッチに分ける。
   各バッチに推奨のギアを書き、計画がユーザーに確認されてから実行する。
2. 通常の実装は high、文書と実行は medium。
3. リスクのある部分だけ xhigh に上げ、終わったら下げる。
4. 後で外部の検証（CI、Test、ユーザーの確認）がある作業は、低めのギアでよい。
   ただし、その変更に対して実際に実行される検証に限り（skip されたものは数えない）、各ギアの定義より下げない。
   外部の検証がない作業は、low の定義に当たる作業を除き、medium を下限とする。
5. 実行中に状況が変わった場合（回帰の発見、範囲の拡大など）、または AGENTS.md §14 冒頭の停止条件に当たった場合は、
   まず止めてユーザーに伝え、計画し直す。黙ってギアやエンジンを上げ下げしない。

## ギアとエンジンを決める人

- 主会話のエンジン、ギア、ultracode の切り替え：ユーザーだけが決める。
- workflow 内の各サブ Agent、および Claude が別に開く session のエンジンとギア：
  Claude が設定し、開始前に「どの Agent に、どのエンジンとギアを、なぜ」を説明する。
  どちらかの軸で主会話を上回る場合、または承認済み計画の指定を下回る場合は、ユーザーの同意を得る。
  指定しない項目は「継承」と書く。実際の値はユーザーが /tasks で確認できる（環境変数が上書きしうる）。
- サブ Agent に渡す prompt は、起動前に主会話に示す。長い場合は、渡す資料と渡さない資料の一覧を示す。
- ultracode の使用を勧めるときは、先にユーザーに尋ねる。
