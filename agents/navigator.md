# モデルの選択（ナビゲーターの規則）

ギアボックス（`agents/effort-gearbox.md`）は、同じモデルがどれだけ徹底するか（effort）を扱う。
この規則は、どのモデルが処理するかを扱う。
計画はペースノートであり、ナビゲーター（主会話の Claude。計画を読んでサブ Agent を起動する側）は、
計画を読んで、バッチと役割ごとにモデルを割り当てる。

## モデルの順序

2026-11 時点の順序：Fable ＞ Opus ＞ Sonnet ＞ Haiku。

- この規則の「大きい」「小さい」「上回る」「下回る」は、この順序で判断する。
- 「小さいモデル」は Sonnet 以下を指す。
- Fable は、純粋な Code Review（下の節）にだけ使う。ほかの役割には使わない。
- モデル名が変わったときは、この行と下の割り当てを同じ変更で更新する。

## 役割

- 提案者：計画の案を出す。
- 統合者：提案者の案を比べ、一つの計画に統合する。
- 敵対的検査者：統合案（統合者がいない場合は提案者の案）を否定しようとする。
- 実装者：計画に沿って実装する。
- 審査者：code review を行う（純粋な Code Review を除く）。
- 純粋な審査者：純粋な Code Review を行う。
- 検証者：AGENTS.md §14.4 の 1〜5 の記述を実際のデータで確かめる。

`~/.claude/agents/xhigh-reviewer.md` のように定義にモデルがない Agent は、使う役割をその都度決め、
その役割のモデルを起動時に指定する（指定しないと主会話のモデルを継承する）。

## 上段と下段

上段は重い作業、下段はそれ以外を指す。次のいずれかに当たる作業を上段とする。

- Design Invariants、プロトコル、データ形式、公開インターフェース、Architecture の判断に触れる。
- 障害（インシデント）や回帰の修正。
- ユーザーが重要と指定した Feature。
- 上段と下段のどちらか判断できない。

## 純粋な Code Review

コードだけから設計を推し量り、その良し悪しを見る審査。AGENTS.md §3 の審査はこれを指す。

- 読まない：設定（build、CI、Tool の設定）、環境（Platform、機械、CI の状況）、
  文書（Architecture の文書、dev_log、HANDOFF、宣告、commit と PR の説明、コードのコメント）、ガード。
- 読むのはコード（実装と Test）だけ。意図と構造は、審査者がコードから推し量る。
- 見ること：
  - ロジックが合理的か。
  - コードが整っているか（clean code）。
  - 歴史のある（成熟した）デザインパターンを使っているか。
  - ハードコードをしていないか。
- 起動する側は、prompt に対象の範囲（ファイル、または git の範囲）だけを書く。
  設計の意図、計画、経緯は書かない（prompt も文書の経路になるため）。
- モデルは Fable、ギアは high（ギアボックスの code review）。
  Fable を用意できないときは Opus で行い、そのことを報告に書く。
- 起動用の定義は `.claude/agents/pure-code-reviewer.md` にある。この節を変えるときは、同じ変更で更新する。

## ultracode の workflow のモデル

ultracode の workflow（計画に限らず、証拠で示す作業や広範囲の走査を含む）は、
計画ができる前に動くことがあるため、規則で決める。

- 提案者、統合者、敵対的検査者は、上段も下段も Opus とする。
- 同じ重みの Agent は盲点を共有しうる。それを減らすため、敵対的検査者には成果物（統合案）と元の要求だけを渡し、
  提案者と統合者の推論や transcript は渡さない。
- 別の重みによる検査は、コードについてだけ、純粋な Code Review が担う。
  計画と宣告には別の重みによる検査がないことを、承知のうえで受け入れる。
- 上段の計画に入力する偵察・走査には、小さいモデルを使わない（偵察の誤りは計画の誤りになり、後で見つけにくいため）。

## 計画が割り当てるモデル

- 計画は、各バッチについて、上段か下段かとその根拠（当たる条件）、
  実装者・審査者・検証者のモデルと理由を書く。
  ギアと並べて「モデル／ギア」の形で書き、ユーザーの確認を得てから実行する。
- 計画が割り当てるときの下限：
  - 上段のバッチでは、小さいモデルを使わない。
    ただし、上段のバッチの中の low の定型作業（ギアボックスの low の定義に当たるもの）は、計画に書けば小さいモデルを使ってよい。
  - 検証者は、4（緩めた性質が他の判定で引き続き守られているか）を確かめるときも小さいモデルを使わない。
  - 敵対的な検査では、少なくとも 1 人の敵対的検査者に、小さいモデルを使わない。
    小さいモデルは追加の意見としてだけ使う。
- 上段では、主会話より大きいモデルを提案してよい（ユーザーの同意を得る。Fable は除く）。
- 計画に割り当てのない §14.4 の検証者は、そのバッチの実装者の割り当てに従う。
- 計画に割り当てのないその他のサブ Agent も、起動時にモデルを明示し、主会話のモデルを継承させない。
  ultracode の役割と純粋な Code Review に当たらない実装・修正・審査は Opus、
  定型作業（ギアボックスの low の作業）は小さいモデルでよい。
- 実行中に割り当てを変えるときは、まず止めてユーザーに伝える（ギアボックスの切り替えの原則 5）。
- この規則より前に承認された計画は、バッチの開始時に、上段か下段かと実装者・審査者・検証者のモデルを補い、
  ユーザーの確認を得る。

## 失敗したとき

- 原因の判定はギアボックスの「失敗の判定」に従う。3 に当たるときだけ、モデルの変更を提案する。
- 変更先は、元のモデルと別で、元のモデルより小さくないモデルとする（Fable は除く）。
  変更先がないときは、そのことを報告する。
- モデルの変更は、AGENTS.md §14 冒頭の報告の後にユーザーが決める。

## モデルを決める人

- 主会話のモデル：ユーザーだけが決める。
- workflow 内の各サブ Agent、および Claude が別に開く session のモデル：
  計画の割り当て（ultracode の workflow と純粋な Code Review ではこの規則）に従って Claude が設定し、
  起動前にモデル、ギア、種類、渡す資料を主会話に示す。
- 主会話を上回る場合、または承認済み計画の割り当てやこの規則の割り当てを下回る場合は、ユーザーの同意を得る。
  ただし、純粋な Code Review の Fable は、主会話を上回っても改めて同意を求めない。
- モデルとギアは必ず指定する（ギアを継承に任せない理由はギアボックスの規則）。
  モデルを指定できない起動方式（fork など）は、その役割に使わないか、継承されるモデルを起動前に示す。
  定義に model を持つ Agent は、その値を指定とみなす。
  継承される値と定義の値も、その役割の下限と上の同意の規則に従う。
  合わないときは、その起動方式や Agent をその役割に使わない。
  実際の値はユーザーが /tasks で確認できる（環境変数が上書きしうる）。
